The **event lattice** is Axocoatl's shared typed event fabric. Skills and
runtime components publish events; the Automation trigger runtime, configured
webhooks, and retained API/WebSocket observers subscribe to the same feed.

It is important to separate that event path from execution. Manual Automations
run through an explicit DAG executor. Multi-agent directory sessions run their
configured agents in dependency order. The daemon does not use lattice signal
thresholds as a second workflow scheduler.

## How it works

Publishing an event stores its type, payload, producer, and timestamp, then
broadcasts a notification to subscribers. Built-in events include agent and
task lifecycle events; Skills publish configured custom event names with a
producer of `skill:<skill-id>`.

The reusable coordination crate also contains pheromone-style signal
accumulators and returns the registered agent ids whose thresholds cross. The
standalone `stigmergic-workflow` and `skills-lattice` examples demonstrate those
primitives. In the product daemon, that returned activation list is not an
agent execution path: current consumers react to the event notification feed.

## A Skill-to-Automation example

1. A session agent calls an enabled `skill_review-ready` tool, or a user fires
   that Skill from Settings or `POST /api/skills/review-ready/fire`.
2. The Skill publishes each name in its `emits` list. Every notification is
   tagged `produced_by: skill:review-ready`.
3. An enabled `OnSkill` Automation for `review-ready` matches that exact
   producer. An `OnEvent` Automation can separately match one emitted event
   type.
4. The shared trigger runtime starts each matching Automation through the
   explicit DAG executor. It prevents the same automatic Automation from
   overlapping itself and applies a cooldown to event-triggered runs.
5. Configured webhooks and retained API/WebSocket observers receive the same
   published event.

## Why this matters

<Aside type="tip" title="The win is composability">
Events decouple producers from consumers. A Skill can publish one stable event
without knowing whether an Automation, webhook, or UI observer will consume it.
Adding a consumer does not require changing the producer.
</Aside>

The current event path supports:

- **Event-triggered Automations.** `OnEvent` matches an event type exactly;
  `OnSkill` matches a Skill producer exactly.
- **Skill publication.** Enabled session Skills and the manual fire endpoint
  publish their configured custom events.
- **Integrations and webhooks.** The recent-events API, compatibility WebSocket
  frames, and configured outbound webhooks observe the same notifications.
- **Coordination primitives.** Library users and runnable examples can use the
  threshold/signal layer directly.

The `reacts_to` field on a Skill is currently retained as capability metadata
and used by the standalone examples; the product daemon does not automatically
execute every holder from that declaration. Use an `OnSkill` or `OnEvent`
Automation for reachable event-driven work.

## Where auctioning lives: the coordinator

The event feed does not pick a worker. When you want one agent chosen for a
subtask, use the **coordinator role**, a separate execution mechanism.

An agent with `role: coordinator` spawns a pool of `role: worker` agents at
runtime, decomposes its task into subtasks, and assigns each subtask to a
worker via a **capability + budget auction**: every worker bids, and the best
fit by required tools and available budget wins. This is real, on the live
execute path — not roadmap.

The coordinator decomposes, assigns, executes, and synthesizes a run. That
auction is not part of event publication or Automation DAG scheduling.

## Inspect session work

From a session, **Activity** is the conversation and ordered tool stream for
that work. Open **Agent graph** for the configured agent relationships around
the session. The global event-timeline UI retired with Studio; integrations can
still inspect `GET /api/events/recent` and `event` frames on `/ws`.

The [lattice](/concepts/lattice/) carries typed event notifications.
**Automations** are explicit **DAGs**: each node does one thing and edges carry
control flow. Create a net-new record with `POST /api/automations`, or seed the
initial store from legacy YAML on first boot. For an interactive path, use
**Settings → Automations → + Automation** to choose the record and trigger
basics and create a valid Input → Agent starter DAG, then edit, enable, disable,
and run it in the same surface.

## One live source of truth

`AutomationStore` is both the Settings/API source and the live trigger source. Creating
a record through Settings or the API, or editing, enabling, disabling, changing the cadence
of, or deleting an existing record, takes effect in the running daemon without a restart. One
dispatcher reconciles scheduled triggers and subscribes to lattice events; it re-checks
the current record immediately before execution so a stale scan cannot fire a deleted or
changed automation.

The legacy `workflows:`, `schedules:`, and `proactive:` YAML sections are migration input.
When the canonical store file does not exist, Axocoatl projects them into automation
records once. An existing store remains authoritative even if you delete every record;
Settings and the automation APIs do not let YAML resurrect them on restart.

## Node kinds

An automation is a graph of typed nodes. The executor dispatches on the node's
kind:

| Kind | What it does |
|------|--------------|
| **Agent** | Runs an agent with a configurable input. |
| **Tool** | Calls a registry tool directly — no LLM in the loop. Deterministic, fast, cheap. |
| **Conditional** | Evaluates an expression and activates only the matching labeled branch (with an optional default). |
| **Map** | Fan-out: resolves its input to a list and runs a body node once per item; downstream runs once after all iterations finish. |
| **Subgraph** | Calls another automation as a node. Depth-limited to prevent infinite recursion. |
| **TextInput** | A first-class input slot. For manual runs the app renders it as a form field; for scheduled/proactive runs its default value fires. |
| **Interrupt** | Pauses the run and waits for a human. |

## Scheduling is interval-only

Scheduled automations fire on a fixed interval. The `every` field accepts
`s` / `m` / `h` / `d` units — `30s`, `5m`, `2h`, `1d`.

<Aside type="caution" title="No cron">
There is **no cron syntax** and no `cron:` field in the current runtime. If you
need "every 5 minutes," write `every: 5m`; fixed intervals are the supported
cadence today.
</Aside>

## Event and Skill triggers

An automation can act without a user prompt when a lattice event or a specific Skill
publication matches its trigger. This is the autonomous half of "Always-On": the service
keeps the daemon alive, and the canonical trigger runtime decides when the graph runs.

Legacy YAML can seed the equivalent records on first boot:

```yaml
proactive:
  # Fire on a fixed interval.
  - id: morning-digest
    name: Morning digest
    agent: summarizer
    trigger:
      type: schedule
      every: 1d
    input: Summarize what happened overnight.

  # Fire whenever a named lattice event occurs.
  - id: on-failure
    name: Failure responder
    agent: triager
    trigger:
      type: on_event
      event: AgentFailed
    input: An agent failed. Investigate and report.
```

- **Schedule** runs on a fixed interval (`s`/`m`/`h`/`d`).
- **OnEvent** matches the lattice event type exactly — a built-in event like
  `AgentFailed` or a custom event.
- **OnSkill** matches events whose producer is exactly `skill:<skill-id>`.

One automatically triggered automation cannot overlap itself. Event-triggered runs also use a cooldown before and
after execution so their own downstream activity cannot form an immediate loop. A failed
provider or graph run is recorded on that automation and does not stop the dispatcher.

## Run outcomes

The Runs drawer shows node checkpoints and the preserved diagnostic detail attached to a
failed node. If the daemon restarts with a run still recorded as `running` and no executor
owns it in the new process, bootstrap records that run as `failed` with a durable restart
reason. This is failure reconciliation, not continuation of arbitrary in-flight work.

`final_content` contains every executed runtime-sink output in Automation declaration
order. A runtime sink is an executed node with no activated edge to another executed node,
so a terminal Tool, Map, or Subgraph result is retained and disconnected terminal results
do not depend on hash-map or scheduler order.

## Human-in-the-loop

An **Interrupt** node pauses a run and waits for a person. While paused, the
app lists the interrupt with its message and payload so an operator can
decide what to do, then:

- **Resume** — `POST /api/automations/{id}/runs/{run_id}/nodes/{node_id}/resume`.
  The operator's value either replaces the node's output or appends to the
  paused message, depending on the node's resume strategy.
- **Skip** — `POST /api/automations/{id}/runs/{run_id}/nodes/{node_id}/cancel`.
  The Interrupt wakes with an empty output, emits a distinct `Cancelled` event,
  and the remaining run continues.

Runs and node outcomes are recorded for inspection. A top-level parked Interrupt and
its pending operator prompt are durable: daemon bootstrap reconstructs the prompt, and
Resume continues from saved outputs and edges without replaying completed nodes.

That recovery boundary is the top-level operator pause. It does not reconstruct an
arbitrary provider or tool call that was in flight when the daemon stopped. An Interrupt
inside a nested Subgraph remains process-local because nested execution does not yet own
an independent durable parent-continuation record.

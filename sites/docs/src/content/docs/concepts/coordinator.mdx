The [event lattice](/concepts/lattice/) carries notifications; Automations run
explicit DAGs. The **coordinator** is a third path for a goal that must be
decomposed and assigned dynamically at runtime.

An agent with `role: coordinator` runs the coordinator behavior. The hierarchy
lives inside that agent's execution: it plans, selects workers, joins their
results, and returns one synthesized answer.

## What a coordinator does

When a coordinator agent executes, it runs one coordination pass:

1. **Decompose** the goal into subtasks.
2. **Auction** each subtask to the worker pool — the best fit by required
   tools and available budget wins.
3. **Spawn** the winning workers and run them **in parallel**.
4. **Join** every worker, then **synthesize** their outputs into one answer.

Workers are stopped and joined at the end of every run — on success and on
every error path — so no worker is ever left running.

## Decomposition: HTN, then LLM

Decomposition has two paths, and which one runs is a configuration choice:

- **Symbolic HTN.** When the coordinator's workflow sets `htn_methods_file`,
  it decomposes with a Hierarchical Task Network planner — no LLM call for the
  parts the methods already cover. Any task the methods leave open (an "LLM
  frontier") is decomposed by the model, task-by-task, not the whole goal.
- **LLM.** With no methods file, the coordinator asks the model to break the
  goal into 2–5 independent subtasks.

<Aside type="caution" title="HTN is opt-in">
Auctioning and worker spawning are always on. **Symbolic HTN only runs when
you provide an `htn_methods_file`** — otherwise decomposition is the LLM's job.
Don't read "HTN" as the default.
</Aside>

## The auction

Each subtask declares the tools it needs. Every worker in the pool computes a
**bid** scored on two things: how well its tools cover the subtask's required
tools, and how much token budget it has. The highest bidder wins and is
removed from the pool for that pass.

If the pool is empty, or no pooled worker can cover a subtask's tools, the
coordinator spawns an **ad-hoc worker** granted exactly the required tools and
running on the coordinator's own model — so a subtask is never forced onto an
unfit worker, and a worker with no model never falls back to a cloud default.

The event lattice does not select a worker. Arbitration to a single winner
lives here, in the coordinator.

## Workers are first-class agents

A worker isn't a bare provider-plus-tools shell. Every spawned worker gets the
full agent stack: [checkpointing](/concepts/checkpointing/), the four
[memory](/concepts/memory/) tiers (daily log, core memory, semantic recall),
and the global hook registry. A worker is an agent that happens to be driven by
its coordinator rather than by an Automation edge or direct session call.

## Resumable runs

The coordinator checkpoints its own orchestration — the plan plus each worker's
outcome — after decomposition and after every worker finishes. If the process
crashes mid-run, the next run for the same goal **resumes**, skipping subtasks
that already completed and re-running only what's left. If every worker fails,
the coordinator returns an error rather than synthesizing from nothing.

## A minimal config

```yaml
agents:
  - id: lead
    name: Lead
    provider: ollama
    model: llama3.2
    role: coordinator
    system_prompt: You coordinate a small research team.

  - id: researcher
    name: Researcher
    provider: ollama
    model: llama3.2
    role: worker
    tools: [web_search]

  - id: writer
    name: Writer
    provider: ollama
    model: llama3.2
    role: worker

workflows:
  - id: research
    entry_point: lead
    agents: [researcher, writer]
    # Optional: symbolic decomposition. Drop this line to decompose with the LLM.
    htn_methods_file: ./methods.yaml
```

The legacy workflow record supplies coordinator worker membership and the
optional HTN methods file. `researcher` and `writer` are the pool selected for
`lead`, and the coordinator spawns workers on demand. The auction decides which
worker takes each subtask; the `web_search` tool on `researcher` is what its bid
for a search-shaped subtask is scored on.

## Automation, events, and coordinator

| | Automation | Event lattice | Coordinator |
|---|---|---|---|
| Purpose | Execute a declared graph | Publish and subscribe to typed events | Decompose a goal dynamically |
| Ordering | Explicit DAG edges | No product worker-ordering path | Coordinator plan + auction |
| Worker choice | Agent id on each node | None | One winner per subtask |
| Trigger | Manual, fixed interval, event, or Skill | Publisher-defined | A coordinator agent execution |

Use an Automation for a graph you can draw ahead of time, the lattice to
decouple event producers from subscribers, and a coordinator when the task
shape only becomes clear while it is running.

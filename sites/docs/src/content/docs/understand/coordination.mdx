Axocoatl has five related coordination mechanisms. Each answers a different
question and owns a different recovery boundary.

| Mechanism | Use when | Ordering/choice |
| --- | --- | --- |
| Lead with helpers (the default team) | A native Agent needs a separate read-only look at part of its task | The lead picks an approved helper and writes its task; several calls in one response run their helpers at the same time |
| Native multi-Agent Session | Several configured Agents share one foreground task | Dependency order in one Session |
| Automation | The graph can be declared ahead of time | Explicit DAG nodes and edges |
| Event feed | A Skill should announce something that Automations and webhooks react to | Publish/subscribe notification of a Skill's declared events |
| Coordinator Agent (legacy Sessions) | Task shape and worker choice emerge at runtime | Decomposition, then the first declared worker that can call each subtask's tools |

## Automations

The canonical Automation store supplies manual, fixed-interval, event, and
Skill-triggered graphs. The DAG executor schedules ready nodes and records run
and node outcomes. See [Automations](/configure/automations/) for the operator
workflow.

Legacy workflows are compatibility seed/input. They do not constitute a
second live scheduler after the canonical store exists.

## Native Session teams

Use **Team & budget** to review the exact team, dependencies, Agent templates,
explicit limits, and expiry for future native turns. Apply retains an immutable
team revision. Each activation has its own input, conversation, grant, and history.
The current-turn inspector separately reviews changes to work that has not started;
it does not replace the future-team configuration.

An Agent whose Team & budget approval names Worker templates as helpers gets a
`delegate` tool. A Coordinator template must have helpers and runs the same way in a
native Session. Each call starts one helper in
its own conversation with only the Session's request and the task the lead wrote, and
reserves the helper's approved limits from the lead's shared allowance. Several calls in
one model response run their helpers at the same time; each is admitted against what the
ones before it reserved. A helper is not started when that reservation would leave the
lead too little to read its answer, counting every helper still running. When a helper
finishes or is stopped, the lead is charged only what it used, so the lead can delegate
again with the rest. A helper must be read-only: its template has no tool that writes
files or runs commands, or it has `writes: []`, which withholds `write_file` and `edit_file` and runs its `bash` where it
cannot change the repository. Any other helper is refused, and the lead is told that
setting `writes: []` on it makes it read-only. The lead waits for the
answer; a failed or refused helper reaches it as a tool error. The helper's command
source, lead activation, and result stay in the same canonical Session history.
Increasing budget or authority requires human review; another model call cannot grant it.

Review is otherwise something a lead may ask a helper for. A team can instead require
it: its **Required review** names a read-only Worker template that the host itself runs
after the required Agents finish and the required checks pass. The reviewer is an
optional node of the admitted turn graph with its own grant and a fresh conversation
for each round, and its verdict is a completion condition over the required Agents'
results. A request for changes continues the turn in a new epoch that revises the lead
with the findings, up to the approved rounds; the lead cannot skip, answer for or
approve its own review. See
[Required review](/configure/agents/#required-review).

## Default team

The configurations written by `axocoatl onboard` and `axocoatl init`, and the
repository's example configurations, define one lead and two helpers:

- **Lead** (`lead`, autonomous) owns the change and is the only one of the three that
  edits files. Its instructions say to delegate focused questions to Scout, ask Reviewer
  for a review before finishing, and verify with the tests.
- **Scout** (`scout`, Worker, `writes: []`) answers the lead's question with file
  paths, line numbers and short evidence.
- **Reviewer** (`reviewer`, Worker, `writes: []`) reviews the change it is given against
  the code, docs and tests, and reports defects with `file:line` or says it found none.

When a new native Session's team is one Agent that may delegate, Team & budget drafts
an approval for it that lists every Worker template with `writes: []` as a helper, with
room for 6 Agents and 5 connections in a turn. The draft approves nothing:
you enter the lead's limits and each helper's limits and choose Apply, and you can
remove a helper or clear delegation first. A configuration without such Worker
templates gets no draft, and an applied team is never changed by one.

In the Agent graph, the lead appears alone until it delegates. Each helper it starts
then appears with a "delegated" edge from the lead; a helper is not a dependency and
does not gate the turn's answer.

Review the lead asks Reviewer for is advice to the lead, not a gate: the lead decides
when to ask for it and what to do with the answer. To make the review decide whether a
turn completes, choose Reviewer under **Required review** in Team & budget. To make a
command decide, add a [required check](/configure/agents/#required-checks).

## Sessions on a 1.0 data root

A data root that still uses the 1.0 format runs one Agent per Session turn. A
single-Agent Session, a one-Agent team, a team whose entry point is a Coordinator,
and a request targeted at one Agent keep working. A turn that would run two or more
Agents is refused before it starts. The message tells you to stop Axocoatl, make a
cold backup, and run `axocoatl session upgrade --confirm`. The upgrade converts 1.0 Sessions, including
multi-Agent Sessions, to native Sessions, where **Team & budget** runs the team.
History recorded before the upgrade still loads and shows each Agent's output.
Removing or renaming a referenced Agent or team does not remove the Session or its
History; a new turn stops before it starts and tells you to restore the reference or
create a new Session with an available selection.

When a team's entry point is a Coordinator, the Session runs only that Coordinator, and
the Coordinator owns its declared Workers. A Worker cannot be selected or targeted directly.

Explore several ways is a separate comparison mechanism and currently requires
a single autonomous-Agent Session. Coordinator and worker roles remain on the normal Session
path rather than becoming nested workers inside a comparison Way.

## Event feed

The daemon publishes one kind of event: firing a Skill publishes each name in its
`emits` list, with producer `skill:<skill-id>`, payload `{"fired_by_skill": "<skill-id>"}`,
and a timestamp. A Skill fires from **Settings → Skills**, from
`POST /api/skills/{id}/fire`, or when an Agent calls its `skill_<id>` tool in a Session
that enables the Skill. Consumers are:

- enabled **On event** Automations matching the event name exactly;
- enabled **On Skill** Automations matching `skill:<skill-id>` exactly;
- configured webhook filters;
- the recent-event API and `event` WebSocket frames.

The feed keeps no history and starts no work on its own. A 1.0 Skill's `reacts_to`,
`agents` and `prompt` keys were removed in 1.1.0: they never ran anything, and the
daemon now warns that they are ignored.

## Legacy Coordinator execution

In a legacy Session, an Agent with `role: coordinator` handles one execution hierarchically:

1. decompose the goal into subtasks;
2. assign each subtask to the first declared worker, in declaration order, that can
   call its required tools (an ad-hoc worker with exactly those tools otherwise);
3. spawn selected worker Agents and run independent work in parallel;
4. join their outcomes and synthesize one result.

The model decomposes the goal, and each subtask names the tools it needs. A
workflow's `htn_methods_file` was removed in 1.1.0 with the symbolic HTN planner;
the daemon warns and ignores it.

Declared Workers resolve their own provider/model/fallback route, budget, sampling, exact tool
policy, hooks, and Session-scoped Tier 1–4 memory/checkpoints beneath the Coordinator identity.
Shared core blocks remain limited to labels that Worker explicitly declares. Ad-hoc Workers
can be created when the pool lacks a fitting target; they are run-scoped and ephemeral.
The Coordinator itself owns Tier-1 Session conversation plus private checkpointed plan/outcome
state, not Tier 2–4 recall tools. That private state is separate from Session History and
Automation run records. Once the Session turn is Completed, Cancelled, Failed, or Interrupted,
Axocoatl records that canonical terminal state first and then reconciles the scoped checkpoint
transaction. It will not start the next turn until reconciliation durably commits the completed
checkpoint or clears resumable orchestration state for Cancelled, Failed, or Interrupted work.
A completed checkpoint is marked nonresumable, so finished subtasks are not silently resumed
as a new request.
When an older single-Agent Coordinator is adopted into this transaction model, Axocoatl imports
checkpoint-only conversation into canonical History before clearing unsafe private and Worker
state. It then rebuilds only Completed Coordinator turns as model context and preserves cumulative
usage; the one-time adoption marker is written after that rebuild succeeds.
Transaction-scoped Agents and Coordinator Workers may read existing Tier 2–4 memory, but cannot
run semantic auto-store, daily-log archive writes, personal/shared core edits, or core
consolidation during the turn. That restriction also applies to Completed work until these durable
tiers support causal transactional promotion.

Decomposition and synthesis are checked against the exact
configured model window before dispatch. If older context must be reduced, Axocoatl omits only
completed User/plain-Assistant text at User boundaries. System messages, the current request
suffix, attachments, and canonical Session History remain intact. This is bounded request-local
projection, not the summarization pipeline used by a stateful autonomous Agent.

<Aside type="note" title="Events do not choose workers">
The event feed carries notifications. Worker arbitration happens inside a
coordinator execution; Automation ordering happens in the DAG executor.
</Aside>

## Observe coordination

**Open Agent graph** shows a turn's Agents and activations in the focused graph
surface. Reloading rebuilds it from canonical Session History. A legacy turn recorded
with several Agents shows each Agent's output; it has no coordination graph.

The Agent graph opens in View mode. Select an Agent to open its
inspector, then choose a recorded activation to review input, output, partial
output, usage, and causal evidence. Older or incomplete records explicitly show
which details are unknown, missing, or not recorded. The graph also supports
ordinary and directly targeted turns using their recorded membership. Historical
inspection alone grants no command authority. Native current work exposes exact
Guide, Stop, Retry, and other controls only when the host reports that capability.
Legacy turns remain read-only, with whole-turn Stop in Conversation. See
[native controls](/workbench/history/#control-native-work).

Integrations can read the Session turn endpoint for the canonical record.
`GET /api/events/recent` and `event` WebSocket frames remain the separate
process-wide notification feed; there is no global event-feed browser destination.
The [HTTP API reference](/reference/http-api/#turn-control-plane) defines the
turn control-plane fields.

An Agent entry is a configured template for a provider, model, prompt, role,
and optional token budget. Autonomous Agents and Coordinators can own durable actors;
Workers are created only by their Coordinator. Sessions and Automations refer to templates by
stable `id`.

## Define an Agent

```yaml
agents:
  - id: coder
    name: Coder
    provider: ollama
    model: qwen2.5-coder:14b
    system_prompt: |
      Work inside the authorized repository. Make small verified changes and
      report the commands used to check them.
    depends_on: [planner]
    role: autonomous
    token_budget:
      per_execution: 20000
      per_call: 8192
      overflow_policy: abort
    sampling:
      temperature: 0
      max_tokens: 4096
```

| Field | Meaning |
| --- | --- |
| `id` | Stable identifier used by Sessions, Automations, APIs, and dependencies |
| `name` | User-facing label |
| `provider`, `model` | Model target for this Agent |
| `system_prompt` | Persistent operating instructions |
| `tools` | Empty inherits the execution path's baseline tools; non-empty is an exact advertisement and dispatch allowlist |
| `writes` | Repository paths the Agent may change in a native Session. Omit it to allow any file; `[]` makes a read-only helper. See [Limit which files an Agent may change](#limit-which-files-an-agent-may-change) |
| `depends_on` | Exact direct-parent completion predicate for a multi-Agent Session turn; also seeds legacy Automation edges during first-boot migration |
| `role` | `autonomous`, `coordinator`, or `worker` |
| `activation_threshold`, `activation_decay` | Removed in 1.1.0. The daemon warns and ignores them; events never start Agents |
| `sampling` | Optional request-generation controls for autonomous Agents, Coordinators, and declared Workers |
| `memory` | Tier 1–4 tuning for autonomous Agents and declared Workers; a Coordinator itself uses Tier 1 plus orchestration checkpointing |

A Coordinator must be the `entry_point` of exactly one workflow and must appear in that
workflow's roster. Every other member must be a Worker, and each Worker can belong to only that
one coordinator-led workflow. Unknown, duplicate, empty, or out-of-roster identities are rejected
because worker membership and HTN selection would otherwise be ambiguous. A Worker cannot run
directly.

## Define a Session team

`Lattice` Sessions select a config-owned team by ID. Workflow IDs are unique,
non-empty stable identities; human-readable punctuation and spaces are allowed. An autonomous
team is an exact, non-empty roster of autonomous Agents. Its `depends_on` graph must be closed
inside that roster, contain no duplicate or self dependency, and be acyclic, so every declared
Agent can actually become ready:

```yaml
workflows:
  - id: feature-team
    name: Feature team
    agents: [planner, coder, reviewer]
    entry_point: planner
```

A legacy Session stores `feature-team`, then resolves current Agent membership and
dependencies when each all-team turn begins. When the roster contains more than one
autonomous Agent, that exact turn graph remains in History even if configuration changes
later. A Coordinator-led team uses its separate hierarchical direct path and does not
fabricate a peer Coordination map. The Automation editor and the
compatibility `/api/workflows` routes operate on the separate canonical
Automation store; editing an Automation does not edit a Session team.

## Native authority and budgets

In a native Session, **Team & budget** captures the selected Agent configuration
and requires explicit activation, invocation, token, cost, and expiry limits.
Those limits govern cumulative reservations before dispatch. A Worker allocation
consumes its Coordinator's approved aggregate allowance; events do not refill it.
Current authority and expansion requests are reviewed from the Agent inspector.

The enforced native provider boundary currently accepts reviewed local Ollama
profiles and eligible [OpenRouter-credit profiles](/configure/providers/#configure-openrouter)
with finite inference bounds. Axocoatl verifies the actual backend and
model capabilities; an OpenAI-compatible endpoint is not itself an enforcement
standard. Local API cost can be known zero while token usage remains incomplete.
This does not promise a cap on an unrelated provider's bill.

## Limit which files an Agent may change

```yaml
agents:
  - id: docs-writer
    name: Docs writer
    provider: ollama
    model: qwen2.5-coder:14b
    tools: [read_file, write_file, edit_file, list_dir, grep, glob, bash]
    writes: [docs/, "*.md"]
  - id: reviewer
    name: Reviewer
    provider: ollama
    model: qwen2.5-coder:14b
    tools: [read_file, list_dir, grep, glob, bash]
    writes: []
```

Each entry is a repository path pattern. A trailing `/` covers everything below that
directory. A pattern without `/`, such as `*.md`, matches that file name in any
directory; a pattern with `/` starts at the repository root. `*` and `?` stay within one
path segment and `**` spans segments. Patterns cannot start with `/`, contain `..` or
name a `.git` directory, and an Agent can name at most 64.

In a native Session:

- `write_file` and `edit_file` refuse any other path, and any path inside `.git`,
  before writing, and never write through a symbolic link. A `.gitignore` decides which
  files are checked, so the Agent may change one only inside a directory it may change
  whole, such as `docs/`. The Agent is told to leave the file unchanged and describe
  the change in its answer.
- Every change the Agent makes is checked after its work, whether or not it has
  `bash`. Axocoatl compares complete manifests of the repository from before and after,
  including Git's own settings and hooks and whatever the Git index says; a change
  outside its paths fails that work and is kept for you to review. The check does not
  undo a change. Files your ignore rules exclude, and anything outside the repository,
  are not checked.
- A shell can still write anywhere in the sandbox, so for an Agent with `bash` the check
  is review evidence rather than confinement. Give an Agent that must stay within its
  paths the file tools without `bash`.
- With `writes: []` the Agent is not offered `write_file` or `edit_file`. Its own `bash`
  commands run under a Linux Landlock write restriction (Landlock ABI 3, Linux 6.2 or
  later), so they cannot change the repository, and each command gets a fresh home
  directory instead of the Session's. Where the runtime cannot apply that restriction,
  its `bash` commands do not run and the read-only file tools still work.

**Team & budget** offers the same choice for each Agent under **May change**: Any file,
Only these paths, or Nothing – read-only helper. The review lists what each approved
profile may change. Work added to a running turn starts from one of the Session team's
Agents and keeps what that Agent may change. A Worker cannot change more than its Coordinator: when the
Coordinator has a list, each of its Workers needs one too, and every path in it must
appear in the Coordinator's list exactly as written.

## Required checks

A native Session team can have required checks: commands Axocoatl runs in the
Session's repository after the required Agents of every turn finish. In **Team &
budget**, open **Required checks** and enter one command per line; each line runs as
`sh -c <line>`. If the Session has a detected check command, **Add detected** offers
it, but it runs only after you add it and apply the team.

After the Agents finish, Axocoatl captures the repository, runs each check, and
captures the repository again. The turn completes only when every check passes and the
checks leave the repository unchanged. A failing check leaves the turn needing
attention, with each check's exit code and output in the turn controls. Fix the cause,
select the check and choose **Continue** to run it again with fresh captures.

Checks run on the allowance of the first required Agent, in graph order, that has the
`bash` tool; Axocoatl holds back invocations for them from that Agent's allowance. Apply
is refused when no required Agent has `bash`, and so is a request sent to a single
Agent without `bash` while the team has checks. Each check may run for up to three
minutes and keeps up to 768 KiB of output and 256 KiB of errors.

## Actor token guards

The YAML `token_budget` is a local guard on actor calls. It also applies when a
native activation uses that actor, but cannot weaken the separately approved
native allowance. Budgets are local preflight controls. Before each model call, Axocoatl reserves
the estimated input plus the explicit or resolved bounded completion and
compares that reservation with both limits:

- `per_call` caps one call's local reservation;
- `per_execution` caps cumulative recorded usage plus the next reservation for
  one activation.

`per_call` must not exceed `per_execution`; `axocoatl validate` rejects that
configuration.

<Tabs>
  <TabItem label="abort">
    Enforce the local guard. A call is not sent when its reservation cannot fit
    either limit. A provider-reported overrun stops the current turn after the
    response. This is the YAML default.
  </TabItem>
  <TabItem label="warn">
    Log the overflow and continue. Use this only when observability is more
    important than stopping locally over-budget work.
  </TabItem>
  <TabItem label="summarize">
    A deprecated compatibility spelling that behaves as `warn`. It does not
    summarize spent tokens.
  </TabItem>
</Tabs>

The estimate includes injected memory and tool schemas, not only the visible
request. A provider can tokenize differently, report usage only after the call,
or ignore a requested output limit, so the guard is not an absolute billing cap.
Budgets are independent of automatic conversation compaction, which keeps
context within a model window but cannot undo token usage.

## Use sampling controls carefully

`sampling` accepts optional `temperature`, `top_p`, `max_tokens`, and
`response_format` (`text` or `json`). The configured values reach autonomous Agents,
Coordinator provider calls, and each declared Worker's own provider calls. Adapter support is
not uniform. Temperature zero can reduce
variation but does not make a generative model deterministic. Omit a field to
use the provider default.

## Tune memory

```yaml
memory:
  max_session_messages: 100
  recall:
    passive_inject: true
    top_k: 5
    min_score: 0.15
  core:
    blocks:
      - { label: persona, limit: 2000 }
      - { label: project, limit: 2000 }
      - { label: team, limit: 1000, shared: true }
```

An omitted or empty core block list creates the default `persona`, `human`, and
`project` blocks. A non-empty list replaces that default set. See
[State and memory](/understand/state/) before changing retention behavior.

Native execution restores exact activation state. Its current actor factory does
not attach daily-log, core-memory, or semantic-recall stores, so those settings do
not enable native recall or shared-memory writes. The following scope rules apply
to compatibility execution.

This memory block config applies to an autonomous Agent or a declared Worker. In a legacy
Session those stores are scoped under the Session runtime identity and survive actor restart;
only labels explicitly marked `shared: true` cross scopes. A Coordinator's provider loop does
not expose core/daily/semantic memory tools in 1.0. Its declared Workers apply their own
`memory` configuration beneath `{session}:{coordinator}:worker:{worker}`, while ad-hoc Workers
are ephemeral.

## Apply changes

For durable changes, edit YAML, validate it, then restart the whole daemon:

```sh
axocoatl validate ./axocoatl.yaml
# stop the running foreground process, then:
axocoatl dev --config ./axocoatl.yaml
```

Settings can edit an Agent and restart it immediately, but that patch is only
in memory for the current daemon process. YAML remains unchanged. The CLI
`axocoatl agents restart coder --config ...` sends a restart request to the
already-running daemon; its config flag does not reload that YAML file.

A `role: worker` Agent cannot be started or restarted directly. Edit its YAML and restart its
Coordinator. Settings disables the standalone Worker actions for the same reason.

The background supervision loop checks Agent liveness every five seconds and
attempts to restart an unexpectedly stopped Agent from its latest checkpoint.
After five consecutive failures it leaves the Agent down until configuration
is corrected and it is restarted deliberately.

<Aside type="caution" title="Checkpoint recovery has a boundary">
Restart restores checkpointed conversation and the latest cumulative provider-usage subtotal
within its supported owner. The completeness flag is sticky: if a dispatched call ended without
terminal usage, Settings keeps showing a lower bound after restart. Checkpoints do not resume an
in-flight provider call or tool, or arbitrary terminal Session work. Coordinator private
orchestration state is cleared after a Completed, Cancelled, Failed, or Interrupted Session turn;
the next turn decomposes fresh.
</Aside>

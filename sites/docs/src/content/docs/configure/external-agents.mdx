---

import { Aside, Steps } from '@astrojs/starlight/components';

A loadout's writer can be an external coding-agent program instead of Axocoatl's own tool
loop: the Claude Code CLI (`runtime: claude-code`) or the Codex CLI (`runtime: codex`).
The program runs inside the Session container, not on your computer, under the same
rules as any loadout Session:

- network `egress`: the program reaches its model API only through a route, and other
  hosts only when the loadout or your configuration lists them;
- the `hardened` workload: it runs as the non-root `writer_user` through the in-sandbox
  supervisor with `--harden`, under its seccomp filter and in a Landlock domain of its
  own;
- the activation is admitted, granted and captured like a native writer: Axocoatl
  captures the repository before and after it, checks the change against the writer's
  `writes`, and then runs the loadout's required checks and review.

The program's credential never enters the container. The container holds a placeholder
in the variable the program reads, and the daemon adds the real value on your computer,
on the route, to each request the route's rules allow. Codex can use either an OpenAI API
key or the sign-in of your ChatGPT plan (`axocoatl connect codex`); for the sign-in, the
daemon also keeps the access token current on your computer.

## Build the image

<Steps>

1. Build a Session image from Axocoatl's pinned recipe:

   ```sh
   axocoatl recipe build claude-code     # or: axocoatl recipe build codex
   ```

   This builds an image named `localhost/axocoatl-recipe-…` with Podman from a base and
   the recipe's pinned versions, prints it, and records its image id in the data root.
   Sessions trust a recipe image by that id, as they do the browser image, without
   `allow_untrusted_images`. Run it with the daemon's `--config` (or
   `AXOCOATL_DATA_DIR`), so the id lands in the data root the daemon reads. Recipes can
   be combined, as in `axocoatl recipe build claude-code e2e`. `axocoatl recipe list`
   shows the recipes and the images built from them. The image's tag carries a digest of
   its recipes, so after an upgrade that changes a recipe, a run asks you to build again.
   The build downloads the base image and the programs; that is network access you start,
   on your computer.

2. Name the recipe in the loadout:

   ```yaml
   environment:
     recipes: [claude-code]
   ```

</Steps>

## Store the credential

### Claude Code: `axocoatl connect claude-code`

```sh
axocoatl connect claude-code
```

This runs `claude setup-token` for you and stores the long-lived OAuth token it creates
as the secret `claude-code-oauth`. You sign in in the browser as `claude setup-token`
asks; you never see, copy, paste or type the token:

- `claude setup-token` runs in a pseudo-terminal the size of your terminal, and is
  resized with it when you resize the window, so its screen looks as it does when you
  run it yourself. In a terminal smaller than 40 columns by 24 rows it gets 40 by 24
  instead (in a smaller one Claude Code may not draw the whole token), and its screen
  may then look broken, but the token is still read whole and hidden. Your terminal is
  in raw mode while it runs (your keystrokes go to it) and is restored when it ends,
  also on an error or a signal. Keystrokes stop going to it the moment it exits: what
  you type while the token is checked stays for your shell.
- Everything it prints reaches your terminal through a filter that keeps a model of the
  terminal, so it sees each character in the cell it lands in, as you would. Claude Code
  draws the token in rows wrapped at the width of its box and placed by cursor movement;
  the filter reads the token from those cells, at any width, with color codes,
  hyperlinks or other escape sequences anywhere inside it, a border or padding around
  it, or in pieces written at different times. Each cell of the token shows the next
  character of `[token hidden by axocoatl]` (then a blank), so the rest of the screen
  stays where Claude Code put it. At most the public prefix `sk-ant` shows before the
  mask. Writes to your clipboard (OSC 52, and the kitty, iTerm2, tmux and screen forms
  of it) are dropped, and so is any other escape sequence holding a token.
- Axocoatl reads the token from that output in memory only: exactly one
  `sk-ant-oat01-…` token must appear, or nothing is stored and the command says why.
  The token ends where it does on screen: the next line Claude Code prints is not
  stored with it, nor is text after a blank on its last row. The token never goes into
  a command line, an environment variable, a log, a temporary file or a message, and
  the buffers that held it are overwritten when they are freed.
- It then checks the token with Anthropic over HTTPS (`GET /v1/models` with the
  token, which costs nothing; the response is never shown). A token Anthropic rejects
  (`401` or `403`) is not stored. When Anthropic cannot be reached, nothing is stored
  either: run the command again, or add `--no-verify` to store the token unchecked.
  The `Authorization` header is built in a buffer that is overwritten when the request
  ends; the copies the HTTP and TLS libraries make while sending it are freed then,
  and the connection is not kept open.
- It stores the token exactly as `axocoatl secret set` does (`secrets/claude-code-oauth`
  in the data root, `0600`, replaced atomically) and prints
  `Connected Claude Code: stored secret claude-code-oauth (the token was never shown)`
  with the next step.

It needs an interactive terminal and the `claude` CLI: the first `claude` on `PATH`,
then `~/.local/bin/claude`, or the path given with `--claude PATH`. `--secret NAME`
stores the token under another name. Like `recipe build`, it uses the data root of
`--config` or `AXOCOATL_DATA_DIR`. Exit codes: 0 stored, 1 rejected by Anthropic, 2 no
single token printed, 3 usage (no terminal, a bad name, no `claude`), 4 not checked
(network), 5 the data directory or the secret store failed, 6 interrupted by a signal.
Run it again whenever the token expires or is revoked.

### Codex with a ChatGPT plan: `axocoatl connect codex`

```sh
axocoatl connect codex                 # signs in in your browser
axocoatl connect codex --device-auth   # shows a code to enter on another device
axocoatl connect codex --no-browser    # does not open the sign-in page for you
axocoatl connect codex --sign-in-timeout 10   # gives the sign-in 10 minutes, not 30
axocoatl connect codex --status        # shows the stored sign-in, never a token
axocoatl connect codex --refresh       # asks the running daemon to refresh it now
axocoatl connect codex --api-key       # also stores the OpenAI API key OpenAI issues (below)
```

This runs the official `codex login` for you and stores the ChatGPT sign-in it makes as
the secret `codex-chatgpt`. You approve the sign-in in the browser (or, with
`--device-auth`, enter the code Codex shows at the address it gives); you never see, copy,
paste or type a token. Nothing but Podman needs to be installed on your computer: by
default the pinned Codex 0.160.1, the one the `codex` recipe installs, runs in a
throwaway container.

- **The image.** It is the `codex` recipe image recorded in the data root by
  `axocoatl recipe build codex`, used by its exact image id. When none is recorded (or
  Podman no longer has it), the command builds and records it first, as
  `axocoatl recipe build codex` would, through the same Podman connection
  (`CONTAINER_CONNECTION` and the rest of Podman's own configuration apply).
- **The container.** It runs as a non-root user with a read-only root file system, no
  capabilities, no new privileges, no log driver and nothing from your computer mounted.
  Its `CODEX_HOME` (also its home and working directory) is a private `0700` tmpfs, in
  memory, and Codex runs `codex -c cli_auth_credentials_store="file" login`, so the
  sign-in is written to a file there, never to a keyring. Your own `~/.codex` and your
  environment (no `CODEX_API_KEY`, `OPENAI_API_KEY` or other variable of yours) do not
  reach it, nor do the proxy variables Podman would otherwise copy in (`http_proxy`,
  `https_proxy`, `ftp_proxy`, `no_proxy`, in either case; it runs with
  `--http-proxy=false`). It is on Podman's default bridge network, not on Axocoatl's
  egress routes: `codex login` reaches `auth.openai.com` directly, without a proxy. Where
  that needs a proxy, sign in with `--codex PATH` instead, which keeps your proxy
  variables. It holds no Axocoatl secret, and Podman stops and removes it when the sign-in time
  has passed, even if Axocoatl is killed: 30 minutes, or 1 to 60 minutes with
  `--sign-in-timeout MINUTES` (it goes to the container's `podman run --timeout`; it
  does not go with `--codex PATH`, where no container runs). The command says so when the
  sign-in starts (`You have 30 minutes to finish signing in.`, with the time chosen).
  When the time runs out first, it says
  ``The Codex sign-in was not completed within 30 minutes; nothing was stored. Run
  `axocoatl connect codex` again.`` (again with the time chosen) and exits with code 2.
- **The browser sign-in** returns to `http://localhost:1455/auth/callback`, the address
  Codex prints. The container publishes that one port on your computer's loopback only
  (`127.0.0.1:1455`); inside it, a small forwarder passes each connection to Codex's
  login server, which listens on the container's own `127.0.0.1:1455` (nothing else
  holds that port there, so Codex never moves to another). When `127.0.0.1:1455` (or
  `[::1]:1455`) is already in use on your computer, the command stops before starting
  anything and suggests `--device-auth`. **The device sign-in** (`--device-auth`)
  publishes no port.
- **Opening the sign-in page.** Codex cannot open a browser on your computer from the
  container, so Axocoatl opens the address Codex prints, once: with `open` on macOS or
  `xdg-open` elsewhere (the first on `PATH`), the address as its only argument, without
  a shell. It then prints `Opened the sign-in page in your browser.` It opens only an
  address shown on screen that is exactly `https://auth.openai.com/oauth/authorize?…`
  (with `--device-auth`, exactly the device page `https://auth.openai.com/codex/device`,
  where you enter the code Codex shows): no other host, look-alike, scheme, port or path,
  and no hyperlink's hidden target. The address is not secret (Codex's PKCE verifier
  never leaves the container), and Axocoatl writes it to no file or log. With
  `--no-browser`, or when there is no opener or it fails, nothing is opened: open the
  address Codex prints in a browser on this computer yourself.
- `codex login` runs with `podman exec --interactive --tty` in the same pseudo-terminal as
  `claude setup-token` above, and its output reaches your terminal through the same
  filter, which here also hides OpenAI API keys (`sk-…`) and JWTs (`eyJ…`, all three
  parts), each at the start of a word, as `[token hidden by axocoatl]`, and drops
  clipboard writes. Codex 0.160.1 prints no token: it shows the sign-in address (or the
  device code) and writes the tokens to `auth.json`. Ctrl-C goes to Codex, as it would
  on your computer. Once Codex has exited, Ctrl-C (or closing the terminal) reaches
  Axocoatl, which catches it; the `podman` commands that start the container, read the
  sign-in and remove the container run in a process group of their own, so it does not
  stop them.
- Axocoatl reads the tokens from that file, never from the screen: `podman exec` prints
  `auth.json` (a regular file, a link is refused, of at most 64 KiB) straight into
  Axocoatl's memory, and Axocoatl never writes it to disk; the only other copy is
  Codex's own, in the container's tmpfs, which goes with the container. It must hold a
  ChatGPT sign-in, with an access token and a refresh token; an API-key sign-in is
  refused. Axocoatl stores the access token, the refresh token, your ChatGPT account id
  (from the file, or the id token's `chatgpt_account_id`) and the time, as one line, the
  way `axocoatl secret set` stores a value (`secrets/codex-chatgpt` in the data root,
  `0600`, replaced atomically). The id token is not kept, nor is the OpenAI API key Codex
  may have obtained with the browser sign-in, unless you ask for it with `--api-key`
  ([below](#codex-with-an-openai-api-key-axocoatl-connect-codex---api-key)).
- Then the container is removed (`podman rm --force`), and with it its in-memory
  `CODEX_HOME`: after a sign-in, and also when the sign-in fails, is refused or is
  interrupted.
- The tokens are not checked with OpenAI before they are stored: they are the ones
  Codex just obtained, and the first run uses them.

With `--codex PATH`, the Codex CLI at that path on your computer runs instead, and no
Podman is needed:

- It makes a private temporary `CODEX_HOME` in the data root (`connect-codex-<random>`,
  `0700`) and runs `codex -c cli_auth_credentials_store="file" login` there, with
  `CODEX_HOME` set to it (as an absolute path, also when the data root is relative) and
  that directory as its working directory, so the sign-in is
  written to a file in it, never to your system keyring, and no repository's
  `.codex/config.toml` applies. Your own `~/.codex` is not read or written by Axocoatl,
  and Codex is told to use the temporary home instead. Codex 0.160.1 first signs out of
  the sign-in its home holds, revoking it; the temporary home holds none, so your other
  Codex sign-ins are not touched. Codex runs without `CODEX_API_KEY`, `OPENAI_API_KEY`,
  `CODEX_ACCESS_TOKEN`, `OPENAI_BASE_URL`, `CODEX_SQLITE_HOME` and the variables that
  move where it signs in, refreshes or revokes (`CODEX_REFRESH_TOKEN_URL_OVERRIDE`,
  `CODEX_REVOKE_TOKEN_URL_OVERRIDE`, `CODEX_APP_SERVER_LOGIN_CLIENT_ID`,
  `CODEX_AUTHAPI_BASE_URL`, `CODEX_AGENT_IDENTITY_AUTHAPI_BASE_URL`,
  `CODEX_AGENT_IDENTITY_JWKS_BASE_URL`).
- Its output is relayed and filtered the same way, and the sign-in is read from the
  `auth.json` it writes there (opened without following a link) and stored the same way.
  Codex opens the browser sign-in itself, so Axocoatl opens nothing (`--no-browser` does
  not apply).
- Then every file in the temporary home (Codex also writes a log and other state there)
  is overwritten with zeros and removed, and so is the directory: also when the sign-in
  fails, is refused or is interrupted. A temporary home a killed run left is erased by
  the next run once it is 30 minutes old (a sign-in in progress elsewhere keeps its own). On an SSD or a copy-on-write file system an overwrite does
  not guarantee that the old blocks are gone; the data root is readable only by you.

It needs an interactive terminal, and Podman (the first `podman` on `PATH`) unless
`--codex PATH` names an executable Codex CLI. The secret is
always named `codex-chatgpt`, because that is the one the daemon refreshes. Like `recipe
build`, it uses the data root of `--config` or `AXOCOATL_DATA_DIR`. Exit codes: 0 stored,
2 `codex login` stored no ChatGPT sign-in (also when the sign-in was not completed within
the sign-in time), 3 usage (no terminal, no Podman on `PATH`, a `--codex` that is not an
executable, port 1455 in use, `--api-key` with `--device-auth`, a value on the command
line, or a command line `axocoatl connect` does not take, such as
`--sign-in-timeout 0`), 5 the data directory, the secret store, Podman, the image
build, the pseudo-terminal or `auth.json` failed (also when `auth.json` is a link, or
the login container stopped before the sign-in time was up and before the sign-in was
read), 6 interrupted by a signal, 8 with `--api-key` or `--api-key-only`, no API key was
stored ([below](#codex-with-an-openai-api-key-axocoatl-connect-codex---api-key)).
Nothing is stored unless it exits 0, except that with `--api-key` exit code 8 means the
ChatGPT sign-in was stored without a key. Run it again when a run says the sign-in was
refused.

#### Check and refresh the sign-in

`axocoatl connect codex --status` reads the stored sign-in from the data root (the
daemon need not run) and prints whether one is stored, its ChatGPT account id by its
last four characters only (`…4d2f`), when its access token expires (the token's JWT
`exp`, in your computer's time zone, or that it has expired) and when its tokens were
last refreshed or, when there has been no refresh since, signed in. It never prints a
token. Exit codes: 0 a sign-in is stored, 2 none is, 5 the stored value cannot be read
or is not a sign-in `connect codex` stored.

`axocoatl connect codex --refresh` asks the running daemon to refresh the sign-in now,
even when it is not due. It reaches the daemon the way `axocoatl run` does: at `--url`,
`AXOCOATL_URL` or the server address in `--config`, with `AXOCOATL_TOKEN` or the local
API token in the data root. The daemon refreshes through `POST
/api/connect/codex/refresh` with the same broker that refreshes the sign-in before a
request (below): the same request to OpenAI, the same rotation and atomic write under
the secret store's lock, the same remembered refusal, one refresh at a time with the
route's own. The command never sends a refresh token itself. The daemon records the
refresh asked for and how it ended in its log, without a value. The command prints, for
example,

```text
✓ Refreshed the ChatGPT sign-in at 2026-10-12 16:03:00 +02:00 and stored it as secret codex-chatgpt (no token was shown). The new access token expires at 2026-10-22 16:03:00 +02:00 (in 10 days).
```

Exit codes: 0 refreshed (also when a sign-in that `axocoatl connect codex` stored while
the refresh ran is kept instead of the new tokens, which the command says), 1 OpenAI
refused the refresh for good (sign in again with `axocoatl connect codex`; asked again,
the daemon does not send that refresh token again and says so), 2 no sign-in is stored,
3 usage, 4 the refresh could not be completed (the token endpoint could not be reached,
did not answer in time, or gave an answer that is neither new tokens nor a refusal; the
stored sign-in is unchanged), 5 anything else (the stored value is not a sign-in, the
daemon refused the API token, the new tokens could not be written, which the daemon
then keeps in memory and writes again on their next use, or a daemon older than 1.3.1),
7 no daemon answers at that address (start it with `axocoatl serve`). The route answers
only an authenticated request from this computer: a daemon that accepts API requests
without authentication (`server.auth.allow_unauthenticated`) refuses it with `403`, and
so does any daemon for a request from an address that is not a loopback address.

### Codex with an OpenAI API key: `axocoatl connect codex --api-key`

```sh
axocoatl connect codex --api-key        # the API key and the ChatGPT sign-in
axocoatl connect codex --api-key-only   # the API key only
```

A Codex writer's default credential, `codex-openai`, is an OpenAI API key. You get it the
same way as the ChatGPT sign-in, by signing in in the browser: you never see, copy, paste
or type the key. `--api-key` runs the same `codex login` as above, and after the browser
sign-in Codex 0.160.1 asks OpenAI for an API key for your account: it exchanges the id
token it just obtained at `https://auth.openai.com/oauth/token` (an OAuth token exchange,
`requested_token=openai-api-key`) and writes the key it gets as `OPENAI_API_KEY` in its
`auth.json` (`codex-rs/login/src/server.rs` at `rust-v0.160.1`). Axocoatl reads that key
from the same `auth.json`, in memory, as it reads the sign-in, checks that it has the
form Codex writes (`sk-`, then letters, digits, `-` and `_`, 20 to 1024 characters) and
stores it as the secret `codex-openai` (`secrets/codex-openai`, `0600`, replaced
atomically), under the same lock of the secret store as the ChatGPT sign-in, which it
also stores as `codex-chatgpt`. With `--api-key-only` it stores only the key, and the
ChatGPT sign-in goes with the container (or the temporary home). Axocoatl never shows,
logs or writes the key anywhere else, and Codex's own copy in its `auth.json` goes with
the container (or is overwritten and removed with the temporary home); the relay also
hides an `sk-…` key Codex might print, though Codex 0.160.1 prints none.

- **Billing.** Requests a Codex writer makes with `codex-openai` are billed at OpenAI API
  rates to the OpenAI Platform organization the key belongs to, not to your ChatGPT plan.
  A writer with `credential: codex-chatgpt` uses your plan instead.
- **Only the browser sign-in.** Codex exchanges for a key only after the browser sign-in;
  the device-code sign-in gets none. `--api-key` (or `--api-key-only`) with
  `--device-auth` is refused before anything runs, with exit code 3 and a message that
  says why.
- **When OpenAI issues no key.** Codex ignores a failed exchange: the sign-in still
  succeeds, and `auth.json` holds no key (for example when your account has no OpenAI
  Platform organization). Then nothing is stored as `codex-openai`, and the command says
  so plainly: OpenAI issued no API key for this account; API-key mode needs an OpenAI
  Platform organization; ChatGPT mode works with `codex-chatgpt`. With `--api-key` the
  ChatGPT sign-in is still stored as `codex-chatgpt`; with `--api-key-only` nothing is.
  It exits with code 8. A value in `OPENAI_API_KEY` that does not have the form of a key
  is treated the same way (the message says so and never shows it).
- **Nothing on the command line.** `axocoatl connect codex` takes no key: a value after
  `--api-key`, or `--api-key=VALUE`, is refused with exit code 3, and the message never
  repeats it.

Exit codes are those of `axocoatl connect codex` above, with 8 when no API key was stored.
Run it again when a run says the key was rejected.

### Other credentials: `axocoatl secret set`

`axocoatl secret set <name>` stores a credential that no `connect` command obtains, and
Codex's API key or Claude Code's token for automation without a browser (for example in
CI), from an environment variable the automation already has. It reads the value from
standard input, or with `--from-env VAR` from that environment variable of the command,
and stores it in the data root as `secrets/<name>`, a file only your user can read
(`0600`), replaced atomically. It never takes the value as an argument, never prints it, and never writes
it to a log or a record. Standard input must be a pipe or a file: when it is a terminal,
where typing or pasting would show the value, the command refuses and prints how to
pipe it. An unset or empty `--from-env` variable is refused. `--from-env` takes the
variable's name, without `$`: `--from-env "$OPENAI_API_KEY"` would put the key itself
on the command line, so a value there (or after the name) is refused, and the message
never repeats it.

```sh
# Automation without a browser (for example in CI), from the job's environment
axocoatl secret set codex-openai --from-env OPENAI_API_KEY
axocoatl secret set claude-code-oauth --from-env CLAUDE_CODE_OAUTH_TOKEN
```

On your own computer, use `axocoatl connect codex --api-key` and
`axocoatl connect claude-code` instead: you never type or paste a key.

A value is one line of at most 8 KiB with no control characters; one trailing line break
is ignored. If a command prints more than the token, put the token alone in a file and
redirect it. A route sends the value exactly as stored, so `secret set` warns on standard
error, and still stores it, when the value has whitespace inside it, starts with
`Bearer ` (the route adds that itself), looks like JSON or holds several tokens, and, for
`claude-code-oauth` (the secret Claude Code's route sends), when it does not start with
`sk-ant-oat01-`, as the token `claude setup-token` prints does, and, for `codex-chatgpt`,
when it is not a sign-in `axocoatl connect codex` stored (the ChatGPT route refuses
anything else). The warning never shows the value. When the model API rejects a stored
credential (`401` through the route), the run's not-covered reason names the credential
and says how to store it again: for Claude Code, `axocoatl connect claude-code`; for the
ChatGPT sign-in, run again (the daemon asks OpenAI for a new access token after the
rejection) and, if it is rejected again, `axocoatl connect codex`; for Codex's API key,
`axocoatl connect codex --api-key`; for others, `axocoatl secret set <name>`, piping in
only the token.
`axocoatl secret list` prints the stored names, never values, and
`axocoatl secret remove <name>` deletes one. A route's `credential` resolves to a
`credentials` entry in the configuration first, then to a stored secret of that name; a
name found in neither refuses the run (exit code 3).

You supply the credential, for your own account. `axocoatl connect claude-code` obtains
the Claude Code token through `claude setup-token` when you run it, and
`axocoatl connect codex` your ChatGPT sign-in through `codex login` (with `--api-key`,
also the OpenAI API key OpenAI issues with it). The only credential
Axocoatl refreshes by itself is that ChatGPT sign-in (see
[Codex with a ChatGPT sign-in](#codex-with-a-chatgpt-sign-in)).

## Name the program in a loadout

```yaml
schema: axocoatl.loadout/1
id: fix-claude-code
version: 1
name: Fix with Claude Code
kind: fix
params:
  writer_model:   { kind: model, required: true, description: "anthropic:<model> for Claude Code" }
  reviewer_model: { kind: model, required: true, description: a different provider:model }
agents:
  - id: writer
    role: writer
    runtime: claude-code
    model: { param: writer_model }
checks:
  - { name: tests, run: { detected: true }, timeout: 5m }
review:
  model: { param: reviewer_model }
  rounds: 2
  tools: [read_file, list_dir, grep, glob]
budgets:
  agent:    { activations: 3, invocations: 300, tokens: 4000000, cost_usd: 10 }
  reviewer: { activations: 2, invocations: 80, tokens: 1000000, cost_usd: 2 }
  wall_clock: 60m
prompt: |
  {task}
environment:
  recipes: [claude-code]
```

```sh
axocoatl run fix-claude-code --task "…" \
  --model writer=anthropic:<model> --model reviewer=ollama:gpt-oss:120b
```

For Codex, the writer's `credential` says which stored credential its route sends:
`codex-openai` (the default: an OpenAI API key from `axocoatl connect codex --api-key`,
to `api.openai.com`) or `codex-chatgpt` (your ChatGPT sign-in from
`axocoatl connect codex`, to `chatgpt.com`). Both run the same
program from the same `codex` image:

```yaml
agents:
  - id: writer
    role: writer
    runtime: codex
    credential: codex-chatgpt   # or codex-openai, the default
    model: { param: writer_model }
environment:
  recipes: [codex]
```

```sh
axocoatl run fix-codex --task "…" --model writer=openai:gpt-5.5 --model reviewer=ollama:gpt-oss:120b
```

A run whose credential is not stored is refused before it starts (exit code 3), with how
to store it: `axocoatl connect codex --api-key` for the API key, `axocoatl connect codex`
for the sign-in. Claude Code's only credential is `claude-code-oauth`, and a native Agent
names none; `axocoatl loadouts validate` refuses any other name.

For Claude Code the model is `{provider: anthropic, model: …}`, for Codex
`{provider: openai, model: …}` with either credential: the provider whose API the program calls through the route
Axocoatl adds for it, and the model name the program itself takes. Any other provider is
refused: `axocoatl loadouts validate` refuses a literal model such as
`{provider: openrouter, model: openai/gpt-5.5}` on a Codex writer, and a run refuses
`--model writer=openrouter:…` (exit code 3), so the model a run records is the one that
ran. An external program brings its own tools, so `tools` is ignored, and only a `writer`
may be external.

The same-model reviewer check compares that model with the reviewer's, from the loadout,
from the finished turn and in Team and budget, through whichever provider each one runs:
a reviewer on `openrouter:anthropic/claude-haiku-4.5` runs a Claude Code writer's
`anthropic:claude-haiku-4-5`, and one on `openrouter:openai/gpt-5.5` a Codex writer's
`openai:gpt-5.5`, so both are warned about (`same_model_reviewer`). The comparison ignores
case, `.` against `-`, a snapshot date such as `-20251001`, `-latest` and an OpenRouter
`:variant` suffix. A Claude model is compared by its family and version: Claude Code's
aliases count as the model they run (`anthropic:haiku` is `claude-haiku-4-5`, so a
reviewer on `openrouter:anthropic/claude-haiku-4.5` is warned about; `best` and
`opusplan` count as the model they run by default, `claude-fable-5-1` and
`claude-sonnet-5-5`), a `[1m]` suffix is ignored, and the older order of a Claude id
(`claude-3-5-haiku`) is the same model. Claude Code's `default`, which runs your
account's default model, is not resolved.

## The routes Axocoatl adds

You do not list these routes; the run adds them to its Session's egress policy.

| Runtime | Host | Requests allowed | Credential | Added as | Placeholder variable |
| --- | --- | --- | --- | --- | --- |
| `claude-code` | `api.anthropic.com` | `POST /v1/messages` | `claude-code-oauth` | `Authorization: Bearer <value>` | `CLAUDE_CODE_OAUTH_TOKEN` |
| `codex` | `api.openai.com` | `POST /v1/responses` | `codex-openai` | `Authorization: Bearer <value>` | `OPENAI_API_KEY` |
| `codex` with `credential: codex-chatgpt` | `chatgpt.com` | `POST /backend-api/codex/responses` | `codex-chatgpt` | `Authorization: Bearer <access token>` and `ChatGPT-Account-ID: <account id>` | `CODEX_CHATGPT_ACCESS_TOKEN` |

Each route refuses every other request. Claude Code 2.1.292 also asks the route for its
account's policy limits and remote settings (`GET /api/claude_code/policy_limits` and
`GET /api/claude_code/settings`); the route refuses both, the network record shows the
refusals, and Claude Code goes on without them: a run with the pinned version passes
with both refused.

The route stays this small on purpose. The daemon adds your credential to every request
a route's rules allow, so each rule is one more endpoint that receives it; these routes
allow only the model calls a run needs, which is what the pinned versions were seen to
send. A refused request is answered with 403 and a hint that names this route as the
one Axocoatl adds for the writer, not a `sandbox.egress.routes` entry. A loadout that
needs more can list its own route for the same host in its `routes`, which then
replaces this one: give it the same credential, injection and placeholder variable,
and the rules you choose. Claude Code also runs with
`DISABLE_TELEMETRY=1`, `DISABLE_ERROR_REPORTING=1`,
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `DISABLE_AUTOUPDATER=1`. The Session's
certificate authority, which signs the route's TLS on your computer, is trusted through
`NODE_EXTRA_CA_CERTS` and `SSL_CERT_FILE`. How routes check and record requests is in
[Credentials and routes](/configure/credentials/).

## Codex with a ChatGPT sign-in

A Codex writer with `credential: codex-chatgpt` runs `codex exec` with the same HTTP
provider as with an API key, aimed at the ChatGPT backend Codex itself uses for a ChatGPT
sign-in (`https://chatgpt.com/backend-api/codex`, its key in `CODEX_CHATGPT_ACCESS_TOKEN`,
which holds the route's placeholder). Codex in the container has no sign-in of its own:
there is no `auth.json` in the container, and its provider sends that variable's value as
its bearer token and nothing else. So it has no refresh token to refresh, revoke or send;
in Axocoatl's Podman run of the pinned version it made no request but its model calls.

The route to `chatgpt.com` allows only `POST /backend-api/codex/responses`. For each
request it allows, it asks the daemon for the current access token and sends it as
`Authorization: Bearer …`, with your account id as `ChatGPT-Account-ID`, replacing any
`Authorization` or `ChatGPT-Account-ID` (or `ChatGPT_Account_ID`) the program sent. The
daemon keeps the token current on your computer, the way Codex 0.160.1 does:

- **Before a request**, when the access token expires within five minutes (read from its
  JWT `exp`; for a token without one, when it was obtained more than eight days ago), it
  refreshes: one `POST https://auth.openai.com/oauth/token` with
  `{"client_id": <Codex's client id>, "grant_type": "refresh_token", "refresh_token": …}`.
  OpenAI's answer replaces the access token, and the refresh token when it sends a new one
  (it rotates them, and refuses one that was already used); the account id is taken from
  the new id token or access token when one names it. The new sign-in is written back atomically
  (`0600`). Refreshes are serialized, and the daemon writes the new sign-in while holding
  the lock that `axocoatl connect codex`, `axocoatl secret set` and
  `axocoatl secret remove` take on the data root's `secrets` directory, after reading the
  file again: if `axocoatl connect codex` stored a new sign-in while a refresh was under
  way, the new sign-in is kept; if the sign-in was removed (or replaced by another value),
  it stays that way, and the refreshed token is sent with that one request only. When the
  new sign-in cannot be written, the daemon keeps it in memory, uses it and tries to write
  it again on each request for as long as the file still holds the sign-in it replaced,
  so the refresh token OpenAI already rotated is not sent again; a daemon restarted before
  it was written has only the old one, which OpenAI may refuse as reused; then connect again.
- **On request**, with `axocoatl connect codex --refresh` (above), it refreshes the same
  way, whether or not the token is due.
- **After a `401`** to a request sent with the current token, it refreshes the same way,
  so the next request carries the new token. The `401` itself goes back to Codex: the
  route does not send the request again. In Axocoatl's Podman test, the pinned Codex
  0.160.1 sent a model call answered `401` again, and that retry carried the new token.
  When Codex ends with that error, the run's not-covered reason names `codex-chatgpt` and
  says to run again, then to connect again.
- **When OpenAI refuses the refresh for good** (`401`, `invalid_grant`, or a refresh token
  expired, reused or invalidated), the daemon remembers it for that refresh token and does
  not send it again, stores nothing, and refuses the route's requests once the access token
  has expired (`503 credential_unavailable`), saying to run `axocoatl connect codex`; why
  is in the daemon's log, not in the answer to the container. When a refresh fails otherwise (no
  answer, another error), an access token that has not expired yet is still sent, as Codex
  does.
- Refresh tokens and access tokens are never written to a log, a record or a message.

From the container nothing reaches the token endpoint: no route serves `auth.openai.com`,
so a refresh the program attempted would be refused where the Session's connections are
decided, and recorded in the network record, and any request to `chatgpt.com` other than
`POST /backend-api/codex/responses` is refused by the route and recorded. The daemon sends
the access token and account id only on a route to `chatgpt.com` whose credential is the
stored `codex-chatgpt`: this one, or a route to `chatgpt.com` that a loadout lists in its
`routes` in place of this one (or the configuration lists), with whatever requests its
rules allow. A route to any other host whose credential is `codex-chatgpt` reads the
secret as a plain credential, which refuses the stored sign-in, and answers
`503 credential_unavailable` without sending anything. The refresh token is never sent
on any route: it leaves your computer only in the daemon's refresh request to OpenAI's
token endpoint.

<Aside type="caution">
What Axocoatl's tests show and what they do not. A Podman test runs the pinned Codex
0.160.1 from the `codex` recipe image through a whole loadout run in this mode, against a
fake ChatGPT backend at `chatgpt.com` and a fake OpenAI token endpoint: the program's
requests reach the backend with the refreshed token and the account id, the rotated
sign-in is stored, and no token is in the container, its configuration, the network record
or the program's requests. Against OpenAI's own service, on 2026-10-11, a fix run of the
pinned Codex 0.160.1 (`gpt-6-luna`) with a ChatGPT plan passed through Axocoatl
1.3.1-rc2: Codex's 6 requests to `chatgpt.com/backend-api/codex/responses` went through
the route with the sign-in the daemon added and were answered `200`, the container held
only the placeholder, and no token-shaped string appeared in the container, the daemon's
log, the record, the JUnit report or the output. The run cost $0.0014.

OpenAI's documentation recommends API keys for automation, and describes ChatGPT sign-in
on CI runners only for trusted private machines, with one copy of the sign-in per machine
or serialized job stream, kept between runs
([CI/CD authentication](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). Axocoatl keeps
the only copy in the daemon's data root and serializes its refreshes. OpenAI's
documentation does not describe a process other than Codex refreshing a Codex sign-in, as
the daemon does here with Codex's own client id and refresh request. Check your plan's
terms before you use it, and use an API key (`codex-openai`) where they do not allow it.
</Aside>

## What is recorded

- **Every model call.** Each request the program makes on its route is written to the
  Session's network record before it is sent, with the rule that allowed it and the name
  of the credential, never its value. **Session network** shows them.
- **The program's output.** Claude Code's `stream-json` and Codex's JSON Lines output
  (at most 16 MiB) is parsed into the activation's evidence: its text, and bounded
  previews of its tool calls and their results. Its final text is the activation's
  answer, which the checks and the reviewer then judge.
- **The change.** The repository captures before and after the activation, as for any
  writer. A change outside `writes` fails the activation.

## What a run costs

Claude Code reports what its run cost (`total_cost_usd`, its own computation from list
prices), and the run settles to that.

Codex reports tokens but no cost. Axocoatl computes the cost from the tokens Codex reports
(with either credential; with a ChatGPT sign-in, the run counts against your plan's usage
limits, and the computed cost is what those tokens would cost at API list prices, not a
charge),
each part at its rate: uncached input, input read from the prompt cache, input written to
the prompt cache, and output, reasoning included. The rate is the configuration's
[`pricing`](/reference/config/#attempt-pricing) entry for exactly that model name when
there is one, otherwise the list price Axocoatl pins for the model:

| Codex 0.160.1 model | Input | Cached input | Cache writes | Output |
| --- | --- | --- | --- | --- |
| `gpt-6-astra` | $10.00 | $1.00 | $12.50 | $50.00 |
| `gpt-6.1-sol` | $2.00 | $0.10 | $2.50 | $10.00 |
| `gpt-6-sol` | $2.00 | $0.20 | $2.50 | $10.00 |
| `gpt-6-luna` | $0.10 | $0.01 | $0.125 | $0.50 |
| `gpt-5.6-sol` | $4.00 | $0.40 | $5.00 | $20.00 |
| `gpt-5.6-terra` | $2.00 | $0.20 | $2.50 | $12.00 |
| `gpt-5.6-luna` | $0.20 | $0.02 | $0.25 | $1.20 |
| `gpt-5.5` | $5.00 | $0.50 | $5.00 (billed as input) | $30.00 |

Dollars per million tokens: OpenAI's Standard prices for prompts of at most 272K input
tokens, as OpenAI's model pages listed them on 2026-10-08, for the models the pinned Codex
0.160.1 lists for API use. Codex 0.160.1 keeps a 272,000-token context for each of them, so
no request reaches the long-context price, and `codex exec` asks for no service tier, so a
run is billed at Standard rates. GPT-5.6 Sol's is OpenAI's promotional price, which OpenAI
says runs at least through 2026-11-21; when OpenAI changes a price, set it in `pricing`
until Axocoatl's table follows. A `pricing` entry has one input rate, which then applies to
every input token, cached or not.

The run settles to that cost, the activation's work log says how it was computed and at
which price, and the Outcome marks it (`usage.cost_computed: true`): the summary, the
JUnit file's `axocoatl.usage` property, the Run outcome panel and the pull request body
show "$X (includes cost computed from reported tokens at list prices)", never as a charge
a provider reported. A computed cost above what the grant still allowed fails the
activation, as a reported one does.

A Codex model that neither the table nor `pricing` names has no price. Its cost is not
known: each such activation reserves an equal share of the cost left, divided by the
activations left with its own, so a later activation, such as the revision a review asks
for, can still run, and its reservation stays charged. The Outcome then says the cost is
not known (`usage.cost_known: false`), and the summary, JUnit, panel and pull request body
show "cost unknown (reserved up to $X)", where $X is what the run's grants were charged,
never as a price.

Before a run starts, its writer's `tokens` budget must hold one model call of its model,
or the run is refused, naming the budget and the minimum (exit code 3). For a model in
Axocoatl's pinned table, one call can use the context the program keeps plus the model's
output limit, within the model's window: 400,000 tokens for each Codex model above (a
272,000-token context plus 128,000 output tokens), 1,000,000 for a Claude model with a
1M-token window (`claude-fable-5-1`, `claude-mythos-5-1`, `claude-fable-5`,
`claude-mythos-5`, `claude-opus-5-5`, `claude-opus-5`, `claude-opus-4-8`,
`claude-opus-4-7`, `claude-opus-4-6`, `claude-sonnet-5-5`, `claude-sonnet-5`,
`claude-sonnet-4-6`, `claude-haiku-5-5`) and 200,000 for a 200K-token one
(`claude-opus-4-5`, `claude-sonnet-4-5`, `claude-haiku-4-5`), from Anthropic's model
overview and model pages. A dated snapshot such as `claude-haiku-4-5-20251001` counts
as its model.

Claude Code's aliases are checked as the model each one runs in Claude Code 2.1.292: the
aliases in the model catalog bundled in that build, which it goes by since its route
serves it no model list of its own. The refusal names that model:

| Alias | Model | One call |
| --- | --- | --- |
| `opus` | `claude-opus-5-5` | 1,000,000 |
| `sonnet` | `claude-sonnet-5-5` | 1,000,000 |
| `haiku` | `claude-haiku-4-5` | 200,000 |
| `fable` | `claude-fable-5-1` | 1,000,000 |
| `best` | `claude-fable-5-1`, or `claude-opus-5-5` for an account without Fable | 1,000,000 |
| `opusplan` | `claude-sonnet-5-5`, and `claude-opus-5-5` in plan mode | 1,000,000 |

`[1m]` after a model or alias (`sonnet[1m]`, `opus[1m]`, `fable[1m]`) is the same call
when the model's window is already 1M tokens. A model the table does not list (a newer
or retired model, `default`, whose model is your account's or organization's, or `[1m]`
on a 200K-token model such as `haiku[1m]`) is not checked, and the run carries the
warning `external_model_not_pinned`, which also says whether its cost will be known.

## What is enforced, and what is not

| | |
| --- | --- |
| Where it runs | Enforced: inside the Session container, as the non-root writer user, under `--harden`. |
| What it can reach | Enforced: only the route to its model API and the hosts the loadout and your configuration allow. |
| Its credential | Enforced: added on your computer; the container holds a placeholder. A token the API returns in a response body would reach the container, as on any route. A ChatGPT sign-in is refreshed by the daemon, on your computer; the container never holds its refresh token. |
| Its time | Enforced: the activation's wall-clock timeout, and the run's wall clock. |
| Its spend | Bounded, not per call. The activation reserves what its grant still allows before the program starts: all of its tokens and, when its cost will be known, all of its cost. Each request on the route counts against the grant's invocations, and the host stops the program when they run out. Claude Code also gets its own spending stop, `--max-budget-usd`, at what the grant still allows. The program's own usage report settles the reservation; without one, usage is marked incomplete and the reservation stays charged. How the cost is known is in [What a run costs](#what-a-run-costs). |
| Its tool calls | Recorded, not admitted. The program's own tool calls are evidence in the record; Axocoatl does not approve or refuse them one by one. They run as the writer user inside the container, like a writer's `bash`. |

<Aside type="caution">
Check the terms of the account whose credential you store. Axocoatl only runs the program
you choose with the credential you supply.
</Aside>

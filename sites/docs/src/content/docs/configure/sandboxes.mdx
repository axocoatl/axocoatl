Every Session executes repository tools inside a sandbox selected by
`sandbox.backend`. The default is a local rootless Podman container. A remote
E2B Cloud backend is available for compatibility Session execution, with different
network and trust implications. Native repository tools and required checks
currently require local Podman; E2B does not implement their supervised command
boundary.

## Local Podman

```yaml
sandbox:
  backend: podman
  network: bridge
  allow_post_create_command: false
  allow_untrusted_images: false
  require_resource_limits: false
```

The two trust flags default to `false`, so a newly opened repository cannot
default its own post-create command to approved or select an arbitrary image.
The network defaults to `bridge`; set `network: none` for repositories you don't
trust. Enable either trust flag only for repositories you trust.

The Session setup review may select an exact curated image—Alpine 3.20, Debian slim,
Ubuntu, Python slim, Node 20 slim, or Rust bookworm—without enabling arbitrary
images. Other image references require `allow_untrusted_images: true`. Common
Docker Hub aliases of a curated preset are canonicalized to the same trusted
reference; no unknown image is silently substituted. Curated means accepted by
this policy, not audited as safe or guaranteed to contain a project's tools.

Before Ready, local Podman probes the POSIX and Git commands that Files, Source
Control, Ways, and Agent tools require. If any are absent, it attempts
distro-aware provisioning inside the container and probes again. A container
that still lacks the required commands is removed and the Session records a
failed environment instead of deferring the failure to a later tool call.

Repository metadata can propose a setup command. With
`allow_post_create_command: true`, the exact devcontainer post-create command
defaults to checked in an unreviewed Session; that policy is visible, and the
Session checkbox can override it. Lockfile-detected `npm ci` always starts
unchecked, and editing any command clears approval. Clearing the command is an
explicit decision to continue without project setup. On local Podman, a root
Node project's `node_modules` is a container-local volume rather than the host's
native dependency tree. The workspace is still mounted read-write: an approved
command may change tracked or untracked project files, and nested package
directories are not given an additional dependency-volume boundary.

Axocoatl automatically protects its control-plane data root and external daemon-lease
root from that bind. It canonicalizes the Workspace before mounting it. If either
protected root is below the Workspace, Podman overlays that exact directory with a
nested `tmpfs`; if the Workspace is equal to or below a protected root, environment
startup fails with an overlap error. A symlink alias cannot bypass the comparison.
There is no YAML switch to weaken this boundary.

Session startup never invokes a host package manager and never creates a Podman
VM. If Podman is absent or its VM has not been initialized, Axocoatl fails with
manual setup guidance. It may start an existing stopped VM.

`network` accepts:

- `bridge` (the default) — outbound access and explicitly published Preview ports;
- `none` — no container network, which also disables package downloads,
  remote tools called from the container, and port publication;
- `egress` — no container network except loopback; an Agent's commands reach only
  the hosts you list under `sandbox.egress`, through Axocoatl's egress proxy. See
  [Network egress](#network-egress).

Set `network: none` or `network: egress` for repositories you do not trust. Any
other value, such as `None`, `off` or `disabled`, is a configuration error that
`axocoatl validate`, `axocoatl doctor` and daemon start report; it never falls back
to `bridge`.

Axocoatl starts every Podman container with `--http-proxy=false`, so the host's
`HTTP_PROXY`, `HTTPS_PROXY`, `FTP_PROXY` and `NO_PROXY` variables (in either case)
are not copied into it, and a proxy's user name and password stay on the host.

With `network: none`, choose an image that already contains Axocoatl's required
repository commands. Readiness provisioning cannot download missing commands
without a container network, and a repository setup command that needs packages
will likewise fail with retained evidence. Podman may still pull the selected
image as a host operation; that is not Session container egress.

When supported by the host, local Session containers request 2 GiB memory, two
CPUs, and 512 PIDs. With `require_resource_limits: false`, a host that cannot
apply cgroup limits falls back to an uncapped container and logs a warning.
Set it to `true` to fail Session creation instead.

## Network egress

```yaml
sandbox:
  backend: podman
  network: egress
  egress:
    allow:
      - npm
      - pypi
      - host: api.example.com
```

With `network: egress`, a Session container has no network interface other than
loopback. Its only way out is Axocoatl's egress proxy, which connects only to the
hosts and ports you allow. The proxy checks a host name against your list before
anything resolves it, and Axocoatl resolves allowed names on your computer, not in
the container. The container cannot send DNS queries, UDP or IPv6 traffic off the
machine. See [`sandbox.egress`](/reference/config/#sandbox) for the list format and
presets.

How a Session runs under it:

- The proxy runs in a second container, `axo-egr-<session>`, started before the
  Session container. Its image, `localhost/axocoatl-egress:<id>-<arch>`, is built
  locally from Axocoatl's bundled execution supervisor and contains nothing else: no
  shell, no resolver and no environment. It needs no download.
- The Session container runs with `--network none`. Its first process is Axocoatl's
  bridge, which serves the proxy on `127.0.0.1:3128`, so the image's own
  `ENTRYPOINT` does not run under `egress`.
- Each `bash` command of an Agent that may change files, each approved setup
  command, readiness provisioning and each terminal you open gets its own proxy
  credential, in `HTTPS_PROXY`, `HTTP_PROXY`, their lowercase forms, the npm proxy
  settings, `NO_PROXY` and `NODE_USE_ENV_PROXY=1`. The credential ends when that
  command, setup step or terminal does. It reaches the process through an
  environment file that Podman reads, never through a command line.
- Read-only helpers, required checks, Axocoatl's own repository captures,
  background tasks and other commands get no credential, so they have no network.
- Exposed ports still work in Preview. The Session container publishes nothing; its
  first process serves each exposed port as a socket in a volume, and a third
  container, `axo-pvw-<session>`, from the same image as the proxy, publishes those
  sockets on your computer's loopback address. It reaches the Session's app only
  through those sockets and never connects anywhere else.
- Readiness provisioning reaches only the Alpine, Debian and Ubuntu package mirrors.
  If an image needs another package manager, use an image that already has
  Axocoatl's required commands.

The proxy refuses loopback, link-local and other special addresses, the Podman host
gateways (`192.168.127.1` and `192.168.127.254` in a Podman machine, `10.88.0.1` on
Podman's default network, and the gateway of `sidecar_network`) even inside a listed
range, and private addresses unless you list a private range under
`private_destinations`. A refusal is an HTTP answer the tool can show. For example, a host that is not on
the list gets:

```text
HTTP/1.1 403 Forbidden
Content-Type: application/json
X-Axocoatl-Egress: denied; reason=not_allowed

{"error":"egress_denied","reason":"not_allowed","host":"example.org","port":443,
 "hint":"example.org:443 is not in this Session's egress allowlist. Ask the user to allow it for this Session in Session network or to add it under sandbox.egress.allow."}
```

A process without a credential gets `407` with reason `no_credential`, and a name
that resolves to a refused address gets `403` with `private_destination` or
`forbidden_destination`. When a tool call's credential ends, or a person revokes the
host, while its connection is being decided, the connection is refused; one already
open is closed.

Every connection the proxy allows or refuses is written to the Session's network
record before it opens, with the host, port and the tool call whose credential it
presented. Bytes and duration are added when it closes. If the record cannot be
written, the connection is refused. Refusals of connections without a valid
credential, which any process in the container can cause, are recorded one by one
up to 20 at once and then one every 5 seconds; the others are counted in a `limit`
event once a minute, so they cannot fill the record. The record's cap
(`record_max_events`) applies to the Session for as long as it exists, across
runtime restarts. Once it is reached, new connections get `503 record_unavailable`
until you raise the cap and restart the daemon; setup commands, provisioning and
terminals still run, without network.

If Axocoatl's config file is inside the Session's Workspace, its Agents can read
it, and **Session network** says so. Keep secrets in environment variables. Read the record with
[`GET /api/sessions/{id}/network`](/reference/http-api/), or open **Session network**
from an Agent's details in the Session graph. It shows the policy of each scope
(the Session's list, provisioning and, with `browser:` configured, the browser's
declared hosts), allowed and refused counts and each refused connection; a refused
host can be allowed for that Session only with **Allow for this Session**, which is
recorded and applies to new connections at once, in the scope of the refused
connection. Each activation's details also show its tool calls' network activity.

An Agent can ask for a host it was refused. Give a writer Agent the
`request_network_access` tool in its `tools` list; it names one exact host, its ports
and a reason. The request waits in **Session network** under **Hosts Agents asked
for**, with **Approve** and **Reject**, while the Agent's tool call waits for your
answer (two minutes by default, at most ten). **Approve** allows the host for that
Session exactly like **Allow for this Session**, recorded with the request's id;
**Reject** allows nothing. If nobody answers in time, the call tells the Agent the
request is still pending, and the request stays in the panel. Only you can approve:
there is no automatic approval, and no Agent can approve a request. Read-only helpers
cannot ask, and the tool is not offered outside `network: egress`. See
[Hosts Agents ask for](/reference/http-api/#hosts-agents-ask-for).

To change the list for every Session while the daemon runs, edit `sandbox.egress.allow`
or `private_destinations` (or `browser.allow` and `browser.private_destinations`) in
the configuration file and run `axocoatl network reload`, or send
[`POST /api/network/reload`](/reference/http-api/#reload-the-network-allowlists). The
daemon validates the whole file; an invalid file changes nothing. The command
lists every entry each list gains and loses, a preset as each of its hosts. Each
running Session records its new policy and uses it for new connections at once,
open connections that no rule allows any more are closed, and the Session's own
allows stay. A Session whose new policy cannot be recorded keeps its old one; the
command says which and exits with status 1, and running it again retries that
Session. Other settings, such as `network`, `sidecar_network` and `max_connections`,
still need a restart; the command lists the ones that changed. A configuration file
inside a Session's Workspace is never reloaded, because that Session's Agents can
edit it.

If the proxy's control channel is lost, Axocoatl removes the proxy container and
starts it again after 1, 5 and then 30 seconds. After five restarts in ten minutes
it stays stopped, and the bridge answers every proxied request with `502` until the
Session's runtime is started again. The proxy fails closed: while it is down,
nothing gets out.

What it costs, measured on one Mac with rootless Podman 5.8: `npm ci` of an Express
fixture (about 65 packages, empty npm cache) took 1.5 s under `egress` against 0.7 s
under `bridge`; it made 15 connections through the proxy. The wall time of an Agent's
tool call did not change measurably. Your numbers will differ with the registry, the
network and the tool.

What egress does not cover:

- The proxy cannot see inside TLS. A listed host that serves many sites, such as a
  CDN, can be used to reach those sites, and a listed host that accepts uploads
  (`github`, `npm`, `pypi`, `crates`) is a way for data to leave. `validate` and
  `doctor` warn about both.
- Traffic from Axocoatl itself is outside the proxy: model providers, MCP servers,
  `web_search` and `web_fetch`, webhooks and Podman image pulls. The web tools run
  on your computer, so `sandbox.egress` does not limit them; their calls are kept in
  the Session's network record as `web_request` and `web` events.
- Agents in one Session share its container. A read-only helper cannot connect to
  the proxy over TCP, but it can read a running writer's credential from that
  process's environment under `/proc`. Axocoatl does not separate Agents inside one
  Session container.
- Programs that ignore the proxy variables cannot connect at all, for example some
  Go and gRPC clients, and Node's `fetch` before Node supports
  `NODE_USE_ENV_PROXY`.
- Ways attempt containers run with no network under `egress`.
- A Session created before the native Session format cannot use `egress`; start a
  new Session.
- `egress` needs local Podman. E2B is refused.

## Remote E2B backend

```yaml
sandbox:
  backend: e2b
  e2b:
    api_url: "https://api.e2b.dev"
    api_key: "${E2B_API_KEY}"
    template: base
    domain: e2b.app
    git_token: "${GITHUB_TOKEN}"
```

Axocoatl 1.0 targets E2B Cloud with this backend. Third-party E2B API
implementations are not part of the 1.0 support scope.

`git_token` supports
GitHub-compatible token authentication when the
remote VM must clone or push a private repository. The runtime injects it as a
sandbox secret for an origin-scoped Git credential helper rather than writing
it into repository Git configuration. The secret is an environment variable of
the VM, so every command in the VM can read it, including repository scripts,
setup commands and Agent commands. Use a token limited to the repositories and
permissions the Session needs. Other Git hosts may require a different
username or credential flow and are not implied by this field.

The selected template is daemon-global. E2B does not accept a per-Session OCI
image; the Session review shows the configured template and blocks an explicit
or devcontainer image until it is cleared or the daemon switches to Podman.

Before Ready, Axocoatl verifies that the template contains the repository
commands required by Files, Source Control, and Agent tools; a deficient
template fails with retained environment evidence instead of degrading later.

Unlike local Podman, Axocoatl does not package-provision the remote template;
build those commands into the daemon-selected template itself.

E2B does not implement Axocoatl's local Preview transport or exposed-port
mapping. Leave Session ports empty and use the remote provider's deliberate
service-exposure mechanism when needed. `sandbox.network: none` is likewise a
Podman enforcement option; Axocoatl rejects that combination with E2B rather
than claiming to disable remote egress.

With the E2B Cloud backend, Axocoatl persists the exact runtime identity and remote
working root. Closing
a Ready E2B Session pauses that VM; reopening or recovering after a daemon restart
connects to the same runtime, so scratch and uncommitted work are not replaced by
a fresh clone. Failed or interrupted preparation is cleaned up instead. Deleting
the Session or choosing Change/Rebuild runtime is the explicit destructive
boundary from Ready. A missing runtime fails visibly instead of silently creating
a replacement.

<Aside type="caution" title="Remote means the Workspace leaves the machine">
A remote backend transfers repository content and command data to the selected
service. Review its operator, retention, region, access controls, and template
before authorizing sensitive code.
</Aside>

## Choose a policy

| Need | Recommended configuration |
| --- | --- |
| Default local development | Podman, bridge network, trust flags off |
| Review untrusted code without Session egress | Podman, `network: none`, an image already containing required commands, trust flags off, limits required if the host supports them; account separately for host-side image pulls |
| Install packages from known registries only | Podman, `network: egress` with the registries' presets, trust flags off |
| Run a local web app in Preview | Podman `bridge` or `egress` plus an exposed Session port |
| Remote compatibility execution | E2B Cloud with scoped credentials and an approved template; no Axocoatl Preview ports |
| Several isolated Ways | Local Podman |

Sandboxing reduces risk; it does not make prompts, dependencies, images, MCP
servers, webhooks, provider endpoints, or copied secrets trustworthy. See
[Security](/operate/security/) for the complete boundary.

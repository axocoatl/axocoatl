`axocoatl onboard` configures Axocoatl once for the current operating-system
user. It does not create a project directory, Workspace, Session, or repository.
You choose the folders Axocoatl can use later through **Open workspace…** in the
browser app.

## Run the setup wizard

```sh
axocoatl onboard
```

The wizard offers two starting providers for native Sessions:

- Ollama;
- OpenRouter.

For a new installation, choose Ollama or OpenRouter for Session work. New data
roots use native execution, which currently accepts only reviewed local Ollama
profiles and eligible OpenRouter-credit profiles. Anthropic, OpenAI, Gemini, and
Mistral remain compatibility adapters configured manually; they are not eligible
for native Session execution. See [Providers](/configure/providers/).

For a hosted provider, the API-key prompt is masked. A supplied key is stored in
the owner-only user configuration; leaving it blank keeps the provider's
`${PROVIDER_API_KEY}` environment reference instead.

### Ollama

The wizard asks for the Ollama server URL, `http://localhost:11434` by default,
and checks it before it writes anything. Native Sessions use an Ollama server
only when it:

- is reached at a loopback address on this machine, such as `localhost`;
- runs Ollama **0.20.6**, the audited version;
- reports its cloud features disabled in `GET /api/status`
  (`"cloud": {"disabled": true}`).

A URL that is not a loopback address is refused, and the wizard asks for the URL
again. If the server fails another check, the wizard says which one and offers to
check again, to use a different server URL, or to continue with this one. Native
Sessions refuse that server until it is fixed, and `axocoatl doctor` reports it
as a failure. To turn Ollama's cloud features off, do one of these and restart
Ollama:

- add `{"disable_ollama_cloud": true}` to `~/.ollama/server.json` of the user
  that runs Ollama (this also works for the Homebrew service);
- start the server with `OLLAMA_NO_CLOUD=1`, for example
  `OLLAMA_NO_CLOUD=1 ollama serve`. For the macOS app, run
  `launchctl setenv OLLAMA_NO_CLOUD 1`, then quit and reopen Ollama.

`curl -s http://localhost:11434/api/status` then shows `"disabled":true`. You
can also keep your usual Ollama as it is and run a second, cloud-disabled server
on another port, for example
`OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11436 ollama serve`, then give the
wizard `http://127.0.0.1:11436`.

The wizard then lists the models installed on that server and preselects one for
**Lead** and one for **Reviewer**. You can pick any installed model or type
another name.

- For Lead, it prefers a coding model: a Qwen3-Coder tag when one is installed,
  then the largest other coding model, then the largest general model.
- For Reviewer, it prefers a different, larger model, gpt-oss when one is
  installed, so a second model checks Lead's work (see
  [Cross-model review](/configure/cross-model-review/)). Without a larger model,
  Reviewer uses Lead's model.
- Cloud models and embedding models are never suggested.
- If the server has no local model, it suggests `qwen3-coder:30b`, a large
  download.

Scout and the chat Assistant use Lead's model. For a model that is not installed
yet, the wizard offers to run `ollama pull` against that server.

OpenRouter setup uses ordinary OpenRouter credits and asks you to confirm that no
BYOK provider keys are connected. It suggests a non-reasoning text/tool model and sets
an explicit output limit; any eligible model id works, reasoning models included. BYOK support is deferred. Review the Session's **Team &
budget** before execution; see [OpenRouter configuration](/configure/providers/#configure-openrouter).

When using `axocoatl onboard --install-daemon` with a hosted provider, enter the
key during onboarding. The generated service does not inherit shell environment
variables, so onboarding refuses to install it while the configuration still
contains an environment placeholder.

<Aside type="caution" title="The user configuration contains secrets">
A supplied hosted-provider key is stored as plain text in a configuration file
with owner-only permissions (`0600` on supported Unix systems). Axocoatl does
not encrypt that file. Protect it and its backups. The wizard does not create a
`.env.example` file, and Axocoatl does not load dotenv files automatically.
</Aside>

## Default team

Both choices write the same Agents on the provider you choose. With OpenRouter
they all use the model you enter; with Ollama, Reviewer uses the Reviewer model
and the others use the Lead model:

| Agent | Role | Tools | May change |
| --- | --- | --- | --- |
| **Lead** (`lead`) | Autonomous | `read_file`, `list_dir`, `grep`, `glob`, `write_file`, `edit_file`, `bash` | Any file |
| **Scout** (`scout`) | Worker | `read_file`, `list_dir`, `grep`, `glob`, `bash` | Nothing (`writes: []`) |
| **Reviewer** (`reviewer`) | Worker | `read_file`, `list_dir`, `grep`, `glob`, `bash` | Nothing (`writes: []`) |
| **Assistant** (`assistant`) | Autonomous | none | Not used in Sessions by default |

Lead owns the change. Its instructions say to look first, to verify with the tests,
and, if it has helpers, to send a focused read-only question to Scout and to ask
Reviewer for an independent review before finishing. Scout answers with file paths,
line numbers and short evidence. Reviewer reports concrete defects with `file:line`,
or says it found none. Neither changes files.
Assistant is the plain chat Agent for `axocoatl chat`.

This is configuration only: onboarding still creates no project, Workspace, or
Session. A new Session selects Lead unless you choose another Agent, and starts with
Lead alone: in **Team & budget** you enter Lead's limits and choose **Apply** before the
first request. Scout and Reviewer are offered there as Lead's helpers; select **Let this
Agent delegate to helpers** and enter each helper's limits to use them. Required checks
and a required review stay off until you add them.
[Default team](/understand/coordination/#default-team) describes how the helpers run,
and [Agents](/configure/agents/#the-default-team) how to change them.

## User-level locations

Onboarding creates no files in the directory from which you run it:

| Platform | Configuration | Durable data |
|---|---|---|
| macOS | `~/Library/Application Support/Axocoatl/config.yaml` | `~/Library/Application Support/Axocoatl/data/` |
| Linux and WSL2 | `$XDG_CONFIG_HOME/axocoatl/config.yaml`, or `$HOME/.config/axocoatl/config.yaml` when XDG is unset | `$XDG_DATA_HOME/axocoatl/`, or `$HOME/.local/share/axocoatl/` when XDG is unset |

Plain config-aware commands resolve these paths regardless of the current
directory. A repository's `axocoatl.yaml` is never selected implicitly.

Running `axocoatl onboard` again never overwrites an existing user
configuration silently. It reports the existing path and requires an explicit
decision before replacing it.

## Run doctor

```sh
axocoatl doctor
```

Doctor performs these checks against the resolved user configuration:

| Check | Failure level | What to do |
|---|---|---|
| Configuration parses and validates | Required | Fix the reported field, then run `axocoatl validate`. |
| Configured Ollama endpoint responds | Required when configured | Start Ollama or correct `providers.ollama.base_url`. |
| The Ollama endpoint is a loopback address | Required when configured | Native Sessions use only an Ollama server on this machine; set `providers.ollama.base_url` to one. |
| The Ollama server reports version 0.20.6 | Required when configured | Install Ollama 0.20.6, or point `providers.ollama.base_url` at a server that runs it. |
| The Ollama server reports its cloud features disabled (`GET /api/status`) | Required when configured | Add `{"disable_ollama_cloud": true}` to `~/.ollama/server.json` or start the server with `OLLAMA_NO_CLOUD=1`, then restart Ollama; or point `providers.ollama.base_url` at a cloud-disabled server. |
| Every configured Ollama model is present | Required when configured | Run `ollama pull <model>`. |
| Data directory is writable | Required | Fix permissions or set `AXOCOATL_DATA_DIR`. |
| Rust toolchain | Warning | Needed only to build from source. |
| Hosted-provider key appears present | Warning | Supply the key during onboarding or export the referenced environment variable before using that Agent. OpenAI, Anthropic, Gemini, Mistral, and OpenRouter are checked when configured. |
| Daemon IPC is reachable | Warning | Start `axocoatl dev` or `axocoatl serve` when you need it. |
| Podman runtime answers a bounded `podman info --format json` probe | Warning | Required for default folder Sessions and several Ways; follow the reported install, machine, or runtime guidance. |
| Configured webhooks | Egress notice | Confirm that each named destination is intentional. |

Doctor checks the Ollama server requirements of native Sessions, but not each
model's native profile. **Team & budget** performs the exact provider/model and
allowance review before native work starts.

Doctor exits non-zero when a required check fails. A Podman warning does not
make a provider-only one-shot command fail, but it does block the normal local
Session path. Before reporting Podman ready, doctor checks the client, checks
the applicable machine state on macOS, and requires the bounded runtime probe
to return a JSON object successfully.

## Validate without starting the runtime

```sh
axocoatl validate
```

Validation checks identities, provider and model fields, dependencies, MCP
transports, token-budget relationships, and other schema constraints. It does
not prove that a hosted credential is valid or that a model account currently
permits access.

## Advanced: use an explicit configuration

Project-local or operator-managed YAML remains supported, but it must be
selected explicitly:

```sh
axocoatl validate /absolute/path/to/axocoatl.yaml
axocoatl doctor --config /absolute/path/to/axocoatl.yaml
axocoatl dev --config /absolute/path/to/axocoatl.yaml
```

`AXOCOATL_DATA_DIR` overrides the data location. Without that override, an
explicit configuration uses a `data/` directory beside the configuration file.

## Start the workbench

```sh
axocoatl dev
```

By default the app is at `http://localhost:8080`. Keep this process running,
open the `Sign in:` link it prints (or run `axocoatl url`), and choose
**Open workspace…** to authorize the repository you want to use. Then [create your first Session →](/start/first-session/).

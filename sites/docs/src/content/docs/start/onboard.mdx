After the installer, `axocoatl onboard` is the one setup command. It finds what this
computer has, says what is missing, asks before each change to the computer, makes
the change itself, and ends in one of two ways: ready (exit 0), or a numbered list of
the steps still left (exit 1). It never prints a ready line after a failed check.

```sh
axocoatl onboard
```

Onboarding configures Axocoatl for the current operating-system user. It does not
create a project directory, Workspace, Session, or repository; you choose the folders
Axocoatl can use later through **Open workspace…** in the browser app.

## How it asks

- Each change to the computer is its own question, showing the exact command, what it
  downloads, and what else it affects.
- Enter answers **yes** only when the size is shown and the change fits this computer.
  Enter answers **no** for anything that changes an existing setup you did not ask to
  change: an existing Podman machine, an existing Ollama configuration
  (`~/.ollama/server.json`, Homebrew's `services/ollama.env`, a systemd drop-in
  onboarding wrote before). The configuration is the exception: once you choose
  **Update this setup** or **Replace it**, the change to `config.yaml` is shown and
  Enter writes it.
- A command that needs `sudo` asks for your password itself. With `--yes`, such a
  command runs only with `--allow-sudo`; otherwise it is listed as a step left.
- Keys are never pasted into a command line. Claude Code and Codex sign in through
  `axocoatl connect` in the browser. For OpenRouter, onboarding signs you in in the
  browser itself (or uses the key you connected with `axocoatl connect openrouter`);
  an environment variable or a hidden prompt are the other ways.
- Every command onboarding runs, with its exit status, is written to
  `~/Library/Logs/Axocoatl/onboard-<time>.log` on macOS and
  `~/.local/state/axocoatl/onboard-<time>.log` on Linux (`$XDG_STATE_HOME/axocoatl`
  when it is set).
- Running `axocoatl onboard` again keeps what is set up: see
  [Running onboard again](#running-onboard-again).

## What it does

### Step 0: this computer

Onboarding prints what it found, for example:

```text
This computer: macOS 26.6, Apple M5 Pro, 48 GB memory, 18 cores, 412 GB free.
Found: Homebrew 7.0.10, Podman 6.1.4 (no machine), Ollama 0.40.6 at http://localhost:11434 (cloud models on), claude 2.1.292, git 2.39.5.
Not found: codex, gh.
```

It reads the operating system (on Linux, `/etc/os-release` and whether this is WSL),
memory, processors and free disk (for the models, and for Podman when that is another
file system), and looks for Homebrew, Podman, Ollama, `claude`, `codex`, `gh`, `git`,
a running Axocoatl daemon and its version, and an installed Always-On Service. It
checks whether port 8080 is free only when `--port` does not name the port. It stops if it runs as root
(loadout runs need rootless Podman) or in WSL 1 (`wsl --set-version DISTRO 2`, where
DISTRO is the name `wsl -l -v` lists). On macOS a missing `git` is the Command Line
Tools stub, which onboarding does not run (`xcode-select -p` finds no tools; running
the stub opens Apple's installer); onboarding offers `xcode-select --install`. It also
names a platform the release gate does not verify (an Intel Mac, a Linux other than
Ubuntu 24.04, WSL2, SELinux enforcing), and warns when `HTTPS_PROXY`, `HTTP_PROXY` or
`ALL_PROXY` is set: a Session's network connects directly, never through a proxy (see
[Proxies, VPNs and rate limits](/start/install/#proxies-vpns-and-rate-limits)).

### Step 1: who writes the code

```text
Who writes the code?
> Claude Code (your Claude Pro or Max plan; claude found at ~/.local/bin/claude)
  Codex (your ChatGPT plan)
  A local model on this computer (Ollama, no account, needs 48 GB memory or more)
  A hosted model (OpenRouter credits)
```

The default is Claude Code when `claude` is installed, else Codex when `codex` is,
else a local model with 48 GB of memory or more, else OpenRouter. (On Linux,
`MemTotal` leaves out what the kernel reserves, so up to 6% less than 48 GB counts.)
When it updates a setup, the default is the writer that setup has, and `--yes` keeps
it. Every fix run also
needs a reviewer: a different model that only reads the change. Claude Code and Codex
can write but cannot review, so their path sets up a reviewer on Ollama or OpenRouter.

### Step 2: the sandbox

Every Session and every `axocoatl run` uses a rootless Podman sandbox.

On **macOS**:

- Podman missing, Homebrew present: `brew install podman` (about 100 MB). Without
  Homebrew, onboarding points to the installer from podman.io. Podman 6 no longer
  supports Intel Macs; there onboarding names the Podman 5.8 package and does not
  install anything (Axocoatl has not been tested on Intel Macs).
- No machine:

  ```text
  Create the Podman machine your Sessions run in?
        podman machine init --cpus 6 --memory 8192 --disk-size 60
        podman machine start
      This downloads about 0.9 GB and uses up to 8 GiB of memory while it runs. [Y/n]
  ```

  The size is 6 CPUs and 8 GiB, clamped to half the processors and half the memory
  (`--machine-cpus` and `--machine-memory` change it); onboarding prints any other size
  as not yet tested. The machine is never rootful. When
  Podman would create it with a provider other than `applehv` (the podman.io package
  defaults to libkrun), onboarding offers to write `[machine] provider = "applehv"` to
  `~/.config/containers/containers.conf` first. It creates a machine only where
  Podman has no connection defined; a connection that exists but does not answer,
  or a `CONTAINER_HOST` or `CONTAINER_CONNECTION` that does not answer, is a step to
  fix instead.
- A stopped machine: `podman machine start`. (Sessions and runs also start an
  existing stopped machine themselves.)
- A rootful machine (Podman Desktop creates one by default): every `axocoatl run`
  would stop with exit 5, so onboarding asks, with **no** as the default, to switch it:
  `podman machine stop`, `podman machine set --rootful=false`, `podman machine start`.
  This affects other tools that use the machine. Answering no offers the other way
  out, also with **no** as the default: keep that machine and create a separate rootless
  machine named `axocoatl` (`podman machine init … axocoatl`). Only one machine runs at a
  time, so the step left says to stop the other one and to start Axocoatl from a shell
  with `export CONTAINER_CONNECTION=axocoatl` (`axocoatl service install` records it;
  Sessions and runs start that machine). Answering no twice leaves a step that names
  both ways out.
- A machine with less than 4 GiB: onboarding offers `podman machine set --memory`
  (default no).
- Every `podman machine` command names the machine Podman uses when it is not
  `podman-machine-default` (Podman acts on `podman-machine-default` without a name), and
  the machine `CONTAINER_CONNECTION` names when that is set. Through `CONTAINER_HOST`,
  or a `CONTAINER_CONNECTION` that is not a machine, onboarding changes no machine; a
  problem there is a step left.
- Podman installed in a directory that is not on your `PATH` (Homebrew's
  `/opt/homebrew/bin` before `brew shellenv` runs, for example) is a step left:
  `axocoatl dev`, the service and every run look for Podman on `PATH`.

On **Linux and WSL2**:

- Podman missing: the install command for the distribution, which asks for your
  password:

  | Distribution | Command |
  | --- | --- |
  | Ubuntu, Debian and derivatives | `sudo apt-get install -y podman` |
  | Fedora, RHEL and derivatives | `sudo dnf install -y podman` |
  | Arch | `sudo pacman -S --noconfirm podman` |
  | openSUSE, SLES | `sudo zypper install -y podman` |

- Ubuntu 22.04 ships Podman 3.4.4. Axocoatl runs need Podman 4.3 or later (the 1.5.0
  release gate runs Ubuntu 24.04's), so onboarding stops there and asks for Ubuntu 24.04
  or newer. Any other Podman from 4.3 on (4.3 to 4.8, or Fedora's 5.x and Arch's 6.x)
  is accepted and reported as not tested on Linux yet; 4.9 is the tested one.
- No range of subordinate user ids, or fewer than 65536, in `/etc/subuid` and
  `/etc/subgid` (rootless Podman cannot unpack images or start Sessions without one;
  its sandbox container fails with `crun: write to /proc/sys/net/ipv4/ping_group_range:
  Invalid argument`): `sudo usermod --add-subuids <first>-<last> --add-subgids
  <first>-<last> <user> && podman system migrate`, with the first 65536 ids from 100000
  up that no line of either file uses (100000-165535 whenever no line uses those, for
  example when both files are empty). Onboarding and doctor read
  both files and print the exact command; with `--yes`, onboarding runs it only with
  `--allow-sudo`. A range that is in the files but that Podman has not picked up yet
  needs only `podman system migrate`, which stops your running containers. When only
  one of the files is short, only it gets a range. When the files leave no free range
  from 100000 up, onboarding names none and asks you to choose one. Rootless Podman maps
  a range with `newuidmap` and `newgidmap`, which it looks up on `PATH` only. When one is
  missing or may not map (neither setuid nor given file capabilities), Podman maps only
  your own id, or, with a range in the files, `podman info` fails with `command required
  for rootless mode with multiple IDs: exec: "newuidmap": executable file not found in
  $PATH` (once Podman has run before, its logged error also says to try `podman system
  migrate`, which alone changes nothing). Onboarding then offers the package that ships
  them, then `podman system migrate`: `sudo apt-get install -y uidmap` on Debian and
  Ubuntu (Podman only recommends it). When the package is installed but a helper's file
  is gone, or it lost its setuid bit or file capabilities, an install would do nothing,
  so onboarding offers the reinstall: `sudo apt-get install --reinstall -y uidmap`,
  `sudo dnf reinstall -y shadow-utils` on Fedora and RHEL (where shadow-utils is always
  installed), `sudo pacman -S --noconfirm shadow` on Arch. Onboarding and doctor first
  read what the package manager would do: a dpkg diversion, stat override or
  `path-exclude`, dnf set to `nocaps`, an rpm that gives the helpers no privilege, or
  pacman's `NoExtract` or `NoUpgrade` for a helper each keep a reinstall from restoring
  it, and then the fix says what to change first instead of offering the reinstall. If an
  install or reinstall runs and the helpers still cannot map (something on the computer
  changes them afterwards, which no package record shows), or the command fails,
  onboarding says so and keeps what happened in your Axocoatl data directory
  (`onboarding/id-map-attempt.json`): `axocoatl doctor` and later onboarding runs say
  it, with the date, and do not offer the same command again while the helpers are the
  same files (an upgrade that writes them again ends that). A failure says why: a build
  dnf no longer has (run `sudo dnf upgrade -y shadow-utils` instead), apt's out-of-date
  lists (run `sudo apt-get update` first), or what the command reported.
  Helpers in `/usr/bin` while `/usr/bin` is not on `PATH` are reported as such, with no
  install, and so is a copy earlier on `PATH` that the package does not own; on other
  distributions the fix says what to install or reinstall. Doctor names the
  same fix: on its Podman line when `podman info` fails, otherwise on its User ID ranges
  line. With `CONTAINER_HOST`, `CONTAINER_CONNECTION` or a remote connection, this
  computer's files are not read and nothing is run: the range belongs where that Podman
  runs, and there, as that Podman's user, `podman system migrate` runs and then its API
  service restarts (either one alone keeps the old mapping).
- Landlock: below ABI 3 (Linux 6.2) fix, fix-claude-code, fix-codex and audit cannot
  run their read-only reviewer, and onboarding says how to get a newer kernel (Debian
  12: bookworm-backports; WSL: `wsl --update`). ABI 3 works, but read-only helper
  shells need Linux 6.7.
- SELinux is reported with what Axocoatl does about it: Session and browser
  containers run with SELinux labelling off; WSL without systemd is told that
  the Always-On Service is unavailable and that `axocoatl dev` works.

Then one throwaway container proves the setup: onboarding pulls
`docker.io/library/alpine:3.20` (about 4 MB, the image Sessions start from) and runs it
rootless with `--userns=keep-id`, no network, no capabilities and `--rm`. On success it
prints a line such as `✓ Sandbox ready: Podman 6.1.4, applehv, rootless, 6 CPUs / 8 GiB`.

### Step 3A: a local writer and reviewer (Ollama)

1. **Ollama missing.** macOS with Homebrew: `brew install ollama && brew services start
   ollama` (about 40 MB; models download separately); without Homebrew, onboarding
   points to [ollama.com/download](https://ollama.com/download). Linux:
   `curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.40.6 sh`, which sets
   Ollama up as a systemd service and asks for your password (with `zstd` installed
   first when it is missing). When that installer finds no NVIDIA or AMD GPU,
   onboarding says what it means: models run on the CPU alone, much more slowly. In
   WSL it is installed inside the distribution; the Windows app is not reachable from
   WSL in its default NAT mode. At a terminal, when nothing answers at the Ollama
   address, onboarding first asks whether Ollama already runs at another address on
   this computer, and uses that one (`--ollama-url URL` without a terminal).
2. **Version.** Native Sessions accept Ollama 0.40.6 and later. A later 0.40 release
   is accepted as is; a later 0.x release (0.41 or later) is accepted only once the
   contract probes pass on each model, and onboarding, `doctor` and the run's receipt
   say it is newer than the audited 0.40.6. An older Ollama is upgraded after asking
   (`brew upgrade ollama && brew services restart ollama`, or the pinned Linux
   installer). When the `ollama` on PATH is accepted but the server still runs an older
   version, the fix is a restart (`brew services restart ollama`), not another upgrade.
   A pre-release, a development build or a new major release is refused, with the
   install command for 0.40.6; onboarding never suggests `brew upgrade` for a version
   that is too new.
3. **Cloud models off**, which native Sessions require and which a fresh Ollama has on.
   Onboarding changes the setting the running server reads, then waits until
   `GET /api/status` reports `"disabled": true`:
   - the Homebrew service or an `ollama serve` you run: it adds
     `{"disable_ollama_cloud": true}` to `~/.ollama/server.json` (keeping every other
     key and backing the file up first) and runs `brew services restart ollama`, or
     asks you to restart your server;
   - the macOS app: turn off Cloud in Ollama's Settings, then press Enter;
   - the Linux service (it runs as the user `ollama`): it writes
     `/etc/systemd/system/ollama.service.d/axocoatl-no-cloud.conf` with
     `Environment="OLLAMA_NO_CLOUD=1"`, then runs `sudo systemctl daemon-reload` and
     `sudo systemctl restart ollama`.

   This also turns off Ollama's web search.
4. **Models by memory.** Models already installed come first, at any memory size.
   Among those that fit this computer and call tools, onboarding picks a writer
   (Qwen3-Coder first, then the largest coding model, then the largest other model,
   vision models last); when another of them is a gpt-oss model or is larger than that
   writer, it suggests the two, and Enter (or `--yes`) takes them. A model whose
   `capabilities` Ollama lists without `tools`, or Qwen2.5-Coder, which returns its tool
   calls as JSON text that never runs, is offered but never suggested, and onboarding
   says why. Any model larger than about 0.65 of this computer's
   memory is labelled too large and never preselected. With no such pair installed:

   | Memory | Writer | Reviewer | What is known |
   | --- | --- | --- | --- |
   | 96 GB or more | `qwen3-coder:30b` (18.6 GB) | `gpt-oss:120b` (65.4 GB) | gpt-oss 120B is the reviewer Axocoatl has measured |
   | 48 to 95 GB | `qwen3-coder:30b` (18.6 GB) | `gpt-oss:20b` (13.8 GB) | How well this reviewer reviews has not been measured. The 1.5.0 release gate requires runs with the local models onboarding sets up on its Mac to pass, and its evidence names them ([Install](/start/install/)) |
   | Under 48 GB | — | — | Not yet verified with local models. Onboarding offers no local pair by default: it says which of these models fit and offers OpenRouter, Claude Code or Codex instead |

   Under 48 GB onboarding suggests a model only when it fits this computer, as `doctor`
   judges it (at most about 0.65 of its memory): on a 24 GB Mac only `gpt-oss:20b` of
   these models does, and on a Mac with less memory neither does. With no such pair
   installed, at a terminal it first offers OpenRouter for both (the default), Claude
   Code or Codex as the writer (their setup follows), a local writer with OpenRouter
   reviewing, or local models for both. The reviewer must be a different model from the
   writer. Under 48 GB with `--yes` and no such pair installed, `--writer ollama` stays
   local: without `--writer-model` and `--reviewer`, naming the models is a step left
   (onboarding never switches it to OpenRouter by itself).
5. **Pull.** One question shows each size and the free disk, counting a tenth more for
   Ollama's temporary files:
   `Pull qwen3-coder:30b (18.6 GB) and gpt-oss:20b (13.8 GB)? Needs 35.6 GB free; 412.0 GB
   free here.` A model too large for this computer's memory is named in that question,
   and Enter does not pull it; `--yes` pulls it only with `--pull`. Its step left names
   `axocoatl onboard` with the writer you chose, so it does not ask again who writes: a
   smaller model with `axocoatl onboard --update --writer ollama`, or a hosted writer and
   reviewer with `axocoatl onboard --update --writer openrouter` (or `--writer
   claude-code`, or `--writer codex`); for Claude Code and Codex, a smaller reviewer, or
   `--reviewer openrouter:openai/gpt-oss-120b`. `--update` moves the Agents onboarding
   wrote, and `run.models`, to the new models. It says `--replace`, which backs the
   configuration up and writes the team for the new models, when an Agent that `--update`
   keeps as it is (one that differs from what onboarding writes, or your own) runs the
   model. With
   `--yes` or `--pull`, a pull that does not fit the disk is not started but left as a
   step. A failed pull shows Ollama's own error and offers to retry. After a pull,
   onboarding reads the model again: if Ollama pulled a variant native Sessions refuse
   (the MLX variant on Apple silicon), it offers `ollama pull --runner llamacpp <model>`
   (an undocumented Ollama flag) to pull the GGUF one.
6. **Context.** Onboarding loads each model once without generating, reads the context
   Ollama gives it, and runs the contract probes. Ollama picks 4096 tokens below about
   23 GiB of graphics memory, and a fix run's first writer call needs about 9.7k, so a
   context below 16384 is refused. Onboarding offers to set `OLLAMA_CONTEXT_LENGTH=32768`
   for the service and restart it: in Homebrew's service environment,
   `~/.homebrew/services/ollama.env` (`$XDG_CONFIG_HOME/homebrew/services/ollama.env`
   when that is set; Homebrew reads it on `brew services restart`, and onboarding
   writes it only when `brew services --help` says Homebrew reads that file), or in a
   systemd drop-in for the Linux service. For the app or an `ollama serve` you run, it says what
   to set. If the context stays small, it recommends OpenRouter.

### Step 3B: Claude Code

Onboarding finds the `claude` CLI and prints its path and version; without it, it
names the Claude Code install page. Claude Code runs on your Claude Pro or Max plan:
`claude setup-token` needs a subscription, and Anthropic API keys, Bedrock and Vertex
are not supported by fix-claude-code. Onboarding then asks to build the sandbox image
(`axocoatl recipe build claude-code`, about 0.6 to 0.9 GB) and to sign in
(`axocoatl connect claude-code` runs `claude setup-token` and opens your browser; it
needs a terminal), and sets up the reviewer alone:

```text
Choose the reviewer
> Local Ollama gpt-oss:20b (13.8 GB, needs 48 GB memory)
  OpenRouter (hosted, credits)
```

Claude Code runs in your repository's language image (Node.js, Python, Go or Rust,
detected from `package.json`, `pyproject.toml` or requirements, `go.mod` or
`Cargo.toml`), with the dependencies installed first and only the package registries
open for that step; see [Repository toolchains](/configure/toolchains/).

### Step 3C: Codex

Codex works the same way through `axocoatl connect codex`, which builds the Codex
sandbox image (about 0.8 to 1.2 GB) once and signs in through the browser. Codex runs
bill to your ChatGPT plan: onboarding names that credential on the run command it prints
(`--param credential=codex-chatgpt`), so a key stored later does not move the setup to
API billing. 1.5.0 stores no OpenAI API key for Codex (`axocoatl connect codex
--api-key` is not available); a configuration that already names `codex-openai` keeps it
when that key is stored, and otherwise moves to your ChatGPT plan and says so.

### Step 3D: OpenRouter

Onboarding first says what BYOK is: another provider's API key (OpenAI's, say) added
to your OpenRouter account at `https://openrouter.ai/settings/integrations`, so that
provider bills you and Axocoatl cannot count the cost. Native Sessions refuse it, and a
new account has none. It asks you to confirm that OpenRouter credits pay and the
account has no BYOK keys, then asks for two models: the writer (default
`qwen/qwen3-coder-30b-a3b-instruct`) and the reviewer (default `openai/gpt-oss-120b`, another vendor),
and refuses the same model for both. The writer's output limit is 4096 tokens.

The key, in this order:

1. `--openrouter-key-env VAR`: the configuration names the variable, not the key.
2. A key you connected in the browser: the secret the configuration names in
   `api_key_secret`, or, when it names no key, the secret `openrouter` that
   `axocoatl connect openrouter` stores. When Axocoatl's secret store holds it (the
   check `axocoatl doctor` makes), onboarding uses it without asking, at a terminal
   and with `--yes`.
3. The key the configuration has when onboarding updates a setup: a `${VAR}`
   reference is used when `VAR` is set; at a terminal you can answer no and give
   another key.
4. `OPENROUTER_API_KEY` when it is set, after asking (the configuration then names
   the variable, not the key).
5. At a terminal, onboarding asks how to get the key:
   - **Sign in to OpenRouter in your browser (recommended)**, the default: the same
     sign-in as [`axocoatl connect openrouter`](/configure/providers/#configure-openrouter).
     It checks both models in OpenRouter's catalog, opens OpenRouter's sign-in page
     in your browser (in WSL with `wslview`, in Windows' browser) and prints its
     address, waits up to 10 minutes for the browser to return to
     `http://127.0.0.1:<port>/callback`, and stores the key OpenRouter issues as the
     secret `openrouter` in Axocoatl's secret store (`0600`), never showing it. When
     the 10 minutes end without a sign-in, it asks whether to keep waiting (Enter
     waits 10 minutes more). Each connection to that address is written to the
     onboarding log, its method, path and `Host` only, never the code, so a sign-in
     that never comes back can be diagnosed. The configuration gets
     `api_key_secret: openrouter` and
     `openrouter_billing: credits`, never the key. The callback is a loopback port,
     so from a VM, open the link in a browser that can reach that port: Lima
     forwards a guest's loopback ports to the host unless the VM is plain
     (`limactl create --plain`, or `plain: true`), which turns forwarding off. In a
     plain or cloud VM, forward the port first from the computer with the browser,
     with `ssh -L PORT:127.0.0.1:PORT` and the VM's address, as onboarding says when
     it cannot open a browser itself. Cancelling in the browser or running out of
     time stores nothing, and the step left says to run onboarding again.
   - **Read it from an environment variable**: you name it (default
     `OPENROUTER_API_KEY`); the configuration names the variable, not the key.
   - **Enter it at a hidden prompt**: the key is then stored in the owner-only
     configuration. Before the prompt, onboarding says to create a key at
     `https://openrouter.ai/settings/keys` and add credits at
     `https://openrouter.ai/settings/credits`.

With `--yes` and no key from 1 to 4, nothing is asked: the step left says to sign in
with `axocoatl connect openrouter` first, then run the same `axocoatl onboard` command
again, which uses that key. Without a key nothing is saved, and the step left gives the
`axocoatl onboard` command with the writer and models you chose (Codex asks again which
account pays). With `--writer openrouter` the reviewer runs on OpenRouter too; a
`--reviewer ollama:…` is a usage error. Before writing anything, onboarding checks that
OpenRouter accepts the key and lists both models (after a sign-in, the sign-in has
checked both). A key you connected that OpenRouter refuses, or a stored secret that
holds no OpenRouter key: at a terminal, onboarding offers its browser sign-in in its
place; with `--yes` it is a step left that signs in again with `axocoatl connect
openrouter`. When the browser sign-in replaces a key that was written in the
configuration file, the backup onboarding makes leaves that key out (it is no longer
used; delete it at `https://openrouter.ai/settings/keys`).

Onboarding then reads each model's endpoints as a run does. A run uses an endpoint
only while OpenRouter reports it healthy (status 0), since it stays on one endpoint
with no fallback, so a model whose every usable endpoint OpenRouter reports
unavailable or degraded right now, or that has no endpoint native Sessions can use,
cannot run now. Onboarding says so, with each endpoint's status and its success rate
over the last 30 minutes for OpenRouter's status (which can pass, so running
onboarding again later may work), or why no endpoint fits (which waiting does not
change); at a terminal you can name another model (Enter takes the
first of `qwen/qwen3-coder-30b-a3b-instruct`, `z-ai/glm-4.6`,
`deepseek/deepseek-chat-v3.1`, `qwen/qwen3-coder` and `openai/gpt-oss-120b` that can
run now and is not the other role's model), and with `--yes` it is a step left that
names that model, and nothing is saved.
OpenRouter uses your OpenRouter credits; BYOK is not supported for native Sessions.

### Step 4: the configuration

Onboarding shows what it writes and writes `config.yaml`: for a new file, what it
sets (the run models, the workbench team, the Ollama server or where the OpenRouter key
comes from, and the port); for an existing file, the change as a diff, which it writes
after one question (Enter writes it), backing the file up as `config.yaml.bak-<time>`
next to it. Besides the
[default team](#default-team) and the provider it needs, the configuration holds the
defaults `axocoatl run` uses, so `axocoatl run fix --task "…"` needs no `--model`:

```yaml
# Writer: ollama (axocoatl run fix)
run:
  models:
    writer: "ollama:qwen3-coder:30b"
    reviewer: "ollama:gpt-oss:20b"
```

`--model writer=…` or `--model reviewer=…` on the command line overrides them. For
Claude Code and Codex only the reviewer is written; their loadouts name the writer's
model. The `# Writer:` comment records who writes (for Codex, also the credential, as
in `# Writer: codex (axocoatl run fix-codex --param credential=codex-chatgpt)`), so
`doctor` and a later `axocoatl onboard` know the setup. The workbench uses port 8080 when it is free, otherwise the first free port
after it, written to `server.port` (`--port` chooses one).

### Step 5: check

Onboarding runs the same checks as [`axocoatl doctor`](#run-doctor), without loading
again the models Step 3 just loaded, and says exactly what is ready. A `·` marks a
writer you have not set up, which is optional, not a failure, and a `!` one you set up
only in part (its image without its sign-in, say); its command builds the writer's
image and signs in, and leaves the configuration as it is (`axocoatl onboard
--update --writer claude-code` would also record Claude Code as this setup's writer, drop
`run.models.writer` and move the team's Agents to the reviewer's model):

```text
Ready for: axocoatl run fix, workbench Sessions
  ✓ axocoatl run fix (writer ollama:qwen3-coder:30b, reviewer ollama:gpt-oss:20b)
  · axocoatl run fix-claude-code (not set up: run `axocoatl recipe build claude-code && axocoatl connect claude-code`)
  · axocoatl run fix-codex (not set up: run `axocoatl connect codex`)
  ✓ workbench Sessions (Lead ollama:qwen3-coder:30b)
Ready: yes
```

or the steps left, with exit 1:

```text
Not ready yet, 2 steps left:
  1) …
  2) …
```

When Step 4 wrote nothing (no OpenRouter key, say), the last line says so: nothing was
saved, or your configuration was not changed.

### Step 6: start Axocoatl

```text
How should Axocoatl run?
> In this terminal now (axocoatl dev)
  Always on, starting at login (a launchd or systemd service)
  I'll start it later
```

The service is installed only after this question (or `--start service`): onboarding
runs `axocoatl service install` and then `axocoatl service restart`, which starts the
service, or, when one already runs (it asks first, since that ends its Session turns
and runs in progress), restarts it with the new definition and configuration. A service
cannot read keys from your shell's environment, so onboarding refuses to install one
while the configuration names an environment variable for a key. On Linux the service
is a `systemctl --user` unit: in a login without a systemd user session (reached with
`su -`, `sudo -iu`, or an SSH login that started none, where `systemctl --user` reaches
no manager) onboarding does not offer it and says to log in as that user directly,
and, unless linger is on already, to run `loginctl enable-linger USER` in that login
to keep it running after you log out.
The terminal choice starts `axocoatl dev` as its own process; Ctrl+C stops it.

A Podman machine that onboarding starts (Step 2) runs in a session of its own: a
Ctrl+C during onboarding, or closing its terminal, ends onboarding but not the machine.

### Step 7: a first run

```text
Run a first fix now on a small sample repository to prove the setup end to end?
It runs locally. [Y/n]
```

(For Claude Code it uses your Claude plan's quota, for Codex your ChatGPT plan or
OpenAI credits, for OpenRouter your OpenRouter credits.)

Onboarding copies a small Node repository with one failing `node --test` to a new
temporary directory only you can open, uses the daemon that runs (it waits for the
Always-On Service Step 6 just started, or a daemon that already runs, and never starts
a second one beside it), or starts one for the run and stops it afterwards (its first
start downloads an 87 MB embedding model once). A daemon that started before the
configuration last changed would run the old configuration, and one that is another
version than this `axocoatl` (any before 1.5.0, which does not say when it started) would
not run this one: onboarding asks to restart the Always-On Service, or to stop that
daemon (either ends its Session turns and runs in progress; `--yes` answers yes), and
waits for it to exit (at its port, when its process cannot be seen). When the service
runs another `axocoatl` than this one (an older release at another path), onboarding
installs it again from this one before it restarts it, and uses it only once it
answers as this version. It then runs
`axocoatl run fix --task "Fix the bug: paging skips the last item"` (or fix-claude-code or
fix-codex) with your models and a receipt beside the copy, and checks the receipt with
`axocoatl receipt verify <receipt> --key "$(axocoatl receipt key)" --repo <copy>`. It
ends with the next command for your own repository.

## Without a terminal, and dry runs

Without a terminal, onboarding answers nothing by itself: it exits 3, changes nothing
and points to `--yes`. With `--yes` and the flags below it runs unattended. `--writer`
takes `claude-code`, `codex`, `ollama` or `openrouter`; for example, for Claude Code:

```sh
axocoatl onboard --yes --writer claude-code
```

Add any of the flags in the table to answer the other questions.

| Flag | Meaning |
| --- | --- |
| `--yes` | Answer yes to every question. A `sudo` step also needs `--allow-sudo`; the Claude Code and Codex sign-ins also need `--connect` and a terminal, otherwise each is a step left. OpenRouter's key must already be there: one you connected with `axocoatl connect openrouter`, the configuration's, `--openrouter-key-env` or `OPENROUTER_API_KEY`; otherwise the step left says to connect it |
| `--writer` | Who writes the code (Step 1). With `--update` and without it, the writer the setup has |
| `--reviewer`, `--writer-model` | The models as `ollama:MODEL` or `openrouter:VENDOR/MODEL` (a Claude Code writer model is `anthropic:MODEL`, a Codex one `openai:MODEL`). The same model for both, or a non-OpenRouter reviewer with `--writer openrouter`, is a usage error |
| `--ollama-url` | The Ollama server native Sessions use (default `http://localhost:11434`); it must be on this computer |
| `--podman create`, `--podman skip` | `create` (the default) sets up a missing Podman where onboarding can: on a Mac with Apple silicon and Homebrew it installs Podman with Homebrew, and on a Mac it creates and starts the machine; on Linux it installs Podman with apt-get, dnf, pacman or zypper, with sudo. Elsewhere, and on Ubuntu 22.04, whose Podman is too old, it says what to do. `skip` leaves Podman as it is |
| `--machine-cpus`, `--machine-memory` | The size of a new Podman machine (memory in MiB) |
| `--pull`, `--no-pull` | Pull the chosen Ollama models, or leave the pulls as steps left |
| `--recipe-build`, `--no-recipe-build` | Build the Claude Code or Codex sandbox image |
| `--connect`, `--no-connect` | Sign in to Claude Code or Codex now, or not |
| `--openrouter-key-env VAR` | Read the OpenRouter key from `VAR` instead of a browser sign-in; the configuration names the variable |
| `--port` | The workbench port |
| `--start dev\|service\|none` | Step 6 (`none` with `--yes` when not given) |
| `--smoke-test`, `--no-smoke-test` | Step 7 (off with `--yes` when not given) |
| `--update`, `--replace` | What to do with an existing configuration (update with `--yes` when not given) |

`axocoatl onboard --plan` prints what this computer has and every action onboarding
would take, as Enter at each question would answer it, from Step 0 to Step 7 (the
Podman checks, the service and the first run included), and writes no file. It exits
0. (Podman, asked for its version or state, may create its own empty settings
directories in a home directory that has none.)

Exit codes: **0** ready (and the first run passed, when it ran), **1** not ready, with
the steps left listed, **3** a command line onboarding does not take, or no terminal
and no `--yes`.

## Running onboard again

With a configuration already there, onboarding offers:

- **Update this setup** (the default, and what `--yes` does): keep the file, back it
  up, and change only what is missing or what this run chose: a provider section it
  needs, the OpenRouter key when you chose another, `run`, `server.port`, and the
  Agents onboarding wrote. The writer, the run models, the Codex credential and the
  OpenRouter key the setup has are kept unless a flag names others (a key connected in
  the browser is used without asking); `axocoatl onboard --update --port 8081` changes
  only the port of a setup this release wrote. The Agents onboarding wrote (Lead,
  Scout, Reviewer and the Assistant, as this release or 1.1.0 to 1.4.0 wrote them) are
  written as this release writes them, each where it is in the file: on the models
  chosen, and with this release's prompts (a Lead from an earlier release gets this
  release's Lead prompt). An Agent that differs from what onboarding writes (one you
  edited: its prompt, tools or another field, or a model that is not the one onboarding
  gave it; or 1.0's Assistant, which had no tools), and an Agent of your own, stay as
  they are, and onboarding names the Agents of its team it kept on other models.
  Everything else, comments included, stays as it was, and the change is shown as a
  diff first, with every secret value hidden.
- **Replace it**: write a new configuration; the old file is backed up first and is
  not shown (only the new file is, with its key hidden).
- **Leave it unchanged**: check the file as it is (Step 5) and stop: exit 0 when it is
  ready, 1 with the steps left otherwise.

<Aside type="caution" title="The user configuration can contain a key">
An OpenRouter key typed at the hidden prompt is stored as plain text in a configuration
file with owner-only permissions (`0600` on supported Unix systems). Axocoatl does not
encrypt that file. Protect it and its backups, or sign in to OpenRouter in the browser
instead (the key then stays in Axocoatl's secret store and the file only names it), or
give the key in an environment variable. Axocoatl does not load dotenv files.
</Aside>

## Default team

Every setup writes the same Agents. Lead, Scout and the chat Assistant run on the
writer's model, or, for Claude Code and Codex, on the reviewer's model, since the
workbench does not run Claude Code or Codex; Reviewer runs on the reviewer's model:

| Agent | Role | Tools | May change |
| --- | --- | --- | --- |
| **Lead** (`lead`) | Autonomous | `read_file`, `list_dir`, `grep`, `glob`, `write_file`, `edit_file`, `bash` | Any file |
| **Scout** (`scout`) | Worker | `read_file`, `list_dir`, `grep`, `glob`, `bash` | Nothing (`writes: []`) |
| **Reviewer** (`reviewer`) | Worker | `read_file`, `list_dir`, `grep`, `glob`, `bash` | Nothing (`writes: []`) |
| **Assistant** (`assistant`) | Autonomous | `read_file`, `list_dir`, `grep`, `glob` | Not used in Sessions by default |

Lead owns the change. Its instructions say to look first, to verify with the tests,
and, if it has helpers, to send a focused read-only question to Scout and to ask
Reviewer for an independent review before finishing. Scout answers with file paths,
line numbers and short evidence. Reviewer reports concrete defects with `file:line`,
or says it found none. Neither changes files.
Assistant is the plain chat Agent for `axocoatl chat`.

A new Session selects Lead unless you choose another Agent, and starts with Lead alone:
in **Team & budget** you enter Lead's limits and choose **Apply** before the first
request. Scout and Reviewer are offered there as Lead's helpers; select **Let this
Agent delegate to helpers** and enter each helper's limits to use them. Required checks
and a required review stay off until you add them.
[Default team](/understand/coordination/#default-team) describes how the helpers run,
and [Agents](/configure/agents/#the-default-team) how to change them.

## User-level locations

Onboarding creates no files in the directory from which you run it:

| Platform | Configuration | Durable data |
|---|---|---|
| macOS | `~/Library/Application Support/Axocoatl/config.yaml` | `~/Library/Application Support/Axocoatl/data/` |
| Linux and WSL2 | `$XDG_CONFIG_HOME/axocoatl/config.yaml`, or `$HOME/.config/axocoatl/config.yaml` when XDG is unset | `$XDG_DATA_HOME/axocoatl/`, or `$HOME/.local/share/axocoatl/` when XDG is unset |

Plain config-aware commands resolve these paths regardless of the current
directory. A repository's `axocoatl.yaml` is never selected implicitly.

## Run doctor

```sh
axocoatl doctor
axocoatl doctor --json
```

Doctor runs the checks onboarding's Step 5 runs, against the resolved user
configuration, and reports each item as OK, WARN or FAIL in four sections, then what
is ready to run and the steps left. It exits 0 when nothing failed and 1 otherwise; the
last line is `Ready: yes` or `Ready: no`. With `--json` it prints the same report as one
document: `ready`, `config`, `sections` (`sandbox`, `models`, `writers`, `daemon`, each a
list of `{"name", "status": "ok|warn|fail", "detail", "fix"}`), `ready_for` and
`steps_left`.

| Section | Checks | Failure level |
|---|---|---|
| Sandbox | Podman installed, its machine (on macOS) created, rootless, 4.3 or later, and, rootless, a range of subordinate ids; the client and server versions, the machine's provider, CPUs and memory (under 4 GiB warns), the kernel | FAIL, except a stopped machine (OK: it starts on first use), an untested version or provider, and a small machine (WARN) |
| Sandbox | Landlock ABI on Linux (below 3 fails, 3 warns; on ABI 1 it also says that Rust builds fail with "Invalid cross-device link"); SELinux on Linux (OK: containers run with its labelling off); the cgroup controllers rootless Podman can use for Session containers' memory, CPU and process caps (a missing one warns) | As described |
| Sandbox | The platform: macOS on Apple silicon and Ubuntu 24.04 are what the release gate verifies; an Intel Mac, another Linux release, WSL2 (keep repositories off `/mnt/c`), SELinux enforcing, and local models below 48 GB of memory are named as not yet verified. With `sandbox.backend: e2b`, that `axocoatl run` still runs in Podman | WARN (OK when verified) |
| Sandbox | Network, workload users, egress routes and credentials (names only), browser image | WARN when something needs attention |
| Models | The Ollama server: reachable, on this computer, an accepted version (a newer 0.x minor warns), cloud models off | FAIL |
| Models | Each configured Ollama model: pulled, GGUF, tool calling for an Agent with tools, its size against memory (too large warns), its loaded context (below 16384 fails) and how much of it is in GPU memory; doctor loads each model once to read it and runs the contract probes. While a daemon runs, a model Ollama already holds is not loaded or probed again (a run may be using it): its context is read from Ollama | FAIL |
| Models | OpenRouter and other hosted-provider keys present (not checked with the provider): a key in the file, or the stored secret `api_key_secret` names. Without `providers.openrouter`, the fix is `axocoatl connect openrouter`, which adds it and changes nothing else, and a secret that is not stored names the same command; for a configuration other than the default one, both add `--config` with its path, so the key is stored in that configuration's data directory | FAIL when an Agent or `run.models` uses OpenRouter without a key, otherwise WARN |
| Writers | Claude Code and Codex: sandbox image built and credential stored (for Codex, the credential the setup names); the `claude`, `codex` and `gh` CLIs (`gh` signed in, for `--keep pr`); the names of stored credentials | FAIL for the writer the configuration names (its `# Writer:` comment); WARN for one partly set up |
| Daemon | Configuration valid; data directory writable and owned, and an interrupted Session storage upgrade in it; `git`, which the daemon runs on your repositories (on macOS, the Command Line Tools); on Linux the systemd user session the Always-On Service needs, and linger when the service is installed; a running daemon and its version against the CLI's (one older than 1.5.0, which does not report it, is named as older); the Always-On Service's program; the configured port when no daemon runs; webhooks; a `hooks:` section, which this version checks but never runs; a proxy variable, which a Session's network does not use | FAIL for the configuration, the data directory (and a copy of a data directory whose upgrade stopped half-way) and a missing `git`; otherwise WARN |

Each FAIL names its fix: the exact command, or `axocoatl onboard`, which makes the
change after asking. `Ready for` lists `axocoatl run fix` for a local or OpenRouter
writer and `axocoatl run fix-claude-code` or `fix-codex` for those writers. With
`sandbox.backend: e2b`, Podman problems warn (workbench Sessions use E2B), but the
`axocoatl run` lines stay not ready until Podman is: runs always use it.

## Validate without starting the runtime

```sh
axocoatl validate
```

Validation checks identities, provider and model fields, dependencies, MCP
transports, token-budget relationships, and other schema constraints. It does
not prove that a hosted credential is valid or that a model account currently
permits access.

## Advanced: use an explicit configuration

Project-local or operator-managed YAML remains supported, but it must be
selected explicitly:

```sh
axocoatl validate /absolute/path/to/axocoatl.yaml
axocoatl doctor --config /absolute/path/to/axocoatl.yaml
axocoatl dev --config /absolute/path/to/axocoatl.yaml
```

`AXOCOATL_DATA_DIR` overrides the data location. Without that override, an
explicit configuration uses a `data/` directory beside the configuration file.

## Start the workbench

```sh
axocoatl dev
```

The app is at `http://127.0.0.1:8080`, or the port onboarding wrote to `server.port`.
`dev` holds the port before it starts; when another program already listens there,
it says which port and how to choose another, and exits. Keep this process running,
open the `Sign in:` link it prints (or run `axocoatl url`), and choose
**Open workspace…** to authorize the repository you want to use. Then
[create your first Session →](/start/first-session/).

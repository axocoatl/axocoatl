The dashboard is where you ask an Agent to work and inspect what it changed.
A **Workspace** names your existing project folder. A **Session** keeps the
conversation and working state inside it. Start with a clean Git repository or a
disposable copy, and know the command that checks whether a change works.

This guide uses a native Ollama or OpenRouter Agent. If you selected Claude Code or
Codex during onboarding, the dashboard's team uses your reviewer's native model.
[Headless runs](/start/first-fix/) use those external programs as writers.

## Open the dashboard

[Install and set up Axocoatl](/start/onboard/#recommended-setup) first. After
`axocoatl doctor` reports ready, start the daemon if it is not already running:

```sh
axocoatl dev
```

Leave that terminal running. In a second terminal, run `axocoatl url` and open
the sign-in link in your browser. If onboarding or the Always-On Service already
started the daemon, use that existing daemon and run `axocoatl url` for its link.
Keep the sign-in link private.

## 1. Open your repository and create a Session

<Steps>

1. In the Workspace switcher, choose **Open workspace…** and select your existing
   project folder. Confirm its display name; renaming it does not rename the folder.
2. Choose **New session** beside **Sessions**, and give it a name for the work.
   Keep **Single agent** and the configured **Lead** for this first task.
3. Review the proposed environment and repository setup. A command such as
   `npm ci` runs only when you approve it; you can edit it or explicitly continue
   without a setup command. Leave **Exposed ports** empty unless you need Preview.
4. Wait for the environment to show **Ready**. If it needs attention, use
   **Review setup** and resolve the named step before sending work.

</Steps>

Onboarding configures Axocoatl for the current OS user; it has not created a project
or authorized this folder. **Open workspace…** is that deliberate authorization.

## 2. Review Team & budget

The first Send button reads **Set budget**. Select it to open **Team & budget**.
Choose **Edit** and inspect the selected Agent, model and limits. Open
**Required checks** and add the command that verifies your task. For the Node
project in the video, that is `npm test`; use your repository's own check command.
Then choose **Preview changes → Apply to this Session**. Nothing is approved until
you apply it.

Keep one Agent for a small first task. Read-only helpers, required checks and a
required review are opt-in. They are separate choices: asking a helper to review
is not the same as requiring the host to run a review before the turn completes.
See [Agents and budgets](/configure/agents/) when you want those controls.

A required check makes the host run the command after the Agents finish. Asking
the Lead to run tests in your message does not configure that requirement.
[How required checks work →](/configure/agents/#required-checks)

## 3. Ask for one result in Conversation

Use the composer to describe the outcome and the check that should pass. For a
repository you have not explored yet, start with:

```text
Inspect this repository without changing files. Identify its purpose, the command
used for its automated checks, and the three files most relevant to a small first fix.
If you can verify a small issue, report its reproduction too. State uncertainty explicitly.
```

Choose a specific issue from that report. Name the behavior to fix, what must stay
unchanged and how to check it. Adapt this example from the video to your project:

```text
Fix pagination losing the final page when the item count is an exact multiple
of the page size. Preserve the public API and all existing tests. Add regression
tests for one full page and page size one. Run npm test, summarize the actual
result, and do not commit.
```

### Follow the work

Watch Conversation and expand tool calls to see the files and commands used.
Open **More → Agent graph** to follow the Lead and any helpers you enabled;
select an Agent to inspect its recorded work. Return to Conversation for the result.

**Stop** addresses the active turn. If a turn fails, read its reason and inspect
what already changed before using **Turn controls → Continue**. Failed and
interrupted work remains in **History**. The recording includes recovery requests
and a later model change; these are responses to that task's failures, not setup
steps to repeat. [Recovery controls →](/workbench/history/#control-native-work)

## 4. Inspect the files and review the diff

The final answer is a starting point for review. Inspect the result in the dashboard:

1. Open **Files** and read the edited file.
2. Open **Source Control → Last turn** to see the paths attributed to the most
   recent Agent turn. It shows their current diff, not a frozen copy. After several
   requests or recovery, also select **All changes** to review the full working diff.
   Check that original tests and behavior you asked to preserve are still present.
3. Open **More → Agent graph → Turn controls → Required checks** to read the
   host's check output and exit code. If no required check was configured, inspect
   the actual tool output in Conversation or run the repository check in the
   dashboard's **Terminal**. A model saying “tests pass” is not the check result.
4. Use **Preview** when the task changes a running web app.
5. Stage and commit only after the diff and check results satisfy your request.

If review finds a missing requirement, send a specific correction in Conversation
and repeat the checks and diff review. In the video, that meant restoring the
original tests before accepting the fix.

<Aside type="note" title="You decide what to commit">
The normal result leaves edits in the Session working tree. Source Control offers
stage, unstage, discard, hunk review and commit as deliberate actions. Workbench
turns retain their evidence in History; they do not issue headless-run receipts.
</Aside>

## Setup details

<details>
  <summary>Readiness and repository boundaries</summary>

The browser keeps its sign-in for 30 days. Its first screen checks what a Session
needs, as `axocoatl doctor` does. The rail shows **N setup steps left** until it
shows **ready**; select it for the checklist and each exact fix. Without Podman or
its machine, **Create session** stays blocked. The New Session dialog refreshes
Podman readiness and waits at most ten seconds for that check.

The folder picker starts in your home folder. Opening that folder, a folder above
it, or a folder containing Axocoatl's directories requires typing the folder's
name to confirm; Axocoatl's own directories never open as Workspaces.

</details>

<details>
  <summary>Runtime images and setup commands</summary>

A root `package-lock.json` can suggest the curated Node 20 image. A devcontainer's
exact image is shown as repository input and may require arbitrary-image trust.
Under E2B, clear the per-Session image: the daemon-global template is the runtime.
New data roots use native execution with local Podman for repository tools and
required checks.

A detected setup command is a proposal, not permission. An operator's policy may
default an exact devcontainer command to checked, but that policy is visible and
your reviewed checked or unchecked choice wins. A successful doctor check does not
replace this environment review or Team review.

</details>

<details>
  <summary>Default budgets and helpers</summary>

Team limits come filled in from
the built-in `fix` loadout: 4 activations, 400 provider and tool invocations
and 4,000,000 tokens per Agent, $0 of cost for a local Ollama model (a hosted
model gets the loadout's $10 cap), and an expiry 24 hours from now. Switch to
**Edit** to review or change them, then **Preview** and **Apply**; nothing is
approved until you do. With the default team, Lead's panel also offers Scout and
Reviewer as read-only helpers. Lead works alone unless you select **Let this Agent
delegate to helpers**; their limits come filled in too (3 activations, 120
invocations, 1,500,000 tokens each), within Lead's. Preview refuses a token limit
a turn cannot use and names the minimum: each model call reserves the model's
whole context plus its output, and a turn with tools needs a call and the one
after it, for example 73,728 tokens for a 32,768-token context and 4,096 output
tokens. An expiry must be within a year.

</details>

## If creation fails

- Run `axocoatl doctor` and resolve what it reports for Podman. When local Podman
  cannot run the Session yet (no Podman machine, for example), **Create session**
  saves nothing and says what to run; it starts a stopped machine itself.
- Confirm the selected Agent exists in the active user configuration (or the
  explicit file passed with `--config`).
- An image outside Axocoatl's curated presets is rejected unless
  `sandbox.allow_untrusted_images: true`.
- Session startup never installs Podman or creates its VM; `axocoatl onboard` does,
  after asking, where it can (Homebrew on Apple silicon, or a package manager it knows
  on Linux; otherwise it names the installer). Run it, or follow the `doctor` guidance,
  then retry.
- With `sandbox.network: none`, the local image must already contain Axocoatl's
  required repository commands; offline startup cannot download missing tools.
- E2B uses one daemon-global template and rejects a per-Session or devcontainer
  OCI image. Clear the image or switch the daemon to Podman.
- A detected repository setup command is only a proposal. Open **Review setup**
  and approve the exact command or explicitly continue without one.

## Open the workbench from another computer

The workbench listens only on the loopback address of the computer that runs
`axocoatl dev` or the [Always-On Service](/operate/service/), and answers only requests
that reach it there. On a Linux server or VM without a desktop that you reach over SSH,
forward its port from the computer whose browser you use:

```sh
ssh -N -L 8080:127.0.0.1:8080 you@server
```

Keep the same port number on both ends: 8080, or the `server.port` the server's
configuration sets, because the sign-in link names it. Then run `axocoatl url` on the
server and open the link it prints in that browser. Previews open on `*.localhost`
names at the port the browser used, which browsers send to the loopback address, so they
reach the server through the same forward. While the forward runs, a program on your
computer can reach that port as a program on the server can; the sign-in link is what
lets a browser in, so keep it private.

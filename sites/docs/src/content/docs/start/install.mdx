Axocoatl publishes release binaries for Linux and macOS 11 or newer on x86_64 and aarch64.
On Windows it runs inside WSL2 (not yet verified): run the installer in the Linux
distribution, not in PowerShell; there is no native Windows binary.
The Linux archives target GNU libc 2.35 or newer. They do not run on
musl-based distributions such as Alpine; use the Cargo or source path there.

| | |
| --- | --- |
| Tested end to end | macOS 26 on Apple silicon, rootless Podman 5.8, a 48 GB Mac |
| Verified in CI | Ubuntu 24.04 on x86_64, rootless Podman 4.9.3, against a stub model server |
| Not yet verified | Intel Macs, Podman 6, arm64 Linux, Ubuntu 22.04, Debian 12, Fedora with SELinux, WSL2 on Windows |

## Install the binary

<Tabs syncKey="install">
  <TabItem label="Release binary">
    ```sh
    curl -fsSL https://axocoatl.ai/install.sh | sh
    ```

    The installer resolves the latest GitHub release, downloads the tarball for
    the current OS and architecture, and requires its matching SHA-256 file.
    A missing, malformed, or mismatched checksum stops installation. The script
    also stops before download when Linux does not report GNU libc 2.35 or
    newer, or when macOS is older than version 11. It installs to
    `/usr/local/bin` when writable and otherwise to `~/.local/bin`. When that
    directory is not on your `PATH`, it asks, on the terminal, before adding one line
    to your shell's profile, and prints that line when it cannot ask.
  </TabItem>
  <TabItem label="Cargo">
    ```sh
    cargo install axocoatl-cli
    ```

    Building from crates.io requires Rust 1.88 or newer.
  </TabItem>
  <TabItem label="Source checkout">
    ```sh
    git clone https://github.com/axocoatl/axocoatl
    cd axocoatl
    cargo build -p axocoatl-cli --release
    ./target/release/axocoatl --version
    ```

    The root package is not the CLI. Keep the explicit `-p axocoatl-cli`.
  </TabItem>
</Tabs>

All three paths install one `axocoatl` executable. Cargo and source builds compile
the host application and include Axocoatl's prebuilt Linux process supervisor for
its sandbox. There is no separate supervisor installation or startup download.
The [supervisor source](https://github.com/axocoatl/axocoatl/tree/main/crates/axocoatl-exec)
and [explicit rebuild instructions](https://github.com/axocoatl/axocoatl/blob/main/docs/EXEC_SUPERVISOR_BUILD.md)
are available for contributors who want to rebuild those embedded bytes.

Verify that your shell can find the binary:

```sh
axocoatl --version
axocoatl --help
```

If `axocoatl` is not found, the installer used `~/.local/bin` and did not add it to
your `PATH`. Open a new terminal if you let it add the line; otherwise add the line it
printed to your shell's profile (`~/.zprofile` for zsh on macOS, `~/.bashrc` for bash on
Linux), or set it for this shell only:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

`AXOCOATL_MODIFY_PATH=yes` makes the installer add the line without asking, and
`AXOCOATL_MODIFY_PATH=no` stops it from asking:

```sh
curl -fsSL https://axocoatl.ai/install.sh | AXOCOATL_MODIFY_PATH=no sh
```

The binary is installed once for the current user or system. The next command,
`axocoatl onboard`, creates user-level Axocoatl configuration and data; it does
not create a repository or Workspace.

## What it needs and downloads

Every run has a writer, which changes the code, and a reviewer, a different model that
only reads. `axocoatl onboard` sets up both, and Podman, and asks before each download
or change.

- **Writer.** Claude Code needs a Claude Pro or Max plan and the `claude` CLI on this
  computer. Codex signs in with your ChatGPT plan. A local writer runs on Ollama.
- **Reviewer.** A local model on Ollama, or a hosted one paid with OpenRouter credits.
- **Memory for local models.** The local pair, `qwen3-coder:30b` writing and
  `gpt-oss:20b` reviewing, was tested on a 48 GB Mac, one model loaded at a time. No
  local pair has been tested with less memory: there, use a reviewer through
  OpenRouter. `gpt-oss:120b`, the reviewer we measured, needs about 96 GB or more.
- **Docker** is not supported; Axocoatl runs Podman, which can run alongside Docker.
- **For `--keep pr`:** `git`, the `gh` CLI signed in, and a GitHub remote.

| Download | Size |
| --- | --- |
| Podman machine image (macOS) | about 0.9 GB |
| Claude Code image | about 0.6 to 0.9 GB |
| Codex image | about 0.8 to 1.2 GB |
| `qwen3-coder:30b` | 18.6 GB |
| `gpt-oss:20b` | 13.8 GB |
| `gpt-oss:120b` (about 96 GB of memory) | 65.4 GB |
| Embedding model, from huggingface.co on the first daemon start | 87 MB |

A run's sandbox also pulls its base image and packages the first time it starts.

## Runtime prerequisites

The binary can start without every optional dependency, but the normal local
workbench path uses:

- **Podman** for folder-anchored Session tools and parallel attempts;
- at least one configured model provider;
- **Ollama** plus a pulled model for the simplest local first run.

On macOS, Podman runs containers in a Linux virtual machine that you create once.
After `brew install podman` (or the installer from podman.io), create and start it:

```sh
podman machine init --cpus 6 --memory 8192
podman machine start
```

Axocoatl is tested on macOS with this size of machine; the Claude Code and Codex
images and your project's checks run inside it, while Ollama runs on the Mac
itself. Without a running machine, `axocoatl doctor` warns and prints these
commands. On Linux, Podman runs containers directly and needs no machine.

Native Sessions use Ollama **0.40.6 or a later 0.40 release** on this machine with
its cloud features disabled ([ollama.com/download](https://ollama.com/download), or
`brew install ollama`). For a local Ollama setup, start the server with cloud disabled
and pull a coding model and a different reviewer model:

```sh
OLLAMA_NO_CLOUD=1 ollama serve
ollama pull qwen3-coder:30b
ollama pull gpt-oss:20b
```

Run `ollama serve` in its own terminal or as its own service. If Ollama already
runs as the macOS app or a Homebrew service, add
`{"disable_ollama_cloud": true}` to `~/.ollama/server.json` instead and restart
it. A coding model such as `qwen3-coder:30b` (19 GB) suits Lead, the Agent that
writes, and `gpt-oss:20b` (14 GB) reviews its change; both fit a 48 GB Mac, one at a
time. They are large downloads, so pull models that fit your machine's memory.
Native Sessions run only GGUF models: on Apple silicon, Ollama pulls the MLX variant
of some models, which Axocoatl refuses; `ollama pull --runner llamacpp <model>` (an
undocumented Ollama flag) pulls the GGUF one. Onboarding suggests models from the
ones installed on your server; see [Configure Axocoatl](/start/onboard/#ollama).

## Windows through WSL2

WSL2 is not yet verified: no Windows run has been done yet. These are the steps it is
designed for.

<Steps>

1. In an administrator PowerShell, install WSL2 and reboot when requested:

   ```powershell
   wsl --install
   ```

2. Open the Linux distribution and install Podman, or let `axocoatl onboard` install
   it in step 3. On Ubuntu:

   ```sh
   sudo apt-get update
   sudo apt-get install -y podman
   ```

3. Run the release installer **inside WSL2**, not in PowerShell, then continue with
   [user-level onboarding](/start/onboard/).

</Steps>

`axocoatl dev` runs inside WSL2. Open the sign-in link it prints
(`http://localhost:8080/?token=…`) in the Windows browser; WSL2 normally
forwards that loopback port to the host.

<Aside type="caution" title="The default sandbox still needs Podman">
Installing the Axocoatl binary does not install or start Podman; `axocoatl onboard`
does, after asking. Without a ready Podman runtime, `doctor` reports it, and Sessions
and runs cannot use the default local sandbox. A deliberately configured E2B Cloud
backend is the separate remote option.
</Aside>

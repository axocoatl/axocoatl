Axocoatl publishes release binaries for Linux and macOS 11 or newer on x86_64 and aarch64.
On Windows it runs inside WSL2 (not yet verified): run the installer in the Linux
distribution, not in PowerShell; there is no native Windows binary.
The Linux archives target GNU libc 2.35 or newer. They do not run on
musl-based distributions such as Alpine; use the Cargo or source path there.

The 1.5.0 release gate requires each of these paths to pass on the release commit,
starting from the published install command, and lists the steps each must show. The
release workflow publishes nothing until the signed evidence holds every one of them;
the only way past it is a logged override that only maintainers listed in the
repository can start, and the release notes must then name the paths not run.

| | |
| --- | --- |
| macOS, end to end | Apple silicon, with a person answering onboarding at the Mac, on an account that starts without Axocoatl, its data or stored credentials, without Podman or a Podman machine, and without Ollama or its settings (Ollama's downloaded models may stay): onboarding installs Podman and Ollama with Homebrew, creates the Podman machine, turns Ollama's cloud models off and ends ready with a passing first run. It signs in Claude Code, and Codex with a ChatGPT plan, in the browser, and connects OpenRouter through its browser sign-in without writing the key to the configuration |
| Linux, end to end | A new user who starts without Axocoatl, its data or stored credentials, or Podman, and whose subordinate ids the gate removes first (the gate's instructions use a new Ubuntu 24.04 VM): onboarding installs Podman with apt and adds a range of subordinate ids that overlaps no other user's, each with `sudo` after asking, connects OpenRouter through its browser sign-in for the OpenRouter models the runs use, and installs no Ollama |
| Linux, in CI | Ubuntu 24.04 on x86_64 and arm64: the same install command, then onboarding with no terminal against a scripted model server (Podman already on the runner, no first-run sample), and `axocoatl run fix` |
| Repositories | `fix` passes on Node.js (with and without dependencies), Python (pytest), Rust and Go repositories on each, with local models on the Mac; on the Mac, `fix-claude-code`, `fix-codex` and `fix` with OpenRouter models pass on Node.js and Python, and `fix-claude-code` with `--keep pr` opens a pull request whose receipt the [verify-receipt Action](/workbench/receipts/#checking-pull-requests-in-github-actions) verifies ([how toolchains work](/configure/toolchains/)) |
| Also on the Mac | The [Always-On Service](/operate/service/), chosen in onboarding, runs a passing fix, restarts when `onboard --update` changes the configuration, then stops and uninstalls (on Ubuntu, as a systemd user unit); a run with the Podman machine stopped starts it and passes; timed runs on real repositories each end with a verdict; the workbench in Safari goes from the sign-in link to a commit, shows a Session's Preview inside the workbench only (a Preview address opened in a tab, reached by a redirect or Command-clicked gets Axocoatl's refusal page), and stays as the docs say when another page floods `localhost` with cookies |
| Evidence | Every receipt and record verified; each path's transcript, times, downloads and tool versions, the models, the system, its memory and the account, and who answered each question (the person, or for the workbench's questions up to the commit, a WebDriver driver in Safari), in the signed bundle under `release-evidence/1.5.0/` in the repository ([the gate](https://github.com/axocoatl/axocoatl/blob/main/docs/RELEASE_GATE.md)) |
| Not yet verified | Intel Macs, Macs with less than 48 GB for local models, Ubuntu 22.04, Debian 12, Fedora with SELinux, WSL2 on Windows |

## Install the binary

<Tabs syncKey="install">
  <TabItem label="Release binary">
    ```sh
    curl -fsSL https://axocoatl.ai/install.sh | sh
    ```

    The installer resolves the latest GitHub release, downloads the tarball for
    the current OS and architecture, and requires its matching SHA-256 file.
    A missing, malformed, or mismatched checksum stops installation. The script
    also stops before download when Linux does not report GNU libc 2.35 or
    newer, or when macOS is older than version 11. It installs to
    `/usr/local/bin` when writable and otherwise to `~/.local/bin`. When that
    directory is not on your `PATH`, it asks, on the terminal, before adding one line
    to the startup files your shell reads in a new terminal and a new login, and prints
    that line when it cannot ask or you answer with end of input (Ctrl-D). The line adds
    the directory only when `PATH` does not have it. A file that has the installer's
    marked line, or its guarded `case` line, anywhere in it gets none, so installing again
    adds nothing. So does a file with the `export PATH` line 1.4.0 printed, fish's
    `fish_add_path` line, or the lines Ubuntu's and Debian's `~/.profile` use to add
    `~/.local/bin`, when they are at its top level where the installer can tell nothing
    before them keeps them from running (it cannot see `set -e` and a failing command, a
    sourced file that exits, or a syntax error, and it can misread a valid file in other
    ways). Its line goes at the end of the file; when something before that end can stop
    a new terminal from reading it (a `return`, `exit` or `exec` outside a function or a
    `( )` subshell, other than one only for shells that are not interactive, as in
    Ubuntu's `~/.bashrc`, and other than an `exec` with only redirections; or a line the
    installer cannot follow), it says so and to move the line above that point, instead
    of saying new terminals find `axocoatl`.
    In a GitHub Actions step it adds the directory to `$GITHUB_PATH` instead, for the
    job's later steps.
  </TabItem>
  <TabItem label="Cargo">
    ```sh
    cargo install axocoatl-cli
    ```

    Building from crates.io requires Rust 1.88 or newer.
  </TabItem>
  <TabItem label="Source checkout">
    ```sh
    git clone https://github.com/axocoatl/axocoatl
    cd axocoatl
    cargo build -p axocoatl-cli --release
    ./target/release/axocoatl --version
    ```

    The root package is not the CLI. Keep the explicit `-p axocoatl-cli`.
  </TabItem>
</Tabs>

All three paths install one `axocoatl` executable. Cargo and source builds compile
the host application and include Axocoatl's prebuilt Linux process supervisor for
its sandbox. There is no separate supervisor installation or startup download.
The [supervisor source](https://github.com/axocoatl/axocoatl/tree/main/crates/axocoatl-exec)
and [explicit rebuild instructions](https://github.com/axocoatl/axocoatl/blob/main/docs/EXEC_SUPERVISOR_BUILD.md)
are available for contributors who want to rebuild those embedded bytes.

Verify that your shell can find the binary:

```sh
axocoatl --version
axocoatl --help
```

If `axocoatl` is not found, the installer used `~/.local/bin` and did not add it to
your `PATH`. Open a new terminal if you let it add the line; otherwise add the line it
printed to the startup files it named (`~/.zprofile` for zsh on macOS; for bash on Linux
`~/.bashrc` and `~/.profile`, or `~/.bash_profile` when you have one, and `~/.bashrc`
alone when `~/.profile` adds `~/.local/bin` already, as Ubuntu's does), or set it for this
shell only:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

`AXOCOATL_MODIFY_PATH=yes` makes the installer add the line without asking, and
`AXOCOATL_MODIFY_PATH=no` stops it from asking:

```sh
curl -fsSL https://axocoatl.ai/install.sh | AXOCOATL_MODIFY_PATH=no sh
```

`AXOCOATL_VERSION` installs a given release instead of the latest one, and
`AXOCOATL_INSTALL_BASE_URL` (`https://` or `file://`, together with `AXOCOATL_VERSION`)
names a directory that holds that release's archive and its `.sha256` file, such as a
mirror or a release you built; the checksum is still required:

```sh
curl -fsSL https://axocoatl.ai/install.sh | AXOCOATL_VERSION=v1.5.0 sh
```

The binary is installed once for the current user or system. The next command,
`axocoatl onboard`, creates user-level Axocoatl configuration and data; it does
not create a repository or Workspace.

## What it needs and downloads

Every run has a writer, which changes the code, and a reviewer, a different model that
only reads. `axocoatl onboard` sets up both, and Podman where it can install it
([below](#runtime-prerequisites)), and asks before each download or change.

- **Writer.** Claude Code needs a Claude Pro or Max plan and the `claude` CLI on this
  computer. Codex signs in with your ChatGPT plan. A local writer runs on Ollama.
- **Reviewer.** A local model on Ollama, or a hosted one paid with OpenRouter credits.
- **Memory for local models.** Models already on your Ollama server come first: when
  they include a pair that fits this computer, a writer and a gpt-oss model or a larger
  one to review it ([how it picks them](/start/onboard/)), onboarding suggests those.
  Otherwise, with 48 to 95 GB it offers the local pair, `qwen3-coder:30b` writing and
  `gpt-oss:20b` reviewing; a fix run calls the reviewer only after the writer and the
  checks finish. With less memory onboarding offers no default local pair: it first offers
  OpenRouter for the reviewer (or for both), or Claude Code or Codex as the writer, and
  suggests local models only if you then choose them, and only ones that fit.
  `gpt-oss:120b`, the reviewer we measured, needs about 96 GB or more; how well
  `gpt-oss:20b` reviews has not been measured. The 1.5.0 release gate requires
  `axocoatl run fix` with the local models onboarding sets up to pass end to end on a Mac
  on Apple silicon; its evidence names the models and the Mac's memory.
- **Docker** is not supported; Axocoatl runs Podman, which can run alongside Docker.
- **For `--keep pr`:** `git`, the `gh` CLI signed in, and a GitHub remote.

| Download | Size |
| --- | --- |
| Podman machine image (macOS) | about 0.9 GB |
| Claude Code image | about 0.6 to 0.9 GB |
| Codex image | about 0.8 to 1.2 GB |
| `qwen3-coder:30b` | 18.6 GB |
| `gpt-oss:20b` | 13.8 GB |
| `gpt-oss:120b` (about 96 GB of memory) | 65.4 GB |
| Embedding model, from huggingface.co on the first daemon start | 87 MB |

A run's sandbox also pulls its base image and packages the first time it starts.

### Proxies, VPNs and rate limits

Axocoatl 1.5.0 does not support an HTTP proxy (`HTTPS_PROXY`, `HTTP_PROXY`,
`ALL_PROXY`) for Sessions and runs:

- A run's network, which it uses for its dependency install, web tools, and Claude
  Code's and Codex's model calls, goes through Axocoatl's egress broker on this
  computer, which connects to each allowed host directly; a workbench Session with
  `sandbox.network: bridge` reaches the internet through Podman's network, also
  directly. Neither reads the proxy variables, and the containers do not get them
  ([Sandboxes](/configure/sandboxes/)). On a network that reaches the internet only
  through a proxy, a run cannot install its dependencies or reach a model API from the
  sandbox. `axocoatl doctor` and `axocoatl onboard` warn when `HTTPS_PROXY`,
  `HTTP_PROXY` or `ALL_PROXY` is set.
- Requests to this computer (`localhost`, `127.0.0.0/8` and `::1`) never use a proxy,
  whatever the variables say: when one is set, Axocoatl adds these to `NO_PROXY` for
  itself. That covers `axocoatl run` and the other commands' requests to the daemon, so
  its API token never reaches a proxy, a Session's Preview, and a model provider,
  webhook or MCP server whose address is on this computer (such as a `base_url` for LM
  Studio). Requests to Ollama never use a proxy either, wherever Ollama runs.
- Every other request the daemon and the CLI make themselves (a native Agent's model
  calls to OpenRouter or another hosted provider, onboarding's checks of OpenRouter's
  catalog, a webhook or an MCP server on another computer) follows the proxy variables
  and `NO_PROXY`, as the HTTP library Axocoatl uses reads them. None of this has been
  tested behind a proxy.

Neither has a VPN that the Podman machine's network (gvproxy, on macOS) must use been
tested. The installer resolves the latest release with one request to
`api.github.com` without a token, which GitHub answers at most 60 times an hour for one
address; set `AXOCOATL_VERSION` (as above) to skip it. The installer's downloads use
`curl`, which reads `https_proxy` and `HTTPS_PROXY` itself (not tested). Session base
images come from Docker Hub, which limits pulls without a sign-in per address;
`podman login docker.io` raises it to your Docker account's limit (not tested).

## Runtime prerequisites

`axocoatl onboard` sets these up where it can, asking before each change; see
[Set up Axocoatl](/start/onboard/). What it needs:

- **Rootless Podman**, for every Session and every `axocoatl run`. On macOS Podman runs
  containers in a Linux virtual machine. On Apple silicon with Homebrew, onboarding
  installs Podman (`brew install podman`) after asking; without Homebrew it points to
  the installer from podman.io, and on an Intel Mac to the Podman 5.8 package. It then
  creates and starts the machine:

  ```sh
  podman machine init --cpus 6 --memory 8192 --disk-size 60
  podman machine start
  ```

  Onboarding creates this size of machine, or one with half the computer's processors
  and memory when that is less; the Claude Code and Codex images and your
  project's checks run inside it, while Ollama runs on the Mac itself. A rootful
  machine (Podman Desktop's default) does not work for `axocoatl run`; onboarding
  offers to switch it to rootless. On Linux, Podman runs containers directly and needs
  no machine: install Podman 4.3 or later (the 1.5.0 release gate runs Ubuntu
  24.04's; Ubuntu 22.04 ships 3.4.4, which onboarding refuses, so Ubuntu 22.04 is
  not yet verified), for example `sudo apt-get install -y podman`; onboarding runs
  that, after asking, with apt, dnf, pacman or zypper, and names what to install on other distributions. For the subordinate ids rootless Podman needs, run `axocoatl
  onboard` or `axocoatl doctor` and use the exact command it prints: when your user has
  no range in `/etc/subuid` and `/etc/subgid`, or fewer than 65536 ids, onboarding
  offers to run it and doctor fails "User ID ranges" with it. It is `sudo usermod
  --add-subuids <first>-<last> --add-subgids <first>-<last> <user> && podman system
  migrate` (with one of the two options when only one file is short), with the first
  65536 ids from 100000 up that no line of either file uses. Do not copy a range from
  elsewhere: it is `100000-165535` whenever no line of either file uses those ids, for
  example when both files are empty, and on Ubuntu the first user created usually has
  that one already, so yours differs.
- **A writer and a different reviewer model**: Claude Code (a Claude Pro or Max plan),
  Codex (a ChatGPT plan), a local Ollama pair, or OpenRouter
  credits. Claude Code and Codex write but do not review, so they need a reviewer on
  Ollama or OpenRouter.
- **Ollama**, for local models: Ollama **0.40.6 or later** on this computer with its
  cloud features disabled. Later 0.40 releases are accepted; a later 0.x release (0.41
  or later) is accepted once the contract probes pass on each model. Onboarding
  installs it (`brew install ollama && brew services start ollama` on macOS;
  `curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.40.6 sh` on Linux),
  turns the cloud features off where the running server reads them, and pulls the
  models.

Local models need memory. Unless models already on your Ollama server include a pair
that fits this computer, which onboarding then suggests, from 48 GB it offers
`qwen3-coder:30b` (18.6 GB) to write and `gpt-oss:20b` (13.8 GB) to review, and a fix
run calls them in turn; with 96 GB or more the reviewer is `gpt-oss:120b` (65.4 GB), the
one Axocoatl has measured. Below 48 GB onboarding has no default local pair, and it
first offers OpenRouter for the reviewer or for both, or Claude Code or Codex as the
writer.
They are large downloads. A fix run needs a context of at least 16384 tokens, and
Ollama gives a model 4096 on computers with less than about 23 GiB of graphics memory;
onboarding then offers to set `OLLAMA_CONTEXT_LENGTH=32768` for the Homebrew or
systemd Ollama service and restart it (for the app or an `ollama serve` you run, it
says what to set). Native
Sessions run only GGUF models: on Apple silicon, Ollama pulls the MLX variant of some
models, which Axocoatl refuses; `ollama pull --runner llamacpp <model>` (an
undocumented Ollama flag) pulls the GGUF one.

## Windows through WSL2

WSL2 is not yet verified: no Windows run has been done yet. These are the steps it is
designed for.

<Steps>

1. In an administrator PowerShell, install WSL2 and reboot when requested:

   ```powershell
   wsl --install
   ```

2. Open the Linux distribution and install Podman, or let `axocoatl onboard` install
   it with apt after asking in step 3 (it refuses Ubuntu 22.04 and older, whose Podman
   is too old). On Ubuntu 24.04:

   ```sh
   sudo apt-get update
   sudo apt-get install -y podman
   ```

3. Run the release installer **inside WSL2**, not in PowerShell, then continue with
   [user-level onboarding](/start/onboard/).

</Steps>

`axocoatl dev` runs inside WSL2. Open the sign-in link it prints
(`http://localhost:8080/?token=…`) in the Windows browser; WSL2 normally
forwards that loopback port to the host.

<Aside type="caution" title="The default sandbox still needs Podman">
Installing the Axocoatl binary does not install or start Podman. `axocoatl onboard`
installs it after asking where it can (Homebrew on an Apple-silicon Mac; apt, dnf,
pacman or zypper on Linux) and otherwise says what to install. Without a ready Podman
runtime, `doctor` fails, and neither Sessions nor `axocoatl run` can use the default
local sandbox. A deliberately
configured E2B Cloud backend is the separate remote option for workbench Sessions.
</Aside>

Local-first describes where Axocoatl can run and store its durable state. It
does not mean every execution is offline or that an Agent, repository, package,
provider, MCP server, webhook, or model response is trusted.

## What Axocoatl controls, and what it does not

Axocoatl decides who writes, what helpers may do, what a run may spend, and
whether required checks and review pass. It records all of it in the Session:
every grant, budget decision, activation, and tool invocation.

Sandbox runtimes, for example NVIDIA OpenShell, control what a process can reach:
files, network destinations, and credentials. Axocoatl runs repository tools in a
rootless Podman container with the defaults described below. With
`network: egress` it also controls network egress for Session containers: an Agent's
commands reach only the hosts and routes you list and the hosts you allow for one
Session, through a proxy that writes each connection it allows, and each refusal of a
connection that presents a valid credential, to the Session's record before the
connection opens. Axocoatl implements this itself, rather than running Sessions in a
sandbox runtime, so that it works in the Podman
containers it already manages on macOS and Linux and so each connection is joined
to the tool call that made it. For hosts you list as egress routes it also ends TLS
on your computer, checks each request's method, path and query, and adds the
route's credential there, so the token never enters the container; a token or
session the host issues in return can (see
[Credentials the host issues](/configure/credentials/#responses)). In a Session
container with [workload users](/configure/sandboxes/#workload-users), the default
under `egress`, the record of each connection also names the program that opened it,
with its path, SHA-256 and user, when the container's first process finds it in time;
otherwise the connection is still allowed and recorded with only its user and the
reason. Agents can neither stop that process nor stand in for it. The record names
programs; it does not yet limit a host to some of them. See
[Control network egress](#control-network-egress) and
[Compared with OpenShell](#compared-with-openshell).

With local Podman, model provider API keys stay in the Axocoatl daemon and are not
passed into the container. Files in the Workspace, such as a `.env` file, are
visible to tools, and on E2B the Git token is visible to every command in the VM.

## Loadout runs

A Session that [`axocoatl run`](/reference/run/) creates for a
[loadout](/configure/loadouts/) does not use your global network default:

- it runs under `network: egress` (or `none`, when the loadout says so), with the
  daemon's egress lists plus the loadout's own `egress` and `routes`, for that Session
  only;
- it runs the `hardened` workload: Agents' commands, setup and required checks as the
  non-root writer user, read-only Agents as the non-root helper user, tool calls and
  checks under the supervisor's seccomp filter and in a Landlock domain of their own;
- a loadout cannot ask for `bridge` or the `image` workload, and when the host cannot
  provide `egress` and the `hardened` workload (rootful Podman, `backend: e2b`) the run
  fails with exit code 5 instead of running with less.

`sandbox.network` and `sandbox.workload` keep the values you set for every other
Session. What `egress` and the workload users cover, and what they do not, is the same
as below.

An [external agent](/configure/external-agents/) (Claude Code or Codex CLI) runs inside
that container as the writer user. Its model credential is added on your computer by a
route; the container holds a placeholder. Its own tool calls are recorded as evidence but
not admitted one by one, and its spend is bounded by an up-front reservation, the route's
request count and the program's own usage report, not per call.

[Keep as PR](/workbench/keep-as-pr/) runs `git` and `gh` on your computer with your own
credentials. It never force-pushes and refuses the remote's default branch.

The [record bundle](/reference/run/#record-bundle) ends with a SHA-256 over its contents.
It shows that the file was not changed after it was written; it is not a signature, so
anyone who can write the file can write a new digest too.

## Keep the server local by default

The default listener is `127.0.0.1:8080`. Same-origin CORS is the default and
rate limiting is off.

### The local API token

On a loopback listener with no configured credentials, the API requires a
per-daemon token. The user's signed-in browser and tools that can read the data
root can use it. Another user's process, or code in a Session container that
reaches the host, cannot, unless the token reaches it another way. The most
likely way is through a web server you open on another `localhost` port, as
described after this list.

- On first start the daemon creates 32 random bytes from the OS random number
  generator, encodes them as base64url, and writes them to `local-api-token` in
  the data root with mode `0600`. Later starts reuse the file. A file that is a
  symlink, is not a regular file, is readable or writable by other users, or
  does not hold a token stops startup.
- `axocoatl dev` and `axocoatl serve` print a sign-in link,
  `http://localhost:<port>/?token=<token>`, when their output is a terminal.
  `axocoatl url` prints it again from the configured port and the token file.
  Under a service manager, run `axocoatl url` with the same `--config` and
  `AXOCOATL_DATA_DIR`.
- Opening the link sets the cookie `axocoatl-token-<port>` (HttpOnly,
  SameSite=Strict, `Path=/`, 30 days) and redirects to the same page without
  the token, with `Referrer-Policy: no-referrer`. Request logs show the
  parameter as `token=REDACTED`.
- The link also sets `axocoatl-token-<port>-signed-in=1` (HttpOnly,
  SameSite=Lax, `Path=/`, 30 days). It holds no secret and is never a
  credential. Safari leaves a SameSite=Strict cookie off a navigation that was
  redirected from another site, and `127.0.0.1` and `localhost` are different
  sites, so a `127.0.0.1` bookmark or link reached `localhost` without the
  token cookie. When a navigation you started yourself (a typed address, a
  bookmark, a link opened from another app: `Sec-Fetch-Site: none`) reaches
  `/` without a valid token cookie but with this one, the daemon answers with
  a page that opens the same address again from `localhost` itself, which
  every browser sends the token cookie with. The request that page makes is
  same-origin, so a navigation passes through it at most once. The page also
  clears the cookie, and the next workbench load sets it again. Chromium
  already sends the token cookie on these navigations, so no browser is
  signed in on one that Chromium would refuse. A link or form on another site
  still gets the sign-in page. A Session's app cannot set this cookie through
  the Preview proxy. In Safari on macOS, script on a page of another
  `*.localhost` address that runs in a tab of its own (never a Preview: the
  daemon refuses that in Safari) can set it as a `Domain=localhost` cookie
  ([see below](#safari-shares-domainlocalhost-cookies)),
  which the retry page cannot clear: while that browser is signed out, each
  navigation you start then passes through the retry page once before the
  sign-in page. It never signs anyone in.
- Scripts send the token as `Authorization: Bearer <token>` or
  `x-api-key: <token>`. Comparisons are constant time.
- The cookie counts only on same-origin requests, typed navigations, and
  requests without Fetch Metadata such as WebSocket upgrades. A request marked
  `Sec-Fetch-Site: cross-site` or `same-site` must send a header instead.
- The daemon reads the `Cookie` header as bytes, one cookie at a time, and
  accepts the request when any `axocoatl-token-<port>` value in it matches.
  Another cookie whose value or name is not ASCII, or a second
  `axocoatl-token-<port>` with another value, does not hide the token cookie.
- Health probes, the sign-in page, and static assets (`/ui/`, `/vendor/`,
  `/lattice/`, `/brand/`, `/axo-tap.js`) stay public. Every route that reads
  or changes state requires the token, including `/ws`, terminal WebSockets,
  and `/a2a/*`.
- A loopback listener holds its port on both `127.0.0.1` and `[::1]` when
  the host has both. Browsers, curl, and Node try `[::1]` first for
  `localhost`, so a process listening there would receive the sign-in link.
  If another process already listens on either address and port, Axocoatl
  does not start.
- Rotate the token by stopping Axocoatl, deleting `local-api-token`, and
  starting it again. Open the new link in each browser.

The cookie value is the token itself, and browsers do not separate cookies by
port. Any web server you open on another `localhost` port in the same browser
receives the token in its request headers. It can then use the API from
outside the browser, so the Fetch Metadata rule does not help. This includes
another user's server and a Session port mapped to `localhost` that you open
directly. Treat opening such a server like sharing the token, and rotate the
token afterwards. Session containers have no mount of the data root, so Session
code cannot read the token file, and Preview origins never receive the cookie.

`server.auth.allow_unauthenticated: true` turns the token off on loopback, for
an authenticating reverse proxy on the same host. Axocoatl logs a warning when
it does. The Host check against DNS rebinding still applies, so the proxy must
send `Host: localhost` or a loopback IP literal.

### Configured credentials

Binding to a non-loopback address fails closed unless API-key or bearer-token
authentication is configured, or the operator explicitly opts out:

```yaml
server:
  host: "0.0.0.0"
  port: 8080
  auth:
    api_keys: ["${AXOCOATL_API_KEY}"]
    bearer_tokens: []
    allow_unauthenticated: false
  cors_origins:
    - "https://workbench.example.internal"
  rate_limit:
    enabled: true
    max_requests: 100
    window_secs: 60
```

Clients may send either `x-api-key` or `Authorization: Bearer <token>`. The
health probes remain public. Configured credentials replace the local token:
there is no sign-in cookie, and an empty configured value never matches. CORS controls browser origins, not network access
or authentication. Allowlisted cross-origin browser clients may preflight HEAD,
GET, POST, PUT, PATCH, and DELETE.

<Aside type="danger" title="Do not expose an unauthenticated workbench">
The API can execute Agents, read and change Session repositories, run terminal
commands, operate Git, and manage Automations. `allow_unauthenticated: true` is
an explicit operator escape hatch, not a safe internet-facing default.
</Aside>

## Preview uses a separate browser origin

Each local Preview is served from a validated
`<session>-p<port>.localhost:<listener-port>` origin. The Host boundary
runs before the workbench router and can reach only that Session's configured
Preview transport; a Preview request cannot fall through to the app shell,
control API, or workbench WebSockets. On a loopback listener without configured
credentials, even with `allow_unauthenticated`, Hosts other than `localhost` and
loopback IP literals are rejected with 421 to prevent DNS rebinding. Preview origins never receive the workbench
sign-in cookie, and the Preview proxies remove `axocoatl-token-*` cookies from
forwarded requests and drop upstream `Set-Cookie` headers that would set one.
From every other upstream `Set-Cookie` they remove the `Domain` attribute, so
the browser keeps an app's cookies host-only on its own Preview origin.

The legacy `/api/sessions/{id}/proxy/{port}` path also reaches a Session's
app, from the workbench's own origin and behind its sign-in. In every browser
it answers only `fetch()` and `XMLHttpRequest` (`Sec-Fetch-Dest: empty`) and
programs that send no Fetch Metadata. A page, frame, script, image or anything
else a browser would show or run there gets 403 and a line of text, without
the app being asked, and the path forwards none of the app's `Set-Cookie`
headers. Before 1.5.0 a link to it opened the app's page on the workbench's
origin. That page ran with an opaque origin (the path sends
`Content-Security-Policy: sandbox` without `allow-same-origin`), so its script
could not use the workbench's API, but the app's cookies were stored for
`localhost`, the workbench's host, and its redirects were followed (measured in
Playwright's Chromium and WebKit on macOS).

If the workbench document is opened through a loopback IP literal, its exact
root navigation redirects to `localhost` on the same listener. This gives the
browser one canonical workbench origin without redirecting API, health, asset,
or non-loopback operator requests.

The Preview frame may use scripts, modules, same-origin fetch, forms, storage,
streamed responses, and development-server WebSockets within its own virtual
origin. Modern third-party-cookie policy can block ordinary cookies in the
embedded frame. **Open full preview** opens that exact virtual URL top-level
with `noopener`; it does not reveal the logical sandbox URL. Host-only cookies
then work, and stay with that Session and port. Safari is the exception: there
a Preview never runs top-level. The daemon refuses it, and the workbench keeps
every Preview embedded and offers no **Open full preview**
([see below](#safari-shares-domainlocalhost-cookies)). Preview remains
cross-origin from the parent workbench. DOM-pick messages are accepted only
from the exact frame window and expected origin in both directions.

### Safari shares `Domain=localhost` cookies

Whether a page on a `*.localhost` address may set a cookie for the parent
domain, `Domain=localhost`, is the browser's decision. Chromium refuses such a
cookie, and so does WebKit on Linux. **Safari on macOS accepts it** when a page
that runs top-level sets it from script (`document.cookie`), and then sends it
to the workbench at `localhost` (on every port) and to every Session's
Preview. An app's server cannot do the same through the Preview proxies: they
remove `Domain` from each `Set-Cookie` they forward. Embedded in the
workbench, Safari gives a Preview no cookies at all, so it cannot set one there
and receives none.

So **in Safari a Preview never runs top-level**. The daemon answers every
request for a Preview page that Safari would show in a tab or window of its
own with `403` and a short page that says why and links to the workbench, and
never asks the app. That holds whatever led there: a link, a redirect,
Command-click on a link inside the Preview (Safari opens a new tab whatever the
frame's sandbox says), the context menu, a window the Preview's code opens, or
an address typed or pasted. The page runs no script and sets no cookie. The
Preview in the workbench's pane (`Sec-Fetch-Dest: iframe`) and every request
its page makes are served as before. Other browsers are unchanged and keep
**Open full preview**.

- The daemon recognizes Safari's engine by its user agent: `AppleWebKit` on a
  Mac without a Chromium or Firefox token (Safari, and apps that show pages
  with WebKit), and every browser on iPhone and iPad, which all use Safari's
  engine. A Safari whose user agent was changed to another browser's is taken
  for that browser, and a browser that sends Safari's user agent is taken for
  Safari wherever it runs: Playwright's WebKit on Linux does. Chrome and
  Firefox on Linux, and WebKitGTK and WPE with their default user agent, name
  Linux in theirs and keep **Open full preview**.
- Safari 16.4 and later say whether a request is for a page of its own
  (`Sec-Fetch-Dest: document`) or for a frame. An older Safari does not say,
  so it gets the refusal page for the embedded Preview too.
- The workbench says the same before you try: it offers no **Open full
  preview** (the control stays disabled, and a line under the Preview's address
  says why), the Preview frame may not open windows (its sandbox leaves out
  `allow-popups`; in every browser it also leaves out top navigation), and no
  link in the workbench opens a `*.localhost` address in a tab of its own. A
  Markdown link to one in the conversation keeps its text and loses its
  address; a click, Command-click, middle click, context menu or drag on any
  other such link is refused, and so are `window.open` (the file editor's
  links) and a link a program prints in the Terminal.

This was measured in Playwright's WebKit 27.2 on macOS: a typed Preview
address, a redirect from another site to one, and a real Command-click on a
Preview link inside the Preview's frame and inside the Files view's frame each
got the refusal page, and no cookie was set. It was not measured in Safari
itself, or on iPhone or iPad.

What remains in Safari on macOS is a page Axocoatl does not serve that runs
top-level on a `*.localhost` address and sets such cookies: a development
server you run yourself, for example. A Session's app is also published on a
loopback port of this computer, which the workbench never shows; opened there
directly, as `<name>.localhost:<that port>`, it runs without the daemon. A
service worker that a Preview registered while it ran top-level in Safari,
before 1.5.0, would also answer a navigation to that Preview's address without
the daemon seeing it (not measured). Such a page cannot reach a Session's app
through the Preview: Safari would send its cookies to a Preview only with a
top-level request, which the daemon refuses. It can:

- Reach any other web app you open on `localhost` or `*.localhost` in Safari,
  on any port.
- Send the workbench `axocoatl-token-<port>-signed-in=1`. While that browser is
  signed out, each navigation you start then passes through the retry page once
  before the sign-in page.
- Sign the workbench out of its API. Safari sends at most about 200 KB of
  cookies with a request, puts the cookies with the longest path first, and
  leaves out each one that no longer fits. Cookies for `localhost` with
  `Path=/api`, 51 of 4,000 bytes and then smaller ones that fill what is left
  (the large ones alone still leave room for it), leave the token cookie off
  every API request, while `/` still gets it, so the API answers 401. The
  workbench page then reloads once and shows "This browser is signed out" with
  what to do; it reloads at most once a minute, where it used to reload without
  end. Opening the sign-in link again
  does not help while those cookies stay, and they stay until they expire or
  you remove them: remove localhost's data in Safari > Settings > Privacy >
  Manage Website Data, then open the sign-in link again (`axocoatl url`).
- Sign that browser out of the workbench entirely, with the same cookies for
  `Path=/`: the token cookie then stays off every request, `/` included, so
  the open workbench page and a new one both get the sign-in page, not the
  signed-out message. Opening the sign-in link again signs back in, until the
  page's code writes the cookies again. Remove localhost's data in Safari >
  Settings > Privacy > Manage Website Data, close that page, then open the
  sign-in link again.
- Keep the workbench's live connection from opening, with the same cookies
  for `Path=/ws`. The workbench loads and its API answers, but live updates
  stop and the status bar says the live connection is reconnecting. Removing
  localhost's data and signing in again restores it.
- Sign out a browser that signed in a few seconds earlier and has no
  workbench page open, by writing about 1,000 cookies at once. WebKit then
  dropped every cookie the browser held, and the workbench answered with the
  sign-in page. This needs no `Domain=localhost`: 1,000 host-only cookies of a
  page on `127.0.0.1` did the same, so any page open in Safari can do it. With
  the workbench page still open, or 20 seconds between the sign-in and the
  cookies, the sign-in survived, and 300 cookies changed nothing. Open the
  sign-in link again (`axocoatl url`) to sign back in.

It cannot:

- Sign in or use the API. A forged `axocoatl-token-<port>` cookie never matches
  the token, and the signed-in cookie is never a credential.
- Sign the workbench out with a cookie that is not ASCII, a forged
  `axocoatl-token-<port>` sent before or after the real one, or 40 cookies of
  1 KB. The daemon reads the `Cookie` header as bytes, so the token cookie
  stays readable beside them (Safari sends `é` as the byte 0xE9): the
  workbench reloads, connects, and its API answers. Safari refuses a cookie
  that holds a control character other than tab.
- Read the workbench's cookies. They are host-only on `localhost` and HttpOnly,
  so Safari never sends them to a Preview origin. The Preview proxies also
  strip every `axocoatl-token-*` cookie before an app sees a request.
- Reach `127.0.0.1` or `[::1]`.

For a full-page Preview, use the workbench in a Chromium-based browser. The
Safari cookie behaviour on this page was measured in Playwright's WebKit on
macOS (26.4), which uses the system's cookie store, not in Safari itself.

## Understand Workspace authorization

Creating a Session asks the daemon to canonicalize an existing directory. The
current server has no configured folder allowlist. Anyone who can authenticate
to the API may therefore attempt to select any daemon-readable directory.
Restrict server access and run the daemon under a least-privileged OS account.

## Protect the control plane

On supported Unix hosts, the daemon opens the resolved data root once and keeps
that directory handle as its state authority. Managed reads, writes, replacements,
and cleanup stay relative to opened directories. Symlinked path components, final
symlinks, and multiply linked managed files fail closed. Atomic replacement uses an
unpredictable owner-only temporary file in the destination directory, then fsync and
rename. This protects path ownership; it does not encrypt state or erase it securely.

One daemon or direct bootstrap owns a root through an external per-root lock, the
retained 0.1-compatible `.axocoatl-daemon.lock`, and a lock on the opened directory
inode. The locks are acquired before runtime reconciliation or mutable Session state
is read. At bootstrap, Axocoatl inspects reserved-name Podman containers
and removes by immutable id only non-current containers whose bind mounts prove they
expose the data root or external lease root. It then verifies that both paths still
resolve to the opened directories. Invalid Session records cannot supply a replacement
cleanup id.

The normal data root is user-level and outside every Workspace: under macOS
Application Support or the Linux/WSL XDG data directory. An explicit
project-local `--config` uses a sibling `data` directory unless
`AXOCOATL_DATA_DIR` overrides it. If a protected data or lease root is a
descendant of the canonical Workspace, local Podman places an exact nested
`tmpfs` over it. A Workspace equal to or below a protected root is rejected
instead, when it is opened and again when its environment starts. The per-user
configuration directory is protected the same way when the daemon loaded the
per-user configuration file; a project's own file loaded with `--config` is not,
and a Session whose Workspace contains it shows a warning. Opening the home
folder, a folder above it, or a folder that contains a protected root as a
Workspace needs a typed confirmation, because a Session can read and change
everything in its Workspace that is not protected. This boundary prevents repository tools from reaching Axocoatl
control-plane state; it does not protect secrets deliberately placed elsewhere
in the read-write Workspace.

## Constrain sandbox execution

The local default is rootless Podman with `no-new-privileges`, dropped
capabilities, fixed resource-limit requests, and trust gates for custom images
and repository post-create commands. Two defaults are open: `network: bridge`
lets Session containers make outbound connections, and
`require_resource_limits: false` lets a Session start without resource limits
when the host cannot apply them. For a repository you do not trust, set:

```yaml
sandbox:
  backend: podman
  network: none
  allow_post_create_command: false
  allow_untrusted_images: false
  require_resource_limits: true
```

`network` accepts only `bridge`, `none` or `egress`. Any other value, such as
`None` or `off`, is a configuration error: `axocoatl validate`, `axocoatl doctor`
and daemon start report it instead of starting a container with a network.

Podman containers do not receive the host's proxy variables (`HTTP_PROXY`,
`HTTPS_PROXY`, `NO_PROXY` and the others Podman would copy by default), so a
proxy URL with a user name and password stays on the host.

`allow_post_create_command: true` is not a hidden execution hook. It defaults
only the exact devcontainer command to checked for an unreviewed Session; the
visible per-Session decision wins. It never approves a separately detected or
edited command.

The built-in Alpine, Debian slim, Ubuntu, Python slim, Node slim, and Rust
bookworm references are a fixed allowlist, not an audit or a guarantee that an
image contains safe dependencies. Local readiness verifies Axocoatl's own
repository commands and may provision missing commands inside a supported
container. If that cannot succeed, the environment fails and the incomplete
container is removed. Session startup never invokes a host package manager or
creates a Podman VM.

The Workspace is still a read-write host bind. A root Node project additionally
mounts a Podman-managed volume over root `node_modules` so Linux does not consume
host-native packages; it is a separate writable sandbox resource, not a second
host bind. Protected Axocoatl data and lease directories below that bind are
automatically masked as described above. Keep all other secrets and unrelated data
outside the Workspace.

An Agent configured with `writes: []` is a read-only helper. A required reviewer that
has `bash` must have `writes: []`, so the same applies to it. It is not offered
`write_file` or `edit_file`, and the host refuses them if it asks. Its own `bash`
commands run under a Linux Landlock restriction: no file in the repository, including
`.git`, can be written, created, renamed or deleted, and only `/tmp`, `/var/tmp` and
`/dev` (but any of them that contains the repository, so with the repository under `/tmp`
not `/tmp`) and a temporary directory of the command's own are writable; with
[workload users](/configure/sandboxes/#workload-users), only that temporary directory and
`/dev/null`, `/dev/zero`, `/dev/tty` and `/dev/urandom`. The temporary directory is the
command's `TMPDIR`: Axocoatl's execution supervisor makes it for each command, private to
the user the command runs as and outside the repository, and removes it when the command
ends (a command that may write the directory holding it, such as `/tmp` when the
repository is elsewhere, can move it aside first, as it can leave any file there). Landlock does not cover a file's permission bits, owner or
timestamps. A helper that runs as root, as under `sandbox.workload.mode: image` with an
image whose user is root, can change them; on macOS, where the Podman machine's shared
folder reports every file as the caller's, any helper's shell can change permission
bits and timestamps. Each command gets a
scratch home directory, removed when it ends, so the helper cannot leave
configuration in the Session's shared home for later commands. The same restriction
refuses every TCP connection and every TCP bind, on any address including loopback,
whatever the sandbox's `network` setting: the helper's shell cannot connect anywhere
over TCP, with `curl`, `git` or a package manager for example, including to a server
running in the container. In every network mode the sockets for the Session's apps,
which the browser tools and, under `network: egress`, Preview use, live in a separate
forwarder container, never in the Session container, so they do not open another way
in. Landlock does not cover Unix sockets. With
[workload users](/configure/sandboxes/#workload-users), the default under
`network: egress`, every process of a helper also runs as a user of its own, which
cannot read the environment of a writer's processes or signal them, under a seccomp
filter that refuses Unix sockets, so an app's own socket in the container, abstract or
not, is out of its reach, and that also refuses System V IPC and POSIX message
queues. Its file tools cannot open a socket of any kind. That user reads the
repository whatever its file modes, through a view that also confines what it reads outside it to what any user may read.
The same view keeps its file tools from writing anything, or changing a file's mode,
owner or times, and its shell from writing outside a temporary directory of its own;
see [Sandboxes](/configure/sandboxes/#workload-users). Under
`sandbox.workload.mode: image` an app in the container that listens on a Unix socket of
its own is still within a helper's reach, an abstract socket always and a socket file
whenever its permissions let the helper connect. A helper whose
template lists `browser` can still drive those apps
through the browser, which can do whatever the apps allow; see
[Browser](/configure/browser/#helpers-and-reviewers). Landlock does not cover UDP, so name lookups and other UDP
traffic still follow `network`. Nor does it cover a socket that listens without binding
first, which the kernel gives a random port that the host or other containers may be
able to reach. `network: none` stops both. The restriction needs Landlock ABI 4 (Linux
6.7 or later) and a container runtime that allows it. Where it cannot be applied in
full, the helper's `bash` commands do not run and its read-only file tools still work.
Axocoatl's own before-and-after repository captures run without the restriction; they
read no Git configuration, attributes or ignore file from outside the repository and run
no program that the repository's configuration names.

An Agent that may change only some paths gets no kernel restriction. Its `write_file`
and `edit_file` refuse other paths, and any path inside `.git`, before writing. Every
change it makes is then checked after it finishes, whether or not it has `bash`:
Axocoatl compares a complete manifest of the repository from before its work, kept in
the sandbox and verified by its digest, with one from after. The manifest covers each
tracked and untracked file's actual content whatever the Git index says, the index
entries, every `.gitignore` Git reads, and `.git/config`, hooks and `info`. A change
outside the Agent's paths, or captures that cannot establish every change, fail that
work and keep the change for you to review. The check does not undo a change, and it
does not cover files your ignore rules exclude or anything outside the repository. A
shell can still write anywhere in the sandbox, and in a sandbox that runs as root it
can replace the tools the check itself runs, so treat the check of an Agent with `bash`
as review evidence. An Agent held to its paths with file tools only, without `bash`,
cannot do either. See
[Limit which files an Agent may change](/configure/agents/#limit-which-files-an-agent-may-change).

A team's required reviewer must be read-only in the same sense: Apply and turn
admission refuse a reviewer template that could change files or run commands that can.
The host, not the lead, starts it after the required Agents and checks finish, on its
own approved budget, and the turn completes only when it approves the exact answers and
repository tree it was shown. It fails closed: an answer without a readable verdict, a
reviewer that did not finish, or a tree that changed while it read approves nothing.
The review is a model's judgement, not verification; a reviewer can miss a defect or be
misled by what it reads in the repository. See
[Required review](/configure/agents/#required-review).

`network: none` blocks container egress and Preview ports, but does not block
the host daemon itself from reaching model providers, MCP servers, web search in
legacy Sessions, webhooks, a remote sandbox service, or a registry for a Podman
image pull. It also prevents readiness/setup processes inside the container from
downloading missing commands or dependencies, so use an image that already contains
the required repository command surface.

Native Sessions refuse the web tools under `network: none`. A legacy (1.0-format)
Session still offers `web_search`, unrecorded, to every Agent whose `tools` list is
empty or names it. It offers `web_fetch` only to an Agent whose `tools` list names
it, and never under `network: none`.

## Control network egress

`network: egress` sits between `bridge` and `none`: a Session container gets no
network interface other than loopback, and an Agent's commands reach only the hosts
and ports listed under `sandbox.egress`. The
[Sandboxes page](/configure/sandboxes/#network-egress) describes how it runs.

| Threat | What `egress` does |
| --- | --- |
| A command connects to an unlisted host | The proxy refuses it with `403 not_allowed`, before anything resolves the name, and records the refusal. |
| A command skips the proxy (`--noproxy`, raw sockets, a hard-coded address) | There is no route: the container has only loopback. |
| DNS, UDP or IPv6 used to send data out | No interface carries them off the machine. |
| An allowed name resolves to loopback, link-local (including the `169.254.169.254` metadata address) or another special address | Refused as `forbidden_destination`, including IPv4 embedded in IPv6 forms. |
| An allowed name or listed range leads to the Podman host gateway | Refused as `forbidden_destination` even when you list a range that contains it: `192.168.127.1` and `192.168.127.254` in a Podman machine, `10.88.0.1` on Podman's default network, and the gateway of `sidecar_network`. Through them the proxy could reach services on your computer. `validate` warns about a range that contains one. |
| An allowed name resolves to another private address | Refused as `private_destination` unless you list the range. |
| A container's own resolver is poisoned | Not used: names resolve on your computer, after the allowlist check. |
| A command needs a token for a host, such as a `git push` or an API call | Under a [route](/configure/credentials/) the daemon adds the credential to the requests the route's rules allow. The token is never in the Session container, the proxy container, the record or the logs. A credentialed route removes `Set-Cookie` from responses, but a token the host issues in a response body, such as from a login or `/token` endpoint the rules allow, reaches the container. Without a route, the token must be in the container. |
| A command uses an allowed host for something else: another repository, a delete, another site on the same CDN | For a route's host each request's method, path and query must match the route's rules, and the TLS server name and `Host` must be the route's host; anything else gets a JSON refusal, is recorded, and is never sent. A host listed only under `allow` is an opaque tunnel. |
| A read-only helper or required check uses the network | They get no credential; a helper's TCP connection to the proxy is refused by Landlock. With workload users, the default under `egress`, a helper runs as a user of its own: it cannot read a running writer's credential under `/proc`, and it cannot open a Unix socket, so the proxy's socket, in a directory only root can enter, is out of its reach; its file tools cannot open any socket, so they do not reach the proxy over TCP either. With `sandbox.workload.mode: image`, a direct connection to the proxy's socket gets `407`, which is recorded. |
| You need to know which program made a connection | With workload users each connection's record names the program that opened it: its path, the SHA-256 of its file, its user and group, and its parent programs, found by the container's first process in `/proc`. The workload users cannot reach the proxy's socket, and a line a program writes to claim another identity is refused. A program made to act for another, for example with `LD_PRELOAD`, is named as itself. When the first process cannot find or read the program in time, the connection is still allowed and recorded with only its user and the reason (`timeout`, `not_found` or `no_access`); **Session network** shows it as an unknown program. |
| A command uses kernel interfaces to inspect other processes or leave the container: `ptrace`, user namespaces, `io_uring`, keyrings, mounts, file handles | With workload users, every process of an Agent's tool call in a native Session and every required check runs under Axocoatl's seccomp filter, on top of Podman's, which refuses them, and in a Landlock domain of its own, so it cannot read the memory or environment of a process it did not start. A read-only helper's processes cannot read any process's `/proc` entries. Terminals you open, setup commands, background tasks you start and Ways checks run without the filter. |
| A process started during setup keeps running afterwards | Its credential ended with the setup step; each later attempt gets `407 unknown_credential`. The first 20 are recorded with the old credential's tag, then one every 5 seconds, and the rest are counted in a `limit` event, so the process cannot fill the record. |
| A credential ends, or a host is revoked, while a connection is being decided | The connection is refused before its tunnel opens (`407 binding_ended`, `403 not_allowed` or `403 revoked`). |
| The proxy stops or its control channel breaks | Connections are refused (`502` from the bridge, or `503` from the proxy) and connections in progress are recorded as `interrupted`. |
| The record cannot be written | New connections are refused with `503 record_unavailable`; setup commands, provisioning and terminals still run, without network. The record has no event cap: it keeps every event for the Session's life in sealed, hash-chained segments. |
| A process in the container replaces a port socket with a symlink | The Session container holds no port socket. In every network mode the port sockets are made in a separate forwarder container that the Session container cannot reach, and its bridge creates each socket with its final mode instead of changing it afterwards. |
| Axocoatl's config file is inside the Workspace | Agents can read it, and under `egress` send it to an allowed host that accepts uploads. **Session network** warns about it; keep secrets in environment variables. A writer can also edit it, so `axocoatl network reload` refuses to apply it; a restart still reads it. |

What `egress` does not do:

- It does not see inside TLS to a host listed only under `allow`. A tunnel to a host
  that fronts other sites, such as a CDN, can reach those sites, and a listed host
  that accepts uploads is a way for data to leave. The model you use is also a
  channel.
- Agents in one Session share its container, and per-Agent network limits are not
  enforced inside one Session container. Writers share one user, so they can change
  each other's files. With [workload users](/configure/sandboxes/#workload-users), the
  default under `egress`, a helper cannot read a writer's credential, and neither can
  another tool call's processes, but a terminal you open, a setup command or a
  background task can; with
  `sandbox.workload.mode: image` any command can read a running writer's credential
  from `/proc`.
- The program named in the record is the one that opened the connection. Allow
  entries and routes cannot be limited to some programs, and a program can be made to
  act for another (`LD_PRELOAD`, an interpreter, a connection passed to a child). The
  first process looks for the program for at most 100 ms and in at most 4096
  processes, lowest ids first; when it cannot find or read it, the connection is still
  allowed and recorded with only its user and the reason (`timeout`, `not_found` or
  `no_access`). The record is not complete attribution.
- `for` on a route tells processes apart by the kind of credential they present, not
  by who controls them. Agents' commands share the writer's user, home directory and
  Workspace with terminals and setup commands, so an Agent can leave code that a
  terminal or setup step runs later and use a `for: [terminal]` or `for: [setup]` route
  that way; see [Who `for` keeps out](/configure/credentials/#who-for-keeps-out).
- The browser's declared hosts and the Session's list are told apart by the
  credential presented, not by the container. While a `browser_check` call runs, its
  test holds the browser's credential and can pass it to the Session container; see
  [Declared hosts](/configure/browser/#declared-hosts).
- Route rules check the method, path and query of HTTP/1.1 requests, so GraphQL
  operations and JSON-RPC or MCP methods look alike, and they do not handle WebSocket
  messages. A request a route allows can still carry data out in its body. A route to a
  model API (`api.anthropic.com`, `api.openai.com`, `chatgpt.com`, `openrouter.ai`,
  `generativelanguage.googleapis.com`, `api.mistral.ai`, `api.x.ai`,
  `ai-gateway.vercel.sh`) also reads each body, and refuses one that asks the provider
  to fetch a URL, search the web, connect to an MCP server or run a tool itself
  ([Requests to model APIs](/configure/credentials/#requests-to-model-apis)); settings
  stored with your provider account, such as an OpenRouter account's default plugins,
  presets or Vercel AI Gateway routing rules, are not seen. The route to Ollama on this computer
  ([`sandbox.egress.host_ollama`](/reference/config/#sandboxegresshost_ollama)) carries
  only Ollama's inference and model listing, and refuses a request for a cloud model,
  in a body or in the path of `GET /v1/models/<model>`; pulling, creating and pushing
  models, Ollama's account endpoints and its web search and fetch are refused, since
  those reach other hosts. Ollama 0.40 adds `/api/codex/…`, a proxy that forwards to
  api.openai.com and chatgpt.com and checks only that the caller is on this computer,
  even with Ollama's cloud features disabled; native Sessions never call it, and the
  route refuses it like Ollama's other new endpoints (`/api/balance`, `/api/usage`,
  `/v1/systemone`, …). A local copy of a cloud model (`ollama cp gpt-oss:20b-cloud
  mygpt`) keeps its cloud host under a name the route cannot recognize, so the route is
  opened only to an Ollama that reports its cloud features disabled, and sends each
  request only after Ollama reports them disabled again (`403 ollama_cloud_not_off`
  otherwise). A credential is added only as a header: query, path and body
  credentials, request signing such as AWS SigV4, and OAuth token exchange are not
  supported. A tool that pins certificates or keeps its own trust store cannot use a
  route.
- Traffic from Axocoatl itself (model providers, MCP servers, `web_search` and
  `web_fetch`, webhooks, Podman image pulls) does not go through the proxy. Requests
  on routes leave from the daemon on your computer, only to the addresses checked
  for their connection, and each is recorded before it is sent.
  `sandbox.egress` does not limit the web tools; their calls are written to the
  network record, and an Agent gets them only when its `tools` list them.
- It is not available with E2B or for Sessions created before the native Session
  format. Ways attempt containers use their Session's proxy, with credentials of
  their own.
- The image `ENTRYPOINT` does not run under `egress`.
- With workload users the container's first process and readiness provisioning still
  run as root, and keep `CAP_SYS_PTRACE` to name programs; with
  `sandbox.workload.mode: image` every command runs as the image's user, often root.
  The root file system is writable; terminals you open, setup commands, background
  tasks you start, Ways checks and, without workload users, every command have only
  Podman's default seccomp profile; and on macOS the Podman VM mounts your home
  directory.

- What the 1.5.0 release gate verified, end to end: macOS 26.6 on Apple silicon (48 GB)
  with rootless Podman installed by onboarding, and Ubuntu 24.04 on arm64 with rootless
  Podman from apt, in a VM; in CI, Ubuntu 24.04 on x86_64 and arm64 against a scripted
  model server. Loadout runs there go through `egress` with the `hardened` workload. The
  Podman versions are in the release's signed evidence bundle, under
  `release-evidence/1.5.0/` in the repository.
- Not yet verified: Intel Macs, Ubuntu 22.04, Debian 12, Fedora with SELinux
  enforcing, WSL2 on Windows, and rootful Podman, which loadout runs refuse.

### Compared with OpenShell

How `network: egress` lines up with the mechanisms of a sandbox runtime such as
NVIDIA OpenShell:

| Mechanism | `network: egress` | Detail |
| --- | --- | --- |
| Workload without a network, supervisor over a socket | Match | The Session container has only loopback. The proxy runs in its own container, and the daemon decides each connection. |
| Deny-by-default host and port allowlist | Match, with presets | |
| No DNS in the workload | Stronger | There is no resolver in the container. Names resolve on your computer, after the allowlist check. |
| SSRF and metadata block | Match | Includes IPv4 embedded in IPv6 forms and the Podman host gateways. |
| UDP and IPv6 | Match | No interface carries them. |
| Fail closed | Match | A lost proxy, a lost heartbeat or a decision that times out refuses connections. |
| Enforce only | Match | There is no audit-only mode. |
| Denial JSON with next steps | Match | `403` and `407` answers are JSON with a `hint`. |
| Live policy change | Match for allowlists and routes | `axocoatl network reload` applies `sandbox.egress` and `browser` allowlists, routes and credentials to running Sessions, and an allow or revoke in **Session network** applies at once. The network mode, the sidecar network and the limits need a restart. |
| Approve denied requests | Match, human approval only | You allow a refused host in **Session network**, or approve an Agent's `request_network_access` proposal. Nothing approves a request by itself. |
| Audit record | Stronger | Each allowed connection, and each refusal of one that presents a valid credential, is written before the connection opens, and each request on a route before it is sent; both are joined to the tool call that made them. Refusals without a valid credential are rate-limited and counted. |
| Per-program identity | Partial: recorded, not enforced | With workload users, the default under `egress` with rootless Podman, each connection's record names the program that opened it (path, SHA-256, user and parents), as the container's first process found it. When it cannot find the program in time, the connection is still allowed and recorded with only its user and the reason. Allow entries and routes cannot yet be limited to programs. As with any such identity, a program can be made to act for another. |
| L7 rules and TLS termination | Match for REST over HTTP/1.1 | For hosts under `sandbox.egress.routes`, TLS ends in the daemon with a certificate from an authority made for the Session, and each request's method, path and query must match the route's rules; the server name and `Host` must be the route's host. No WebSocket, GraphQL, MCP or JSON-RPC rules. Hosts listed only under `allow` stay opaque tunnels. |
| Credential injection | Match for header credentials | The daemon reads a route's credential when a request needs it and adds it as `Authorization` or a named header; it never enters a container. A token or session the host issues in return does, unless it comes as a cookie, which credentialed routes remove. No query, path or body rewriting, SigV4 or OAuth token grants. |
| Non-root workload and seccomp hardening | Match for Agents' commands | With workload users, the default under `egress` with rootless Podman, Agents' commands, setup commands, terminals and required checks run as one non-root user without capabilities, and read-only helpers as another, whose only capability (`CAP_DAC_READ_SEARCH`) reads the repository through a Landlock view that keeps the rest of what it reads to what any user may. Agents' tool calls and required checks also run under a seccomp denylist from Axocoatl's supervisor, on top of Podman's profile, each in a Landlock domain of its own. Terminals you open, setup commands, background tasks you start and Ways checks run as the non-root writer without that filter. |

## Inventory egress

Review every path by which content can leave the machine:

- hosted model providers and an Ollama `base_url` that is not loopback;
- E2B Cloud remote sandboxes, including repository transfer;
- remote MCP servers and tools;
- configured web search: a managed SearXNG sends model-written queries to public
  search engines, and `web_fetch` requests public pages from the daemon process
  (see [Web research](/configure/web/#what-leaves-your-computer) and what it
  refuses under
  [Private and local addresses](/configure/web/#private-and-local-addresses));
- hosts declared under `browser.allow`, which the browser container reaches through
  Axocoatl's egress proxy, and the downloads `axocoatl browser install` makes;
- event webhooks and their headers;
- package downloads or repository scripts inside a bridged container, or to the
  hosts listed under `sandbox.egress`;
- requests on egress routes, which the daemon sends from your computer with the
  route's credential;
- embedding-model downloads during first use.

`axocoatl doctor` prints configured webhook destinations as an egress notice.
It does not prove the safety of any destination.

## Bound hosted model spend

A native Session's budget is enforced before each model call: the call reserves an
upper bound of what it can use, and the provider's own report of the call settles it.
For OpenRouter that bound is computed from the exact request (its bytes plus a fixed
template allowance for the prompt, and its output limit plus a reasoning allowance for
the response) at the highest input and output prices the endpoint lists, including
cache writes and every price tier. A response that reports more than its reservation
is refused and keeps its reported spend. The response bound relies on `max_tokens`
capping reasoning and visible output together, which OpenRouter documents for most
providers, not all: a provider that bills reasoning beyond `max_tokens` is caught only
after the call, so its overrun is spent. See
[What each request reserves](/configure/providers/#what-each-request-reserves).

What leaves your computer with a native OpenRouter request is its messages, tool
definitions and tool results, and, for a reasoning model, the reasoning blocks of
earlier tool turns, which Axocoatl sends back unmodified and keeps in the Session's
history. The request turns OpenRouter's web plugin and context compression off and
offers no OpenRouter server tools, so OpenRouter does not search the web, fetch pages or
drop messages for it; a response that shows otherwise is refused. It never opts into a
service tier, and a response served at another tier is refused. Your OpenRouter account settings still apply: an account
that forces a plugin with **Prevent overrides**, or connects BYOK provider keys, breaks
this contract, and Axocoatl cannot change or always detect those settings.

## Handle secrets

- The onboarding wizard uses a masked prompt. A supplied hosted-provider key is
  stored literally in the current user's `config.yaml`; leaving it blank keeps
  an environment placeholder. Axocoatl creates no `.env` file.
- On supported Unix hosts, onboarding restricts the user configuration
  directory and data directory to `0700` and the configuration file to `0600`.
  These permissions do not encrypt the literal key at rest.
- For environment placeholders, inject credentials into the process or service
  through an approved OS secret mechanism.
- `axocoatl secret set <name>` stores a route credential in the data root as
  `secrets/<name>` (`0600`). It reads the value from standard input or, with
  `--from-env VAR`, from an environment variable, never from an argument, so the value
  is not in the process list. `axocoatl connect claude-code` stores the Claude Code
  token the same way, read from `claude setup-token`'s output in memory and hidden on
  screen, so it is never shown, copied or typed. `axocoatl connect codex` stores a
  ChatGPT sign-in (access token, refresh token and account id) the same way, read from
  the `auth.json` that `codex login` writes in a private `CODEX_HOME`: by default an
  in-memory one in a throwaway container of the pinned Codex (read straight into memory,
  then the container is removed), or with `--codex PATH` a temporary one in the data root
  (then overwritten and removed); the daemon refreshes that sign-in itself, on your
  computer, at OpenAI's token endpoint, and writes the new tokens back to the same file
  (also when `axocoatl connect codex --refresh` asks it to, through an API route that
  answers only an authenticated request from a loopback address and returns no token).
  Its access token goes only on a route to `chatgpt.com`; a request on a route to another
  host that names it is refused, and its refresh token goes only to OpenAI's token
  endpoint. `axocoatl connect codex --api-key` also stores, as `codex-openai`, the OpenAI
  API key Codex writes to that `auth.json` after the browser sign-in, read the same way
  and never shown.
  A route adds it on your computer; it never enters a container, a record or a log. It is not encrypted at rest, and a backup of the data
  root includes it.
- Scope E2B Git tokens, MCP credentials, webhook headers, API keys, and bearer
  tokens to the smallest usable authority. The E2B Git token is an environment
  variable of the remote VM, so every command in that VM can read it, including
  repository scripts and Agent commands.
- Protect the data root, backups, config, service definition, and logs. Axocoatl
  has no application-level at-rest encryption.
- The data root holds `local-api-token`. A backup includes it, and a restore
  reuses it. Delete the file and restart to issue a new one.

The runtime attempts to set its data root to mode `0700`; selected memory and
checkpoint files use `0600`. Do not assume every persisted file is encrypted or
individually mode `0600`.

## Treat model and tool input as untrusted

Repository files, attachments, retrieved pages, MCP results, and model output
can contain instructions designed to redirect an Agent. Human approval narrows
first-use MCP calls but is not content validation. Inspect arguments, prefer
one-call approval, review Git and external effects, and do not expose broad
credentials to an Agent that does not need them.

Model-facing file, search, command, web-search, and MCP results are retained
through bounded outputs with explicit truncation metadata. Those availability
limits reduce accidental or hostile output amplification; they do not make the
returned content trustworthy.

MCP limits apply after the current protocol client decodes one transport
message. Its stdio and Streamable HTTP transports do not expose a per-message
receive cap, so a malicious configured server can still exhaust daemon memory
with one oversized line, response body, or SSE event. Treat every configured
MCP server as trusted for availability as well as reviewing its data access.

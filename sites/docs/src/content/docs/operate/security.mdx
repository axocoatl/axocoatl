Local-first describes where Axocoatl can run and store its durable state. It
does not mean every execution is offline or that an Agent, repository, package,
provider, MCP server, webhook, or model response is trusted.

## What Axocoatl controls, and what it does not

Axocoatl decides who writes, what helpers may do, what a run may spend, and
whether required checks and review pass. It records all of it in the Session:
every grant, budget decision, activation, and tool invocation.

Sandbox runtimes, for example NVIDIA OpenShell, control what a process can reach:
files, network destinations, and credentials. Axocoatl runs repository tools in a
rootless Podman container with the defaults described below. With
`network: egress` it also controls network egress for Session containers: they
reach only the hosts you list, through a proxy that writes each decision to the
Session's record before the connection opens. Axocoatl implements this itself,
rather than running Sessions in a sandbox runtime, so that it works in the Podman
containers it already manages on macOS and Linux and so each connection is joined
to the tool call that made it. It does not broker credentials, apply rules to the
content of HTTPS requests, or tell programs in one container apart. See
[Control network egress](#control-network-egress).

With local Podman, model provider API keys stay in the Axocoatl daemon and are not
passed into the container. Files in the Workspace, such as a `.env` file, are
visible to tools, and on E2B the Git token is visible to every command in the VM.

## Keep the server local by default

The default listener is `127.0.0.1:8080`. Same-origin CORS is the default and
rate limiting is off.

### The local API token

On a loopback listener with no configured credentials, the API requires a
per-daemon token. The user's signed-in browser and tools that can read the data
root can use it. Another user's process, or code in a Session container that
reaches the host, cannot, unless the token reaches it another way. The most
likely way is through a web server you open on another `localhost` port, as
described after this list.

- On first start the daemon creates 32 random bytes from the OS random number
  generator, encodes them as base64url, and writes them to `local-api-token` in
  the data root with mode `0600`. Later starts reuse the file. A file that is a
  symlink, is not a regular file, is readable or writable by other users, or
  does not hold a token stops startup.
- `axocoatl dev` and `axocoatl serve` print a sign-in link,
  `http://localhost:<port>/?token=<token>`, when their output is a terminal.
  `axocoatl url` prints it again from the configured port and the token file.
  Under a service manager, run `axocoatl url` with the same `--config` and
  `AXOCOATL_DATA_DIR`.
- Opening the link sets the cookie `axocoatl-token-<port>` (HttpOnly,
  SameSite=Strict, `Path=/`, 30 days) and redirects to the same page without
  the token, with `Referrer-Policy: no-referrer`. Request logs show the
  parameter as `token=REDACTED`.
- Scripts send the token as `Authorization: Bearer <token>` or
  `x-api-key: <token>`. Comparisons are constant time.
- The cookie counts only on same-origin requests, typed navigations, and
  requests without Fetch Metadata such as WebSocket upgrades. A request marked
  `Sec-Fetch-Site: cross-site` or `same-site` must send a header instead.
- Health probes, the sign-in page, and static assets (`/ui/`, `/vendor/`,
  `/lattice/`, `/brand/`, `/axo-tap.js`) stay public. Every route that reads
  or changes state requires the token, including `/ws`, terminal WebSockets,
  and `/a2a/*`.
- A loopback listener holds its port on both `127.0.0.1` and `[::1]` when
  the host has both. Browsers, curl, and Node try `[::1]` first for
  `localhost`, so a process listening there would receive the sign-in link.
  If another process already listens on either address and port, Axocoatl
  does not start.
- Rotate the token by stopping Axocoatl, deleting `local-api-token`, and
  starting it again. Open the new link in each browser.

The cookie value is the token itself, and browsers do not separate cookies by
port. Any web server you open on another `localhost` port in the same browser
receives the token in its request headers. It can then use the API from
outside the browser, so the Fetch Metadata rule does not help. This includes
another user's server and a Session port mapped to `localhost` that you open
directly. Treat opening such a server like sharing the token, and rotate the
token afterwards. Session containers have no mount of the data root, so Session
code cannot read the token file, and Preview origins never receive the cookie.

`server.auth.allow_unauthenticated: true` turns the token off on loopback, for
an authenticating reverse proxy on the same host. Axocoatl logs a warning when
it does. The Host check against DNS rebinding still applies, so the proxy must
send `Host: localhost` or a loopback IP literal.

### Configured credentials

Binding to a non-loopback address fails closed unless API-key or bearer-token
authentication is configured, or the operator explicitly opts out:

```yaml
server:
  host: "0.0.0.0"
  port: 8080
  auth:
    api_keys: ["${AXOCOATL_API_KEY}"]
    bearer_tokens: []
    allow_unauthenticated: false
  cors_origins:
    - "https://workbench.example.internal"
  rate_limit:
    enabled: true
    max_requests: 100
    window_secs: 60
```

Clients may send either `x-api-key` or `Authorization: Bearer <token>`. The
health probes remain public. Configured credentials replace the local token:
there is no sign-in cookie, and an empty configured value never matches. CORS controls browser origins, not network access
or authentication. Allowlisted cross-origin browser clients may preflight HEAD,
GET, POST, PUT, PATCH, and DELETE.

<Aside type="danger" title="Do not expose an unauthenticated workbench">
The API can execute Agents, read and change Session repositories, run terminal
commands, operate Git, and manage Automations. `allow_unauthenticated: true` is
an explicit operator escape hatch, not a safe internet-facing default.
</Aside>

## Preview uses a separate browser origin

Each local Preview is served from a validated
`<session>-p<port>.localhost:<listener-port>` origin. The Host boundary
runs before the workbench router and can reach only that Session's configured
Preview transport; a Preview request cannot fall through to the app shell,
control API, or workbench WebSockets. On a loopback listener without configured
credentials, even with `allow_unauthenticated`, Hosts other than `localhost` and
loopback IP literals are rejected with 421 to prevent DNS rebinding. Preview origins never receive the workbench
sign-in cookie, and the Preview proxies remove `axocoatl-token-*` cookies from
forwarded requests and drop upstream `Set-Cookie` headers that would set one.

If the workbench document is opened through a loopback IP literal, its exact
root navigation redirects to `localhost` on the same listener. This gives the
browser one canonical workbench origin without redirecting API, health, asset,
or non-loopback operator requests.

The Preview frame may use scripts, modules, same-origin fetch, forms, storage,
streamed responses, and development-server WebSockets within its own virtual
origin. Modern third-party-cookie policy can block ordinary cookies in the
embedded frame. **Open full preview** opens that exact virtual URL top-level
with `noopener`; it does not reveal the logical sandbox URL. Host-only cookies
then work. The Chromium journey verifies that its current cookie policy rejects
an attempted `Domain=localhost` parent cookie, so a sibling Session or port does
not receive it; that rejection is enforced by the user agent rather than the
Axocoatl proxy. Preview remains cross-origin from the parent workbench. DOM-pick
messages are accepted only from the exact frame window and expected origin in
both directions.

## Understand Workspace authorization

Creating a Session asks the daemon to canonicalize an existing directory. The
current server has no configured folder allowlist. Anyone who can authenticate
to the API may therefore attempt to select any daemon-readable directory.
Restrict server access and run the daemon under a least-privileged OS account.

## Protect the control plane

On supported Unix hosts, the daemon opens the resolved data root once and keeps
that directory handle as its state authority. Managed reads, writes, replacements,
and cleanup stay relative to opened directories. Symlinked path components, final
symlinks, and multiply linked managed files fail closed. Atomic replacement uses an
unpredictable owner-only temporary file in the destination directory, then fsync and
rename. This protects path ownership; it does not encrypt state or erase it securely.

One daemon or direct bootstrap owns a root through an external per-root lock, the
retained 0.1-compatible `.axocoatl-daemon.lock`, and a lock on the opened directory
inode. The locks are acquired before runtime reconciliation or mutable Session state
is read. At bootstrap, Axocoatl inspects reserved-name Podman containers
and removes by immutable id only non-current containers whose bind mounts prove they
expose the data root or external lease root. It then verifies that both paths still
resolve to the opened directories. Invalid Session records cannot supply a replacement
cleanup id.

The normal data root is user-level and outside every Workspace: under macOS
Application Support or the Linux/WSL XDG data directory. An explicit
project-local `--config` uses a sibling `data` directory unless
`AXOCOATL_DATA_DIR` overrides it. If a protected data or lease root is a
descendant of the canonical Workspace, local Podman places an exact nested
`tmpfs` over it. A Workspace equal to or below a protected root is rejected
instead. This boundary prevents repository tools from reaching Axocoatl
control-plane state; it does not protect secrets deliberately placed elsewhere
in the read-write Workspace.

## Constrain sandbox execution

The local default is rootless Podman with `no-new-privileges`, dropped
capabilities, fixed resource-limit requests, and trust gates for custom images
and repository post-create commands. Two defaults are open: `network: bridge`
lets Session containers make outbound connections, and
`require_resource_limits: false` lets a Session start without resource limits
when the host cannot apply them. For a repository you do not trust, set:

```yaml
sandbox:
  backend: podman
  network: none
  allow_post_create_command: false
  allow_untrusted_images: false
  require_resource_limits: true
```

`network` accepts only `bridge`, `none` or `egress`. Any other value, such as
`None` or `off`, is a configuration error: `axocoatl validate`, `axocoatl doctor`
and daemon start report it instead of starting a container with a network.

Podman containers do not receive the host's proxy variables (`HTTP_PROXY`,
`HTTPS_PROXY`, `NO_PROXY` and the others Podman would copy by default), so a
proxy URL with a user name and password stays on the host.

`allow_post_create_command: true` is not a hidden execution hook. It defaults
only the exact devcontainer command to checked for an unreviewed Session; the
visible per-Session decision wins. It never approves a separately detected or
edited command.

The built-in Alpine, Debian slim, Ubuntu, Python slim, Node slim, and Rust
bookworm references are a fixed allowlist, not an audit or a guarantee that an
image contains safe dependencies. Local readiness verifies Axocoatl's own
repository commands and may provision missing commands inside a supported
container. If that cannot succeed, the environment fails and the incomplete
container is removed. Session startup never invokes a host package manager or
creates a Podman VM.

The Workspace is still a read-write host bind. A root Node project additionally
mounts a Podman-managed volume over root `node_modules` so Linux does not consume
host-native packages; it is a separate writable sandbox resource, not a second
host bind. Protected Axocoatl data and lease directories below that bind are
automatically masked as described above. Keep all other secrets and unrelated data
outside the Workspace.

An Agent configured with `writes: []` is a read-only helper. A required reviewer that
has `bash` must have `writes: []`, so the same applies to it. It is not offered
`write_file` or `edit_file`, and the host refuses them if it asks. Its own `bash`
commands run under a Linux Landlock restriction: no file in the repository, including
`.git`, can be written, created, renamed or deleted, and only `/tmp`, `/var/tmp` and
`/dev` are writable. Landlock does not cover a file's permission bits, owner or
timestamps. A helper that runs as root, as under `sandbox.workload.mode: image` with an
image whose user is root, can change them; on macOS, where the Podman machine's shared
folder reports every file as the caller's, any helper can change permission bits and
timestamps. Each command gets a
scratch home directory under `/tmp`, removed when it ends, so the helper cannot leave
configuration in the Session's shared home for later commands. The same restriction
refuses every TCP connection and every TCP bind, on any address including loopback,
whatever the sandbox's `network` setting: the helper's shell cannot connect anywhere
over TCP, with `curl`, `git` or a package manager for example, including to a server
running in the container. In every network mode the sockets for the Session's apps,
which the browser tools and, under `network: egress`, Preview use, live in a separate
forwarder container, never in the Session container, so they do not open another way
in. Landlock does not cover Unix sockets, though: an app in the container that listens
on one of its own is still within a helper's reach, an abstract socket always and a
socket file whenever its permissions let the helper's user connect. With
[workload users](/configure/sandboxes/#workload-users), the default under
`network: egress`, every process of a helper also runs as a user of its own, which
cannot read the environment of a writer's processes or signal them. A helper whose
template lists `browser` can still drive those apps
through the browser, which can do whatever the apps allow; see
[Browser](/configure/browser/#helpers-and-reviewers). Landlock does not cover UDP, so name lookups and other UDP
traffic still follow `network`. Nor does it cover a socket that listens without binding
first, which the kernel gives a random port that the host or other containers may be
able to reach. `network: none` stops both. The restriction needs Landlock ABI 4 (Linux
6.7 or later) and a container runtime that allows it. Where it cannot be applied in
full, the helper's `bash` commands do not run and its read-only file tools still work.
Axocoatl's own before-and-after repository captures run without the restriction; they
read no Git configuration, attributes or ignore file from outside the repository and run
no program that the repository's configuration names.

An Agent that may change only some paths gets no kernel restriction. Its `write_file`
and `edit_file` refuse other paths, and any path inside `.git`, before writing. Every
change it makes is then checked after it finishes, whether or not it has `bash`:
Axocoatl compares a complete manifest of the repository from before its work, kept in
the sandbox and verified by its digest, with one from after. The manifest covers each
tracked and untracked file's actual content whatever the Git index says, the index
entries, every `.gitignore` Git reads, and `.git/config`, hooks and `info`. A change
outside the Agent's paths, or captures that cannot establish every change, fail that
work and keep the change for you to review. The check does not undo a change, and it
does not cover files your ignore rules exclude or anything outside the repository. A
shell can still write anywhere in the sandbox, and in a sandbox that runs as root it
can replace the tools the check itself runs, so treat the check of an Agent with `bash`
as review evidence. An Agent held to its paths with file tools only, without `bash`,
cannot do either. See
[Limit which files an Agent may change](/configure/agents/#limit-which-files-an-agent-may-change).

A team's required reviewer must be read-only in the same sense: Apply and turn
admission refuse a reviewer template that could change files or run commands that can.
The host, not the lead, starts it after the required Agents and checks finish, on its
own approved budget, and the turn completes only when it approves the exact answers and
repository tree it was shown. It fails closed: an answer without a readable verdict, a
reviewer that did not finish, or a tree that changed while it read approves nothing.
The review is a model's judgement, not verification; a reviewer can miss a defect or be
misled by what it reads in the repository. See
[Required review](/configure/agents/#required-review).

`network: none` blocks container egress and Preview ports, but does not block
the host daemon itself from reaching model providers, MCP servers, web search in
legacy Sessions, webhooks, a remote sandbox service, or a registry for a Podman
image pull. It also prevents readiness/setup processes inside the container from
downloading missing commands or dependencies, so use an image that already contains
the required repository command surface.

Native Sessions refuse the web tools under `network: none`. A legacy (1.0-format)
Session still offers `web_search`, unrecorded, to every Agent whose `tools` list is
empty or names it. It offers `web_fetch` only to an Agent whose `tools` list names
it, and never under `network: none`.

## Control network egress

`network: egress` sits between `bridge` and `none`: a Session container gets no
network interface other than loopback, and an Agent's commands reach only the hosts
and ports listed under `sandbox.egress`. The
[Sandboxes page](/configure/sandboxes/#network-egress) describes how it runs.

| Threat | What `egress` does |
| --- | --- |
| A command connects to an unlisted host | The proxy refuses it with `403 not_allowed`, before anything resolves the name, and records the refusal. |
| A command skips the proxy (`--noproxy`, raw sockets, a hard-coded address) | There is no route: the container has only loopback. |
| DNS, UDP or IPv6 used to send data out | No interface carries them off the machine. |
| An allowed name resolves to loopback, link-local (including the `169.254.169.254` metadata address) or another special address | Refused as `forbidden_destination`, including IPv4 embedded in IPv6 forms. |
| An allowed name or listed range leads to the Podman host gateway | Refused as `forbidden_destination` even when you list a range that contains it: `192.168.127.1` and `192.168.127.254` in a Podman machine, `10.88.0.1` on Podman's default network, and the gateway of `sidecar_network`. Through them the proxy could reach services on your computer. `validate` warns about a range that contains one. |
| An allowed name resolves to another private address | Refused as `private_destination` unless you list the range. |
| A container's own resolver is poisoned | Not used: names resolve on your computer, after the allowlist check. |
| A read-only helper or required check uses the network | They get no credential; a helper's TCP connection to the proxy is refused by Landlock. With workload users, the default under `egress`, a helper runs as a user of its own: it cannot read a running writer's credential under `/proc`, and the proxy's socket is in a directory only root can enter. With `sandbox.workload.mode: image`, a direct connection to the proxy's socket gets `407`, which is recorded. |
| A process started during setup keeps running afterwards | Its credential ended with the setup step; each later attempt gets `407 unknown_credential`. The first 20 are recorded with the old credential's tag, then one every 5 seconds, and the rest are counted in a `limit` event, so the process cannot fill the record. |
| A credential ends, or a host is revoked, while a connection is being decided | The connection is refused before its tunnel opens (`407 binding_ended`, `403 not_allowed` or `403 revoked`). |
| The proxy stops or its control channel breaks | Connections are refused (`502` from the bridge, or `503` from the proxy) and connections in progress are recorded as `interrupted`. |
| The record cannot be written | New connections are refused with `503 record_unavailable`. The cap holds for the Session's lifetime; setup commands, provisioning and terminals still run, without network. |
| A process in the container replaces a port socket with a symlink | The bridge creates each port socket with its final mode instead of changing it afterwards. Under `bridge` and `none`, the browser's port sockets are made in a separate forwarder container that the Session container cannot reach. |
| Axocoatl's config file is inside the Workspace | Agents can read it, and under `egress` send it to an allowed host that accepts uploads. **Session network** warns about it; keep secrets in environment variables. A writer can also edit it, so `axocoatl network reload` refuses to apply it; a restart still reads it. |

What `egress` does not do:

- It does not see inside TLS. A tunnel to a listed host that fronts other sites, such
  as a CDN, can reach those sites, and a listed host that accepts uploads is a way
  for data to leave. The model you use is also a channel.
- Agents in one Session share its container, so a helper can read a running
  writer's credential from `/proc`. Per-Agent network limits are not enforced inside
  one Session container.
- The browser's declared hosts and the Session's list are told apart by the
  credential presented, not by the container. While a `browser_check` call runs, its
  test holds the browser's credential and can pass it to the Session container; see
  [Declared hosts](/configure/browser/#declared-hosts).
- It does not inject or broker credentials. A `git push` from inside the container
  still needs a token there.
- Traffic from Axocoatl itself (model providers, MCP servers, `web_search` and
  `web_fetch`, webhooks, Podman image pulls) does not go through the proxy.
  `sandbox.egress` does not limit the web tools; their calls are written to the
  network record, and an Agent gets them only when its `tools` list them.
- It is not available with E2B, for Ways attempt containers (they run with no
  network), or for Sessions created before the native Session format.
- The image `ENTRYPOINT` does not run under `egress`.
- The container is otherwise unchanged: it may run as root, its root file system is
  writable, it uses Podman's default seccomp profile, and on macOS the Podman VM
  mounts your home directory.
- It has been tested on macOS with rootless Podman 5.8. Linux hosts, rootful Podman
  and WSL2 are not tested.

## Inventory egress

Review every path by which content can leave the machine:

- hosted model providers and an Ollama `base_url` that is not loopback;
- E2B Cloud remote sandboxes, including repository transfer;
- remote MCP servers and tools;
- configured web search: a managed SearXNG sends model-written queries to public
  search engines, and `web_fetch` requests public pages from the daemon process
  (see [Web research](/configure/web/#what-leaves-your-computer) and what it
  refuses under
  [Private and local addresses](/configure/web/#private-and-local-addresses));
- hosts declared under `browser.allow`, which the browser container reaches through
  Axocoatl's egress proxy, and the downloads `axocoatl browser install` makes;
- event webhooks and their headers;
- package downloads or repository scripts inside a bridged container, or to the
  hosts listed under `sandbox.egress`;
- embedding-model downloads during first use.

`axocoatl doctor` prints configured webhook destinations as an egress notice.
It does not prove the safety of any destination.

## Handle secrets

- The onboarding wizard uses a masked prompt. A supplied hosted-provider key is
  stored literally in the current user's `config.yaml`; leaving it blank keeps
  an environment placeholder. Axocoatl creates no `.env` file.
- On supported Unix hosts, onboarding restricts the user configuration
  directory and data directory to `0700` and the configuration file to `0600`.
  These permissions do not encrypt the literal key at rest.
- For environment placeholders, inject credentials into the process or service
  through an approved OS secret mechanism.
- Scope E2B Git tokens, MCP credentials, webhook headers, API keys, and bearer
  tokens to the smallest usable authority. The E2B Git token is an environment
  variable of the remote VM, so every command in that VM can read it, including
  repository scripts and Agent commands.
- Protect the data root, backups, config, service definition, and logs. Axocoatl
  has no application-level at-rest encryption.
- The data root holds `local-api-token`. A backup includes it, and a restore
  reuses it. Delete the file and restart to issue a new one.

The runtime attempts to set its data root to mode `0700`; selected memory and
checkpoint files use `0600`. Do not assume every persisted file is encrypted or
individually mode `0600`.

## Treat model and tool input as untrusted

Repository files, attachments, retrieved pages, MCP results, and model output
can contain instructions designed to redirect an Agent. Human approval narrows
first-use MCP calls but is not content validation. Inspect arguments, prefer
one-call approval, review Git and external effects, and do not expose broad
credentials to an Agent that does not need them.

Model-facing file, search, command, web-search, and MCP results are retained
through bounded outputs with explicit truncation metadata. Those availability
limits reduce accidental or hostile output amplification; they do not make the
returned content trustworthy.

MCP limits apply after the current protocol client decodes one transport
message. Its stdio and Streamable HTTP transports do not expose a per-message
receive cap, so a malicious configured server can still exhaust daemon memory
with one oversized line, response body, or SSE event. Treat every configured
MCP server as trusted for availability as well as reviewing its data access.

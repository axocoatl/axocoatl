Service mode keeps the same daemon, HTTP app, Automations dispatcher,
supervision loop, and memory consolidation running after the foreground shell
closes. It does not itself make Agents act; automatic work still needs an
enabled Automation trigger.

The built-in manager supports a systemd user unit on Linux and a launchd user
agent on macOS.

## Install and start

<Steps>

1. Validate the current user's configuration:

   ```sh
   axocoatl validate
   ```

2. Install the service definition:

   ```sh
   axocoatl service install
   ```

3. If the configuration contains environment placeholders, inject those values
   through the service manager. A literal key supplied during onboarding needs
   no separate environment injection.
4. Start it and enable it at login:

   ```sh
   axocoatl service start
   axocoatl service status
   ```

5. Print the browser sign-in link. The service does not print it, so the token
   stays out of its logs:

   ```sh
   axocoatl url
   ```

   For a service installed with `--config`, pass the same path, and the same
   `AXOCOATL_DATA_DIR` if the service sets one.

</Steps>

Install resolves both the current `axocoatl` executable and the config file to
absolute paths. The default service uses the same user configuration and data
root as foreground commands. An explicit `--config` keeps advanced local mode;
its data defaults to `<config-directory>/data` unless
`AXOCOATL_DATA_DIR` overrides it.

### What install records

A service manager starts the daemon with its own minimal environment, not your
shell's. launchd, for example, gives a LaunchAgent only
`/usr/bin:/bin:/usr/sbin:/sbin` on its `PATH`, which does not contain a Homebrew
Podman in `/opt/homebrew/bin`. Install therefore writes into the definition:

- `PATH`: the directory of the `podman` that your shell finds at install time,
  then the directories of the `git` and `gh` it finds, which
  [Keep as PR](/workbench/keep-as-pr/) runs, followed by
  `/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`;
- `CONTAINER_CONNECTION` and `CONTAINER_HOST`, when they are set at install
  time, so the service uses the same Podman connection as your shell. A
  `CONTAINER_HOST` that contains a password is not recorded.

Install prints what it recorded and warns when it found no `podman`. It never
writes provider keys or other secrets into the definition. Run
`axocoatl service install` again after you move Podman, `git` or `gh`, or change
the Podman connection.
If the service was running, load the new definition with
`axocoatl service stop && axocoatl service start`.

On macOS the daemon's output goes to `~/Library/Logs/Axocoatl/daemon.log`. When
they do not exist yet, install creates that directory owner-only and the file
with mode `0600`; an existing log is kept. On Linux the output goes to the user
journal. The service log never contains the sign-in link: `serve`
writes only a hint to run `axocoatl url`.

For an explicit configuration, validate and install it deliberately:

```sh
axocoatl validate /absolute/path/to/axocoatl.yaml
axocoatl service install --config /absolute/path/to/axocoatl.yaml
```

<Aside type="caution" title="Install does not start the service">
`axocoatl service install` writes/registers the definition. Run `service start`
separately. `axocoatl onboard --install-daemon` installs that real per-user
definition with the user configuration, but it also does not start the service.
For a hosted provider, that combined command requires a key stored by onboarding;
it refuses to install a service that would depend on an uninherited shell
environment placeholder.
</Aside>

## Supply environment variables

Axocoatl interpolates process environment variables in YAML and does not load
dotenv files. The generated service unit/plist does not inject provider keys.
This section applies only when the active configuration retains an environment
placeholder.

<Tabs>
  <TabItem label="Linux systemd">
    Create a root-readable-by-you-only environment file, then add it through a
    user-unit override:

    ```ini
    [Service]
    EnvironmentFile=/absolute/path/to/axocoatl.env
    Environment=AXOCOATL_DATA_DIR=/absolute/path/to/axocoatl-data
    ```

    Open the override with `systemctl --user edit axocoatl`, then apply it:

    ```sh
    systemctl --user daemon-reload
    systemctl --user restart axocoatl
    ```

  </TabItem>
  <TabItem label="macOS launchd">
    The generated LaunchAgent's `EnvironmentVariables` block holds only `PATH`
    and the Podman connection variables, and `axocoatl service install`
    rewrites it. Add required variables through your approved
    launchd/secret-management workflow before starting the agent, then inspect
    the loaded definition. Avoid placing a long-lived API key in a
    world-readable plist.
  </TabItem>
</Tabs>

On Linux, run the hint printed by install when the daemon must survive logout:

```sh
loginctl enable-linger "$USER"
```

## Operate the service

```sh
axocoatl service status
axocoatl service stop
axocoatl service start
axocoatl service uninstall
```

`stop` leaves the definition installed. `uninstall` stops and removes it.

For platform logs:

<Tabs>
  <TabItem label="Linux">

```sh
journalctl --user -u axocoatl --since today
```

  </TabItem>
  <TabItem label="macOS">

```sh
tail -f ~/Library/Logs/Axocoatl/daemon.log
launchctl print gui/$(id -u)/ai.axocoatl.daemon
```

  </TabItem>
</Tabs>

`axocoatl service status` also prints where the logs are.

For an interactive diagnostic run, stop the service first so it releases the
per-user IPC socket, then run:

```sh
RUST_LOG=debug axocoatl dev
```

Pass `--config /absolute/path/to/axocoatl.yaml` as well only when diagnosing an
explicit advanced configuration.

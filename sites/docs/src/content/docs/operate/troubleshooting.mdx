Start with evidence from the same config, data root, and daemon process that the
workbench uses.

## First-response sequence

<Steps>

1. Record the version:

   ```sh
   axocoatl --version
   ```

2. Validate and run doctor against the current user's configuration:

   ```sh
   axocoatl validate
   axocoatl doctor
   ```

3. Check whether another daemon owns the per-user IPC socket:

   ```sh
   axocoatl service status
   ```

4. Stop the service before a foreground diagnostic run:

   ```sh
   axocoatl service stop
   RUST_LOG=debug axocoatl dev
   ```

5. Reproduce once, record the full error, and inspect the browser console for a
   workbench-only failure.

</Steps>

## Startup and state

| Symptom | Likely boundary | Action |
| --- | --- | --- |
| Config parses in one shell but not the service | An environment placeholder is not injected into the service | Configure the service environment; Axocoatl does not create or load `.env` |
| Expected Sessions are missing | The process uses an explicit `--config` or `AXOCOATL_DATA_DIR` different from the normal user paths | Start without the override, or inspect the exact explicit config and sibling/overridden data root |
| “Address/socket already in use” | Another daemon owns HTTP or IPC | Stop the service/other process; do not run two default daemons |
| The first `axocoatl dev` waits before it prints its sign-in link, or a firewall reports a connection to huggingface.co | The first daemon start downloads an 87 MB embedding model (all-MiniLM-L6-v2) from huggingface.co into the data root, once | Let it finish. Without network access the daemon starts anyway and uses lexical search for memory recall instead |
| `axocoatl dev` says “Port 8080 on 127.0.0.1 is already in use” and exits | Another program (or another Axocoatl) listens on the configured port; `dev` and `serve` bind it before they start | Stop that program, or choose another port: `axocoatl onboard --update --port 8081`, or set `server.port` in the configuration |
| `axocoatl doctor` says “Config missing: no configuration at …” | Onboarding has not run for this user (or `--config` names a missing file) | Run `axocoatl onboard` |
| “Data directory is already owned” | Another daemon or direct CLI bootstrap holds the same durable runtime authority | Use the running daemon or stop that process; never point two live Axocoatl processes at one data root |
| “failed data-directory format ownership admission … differently owned manifest” | Axocoatl 1.1.0 through 1.4.0 on a data root that was copied (a restored backup, a migrated Mac) or moved | Start 1.5.0 or later: it records the new location and keeps the Sessions. `axocoatl doctor` says whether the next start will. See [Data and backup](/operate/data-backup/#restore) |
| Non-loopback bind is refused | Authentication is absent | Configure API keys or bearer tokens; keep loopback for local use |
| The browser shows **Sign in to Axocoatl** | This browser has no sign-in cookie for this daemon and port, the cookie expired, or the token was rotated | Run `axocoatl url` with the daemon's `--config` and `AXOCOATL_DATA_DIR`, and open the link |
| The workbench shows **This browser is signed out** | Its API answered 401 while `/` still served the workbench: the sign-in cookie expired or the token was rotated within a minute of a reload, the browser blocks the page's session storage, or, in Safari, a page set so many cookies for `localhost` that Safari leaves the sign-in cookie off API requests | Run `axocoatl url` with the daemon's `--config` and `AXOCOATL_DATA_DIR`, and open the link. In Safari, if it comes back, remove localhost's data in Safari > Settings > Privacy > Manage Website Data and open the link again. See [Safari shares `Domain=localhost` cookies](/operate/security/#safari-shares-domainlocalhost-cookies) |
| A script or `curl` gets `401` | The local API requires the per-daemon token | Send `Authorization: Bearer <token>` with the contents of `local-api-token` in the data root |
| “could not load the local API token” at startup | `local-api-token` is shared with other users, a symlink, or not a token | `chmod 600` it, or delete it and start again to create a new token |
| `doctor` reports that Ollama has cloud models enabled, or a native Session refuses Ollama with "requires server-reported cloud-disabled mode" | The Ollama server runs with its cloud features on (a fresh Ollama does) | Run `axocoatl onboard`: it turns them off where the running server reads them, after asking. By hand: for the Homebrew service or an `ollama serve` you run, add `{"disable_ollama_cloud": true}` to `~/.ollama/server.json` and restart it (`brew services restart ollama`); for the macOS app, turn off Cloud in its Settings; for the Linux service (it runs as the user `ollama`, so your own `~/.ollama` does not apply), `sudo systemctl edit ollama`, add `[Service]` and `Environment="OLLAMA_NO_CLOUD=1"`, then `sudo systemctl restart ollama`. `curl -s http://localhost:11434/api/status` must show `"disabled":true`. See [Set up Axocoatl](/start/onboard/#step-3a-a-local-writer-and-reviewer-ollama) |
| `doctor` reports that native Sessions refuse the Ollama version, or a native Session says "Ollama 0.20.6 is no longer supported" | Native Sessions accept Ollama 0.40.6 and later; 0.20.6 and older, pre-releases, development builds and a new major release are refused | Doctor names the fix for how Ollama runs here: `brew upgrade ollama && brew services restart ollama`, or `curl -fsSL https://ollama.com/install.sh \| OLLAMA_VERSION=0.40.6 sh` on Linux; for a pre-release or a new major release, install 0.40.6 (never `brew upgrade` for a version that is too new). Or point `providers.ollama.base_url` at a server that runs an accepted version |
| `doctor` says “The ollama on PATH is 0.40.6 but the server still runs 0.20.6” | Ollama was upgraded, but the server that answers was started before the upgrade | Restart it: `brew services restart ollama` (Linux: `sudo systemctl restart ollama`; the app: quit and reopen it) |
| `doctor` warns that Ollama is newer than the audited 0.40.6 | A later 0.x release (0.41 or later) | Nothing to do when the models pass: native Sessions and runs use a model on it only after the contract probes pass for that model, and a run's receipt records it as unaudited |
| `doctor` fails a model “loaded with a 4096-token context; a fix run needs at least 16384” | Ollama gives models 4096 tokens on computers with less than about 23 GiB of graphics memory; a fix run's first writer call needs about 9.7k | Set `OLLAMA_CONTEXT_LENGTH=32768` for the Ollama service (`axocoatl onboard` does it after asking: `~/.homebrew/services/ollama.env` for the Homebrew service, a systemd drop-in on Linux) and restart it, or use OpenRouter for that model |
| A Session says "Ollama was upgraded from 0.20.6 to 0.40.6; review Team & budget again" | Its Team was reviewed on Ollama 0.20.6, whose models and engine changed | Open Team & budget and apply it again (a loadout run does this itself) |
| Team & budget refuses an Ollama model because it is not GGUF or runs with MLX | On Apple silicon, Ollama pulls the MLX variant of some models; MLX does not hold `num_ctx` as a hard limit | Pull the GGUF variant with `ollama pull --runner llamacpp <model>` (an undocumented Ollama flag) or choose another model, such as `qwen3-coder:30b` or `gpt-oss:20b` |
| Team & budget refuses an Ollama model with "failed the over-long prompt refusal" or "failed the output limit" check | The contract probes found that this Ollama and model do not refuse a prompt longer than the context, or do not stop at the output limit | Use another model or Ollama release; Axocoatl cannot bound calls to this one |
| A Session or run fails with “ollama stream first-token timeout”, “stream idle timeout” or “Ollama did not finish loading” | The model did not load or start its answer within `first_token_timeout_secs` (600 s for Ollama, 120 s for a hosted provider), or paused longer than `idle_timeout_secs` (90 s): a CPU-only computer, a model on a slow disk, a busy server or a long prompt on a large model | Raise the setting the message names in that provider's block, such as `providers.ollama.first_token_timeout_secs: 1800`, and restart the daemon. Axocoatl closes the connection when it gives up, which makes Ollama abandon that answer or load. See [Providers](/reference/config/#providers) |
| `doctor` passes but a hosted request fails | Doctor checks key presence, not provider access | Verify exported key, model entitlement, endpoint, and provider response |
| OpenRouter credential warning | No key is configured, or the secret `providers.openrouter.api_key_secret` names is not stored | Run `axocoatl connect openrouter`: it signs you in to OpenRouter in the browser and stores the key without showing it. Doctor checks that a key is there but does not ask OpenRouter; `axocoatl connect openrouter --status` does |

## Sessions and tools

| Symptom | Check |
| --- | --- |
| Session needs setup review | Inspect the exact proposed image and command; approve that command explicitly or clear it and continue without setup |
| Session is stuck Preparing after a disconnect | Reopen it; cancellation recovery should mark the exact generation failed and offer Review setup/Rebuild rather than leaving tools enabled |
| Session environment failed | Read the retained setup result/error, correct the runtime or command, then choose Rebuild environment |
| Files, Source Control, Terminal, Preview, or Send returns a lifecycle conflict | The Session is not Ready; review or rebuild its environment. These tools do not fall back to the host checkout |
| Session creation fails | Podman readiness, existing canonical directory, curated/arbitrary image policy, malformed `.devcontainer` metadata, selected Agent |
| Podman is missing, or has no machine | Run `axocoatl onboard`: with Homebrew on Apple silicon, or a package manager it knows on Linux, it installs Podman after asking; otherwise it names the installer. It creates the machine after asking. Session startup, `axocoatl run`, `recipe build` and `connect` never run a package manager or create the machine; they start an existing stopped machine by its name (the one `CONTAINER_CONNECTION` names, else the default one, else the only one) |
| Onboarding says Podman is installed but its directory is not on your `PATH` | Homebrew put Podman in `/opt/homebrew/bin` (or `/usr/local/bin`), and this shell does not have that on `PATH`, so `axocoatl dev` and runs would not find it | Add `eval "$(/opt/homebrew/bin/brew shellenv)"` to `~/.zprofile`, open a new terminal and run `axocoatl onboard` again |
| `axocoatl run` stops with exit 5 and doctor says “Podman runs containers as root” | The machine is rootful (Podman Desktop creates one by default); every built-in loadout needs rootless Podman | `podman machine stop && podman machine set --rootful=false && podman machine start`, with the machine's name after each when it is not `podman-machine-default` (doctor prints the exact commands; it affects other tools that use this machine); `axocoatl onboard` asks to do it. Through `CONTAINER_HOST`, or a `CONTAINER_CONNECTION` that is not a machine, point it at a rootless Podman instead |
| Doctor fails “User ID ranges”, Podman says “potentially insufficient UIDs or GIDs”, or a container fails with “crun: write to `/proc/sys/net/ipv4/ping_group_range`: Invalid argument” | Your Linux user has no range of subordinate ids in `/etc/subuid` and `/etc/subgid` (or fewer than 65536), so rootless Podman cannot unpack images or map a `keep-id` container. `podman info` may still show an old range: Podman's pause process keeps the one it started with | The command doctor prints: `sudo usermod --add-subuids <first>-<last> --add-subgids <first>-<last> $USER && podman system migrate`, with the first 65536 ids from 100000 up that no line of either file uses (100000-165535 whenever no line uses those). When only one file is short, doctor prints only that file's option. If doctor says the files have a range Podman has not picked up, `podman system migrate` alone (it stops your running containers). If doctor says `newuidmap`/`newgidmap` are not installed, missing or cannot map, run the command it prints: an install (`sudo apt-get install -y uidmap`), or, when the package is installed, its reinstall (`sudo apt-get install --reinstall -y uidmap`, `sudo dnf reinstall -y shadow-utils`, `sudo pacman -S --noconfirm shadow`); if it says they are in /usr/bin but /usr/bin is not on PATH, or that a copy earlier on PATH is not the package's file, fix PATH or delete that copy. Do this too when `podman info` fails with “command required for rootless mode with multiple IDs: exec: "newuidmap"”. Then run `podman system migrate`; migrate alone changes nothing. If Podman is reached through `CONTAINER_HOST` or `CONTAINER_CONNECTION`, add the range where that Podman runs, then, as that Podman's user there, run `podman system migrate` and then restart its API service (either one alone keeps one id mapped), or unset the variable (on macOS that selects your default machine); doctor does not judge this computer's files then |
| Doctor says “Podman 3.4.4 is too old” | Ubuntu 22.04 ships Podman 3.4.4; Axocoatl runs need 4.3 or later (`--userns=keep-id` with `uid=` and `gid=`) | Use Ubuntu 24.04 or newer (Podman 4.9) |
| Docker is installed, and Axocoatl still asks for Podman | Docker is not supported; Axocoatl runs only `podman`. Podman can run alongside Docker; on a Mac, both virtual machines need memory |
| A `network: none` Session lacks `git`, `realpath`, or another required command | Select an image that already contains Axocoatl's repository commands; in-container readiness provisioning cannot download them without a network |
| `axocoatl run` exits 3: "the check … cannot run in this run's image" or "can never pass in this run" | The check's program, or a Python module it needs, is not in the run's image after setup, or the check runs none of the repository's tests. Declare it in the repository's dependencies, or pass `--setup`, `--toolchain`, `--image` or `--check`; `--no-probe` skips the probe when it is wrong; see [Repository toolchains](/configure/toolchains/#the-probe) |
| `axocoatl run` exits 5: "the check … cannot run in this run's Session", naming "Invalid cross-device link" | The kernel has only Landlock ABI 1 (Linux 5.13 to 5.18), so the hardened sandbox refuses every rename into another directory; cargo and rustc make such renames in every build. Run on Linux 5.19 or later, or pass `--check` with a check that does not rename across directories. See [Repository toolchains](/configure/toolchains/#the-probe) |
| `axocoatl run` exits 5: "the toolchain setup … failed" | The dependency install failed; the last lines of its output follow the message. Fix the dependency files, give the install with `--setup "<command>"`, or run with `--no-setup`; a host beyond the toolchain's registries goes in `sandbox.egress.allow` |
| Host `node_modules` is absent inside a root Node Session | Expected on local Podman: a Session-owned Linux volume masks the host dependency tree; run approved setup inside the sandbox |
| An empty `node_modules` stays in a repository that had none, after its Sessions closed | Axocoatl made it, as you, for the dependency volume to mount over. It removes it only when no container could mount it, so it stays when Docker is installed, Podman has another connection (every Podman machine on macOS has a rootful one) or rootful Podman's API is enabled (Ubuntu's podman package enables it), and while a container of yours that takes the repository could mount on it (one run privileged, or that neither SELinux nor AppArmor confines); the daemon logs why once. It is yours: install into it or remove it. See [Sandboxes](/configure/sandboxes/) |
| E2B rejects the selected image | Clear the Session/devcontainer OCI image or switch the daemon to Podman; E2B uses one daemon-global template |
| E2B environment fails its command probe | Build the required repository commands into the configured template; Axocoatl verifies but does not package-provision E2B |
| An E2B Session fails to resume | Inspect its retained exact runtime ID and authority error; Axocoatl will not silently replace a missing or unreachable remote workspace with a fresh clone |
| E2B creation remains blocked with an exact creation token | Restore provider access so Axocoatl can reconcile it. If that is impossible, delete every sandbox bearing metadata `axocoatl_creation_token=<exact token>`, then use the exact-token manual confirmation in **Review setup**; confirmation itself does not contact or delete E2B |
| Terminal or Agent command cannot reach the internet | `sandbox.network`, DNS, and host policy; local Podman containers do not receive the host's proxy variables |
| Preview cannot connect | Exposed port at creation, server still running, bind to `0.0.0.0` inside sandbox |
| Preview says the port is not configured | Create a Session with that logical container port under **Exposed ports** |
| Preview transport cannot be allocated | Check Podman health; each Session receives its own dynamic loopback host mapping |
| Files show unexpected changes | `git status --short`, Source Control **All**, then **Last turn** |
| Stop appears ineffective | The current tool may be reaching a safe boundary; inspect active turn and History |
| Close, Delete, Reopen or creating a Session answers `409` `workspace_busy` | Another Session's turn or another operation of the Workspace (named in the error) holds it; lifecycle actions never wait for another Session's work. Try again once it has ended, or stop that turn |
| Podman lists many `axo-egr-`, `axo-egi-`, `axo-svc-` or `axo-ca-` volumes | Sessions closed by Axocoatl 1.2, or a daemon that stopped before Close, left them. Restart the daemon: at start it removes its own whose Session is closed, deleted or unknown, and `axocoatl doctor` says how many. Another daemon's (another data root's) are left alone; remove those with that daemon |
| Podman lists many `axo-ses-<id>-node-modules` volumes | Each is a Node project Session's dependency volume, which Close keeps for Reopen and Delete removes. Delete the closed Sessions you no longer need (a loadout run's too). One whose Session was deleted, or whose data root was removed, is removed when its daemon restarts; `axocoatl doctor` says how many. One made before 1.3.0 has no owner label and goes only when its own data root shows it deleted that Session; another daemon's are left alone |
| A Session says its Workspace folder no longer exists, is no longer a directory, or is a symbolic link | The folder it was made in was deleted, moved, or replaced. Restore the folder at the path named, or delete the Session; until then it is skipped and blocks no other Session or run. Axocoatl never follows a link in its place |
| A Session says it works in one folder but its Workspace's folder is now another | The repository was moved and opened (or run) at its new path, and the Workspace moved with it. Move the folder back to continue that Session, or delete it and start a new Session in the new path |
| Retry is unavailable | The historical turn used immutable attached context; attach it again and send a new turn |

## Ways and Git

| Symptom | Check |
| --- | --- |
| Explore ways is disabled | Autonomous single-Agent Session, local Podman backend, Git repository, no unresolved set |
| Model preflight fails | Exact Agent provider/model and credential availability |
| Checks never finish | Use a bounded non-interactive command, not a watcher/server |
| Judge is disabled | Checks finished and at least two non-empty Attempts passed |
| Keep is in recovery | Reopen the same set and choose **Finish Keep**; do not discard after apply begins |
| Cleanup is incomplete | Choose **Finish cleanup** and inspect `.axo-variants/` only after the UI reports terminal cleanup |

## Settings, MCP, and Automations

| Symptom | Cause/action |
| --- | --- |
| Agent Settings edits vanished | They are in-memory only; copy accepted values into YAML and restart the daemon |
| Editing YAML + `agents restart` had no effect | That command restarts from already-loaded config; restart the daemon |
| Catalog-connected MCP server vanished | Connect/remove is process-local; add durable YAML and restart |
| Existing Agent cannot see a newly connected MCP tool | Agent executors were already built; restart from durable config |
| MCP call remains parked | Resolve the approval; after five minutes or disconnect it denies |
| YAML Skill did not run from `axocoatl skills run` | CLI Skills are separate prompt templates; fire the configured Skill in Settings/API |
| Scheduled Automation did not fire at a calendar time | Only fixed intervals are supported; cron is not |
| Run was `running` across restart | Arbitrary in-flight calls are marked failed; only a top-level Interrupt resumes durably |

## Service problems

On Linux:

```sh
systemctl --user status axocoatl
journalctl --user -u axocoatl --since today
```

On macOS:

```sh
launchctl print gui/$(id -u)/ai.axocoatl.daemon
tail -n 100 ~/Library/Logs/Axocoatl/daemon.log
```

| Symptom | Cause/action |
| --- | --- |
| Sessions started by the service say Podman is not installed, but `podman` works in your shell | The service definition was written before install recorded `PATH`, or Podman moved. Run `axocoatl service install` again from a shell where `podman` works, then `axocoatl service stop && axocoatl service start` |
| The service uses a different Podman machine than your shell | Export `CONTAINER_CONNECTION` (or `CONTAINER_HOST`) before `axocoatl service install`; install records it in the definition |
| The macOS service log is missing | The definition predates the log setting; reinstall and restart the service as above |
| The service restarts every few seconds and is never up | Its start fails each time. `axocoatl service status` shows the line the last failed start logged (1.5.0 and later); fix that cause, such as a copied data root under 1.4.0 above |

Re-run `axocoatl service install` when the binary, the user configuration path,
or the Podman location or connection changes. Use `--config ...` only for an explicit advanced configuration.
Installation does not start the service; follow it with
`axocoatl service start`.

<Aside type="caution" title="Do not clear data as a first fix">
The data root contains Session history, checkpoints, Automations, permissions,
and attachments. Stop the daemon and make a cold backup before moving or
repairing it. A new empty data root can hide the original problem.
</Aside>

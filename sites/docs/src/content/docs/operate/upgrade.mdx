Treat a binary replacement as an operator-controlled change with a cold backup.
The explicit `axocoatl session upgrade` command converts supported legacy Session
storage; it does not install a binary or provide rollback. The
automatic 0.1 compatibility surface is deliberately narrow:

- A pre-1.0 single-agent checkpoint transcript can be imported into canonical
  Session History. The 0.1.x Bincode format takes precedence if markerless bytes
  are also valid temporary unframed Postcard; unframed Postcard is selected only
  when that exact legacy reader does not match.
- Current checkpoints, Agent memory, and Automation run history use portable,
  versioned namespaces. On supported Unix hosts, a store may read its one bounded
  exact-name legacy location after validating the record identity or format as
  applicable. Writes go only to the current namespace and leave the legacy source
  intact.
- Before mutable Session state is read, bootstrap holds both current and 0.1-compatible
  data-root leases plus the directory-inode lock. It removes by immutable id only
  non-current reserved-name Podman containers whose inspected bind mounts expose the
  data or lease root, then verifies the retained directory identities before continuing.

These paths do not replace a complete backup or establish general forward/backward
schema compatibility.

## Upgrade procedure

To convert an existing legacy data root to native Session execution, stop the daemon,
make a cold backup, then run:

```sh
axocoatl session upgrade --config /absolute/path/to/axocoatl.yaml --confirm
```

Without `--confirm`, the command explains the conversion and exits without modifying
data. It retains the old history, exact checkpoint archives, and cumulative usage.
When an old Agent's role was not recorded, its private state stays archived and its
future conversation starts empty. Review **Team & budget** before new work.
The upgrade holds the same exclusive data-root leases as the daemon, and an interrupted
conversion resumes from its recorded source. Older binaries cannot write the upgraded
root. Ordinary startup never implicitly converts an existing legacy root: one that a
daemon has used, or that holds Sessions. A data directory that existed before the
daemon first started, but that no daemon has used and that holds no Session (made with
`mkdir`, or by `axocoatl secret set`), is not a legacy root: it starts in the native
format, as one the daemon creates does, and keeps the files in it.

<Steps>

1. Record the current version and service status:

   ```sh
   axocoatl --version
   axocoatl service status
   ```

2. Finish active work, stop the daemon, and make a
   [complete cold backup](/operate/data-backup/).
3. Replace the binary using the same installation path you chose originally.
4. Validate configuration and run doctor before starting automatic work.
5. Reinstall the service definition if the executable path changed.
6. Start the daemon. A loopback daemon without `server.auth` credentials
   requires its [local API token](/operate/security/#the-local-api-token) on
   the workbench and every API route; 1.1.1 and earlier did not. Print the
   sign-in link with the daemon's config, and its `AXOCOATL_DATA_DIR` if it
   sets one, then open the link and reload any workbench tab that was already
   open:

   ```sh
   axocoatl url --config /absolute/path/to/axocoatl.yaml
   ```

   Scripts send `Authorization: Bearer <token>` with the contents of
   `local-api-token` in the data root.
7. Inspect Sessions, Automation run history, Agent status, and logs before
   resuming automatic triggers.

</Steps>

The replacement remains one `axocoatl` executable. It includes Axocoatl's Linux
process supervisor, so upgrading requires no separate supervisor command or
download. Cargo and source builds compile the host application and retain the
first-party prebuilt supervisor payloads included in the source package. Contributors
can [rebuild those payloads explicitly](https://github.com/axocoatl/axocoatl/blob/main/docs/EXEC_SUPERVISOR_BUILD.md).

Then verify:

```sh
axocoatl --version
axocoatl validate /absolute/path/to/axocoatl.yaml
axocoatl doctor --config /absolute/path/to/axocoatl.yaml
```

<Aside type="caution" title="Rollback is a backup restore">
There is no compatibility promise that an older binary can read state written
by a newer one. Keep the pre-upgrade binary and cold backup together. If you
must return, stop the new daemon and restore the matching binary, data root,
config, environment, and Workspace copies as one set, as
[Restore](/operate/data-backup/#restore) describes.

A restored data root is a copy, and Axocoatl 1.1.0 through 1.4.0 do not start on a
copied data root: they exit with `failed data-directory format ownership admission`.
To return to one of them, restore the set, run `axocoatl session record-location` with
1.5.0 (or later) on the restored data root while Axocoatl is stopped, then start the
older release. That command records the copy's new location and changes nothing else.
This was tested with 1.1.2, 1.2.0, 1.3.2 and 1.4.0, each on a restored backup holding
a Session it had made. Starting 1.5.0 on the restored root also records the location,
but it converts each Session's journals, which 1.2 and earlier then refuse (`unknown
field segments`).
</Aside>

Future-version Session ledger or attachment schemas are rejected rather than
silently interpreted. That protects against accidental corruption, but it is
not an automatic migration path.

## Upgrading from 1.4

Axocoatl 1.5 starts on the data root 1.4 used, in place or as a restored copy, and keeps
its Sessions, their History and the records of `axocoatl run`. Native Sessions now need
Ollama 0.40.6 or later (1.4 needed 0.20.6), so the upgrade includes Ollama.

<Steps>

1. Finish or stop running work, and note the version and the service:

   ```sh
   axocoatl --version
   axocoatl service status
   ```

2. Stop the daemon: `axocoatl service stop` for the Always-On Service, or **Ctrl-C** in
   the terminal that runs `axocoatl dev`.
3. Make a [complete cold backup](/operate/data-backup/#make-a-cold-backup) of the data
   root and the configuration, and keep the 1.4 binary with it. It is the only way back
   to 1.4 (see [Data written by 1.5](#data-written-by-15)).
4. Install 1.5:

   ```sh
   curl -fsSL https://axocoatl.ai/install.sh | sh
   ```

   The installer names the copy it replaces and says when a daemon still runs: a daemon
   keeps running the binary it started from until it restarts.
5. Upgrade Ollama to 0.40.6 or later: `brew upgrade ollama && brew services restart ollama`
   with Homebrew, or `curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.40.6 sh`
   on Linux. With the Ollama app on macOS, download it again from
   [ollama.com/download](https://ollama.com/download), then quit and reopen it so that the
   new version answers. `axocoatl onboard` upgrades a Homebrew or Linux install after
   asking, and says what to do for the app.
6. Check the setup. Doctor says when Ollama still runs 0.20.6, when a configured model is
   missing, and when a daemon that is still running is older than 1.5.0:

   ```sh
   axocoatl doctor
   ```

7. Start the daemon: `axocoatl service start`, or `axocoatl dev`. If the binary is at
   another path than before, run `axocoatl service install` first.
8. In each Session you continue, open **Team & budget**, select **Edit**, then
   **Preview** and **Apply**; nothing needs to change. A Team reviewed on Ollama 0.20.6
   says "Ollama was upgraded from 0.20.6 to 0.40.6; review Team & budget again" until
   then, and so does each helper an Agent delegates to. Apply observes each of its Ollama
   Agents and their Ollama helpers again on the Ollama that runs now. Preview shows each
   such Agent as replaced, with a new conversation, since Ollama 0.40 runs the model in
   another engine; a helper starts a new conversation each time it is given work.
   `axocoatl run` needs nothing: every run applies its loadout's team in a new Session.

</Steps>

## Data written by 1.5

Axocoatl 1.5 records how each model response of a native Session ended (a
`provider_response` event in the Session's history), from the first workbench Session
turn or `axocoatl run` it runs on the data root, and it records a change whose patch is
larger than 512 KiB by the patch's digest, its size and its first 12 KiB. Axocoatl 1.4
reads neither, so 1.4.0 does not start on a data root on which 1.5 ran a turn or a run,
whatever the size of its change. It says:

```text
Failed to bootstrap daemon: Session error: could not recover canonical history for Session '…': Session error: execution content serialization: unknown variant `provider_response`, expected one of `text`, `provider_retry`, `reasoning_summary`, `tool_proposed`, `tool_result` at line 1 column …; existing data was not replaced and no work was replayed
```

or, for a large change, `… invalid execution content: invalid checked repository identity; …`.

No command converts these records into ones 1.4 reads. To go back to 1.4, restore the
cold backup you made before upgrading, as [Restore](/operate/data-backup/#restore)
describes, with the 1.4 binary: start Axocoatl 1.5 on the restored data root once and
stop it, so that it records the copy's location (1.4.0 refuses a restored copy until
then), then start 1.4.0. Work done with 1.5 is not in that backup. Axocoatl 1.4.0 runs
native Ollama Sessions only on Ollama 0.20.6.

The backup holds the data root, not your repositories. A large file that a 1.5 run left
uncommitted in a repository can be a change too large for 1.4.0 to capture: with a
1 MiB file left by a 1.5 run, 1.4.0's runs in that repository end needing attention
("repository command output is incomplete or exceeds its capture bound"). Commit or
move such a file before you run 1.4.0 there.

## Data written by 1.4

Axocoatl 1.4 records, in each repository capture, the digest of every path that differs
from `HEAD`; signed receipts are built from these digests. Axocoatl 1.3 does not know
that field. Once a 1.4 daemon has recorded a capture in a data root, a 1.3 daemon does
not start on that data root, and says
`could not recover canonical history for Session …: unknown field changed_manifest`.
To go back to 1.3, restore the cold backup you made before upgrading, as described
above, and run `axocoatl session record-location` with 1.5.0 on it before you start 1.3
(see the caution above).

## Sessions written by 1.2 and earlier

Axocoatl 1.3 keeps each Session journal in segment files. The first time it opens a
Session that 1.2 or earlier wrote, it converts that Session's journals, and 1.2 and
earlier then refuse the Session. Before the first conversion, Axocoatl copies the
Session's whole directory, `execution-v2/<key>` in the data root, to
`backups/before-segments/<key>/session`, and writes
`backups/before-segments/<key>/backup.json` last, once the copy is complete. `<key>` is
the SHA-256 of the Session id; `backup.json` names the Session, its Workspace, the time
and the version that made the copy. Each Session is copied once and the copy is never
replaced, so work done in the Session after the conversion is not in it. If the copy
cannot be made, for example because the disk is full, the Session is not converted and
does not open; free the space and open it again.

The copies stay until you remove them. They cover Session journals only: to return a
whole data root to 1.2, restore the cold backup you made before upgrading, and run
`axocoatl session record-location` with 1.5.0 on it before you start 1.2 (see the caution
above).

To put a Session back as 1.2 left it:

<Steps>

1. Stop Axocoatl: `axocoatl service stop` for the service, or **Ctrl-C** in a
   foreground terminal.
2. In the data root, find the Session's backup. The directory that holds the
   `backup.json` this prints is the Session's `<key>`:

   ```sh
   cd /absolute/path/to/data
   grep -l '"session_id": "SESSION_ID"' backups/before-segments/*/backup.json
   ```

3. Move the converted Session aside and copy the backup in its place, keeping its
   permissions:

   ```sh
   key=KEY
   mv "execution-v2/$key" "backups/before-segments/$key/converted"
   cp -a "backups/before-segments/$key/session" "execution-v2/$key"
   ```

4. Start the release you want. The restored directory holds exactly the files 1.2
   wrote. Axocoatl 1.3 converts it again and keeps the existing backup. Delete
   `backups/before-segments/<key>/converted` once you no longer need the converted
   Session.

</Steps>

## Release evidence

The 1.5.0 release gate requires each of these paths to pass on the release commit,
starting from the published install command, and lists the steps each must show. The
release workflow publishes nothing until the signed evidence holds every one of them;
the only way past it is a logged override that only maintainers listed in the
repository can start, and the release notes must then name the paths not run.

| | |
| --- | --- |
| macOS, end to end | Apple silicon, with a person answering onboarding at the Mac, on an account that starts without Axocoatl, its data or stored credentials, without Podman or a Podman machine, and without Ollama or its settings (Ollama's downloaded models may stay): onboarding installs Podman and Ollama with Homebrew, creates the Podman machine, turns Ollama's cloud models off and ends ready with a passing first run. It signs in Claude Code, and Codex with a ChatGPT plan, in the browser, and connects OpenRouter through its browser sign-in without writing the key to the configuration |
| Linux, end to end | An account that starts without Axocoatl, its data or stored credentials, or Podman, and whose subordinate ids the gate removes first (the gate's instructions make a new user with `adduser` in a new Ubuntu 24.04 VM): onboarding installs Podman with apt and adds a range of subordinate ids that overlaps no other user's, each with `sudo` after asking, connects OpenRouter through its browser sign-in for the OpenRouter models the runs use, and installs no Ollama |
| Linux, in CI | Ubuntu 24.04 on x86_64 and arm64: the same install command, then onboarding with no terminal against a scripted model server (Podman already on the runner, no first-run sample), and `axocoatl run fix` |
| Repositories | `fix` passes on Node.js (with and without dependencies), Python (pytest), Rust and Go repositories on each, with local models on the Mac; on the Mac, `fix-claude-code`, `fix-codex` and `fix` with OpenRouter models pass on Node.js and Python, and `fix-claude-code` with `--keep pr` opens a pull request whose receipt the [verify-receipt Action](/workbench/receipts/#checking-pull-requests-in-github-actions) verifies ([how toolchains work](/configure/toolchains/)) |
| Also on the Mac | The [Always-On Service](/operate/service/), chosen in onboarding, runs a passing fix, restarts when `onboard --update` changes the configuration, then stops and uninstalls (on Ubuntu, as a systemd user unit); a run with the Podman machine stopped starts it and passes; timed runs on real repositories each end with a verdict; the workbench in Safari goes from the sign-in link to a commit, shows a Session's Preview inside the workbench only (a Preview address opened in a tab, reached by a redirect or Command-clicked gets Axocoatl's refusal page), and stays as the docs say when another page floods `localhost` with cookies |
| Evidence | Each run on those repositories has its receipt and record verified (the `--keep pr` run, its receipt, by the verify-receipt Action), and each timed run on a real repository its receipt; each path's transcript, times, downloads and tool versions, the models, the system, its memory and the account, and who answered each question (the person, or for the workbench's questions up to the commit, a WebDriver driver in Safari), in the signed bundle under `release-evidence/1.5.0/` in the repository ([the gate](https://github.com/axocoatl/axocoatl/blob/main/docs/RELEASE_GATE.md)) |
| Not yet verified | Intel Macs, Ubuntu 22.04, Debian 12, Fedora with SELinux, WSL2 on Windows. The gate checks neither the Mac's memory nor which local models onboarding chose there, so its runs verify local models only on the memory and models the evidence names |

The table describes the release contract. Read the signed bundle for the actual
operators, attempted runs, continuations and limitations; an account name alone does
not identify who answered a prompt. Passing setup and fixture checks is functional
evidence, not a model-quality comparison or a promise that an arbitrary task will pass.

## Verify a development build

Use the procedure below to check that the local runtime and browser app are connected
to the build you intend to evaluate.

### Verify the installed path

```sh
which axocoatl
axocoatl --version
axocoatl --help
```

When working from source, build the explicit CLI package and use that binary:

```sh
cargo build -p axocoatl-cli
./target/debug/axocoatl --version
```

The root package is a benchmark placeholder; a generic root build is not the
same proof as building `axocoatl-cli`.

### Verify Ollama

<Steps>

1. Start Ollama in another terminal, with its cloud features disabled:

   ```sh
   OLLAMA_NO_CLOUD=1 ollama serve
   ```

2. Pull the exact model configured for the Agent:

   ```sh
   ollama pull llama3.2
   ollama list
   ```

3. Validate and run doctor:

   ```sh
   ./target/debug/axocoatl validate axocoatl.example.yaml
   ./target/debug/axocoatl doctor --config axocoatl.example.yaml
   ```

</Steps>

Doctor live-probes Ollama: it requires a loopback Ollama 0.40.6 or later (a later 0.x
release warns and passes only through the contract probes) that reports its cloud
features disabled, and every configured Ollama Agent model to be present as a local
GGUF completion model, with tool calling for an Agent that lists tools; it loads each
model once to read its context (below 16384 tokens fails). Hosted provider checks are
not equivalent: they inspect credential presence—including OpenRouter when
configured—but do not make a live model request. Doctor reports Podman ready only
after a bounded `podman info --format json` probe returns a JSON object, and fails
when Podman is missing, has no machine, runs rootful, is older than 4.3, or, rootless,
has no range of subordinate ids. On Linux, for a Podman on this computer, it reads the
range from `/etc/subuid` and `/etc/subgid`, which new containers are mapped from, not
only from `podman info`, which shows the range Podman's pause process started with (a
Podman reached through `CONTAINER_HOST`, `CONTAINER_CONNECTION` or a remote connection
is judged by its own `podman info`).

### Start the embedded app

```sh
AXOCOATL_DATA_DIR=/absolute/path/to/test-data \
  ./target/debug/axocoatl dev --config axocoatl.example.yaml
```

Open the `Sign in:` link the command prints (or run
`AXOCOATL_DATA_DIR=/absolute/path/to/test-data ./target/debug/axocoatl url --config axocoatl.example.yaml`). The `/` page it opens is the
product workbench. Confirm:

1. the left rail and Session home load without a console error;
2. a folder Session can be created with a configured Agent;
3. the exact image and setup proposal remain visible and unchecked unless you
   approve them; before Ready, Send and repository tools stay gated;
4. after an explicit setup decision, the environment reaches Ready and a
   read-only prompt becomes durable in History;
5. Files, Source Control, Terminal, and Preview are reachable through that
   Session sandbox rather than a host fallback;
6. Settings opens Agents, Skills, MCP servers, and Automations;
7. light, dark, narrow, and reduced-motion states remain usable for the changed
   workflow.

### Run repository gates

From the source checkout:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo test --doc --workspace
cargo build -p axocoatl-cli
```

Some ignored sandbox tests need Podman. Webhook tests bind a local port and may
need to run outside a restricted test sandbox. A route/unit test does not
replace verifying the actual embedded page.

<Aside type="note" title="Use an isolated test Workspace">
Session and Agent tools can change files and execute commands. Use a disposable
or clean Git repository and a dedicated data root for verification.
</Aside>

Axocoatl has three built-in [loadouts](/configure/loadouts/). Each runs as one Session
with network egress and the `hardened` workload, through [`axocoatl run`](/reference/run/),
and ends with an Outcome and an exit code. This page says what each one does and why it
is shaped that way.

## How answers are read

Each loadout asks its Agents to end their answers with named JSON blocks:
`ADJUDICATIONS` (fix), `FINDINGS` and `COVERAGE` (qa), and `AREAS`, `FINDINGS` and
`NOT_REACHED` (audit). The prompts ask for a heading and a fenced block, but models do
not always write one, so the host reads each block in any of these forms:

- **After a heading**, in any case and with or without Markdown marks: `FINDINGS`,
  `## Findings`, `**findings:**` and `- Not reached` all count, with words joined by a
  space, `-` or `_`. The JSON may follow on the heading's line after a colon, on the next
  line, or after a line of text, fenced or not. When the heading appears more than once,
  the last one followed by JSON or a fenced block wins.
- **Between XML-style tags** of the heading's name, in any case: `<FINDINGS>`, then the
  JSON (fenced or not, on the tag's line or below it), then `</FINDINGS>`. The closing
  tag ends the block.
- **With no heading**, an answer that is only the JSON: the array of adjudications; for
  qa, an object with `findings` and `coverage` keys; for audit, an object `{"areas":
  [...]}` or `{"findings": [...]}` (a worker's may also hold `not_reached`), or the
  array alone, or the last fenced block that is such an object.
  An audit object's keys are read in any case, with words joined by `_`, `-`, a space
  or nothing: `FINDINGS`, `NOT_REACHED` and `notReached` all count.

A block that is there but is not the JSON it should be is reported as unreadable, with
the parser's error, never guessed at; what the block would have said is then missing or
not covered.

## Fix

```sh
axocoatl run fix --task "…" \
  --model writer=ollama:qwen3-coder:30b \
  --model reviewer=ollama:gpt-oss:120b
```

One turn with one writer, one required check and a required review:

1. The **writer** (`writer_model`) makes the change with the repository tools.
2. The required check `tests` runs the Session's detected check command, or the
   `--check` command in its place, on the exact final files, with a 3-minute timeout. A
   run with neither is a usage error.
3. The **reviewer** (`reviewer_model`) reads the result in a fresh conversation with
   `read_file`, `list_dir`, `grep` and `glob` only, numbers each finding `F1`, `F2`, …
   and ends with `VERDICT: APPROVE` or `VERDICT: CHANGES`.
4. On `CHANGES` with rounds left, the host sends the findings back to the writer. The
   writer must answer every finding in an `ADJUDICATIONS` block, a fenced JSON array of
   `{"id": "F1", "decision": "accept" | "reject", "reason": "…"}`, and fix each one it
   accepts. The checks and the review run again on the new result, for up to 3 rounds.

Each answer is an **adjudication**, recorded with its round, finding, decision and
reason. A finding the writer did not answer, or answered without a reason, is recorded
as `missing`. An answer with no `ADJUDICATIONS` block, or one whose block cannot be read
("unreadable adjudications block"), makes every finding of that round `missing`. A
rejection with a reason is an answer: a reviewer can be wrong, and the writer is expected
to check each finding against the task before changing code. A missing answer makes the
run need attention (exit code 2).

Adjudications appear in the run summary, the JUnit `adjudications` suite, the Run
outcome panel, the [pull request body](/workbench/keep-as-pr/) and the record.

The run passes (exit code 0) when the check passes on the final result, the reviewer
approves that result, and every finding the host sent back was answered.

### Use a different model to review

When `reviewer_model` is the writer's model, Axocoatl warns, and the warning appears in
validation, Settings, Team and budget, the API, the run output and the record. It does
not refuse the run.

{/* measured: axocoatl-1.1.0 2026-10-01 */}

In our pre-registered benchmark (6 Python maintenance tasks, 25 withheld tests, writer
qwen3-coder 30B running locally, one run per task at temperature 0), another look by the
same model added nothing: self-review, a fresh reviewer on the same model and a panel of
three same-model critics each stayed at 17 / 25 withheld tests, at 2.3× to 4.7× the
tokens of one pass, in a plain agent loop. Through Axocoatl 1.1.0, a required review by
a stronger local model, gpt-oss 120B, raised the writer's 17 / 25 to 19 / 25 at 2.6× the
tokens.

{/* /measured */}

That reviewer was a local model on the same machine. A hosted reviewer through
OpenRouter works the same way in Axocoatl but was not measured. See
[What we measured](/understand/what-we-measured/).

## QA

```sh
axocoatl run qa --task "Check the checkout and account pages" \
  --model explorer=openrouter:<model> \
  --param target_url=http://localhost:3000 \
  --param reference_url=http://localhost:3001
```

One turn with one Agent, the **explorer**, which has the [browser tools](/configure/browser/)
`browser` and `browser_check` and may write only under `axocoatl-qa/`. There are no
scouts, no merge step, no reviewer and no verifier.

The explorer's `write_file` does not create directories, so when the repository has no
`axocoatl-qa/` the run creates it before the explorer's turn, owner-only, and says so
(`preparing: created axocoatl-qa/ in the repository for the explorer's reproductions`).
Every part of that path is opened without following links: when `axocoatl-qa`, or a
directory on the way to it, is a symbolic link or is not a directory, the run is
refused (exit code 3), so nothing is created or written through a link.

The explorer drives the app at `target_url` area by area. For every bug it reports it
writes a Playwright test under `axocoatl-qa/` that fails because of the bug, and it ends
its answer with two fenced JSON blocks:

- `FINDINGS`: each finding's `id`, `title`, `area`, `severity`, `expected`, `actual` and
  `repro`, the path of its test;
- `COVERAGE`: each area as `covered`, `not_reached` or `blocked`, with a reason.

The host then runs each reproduction itself, with `browser_check`, one worker and no
retries, against `target_url` and, when you give one and the test failed there,
`reference_url`, a clean build of the same app. Each run is a `browser_check` call in the
Session's network record:

| Fails on the build under test | Passes on the reference | Classification |
| --- | --- | --- |
| yes | yes | **confirmed** |
| yes | no, it fails there too | **fails on clean build**: listed, never confirmed |
| yes | no reference given | **reproduced** |
| no | — | **not reproduced** |
| the test could not run | | **repro error** |
| no test, or the file is missing | | **missing** |

A finding is confirmed only when its reproduction fails on the build under test and
passes on the reference. Confirmed and reproduced findings make the run need attention
(exit code 2), because the loadout's `fail_on_findings` is on.

The loadout needs the browser tools: a `browser:` block in your configuration and
`axocoatl browser install` (see [Browser](/configure/browser/)). Both URLs must be
reachable from the browser container: an exposed port of the Session,
`http://localhost:<port>`, or a host under [`browser.allow`](/configure/browser/#declared-hosts),
and the reference must not be the build under test. Without a `browser:` block, or with
a URL it cannot reach, the run is refused before it starts (exit code 3). To compare against
a clean build, run it on a second exposed port, or list its host.

### Not covered is never a pass

Everything the explorer did not cover is listed under **not covered**, with a reason:

- each area it reported as `not_reached` or `blocked`;
- when the explorer itself failed, "remaining app", which says which areas it did report
  as covered, with the failure class, such as `provider_refusal` (the provider refused or
  a safety classifier stopped the stream), `provider_failure`, `budget` or
  `runtime_limit`;
- when its answer has no `COVERAGE` block, "whole app (no coverage report)", and with no
  `FINDINGS` block, its findings;
- each finding whose reproduction is missing, or could not run, or that the wall clock
  left unrun.

Each entry makes the run need attention and is a failure in the JUnit file.

### Why one explorer

{/* measured: claude-code-subagents qa 2026-10-04..06 */}

These QA studies ran Claude Opus as Claude Code subagents, not through Axocoatl, so they
are not Axocoatl results. They shaped this loadout.

- On a web app with 16 planted bugs (5 runs per setup; exploratory, not pre-registered),
  one explorer found 97.5% of the bugs at 98.8% precision. Adding a verifier gave 100%
  and 100%, but the verifier removed nothing: the reports it checked were already at 100%
  and 100% before it ran. A lead with two scouts found 98.8% at 95.7% precision with 2.1×
  the tokens.
- On a larger app with 66 planted bugs (pre-registered), a lead with three scouts found
  2.3 points more than one explorer, which was not significant (p = 0.77), and used 31%
  more tokens.

In every setup each finding had to come with an executable reproduction.

{/* /measured */}

The extra Agents mostly added tokens, so the built-in loadout has one explorer, and the
host re-runs each reproduction itself instead of asking another model to judge it.

## Audit

```sh
axocoatl run audit --task "Security-relevant defects in the request parsing code" \
  --model planner=openrouter:<model> \
  --model worker=openrouter:<model> \
  --model integrator=openrouter:<model>
```

`audit` is opt-in: it is listed with the others but runs only when you name it. It runs
its turns in one Session, each with its own Team and budget. Whether an area was
covered is decided by Axocoatl from the files it listed and the files each worker read,
never from what a worker says:

1. **Plan.** The planner, alone and read-only, splits the scope into 2 to 8 areas in one
   `AREAS` JSON block: each area's name, its scope and the paths it covers. An invalid
   plan gets one more turn with the error, and a planner without an answer (a provider
   failure, say) gets one more turn with the same request. A planner stopped by the wall
   clock or by you, or refused by its provider (HTTP 400 to 403), gets none. A second
   attempt without a plan ends the run needing attention: "The whole scope was not
   covered".
2. **Files.** Axocoatl lists the repository's files: in a Git work tree with
   `git ls-files --cached --others --exclude-standard` (tracked and untracked files, not
   ignored ones), elsewhere by walking the directory, skipping what `glob` skips
   (`.git`, `node_modules`, `target` and similar). Links and anything inside `.git` are
   left out, and at most 20,000 files are listed; past that, the rest are not covered.
   Each file goes to the first area whose paths match it. A file no area's paths match
   goes to the area whose paths share the most directories with it (`auth/__init__.py`
   goes to an area named by `auth/tokens.py`), and a file that shares none, such as a
   `README.md` at the root, goes to an area `rest` that Axocoatl makes for them. A
   planned area that ends up with no files is not run.

   An area with more files than one worker can read within its budget is split before
   any worker runs. Axocoatl counts the reads its text files need, one for each default
   `read_file` window of each file (see step 4), and what one worker activation can
   read: its `invocations`, less a fifth (at least 4) held back for looking around and
   its answer, at two invocations a read (the model call that asks for it and the read
   itself), and at most 200. The built-in budget of 300 invocations comes to about 120
   reads. An area that needs more becomes numbered sub-areas, such as `src-1`, `src-2`
   and `src-3`, of consecutive files, each within that budget, each with its own worker;
   a file is never split. The progress lines (`assigned`) and the record show the plan
   as executed and every area's files; each split, and the files given to `rest` or by
   directory, are notes.
3. **Areas.** One worker per area, made from the `worker` Agent: read-only (`writes: []`)
   with `read_file`, `list_dir`, `grep` and `glob` and no shell (in the 1.3.0 re-smoke
   workers with `bash` spent most of their budget on scripts that printed what they had
   already found), each in a fresh conversation, with no dependencies between them,
   so the controller starts them together. Each worker is told the files of its area
   (past 8 KiB of names, the directories they are in, with counts, and to read all of
   them) and reports `FINDINGS` and what it did `NOT_REACHED`. A turn can record only so
   many tool calls, so one turn runs at most 16 workers whose reads add up to at most
   200; more workers run in further turns.
4. **Follow-ups.** From the tool calls each worker's Session recorded, a file counts as
   read only when the `read_file` calls of it returned every byte of it, whatever its
   size: each read covers the bytes its result reports, from its `offset` for its
   `returned_bytes`. Reading part of a file, even a small one, leaves it unread.
   `read_file` returns, from its `offset` (0 by default), a window that fits the model:
   64 KiB, or a quarter of the model's context counted at one token per byte when that
   is smaller (8 KiB for a 32,768-token context). Its description tells the model the
   size, `limit` asks for less, and the result says where the next read starts. Reading
   through `grep`, `glob` or `list_dir` does not count. Empty files and binary
   files (a NUL byte in the first 8,000 bytes) need no read; a file over 256 KiB is not
   read, and is a note. When a worker's turn ends with files of its area unread,
   Axocoatl runs a follow-up turn with a fresh activation of that worker naming exactly
   those files: "read these files and report additional findings in the same format".
   Follow-ups go on for as long as each one reads something of its files that no
   earlier read returned; a worker whose follow-up read nothing new gets no more. The
   wall clock bounds them. A worker without a result gets a follow-up too, unless the
   wall clock, your stop or its provider's refusal of the request (HTTP 400 to 403)
   ended it. A follow-up's findings join its area's report.

   What stays not covered, each with its reason: every file still unread after the
   follow-ups (or when the wall clock or your stop ended them), listed by file; a worker
   without a result; findings beyond a report's first 200; and an area whose worker's
   tool calls could not be read. A worker's own
   `NOT_REACHED` list is a note, never a gap. Each area's coverage is a `coverage`
   progress line: how many of its files were examined, read, empty, binary or too large,
   and which are unread. Notes are in the progress lines, the summary, the Outcome's
   `notes`, the Run outcome panel, the JUnit verdict's `<system-out>` and the record.
5. **Re-asks.** A worker whose answer has no `FINDINGS` block Axocoatl can read (findings
   described in prose, say) gets up to 2 re-asks after the follow-ups. Each is a turn
   with a fresh, read-only activation of that worker that is offered no tools; its
   instructions quote the answer and ask for exactly a `FINDINGS` JSON array in the
   documented format, `[]` when the answer describes none. Like follow-ups, re-asks are
   bounded by the budget and the wall clock and recorded (`applying_team` and `reask`
   progress lines, `audit_reask` turns). Nothing a re-ask does counts as reading.
   Coverage and findings are separate: an area whose files were all read but whose
   findings stay unreadable is not "not covered". It is listed under "Findings
   unreadable" in the summary, the Run outcome panel and the Outcome's
   `unreadable_findings` (with every answer Axocoatl could not read), as a
   `findings_unreadable` failure in the JUnit `findings` suite, and the run needs
   attention: "Findings unreadable for ingest". The integrator still gets that answer as
   text.
6. **Integrate.** The integrator gets every accepted worker report (each up to 24 KiB,
   with a note when cut) and the list of what is not covered, and answers with one
   merged `FINDINGS` block. An integrator without an answer gets one more turn (not
   after the wall clock, your stop or its provider's refusal of the request). One whose
   `FINDINGS` block cannot be read gets up to 2 re-asks, each a fresh activation offered
   no tools that is sent the same reports with its unreadable answer quoted. If the
   answer is still unreadable, or the integrator still has no result for a provider's
   reason, Axocoatl merges the findings itself: every area's findings, each keeping its
   area, without any finding whose file, line and title (in lowercase, punctuation left
   out) match an earlier one's. The note "findings merged by the host" says so, and
   the run does not need attention for it: in the runs measured for 1.3.0, the merge
   step never added a finding.

A finding's location is `path:line`. A location whose line is not a number, such as the
`ingest/feed.go:line_number` a re-ask once answered from prose that named no line, keeps
the file alone: the Outcome's finding has `location: "ingest/feed.go"` and
`line: null`, and the summary and JUnit show the file only.

Axocoatl checks every finding it reports against the files it listed, not against
what a model says:

- A finding at a file the repository does not have is not reported. It becomes the note
  "finding at a path that does not exist: <path> (<title>)". The path is looked up after
  a leading `./` and the repository's place in front of it (an absolute path, or the
  repository's directory name) are removed. In a 1.3.0 test run a planner invented
  `notify/rotate_keys.py`, and a worker's finding at it had reached the Outcome.
- A finding whose line is beyond the end of its file, as Axocoatl counts the file's
  lines, keeps its file with `line: null` and a note.
- After the integration, and after Axocoatl's own merge, findings at the same file and
  the same or a nearby line (at most 2 lines apart) whose titles share most of their
  words are reported once. The one with a line, then the longer detail, is kept, and a
  note names the ones removed. Findings that make different claims about the same line,
  such as "integer overflow" and "missing input validation", both stay.

Audit turns have no required checks and no review. Findings do not fail the run by
default (`fail_on_findings: false`); anything not covered does. Each worker gets the
`worker` Agent's `budget`, or `budgets.agent` without one, for each turn it is in, and
the wall clock bounds every turn. Every file must be read: an area too large for one
worker is split, and a worker that reads less than it was given is followed up while
it keeps reading new files, so a file stays unread only when its worker's last
follow-up read nothing new, or the wall clock, your stop or a failure ended the
follow-ups. When integration has no result for a reason other than an unreadable answer
or a provider failure (the wall clock, your stop), the workers' findings are reported
unmerged and `audit integration` is listed as not covered. The attention line counts
only areas and names the integration apart: "The integration was not read; the area
findings are reported unmerged".

When you stop an audit, no further turn starts: areas planned but not started, files no
follow-up read, and an integration that did not run, are not covered (`stopped`), and
the workers' findings are reported unmerged. When no area has a report there is nothing
to integrate: the integration is skipped and not listed. A worker your stop interrupted is not
covered as `stopped` too, never `blocked`: a read-only worker cannot change a file, so
the repository capture the stop cut short is no reason to doubt it. The Outcome keeps the turns, the
not-covered entries, the findings and the usage observed until the stop; usage is
marked incomplete (`usage.complete: false`) when a stopped turn's usage was not all
reported.

Workers start together and their model calls overlap, but they share one Session
container and one checkout, and a local model server may answer one request at a time.
How much faster parallel workers finish through Axocoatl has not been measured.

### The measured trade-off

{/* measured: claude-code-subagents single-vs-multi 2026-10-06 */}

These numbers come from a pre-registered study that ran Claude Opus as Claude Code
subagents, not through Axocoatl. A planning agent, parallel workers (six on the audit)
and an integrating agent were compared with one agent on the same model.

- **On an audit larger than one context** (5.2 to 5.7 million characters of source per
  instance, 150 planted defects over 5 instances): recall was 11 points higher (99% against
  87%; interval +4 to +19 points), precision 8 points lower, at about 3× the tokens and
  the same wall-clock time. This is a sensitivity analysis, not a pre-registered result:
  the study's pre-registered exclusion rule excluded 9 of the 10 attempts, and these
  figures put them back.
- **On work that fits in one context** (research questions, independent modules, a
  coupled feature change): both setups scored 100%. The multi-agent setup took 1.6× to
  4.9× as long and used 4× to 5.5× the tokens.

{/* /measured */}

Use `audit` when the scope is larger than one model context and finding more matters more
than the extra tokens and the extra false reports. For anything one Agent can hold, run
one Agent.

<Aside>
Findings, adjudications and not-covered entries are evidence about one run with the models
you chose. They do not prove the absence of other defects.
</Aside>

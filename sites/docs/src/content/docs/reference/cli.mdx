This page covers the current command tree. The installed binary remains the
authority for its exact version:

```sh
axocoatl --help
axocoatl <command> --help
```

## Configuration and runtime

| Command | Purpose |
| --- | --- |
| `axocoatl init [NAME]` | Scaffold an advanced project-local config in `NAME` (default `my-axocoatl-project`): local Ollama and the default team. Follow-up commands must pass its path explicitly |
| `axocoatl onboard [--yes] [--plan] [--writer claude-code\|codex\|ollama\|openrouter] [...]` | Set up the current OS user without creating a project or Workspace: the rootless Podman sandbox (Podman installed with Homebrew on Apple silicon or a known Linux package manager, else its installer named; the machine on macOS; rootless), the writer and a different reviewer model (a local Ollama pair chosen by memory, Claude Code or Codex with their image and sign-in, or OpenRouter), the user configuration with `run.models` defaults, a check with doctor's code, and optionally the daemon and a first run. It asks before each change; `--yes` answers yes (sudo also needs `--allow-sudo`), `--plan` changes nothing. Exits 0 ready, 1 not ready (the steps left are listed), 3 usage or no terminal without `--yes`. See [Set up Axocoatl](/start/onboard/) for every flag |
| `axocoatl doctor [-c, --config CONFIG] [--json]` | Report the Sandbox, Models, Writers and Daemon as OK, WARN or FAIL, each with its fix, then what is ready to run and the steps left; exits 0 only when nothing failed. `--json` prints the same report as one document. An omitted path resolves the user configuration |
| `axocoatl validate [CONFIG]` | Parse and validate a config path; an omitted path resolves the user configuration |
| `axocoatl dev [-c, --config CONFIG]` | Run daemon, IPC, HTTP app, triggers, supervision, and consolidation in foreground; config defaults to the user configuration |
| `axocoatl serve [-c, --config CONFIG]` | Run the same runtime entrypoint used by the installed service; config defaults to the user configuration |
| `axocoatl url [-c, --config CONFIG]` | Print the browser sign-in link, `http://localhost:<port>/?token=<token>`, from the configured port and the data root's `local-api-token`. It reads only: it exits with status 1 when the daemon has not created the token yet, and prints the plain server URL when the configuration uses `server.auth` credentials, `allow_unauthenticated`, or a non-loopback host |

The user configuration is
`~/Library/Application Support/Axocoatl/config.yaml` on macOS. On Linux and
WSL2 it is `$XDG_CONFIG_HOME/axocoatl/config.yaml` when XDG is set, otherwise
`$HOME/.config/axocoatl/config.yaml`. Config-aware commands resolve that path
regardless of the current directory; a repository's `axocoatl.yaml` is never
selected implicitly.

Pass `--config /absolute/path/to/axocoatl.yaml` (or the positional path accepted
by `validate`) for an advanced project-local configuration. `AXOCOATL_DATA_DIR`
overrides its data location; otherwise an explicit configuration uses `data/`
beside that file. `axocoatl url` resolves the data root the same way, so pass
the same `--config` and `AXOCOATL_DATA_DIR` the daemon uses.

`dev` and `serve` print the full sign-in link only when standard output is a
terminal; otherwise, for example under a service manager, they print a hint to
run `axocoatl url` so the token stays out of logs. See
[the local API token](/operate/security/#the-local-api-token).

`dev` prints additional startup information, but neither command forces debug
logging. Set `RUST_LOG`, for example:

```sh
RUST_LOG=debug axocoatl dev
```

The daemon logs each HTTP request it answers at `debug`, with any sign-in token as
`REDACTED` (`RUST_LOG=info,axocoatl_server=debug` adds them to the default `info`
logs), and an answer with a server error (5xx) at `warn`, which it shows by default.

## Console chat

```text
axocoatl chat [-a, --agent AGENT] [-c, --config CONFIG] [--session LABEL]
```

Defaults are Agent `assistant` and the resolved user configuration. Chat uses
daemon IPC when reachable and otherwise bootstraps a runtime in process.

<Aside type="caution" title="--session is only a display label">
The console flag does not select or resume a stored Workspace Session. Use the
browser workbench or `axocoatl session` commands when durable folder Session
identity matters.
</Aside>

## Directory Sessions

These commands require a running daemon and use its already-loaded config:

| Command | Purpose |
| --- | --- |
| `axocoatl session new <DIRECTORY> [-a, --agent AGENT] [-n, --name NAME]` | Create a single-Agent folder Session; Agent defaults to `assistant` |
| `axocoatl session list` | List directory Sessions from the running daemon |
| `axocoatl session exec <SESSION_ID> <INPUT>` | Execute one instruction and print the completed output |
| `axocoatl session close <SESSION_ID>` | Soft-close the Session and stop its sandbox |
| `axocoatl session upgrade [-c, --config PATH] --confirm` | Convert supported legacy Session storage while the daemon is stopped; preserves history and archives unproved historical Agent state. See [Upgrade](/operate/upgrade/). |

CLI Session creation does not expose the browser form's Skills, image, port,
or multi-Agent mode options. It also does not approve detected repository
setup. `session new` prints the proposed command as **not run** and directs you
to the browser's **Review setup** flow; it prints `session exec` guidance only
after the environment is Ready. `session list` includes the durable environment
state. An `exec` request against a non-Ready Session fails rather than running
outside the reviewed environment.

## Agents

| Command | Purpose |
| --- | --- |
| `axocoatl agents list [-c, --config CONFIG]` | List configured Agents |
| `axocoatl agents status [-c, --config CONFIG]` | Show status for all Agents |
| `axocoatl agents restart <AGENT_ID> [-c, --config CONFIG]` | Ask the running daemon to restart one Agent |

List/status can use daemon IPC or an in-process fallback. Restart requires a
running daemon. Its config option does not reload that file into the daemon;
the Agent respawns from the daemon's current in-memory config.

## CLI Skills templates

| Command | Purpose |
| --- | --- |
| `axocoatl skills list` | List the compiled prompt templates `summarize`, `code_review`, `research`, and `translate` |
| `axocoatl skills run <NAME> [PARAMS]...` | Render one template from trailing `key=value` parameters and print it |

The rendered prompt is not sent to an Agent. Pipe or paste it into a request if
desired. These commands are separate from configured YAML Skills; use Settings
or `POST /api/skills/{id}/fire` for those event-producing records.

## MCP

| Command | Purpose |
| --- | --- |
| `axocoatl mcp servers [-c, --config CONFIG]` | List connected MCP servers |
| `axocoatl mcp tools [-c, --config CONFIG] [-s, --server SERVER]` | List discovered tools, optionally for one server |
| `axocoatl mcp serve [-c, --config CONFIG]` | Speak MCP over stdio and expose Agents as `agent_<id>` tools |

Queries use the running daemon when available, otherwise an in-process
bootstrap. `mcp serve` reserves stdout for protocol messages; logs use stderr.

## Token report

```text
axocoatl tokens report [-c, --config CONFIG]
```

Prints per-Agent input/output/reasoning usage available to the current daemon or fallback
runtime. It is runtime accounting, not a provider invoice.

## Workflow compatibility

| Command | Purpose |
| --- | --- |
| `axocoatl workflow list [-c, --config CONFIG]` | List manual records projected from the canonical Automation store |
| `axocoatl workflow run <WORKFLOW_ID> -i, --input <INPUT> [-c, --config CONFIG]` | Execute one manual Automation and wait for its result |

This compatibility view does not expose full Automation CRUD, folders,
triggers, run history, or Interrupt controls. Use Settings or the HTTP API.

## Benchmark guidance

```text
axocoatl benchmark [NAME]
```

`NAME` defaults to `all`. The current command does not execute a benchmark; it
prints guidance to use the repository's Criterion harness through `cargo
bench`. Run those commands from a source checkout.

## Background service

| Command | Purpose |
| --- | --- |
| `axocoatl service install [-c, --config CONFIG]` | Write/register a per-user systemd or launchd definition; config defaults to the resolved user configuration and is recorded as an absolute path. Records a `PATH` that contains the install-time `podman`, and `CONTAINER_CONNECTION`/`CONTAINER_HOST` when set; on macOS, logs to `~/Library/Logs/Axocoatl/daemon.log` |
| `axocoatl service start` | Start now and enable at login |
| `axocoatl service stop` | Stop without uninstalling |
| `axocoatl service status` | Report backend, installed/running/enabled state, detail, and where the logs are |
| `axocoatl service uninstall` | Stop, deregister, and remove the definition |

Install supports Linux systemd user units and macOS LaunchAgents. It does not
start the service or load dotenv files. If onboarding left a hosted-provider
environment reference instead of storing a supplied key, inject that variable
through the service manager; see [Run as a service](/operate/service/).

## Browser image

| Command | Purpose |
| --- | --- |
| `axocoatl browser install [--image IMAGE]` | Build the browser tools' image with Podman from the Containerfile and lock files embedded in Axocoatl: Node 22, Playwright 1.60.0 and Playwright's headless Chromium. `IMAGE` defaults to `localhost/axocoatl-browser:pw1.60.0`. Prints the image id |

The build downloads the pinned Node image, the locked Playwright packages and
Chromium. It is network access you start, on the host; Agents never trigger it. See
[Browser](/configure/browser/).

## Network policy

| Command | Purpose |
| --- | --- |
| `axocoatl network reload` | Ask the running daemon, over its IPC socket, to read the configuration file it was started with again and apply `sandbox.egress.allow`, `sandbox.egress.private_destinations`, `sandbox.egress.routes`, `credentials`, `browser.allow` and `browser.private_destinations` to new and running Sessions. Prints what was applied with each entry a list gained (`+`) or lost (`-`), each running Session's new policy revision with the open connections it closed, the Sessions that kept their policy, and the settings that need a restart. Exits with status 1 when the daemon is not running, was not started from a file, the file is invalid or inside a Session's Workspace (these change nothing), or a running Session kept its policy because its new one could not be recorded; running the command again retries those Sessions |

The whole file is validated. Every other difference from the configuration the
daemon started with, such as `sandbox.network`, `sandbox.egress.sidecar_network`,
`max_connections`, adding or removing the `browser` block, Agents or providers, is
listed as `restart_required` and not applied. A configuration file inside the
Workspace of one of the daemon's Sessions is not reloaded, because that Session's
Agents can edit it; check it and restart the daemon instead. The same reload is
[`POST /api/network/reload`](/reference/http-api/#reload-the-network-allowlists). See
[Network egress](/configure/sandboxes/#network-egress).

## Loadout runs

These commands talk to the running daemon over its HTTP API. They find it at `--url`,
else `AXOCOATL_URL`, else the configured server address, and authenticate with
`AXOCOATL_TOKEN`, else the data root's `local-api-token`. They never start a daemon.

| Command | Purpose |
| --- | --- |
| `axocoatl run <LOADOUT> (--task <TEXT> \| --task-file <FILE\|->) [--repo DIR] [--junit FILE] [--record FILE] [--receipt FILE] [--model ROLE=PROVIDER:MODEL]... [--param NAME=VALUE]... [--check CMD] [--setup CMD] [--keep none\|branch\|pr] [--json] [--url URL] [-c, --config CONFIG]` | Run a [loadout](/configure/loadouts/) headless and exit with its code: 0 pass, 1 checks failed, 2 needs attention, 3 usage, 4 daemon unavailable, 5 infrastructure, 6 interrupted, 7 busy. `--receipt` writes the run's [signed receipt](/workbench/receipts/). See [`axocoatl run`](/reference/run/) |
| `axocoatl loadouts list [--url URL]` | List the built-in loadouts (`fix`, `fix-claude-code`, `fix-codex`, `qa`, `audit`) and yours, with kind, version, opt-in, warnings, and the error and path of a file that cannot be used, such as one that declares a built-in id |
| `axocoatl loadouts show <ID> [--url URL]` | Print one loadout's exact text, parameters and graph, and the `axocoatl run` command with its required parameters (`--model ROLE=provider:model` for a `ROLE_model` parameter) |
| `axocoatl loadouts validate <FILE>` | Parse and validate a loadout file without the daemon; prints warnings such as `same_model_reviewer` |
| `axocoatl record verify <FILE>` | Check a [record bundle](/reference/run/#record-bundle)'s header, section order, line count and SHA-256, for schema `axocoatl.record-bundle/2` (with its `receipt` section) and `/1` (Axocoatl 1.3); exits 0, or 2 on a mismatch, 3 when the file cannot be read |
| `axocoatl receipt show <FILE\|-> [--json]` | Print what a [signed receipt](/workbench/receipts/) says (run, verdict, signer, agents, checks, review, files, network policy) without verifying it, and say so; `--json` prints the signed statement. Reads a DSSE envelope or text holding an `<!-- axocoatl-receipt:v1 … -->` block; exits 0, 1 when it is not a receipt, 3 when the file cannot be read |
| `axocoatl receipt verify <FILE\|-> [--key LINE]... [--keys FILE]... [--repo DIR] [--record BUNDLE] [--json]` | Check a receipt's signature against trusted keys (lines as `receipt key` prints them; `#` comments in a file), then with `--repo` each covered file's SHA-256 and each removed path in a checkout, and with `--record` that the bundle verifies and carries this receipt for its run. Needs no daemon, Podman or network. Exits 0 valid, trusted and matching; 1 malformed or a signature that does not verify; 2 valid but signed by a key not given as trusted; 3 usage; 4 files or record that do not match. `--json` prints one JSON document. See [Verifying a receipt](/workbench/receipts/#verifying-a-receipt) |
| `axocoatl receipt key [--rotate] [-c, --config CONFIG]` | Print this data root's public receipt key as one trusted-keys line (`ed25519 <base64> axocoatl@<host> <key id prefix>`), making the key when there is none (said on standard error); `--rotate` replaces it. Use the daemon's `--config` and `AXOCOATL_DATA_DIR`; exits 0, or 5 when the data root or its secret store cannot be read |

## Secrets and recipes

| Command | Purpose |
| --- | --- |
| `axocoatl connect claude-code [-c CONFIG] [--secret NAME] [--no-verify] [--claude PATH]` | Run `claude setup-token` in a pseudo-terminal the size of your terminal (at least 40 columns by 24 rows), resized with it, with your terminal in raw mode until it ends and your keystrokes going to it until it exits, and show its output with every `sk-ant-…` token, however it is wrapped, colored or placed, shown as `[token hidden by axocoatl]` cell for cell and clipboard writes dropped. Before it runs `claude`, it checks that the store can take the token (a link or a directory at `secrets/<NAME>`, or a store already holding 64 secrets, is refused with exit code 5, so no token is made and then lost). Exactly one `sk-ant-oat01-…` token must appear; it is held in memory only, checked with Anthropic (`GET /v1/models`, which costs nothing; skipped with `--no-verify`) and stored as secret `NAME` (default `claude-code-oauth`) as `secret set` stores one. It needs an interactive terminal and finds `claude` on `PATH`, then in `~/.local/bin`, or at `--claude`. Exit codes: 0 stored, 1 rejected by Anthropic (`401`/`403`), 2 no single token printed, 3 usage (no terminal, a bad name, no `claude`), 4 not checked (network or an unexpected answer), 5 data directory or store failure, 6 interrupted. Nothing is stored unless it exits 0. See [Store the credential](/configure/external-agents/#store-the-credential) |
| `axocoatl connect codex [-c CONFIG] [--device-auth] [--codex PATH] [--no-browser] [--sign-in-timeout MINUTES] [--api-key \| --api-key-only]` | Run the official `codex -c cli_auth_credentials_store="file" login` (with `--device-auth`, `codex login --device-auth`, which shows a code to enter on another device) in the same pseudo-terminal relay. By default nothing but Podman is needed on this computer: the pinned Codex 0.160.1 runs in a throwaway container of the `codex` recipe image (the one `recipe build codex` recorded, by image id; built and recorded first when there is none), as a non-root user with a read-only root, no capabilities, no host mount, no host variable (not even Podman's proxy variables) and a private `0700` tmpfs as `CODEX_HOME`, on Podman's default bridge network; the browser sign-in publishes only `127.0.0.1:1455` (loopback only) to Codex's login server, and `--device-auth` publishes nothing. Codex cannot open a browser here from the container, so Axocoatl opens the address it prints once, with `open` (macOS) or `xdg-open` (the first on `PATH`), the address as the only argument and no shell, and prints `Opened the sign-in page in your browser.`; it opens only exactly `https://auth.openai.com/oauth/authorize?…`, or with `--device-auth` exactly `https://auth.openai.com/codex/device`, as shown on screen. `--no-browser` opens nothing (nor does a missing or failing opener): open the printed address yourself. The container lives at most 30 minutes, or 1 to 60 with `--sign-in-timeout MINUTES` (Podman's `--timeout`; not with `--codex`), which the command says when the sign-in starts (`You have 30 minutes to finish signing in.`); when the time runs out first it says ``The Codex sign-in was not completed within 30 minutes; nothing was stored. Run `axocoatl connect codex` again.`` (with the time chosen) and exits 2. With `--codex PATH` that Codex CLI on this computer runs instead, with a private temporary `CODEX_HOME` (`0700`) in the data root as its home and working directory, without Codex's other credential and endpoint variables; that Codex opens the browser sign-in itself. Its output is shown with Anthropic tokens, OpenAI API keys (`sk-…`) and JWTs (`eyJ…`) hidden as `[token hidden by axocoatl]` and clipboard writes dropped. The sign-in is read from the `auth.json` Codex writes (a regular file, never a link; a ChatGPT sign-in with an access and a refresh token), never from the screen, from the container straight into memory, and stored as the secret `codex-chatgpt` (access token, refresh token, account id) as `secret set` stores one. With `--api-key`, the OpenAI API key that Codex 0.160.1 obtains after the browser sign-in (a token exchange at `auth.openai.com`, written as `OPENAI_API_KEY` in `auth.json`) is read from the same `auth.json` in memory, checked for the form Codex writes (`sk-`, then letters, digits, `-` and `_`, 20 to 1024 characters) and stored as the secret `codex-openai` under the same lock, beside `codex-chatgpt`; `--api-key-only` stores only the key. Requests with `codex-openai` are billed at OpenAI API rates to the key's OpenAI Platform organization, not to your ChatGPT plan. When `auth.json` holds no key (OpenAI issued none, for example for an account without an OpenAI Platform organization, or the request for the key failed) or a value that is not one, nothing is stored as `codex-openai`, the command says so (with `--api-key` the ChatGPT sign-in is still stored) and exits 8. `--api-key` or `--api-key-only` with `--device-auth` is refused (exit code 3): the device-code sign-in gets no key. A value on the command line (after `--api-key`, or `--api-key=VALUE`) is refused with exit code 3 and never repeated. Then the container is removed (or every file in the temporary home is overwritten with zeros and removed), also on an error or a signal. It needs an interactive terminal. Exit codes: 0 stored, 2 no ChatGPT sign-in stored by `codex login` (also when the sign-in time ran out), 3 usage (no terminal, no Podman on `PATH`, a `--codex` that is not an executable, port 1455 in use, `--api-key` with `--device-auth`, a value on the command line, a command line it does not take), 5 data directory, store, Podman, image build, pseudo-terminal or `auth.json` failure (also when the login container stopped early), 6 interrupted, 8 with `--api-key` or `--api-key-only`, no API key stored. See [Codex with a ChatGPT plan](/configure/external-agents/#codex-with-a-chatgpt-plan-axocoatl-connect-codex) and [Codex with an OpenAI API key](/configure/external-agents/#codex-with-an-openai-api-key-axocoatl-connect-codex---api-key) |
| `axocoatl connect codex --status [-c CONFIG]` | Read the stored ChatGPT sign-in (`codex-chatgpt`) from the data root, without the daemon, and print whether one is stored, its account id by its last four characters, when its access token expires (its JWT `exp`) or that it has expired, and when its tokens were last refreshed or signed in; never a token. Exit codes: 0 stored, 2 none, 5 it cannot be read or is not a sign-in. See [Check and refresh the sign-in](/configure/external-agents/#check-and-refresh-the-sign-in) |
| `axocoatl connect codex --refresh [-c CONFIG] [--url URL]` | Ask the running daemon (at `--url`, `AXOCOATL_URL` or the configured address, with `AXOCOATL_TOKEN` or the local API token, as `axocoatl run` does) to refresh the stored ChatGPT sign-in now, through `POST /api/connect/codex/refresh` (authenticated callers on a loopback address only; `403` when the daemon accepts unauthenticated API requests). The daemon refreshes with the broker that refreshes before a request: the same request, rotation, atomic write under the secret store's lock and remembered refusal, serialized with it; it logs the refresh and how it ended without a value. Prints the time of the refresh and when the new access token expires, never a token. Exit codes: 0 refreshed, 1 refused by OpenAI (sign in again), 2 no sign-in stored, 3 usage, 4 the refresh could not be completed (network or an answer that is neither tokens nor a refusal; the stored sign-in is unchanged), 5 other failure, 7 no daemon answers. See [Check and refresh the sign-in](/configure/external-agents/#check-and-refresh-the-sign-in) |
| `axocoatl connect openrouter [-c CONFIG] [--secret NAME] [--writer MODEL] [--reviewer MODEL] [--no-browser] [--sign-in-timeout MINUTES] [--credits-only] [--no-config]` | Get an OpenRouter API key by signing in in the browser, through OpenRouter's OAuth PKCE flow, without anyone seeing it. First it asks whether the account pays with OpenRouter credits and has no BYOK provider keys connected (onboarding's question; `--credits-only` answers yes, and without a terminal it is required). `--writer` and `--reviewer` name OpenRouter models (`vendor/model` or `openrouter:vendor/model`, never the same one); each must be in OpenRouter's public catalog (`GET /api/v1/models`) with tool calls and text in and out, checked before the sign-in. Unless `--no-config`, the configuration file must have a block-style top-level `providers:` or none (anything else is refused before the sign-in, with the lines to add). When there is no file at the user's configuration path (no `-c`), a new one is written there after the key is stored (`0600`, never over a file): these entries and the server's defaults, no Agents; a missing file named with `-c` elsewhere is refused before the sign-in. `--secret` refuses a name that reads as a key, without repeating it, and the secrets other commands own (the receipt signing key, `claude-code-oauth`, `codex-chatgpt`, `codex-openai`). It listens on `127.0.0.1` on a port the system picks, opens `https://openrouter.ai/auth?callback_url=http://127.0.0.1:<port>/callback&code_challenge=…&code_challenge_method=S256&state=…&key_label=Axocoatl <date>` with `open` (macOS) or `xdg-open` and prints it (`--no-browser` only prints it), and waits up to 10 minutes (`--sign-in-timeout MINUTES`, 1 to 60) for the browser to return there. A code is used only when its `state` is this sign-in's; any other return with a code is answered `400`, counted and ignored, and the sign-in goes on waiting. The browser returning without a code (a top-level navigation, or a request without `Sec-Fetch-Mode` that carries OpenRouter's `error`) is a cancelled sign-in; any other request without a code is ignored. The code is exchanged with the sign-in's 32-byte random verifier (`POST /api/v1/auth/keys`) for a key, which is checked with `GET /api/v1/key` (its label, credit limit, usage and free-tier status are shown, never the key; a key whose description cannot be read is stored with a note) and stored as secret `NAME` (default `openrouter`) as `secret set` stores one. The configuration then gets `providers.openrouter_billing: credits` and `providers.openrouter.api_key_secret: NAME` (an `api_key` written there before is removed; every other line is kept, and the file is replaced atomically with its permissions). Restart a running daemon to use the key. A value on the command line is refused with exit code 3 and never repeated. Exit codes: 0 stored, 1 OpenRouter refused to issue the key or refused the key it issued, 2 no key (the sign-in was cancelled or did not come back within the time; the message counts returns ignored for another state), 3 usage (a model that is not in the catalog or not usable, the same model twice, a configuration it cannot edit, no terminal without `--credits-only`, a "no" to the billing question), 4 OpenRouter could not be reached or answered unexpectedly, 5 data directory, store or configuration failure (the key may be stored; the message says), 6 interrupted. See [Configure OpenRouter](/configure/providers/#configure-openrouter) |
| `axocoatl connect openrouter --status [-c CONFIG] [--secret NAME]` | Print what the configuration says about OpenRouter's key and whether the secret is stored, then ask OpenRouter about the stored key (`GET /api/v1/key`): its label, credit limit, what is left of it, usage and free-tier status; never the key. A stored value that does not start with `sk-or-` is not sent. Exit codes: 0 stored and accepted, 1 OpenRouter refuses it, 2 none stored, 4 it could not be checked, 5 failure (also a value that is not an OpenRouter key) |
| `axocoatl connect openrouter --remove [-c CONFIG] [--secret NAME] [--no-config]` | Delete the stored key and the configuration's `api_key_secret: NAME` line (the whole `openrouter:` entry when that was all of it; `--no-config` leaves the file). While Agents in the file use provider `openrouter`, the line is kept and the command names them: Axocoatl will not start with that file until you connect again or move them, and `axocoatl doctor` warns until then. The key still works in your OpenRouter account until you delete it at openrouter.ai/settings/keys. Exit codes: 0 removed, 2 nothing to remove, 5 failure |
| `axocoatl secret set <NAME> [--from-env VAR] [-c CONFIG]` | Read one value from standard input, or from the environment variable `VAR` with `--from-env` (unset or empty is refused), never from an argument. `VAR` is the variable's name, without `$` (a letter or `_`, then letters, digits or `_`); a value given there, after `NAME` or as `NAME` is refused with exit code 3 and never repeated in the message, and store it as `secrets/<NAME>` in the data root (`0600`, replaced atomically). Without `--from-env`, standard input must be a pipe or a file; a terminal is refused (exit code 3). It is never printed. A value with whitespace inside it, a `Bearer ` prefix, JSON or several tokens, or a `claude-code-oauth` value that does not start with `sk-ant-oat01-`, or a `codex-chatgpt` value that is not a sign-in `connect codex` stored, is stored with a warning on standard error that never shows it. A route's `credential` can name it. For Claude Code, `axocoatl connect claude-code` obtains and stores the token instead, for Codex with a ChatGPT plan, `axocoatl connect codex`, for Codex's OpenAI API key, `axocoatl connect codex --api-key`, and for OpenRouter, `axocoatl connect openrouter`, so you never type or paste one; `secret set` is for other credentials, and for those keys only in automation without a browser. See [Store the credential](/configure/external-agents/#store-the-credential) |
| `axocoatl secret list` | Print the stored secret names, never values |
| `axocoatl secret remove <NAME>` | Delete one stored secret |
| `axocoatl recipe build <RECIPE>... [-c CONFIG]` | Build one Session image with Podman from Axocoatl's pinned recipes `claude-code`, `codex` and `e2e`, combined in that order, and record its image id in the data root; Sessions trust it by that id |
| `axocoatl recipe list` | List the recipes and the images built from them |
| `axocoatl recipe clear-cache [--repo DIR \| --all] [-c CONFIG]` | Remove the [toolchain cache](/configure/toolchains/#caches-the-second-run-is-offline) volume of the repository `DIR` (default: the current directory), or with `--all` of every repository of this data root, with Podman; the next run installs the packages again. A volume that a container of one of the repository's Sessions still uses is left, and the command names that Session and says to let its run end or close it; it then exits with status 5 |

`connect`, `secret` and `recipe` use the data root of `--config` or `AXOCOATL_DATA_DIR`; give them
the daemon's, so it finds what they store. `recipe build` downloads its base image and the
pinned programs; that is network access you start, on your computer. See [External agents](/configure/external-agents/) and
[The e2e check](/configure/e2e-check/).

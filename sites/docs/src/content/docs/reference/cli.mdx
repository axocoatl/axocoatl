This page covers the current command tree. The installed binary remains the
authority for its exact version:

```sh
axocoatl --help
axocoatl <command> --help
```

## Configuration and runtime

| Command | Purpose |
| --- | --- |
| `axocoatl init [NAME]` | Scaffold an advanced project-local config in `NAME` (default `my-axocoatl-project`): local Ollama and the default team. Follow-up commands must pass its path explicitly |
| `axocoatl onboard [--install-daemon]` | Configure the current OS user without creating a project or Workspace. For Ollama it asks for the server URL, checks that native Sessions can use it (loopback, Ollama 0.20.6, cloud features disabled), and suggests Lead and Reviewer models from those installed. The flag additionally installs the per-user service definition but does not start it, and hosted-provider keys must be supplied rather than left as shell-environment placeholders |
| `axocoatl doctor [-c, --config CONFIG]` | Check environment and config, including the Ollama server requirements of native Sessions; an omitted path resolves the user configuration |
| `axocoatl validate [CONFIG]` | Parse and validate a config path; an omitted path resolves the user configuration |
| `axocoatl dev [-c, --config CONFIG]` | Run daemon, IPC, HTTP app, triggers, supervision, and consolidation in foreground; config defaults to the user configuration |
| `axocoatl serve [-c, --config CONFIG]` | Run the same runtime entrypoint used by the installed service; config defaults to the user configuration |
| `axocoatl url [-c, --config CONFIG]` | Print the browser sign-in link, `http://localhost:<port>/?token=<token>`, from the configured port and the data root's `local-api-token`. It reads only: it exits with status 1 when the daemon has not created the token yet, and prints the plain server URL when the configuration uses `server.auth` credentials, `allow_unauthenticated`, or a non-loopback host |

The user configuration is
`~/Library/Application Support/Axocoatl/config.yaml` on macOS. On Linux and
WSL2 it is `$XDG_CONFIG_HOME/axocoatl/config.yaml` when XDG is set, otherwise
`$HOME/.config/axocoatl/config.yaml`. Config-aware commands resolve that path
regardless of the current directory; a repository's `axocoatl.yaml` is never
selected implicitly.

Pass `--config /absolute/path/to/axocoatl.yaml` (or the positional path accepted
by `validate`) for an advanced project-local configuration. `AXOCOATL_DATA_DIR`
overrides its data location; otherwise an explicit configuration uses `data/`
beside that file. `axocoatl url` resolves the data root the same way, so pass
the same `--config` and `AXOCOATL_DATA_DIR` the daemon uses.

`dev` and `serve` print the full sign-in link only when standard output is a
terminal; otherwise, for example under a service manager, they print a hint to
run `axocoatl url` so the token stays out of logs. See
[the local API token](/operate/security/#the-local-api-token).

`dev` prints additional startup information, but neither command forces debug
logging. Set `RUST_LOG`, for example:

```sh
RUST_LOG=debug axocoatl dev
```

## Console chat

```text
axocoatl chat [-a, --agent AGENT] [-c, --config CONFIG] [--session LABEL]
```

Defaults are Agent `assistant` and the resolved user configuration. Chat uses
daemon IPC when reachable and otherwise bootstraps a runtime in process.

<Aside type="caution" title="--session is only a display label">
The console flag does not select or resume a stored Workspace Session. Use the
browser workbench or `axocoatl session` commands when durable folder Session
identity matters.
</Aside>

## Directory Sessions

These commands require a running daemon and use its already-loaded config:

| Command | Purpose |
| --- | --- |
| `axocoatl session new <DIRECTORY> [-a, --agent AGENT] [-n, --name NAME]` | Create a single-Agent folder Session; Agent defaults to `assistant` |
| `axocoatl session list` | List directory Sessions from the running daemon |
| `axocoatl session exec <SESSION_ID> <INPUT>` | Execute one instruction and print the completed output |
| `axocoatl session close <SESSION_ID>` | Soft-close the Session and stop its sandbox |
| `axocoatl session upgrade [-c, --config PATH] --confirm` | Convert supported legacy Session storage while the daemon is stopped; preserves history and archives unproved historical Agent state. See [Upgrade](/operate/upgrade/). |

CLI Session creation does not expose the browser form's Skills, image, port,
or multi-Agent mode options. It also does not approve detected repository
setup. `session new` prints the proposed command as **not run** and directs you
to the browser's **Review setup** flow; it prints `session exec` guidance only
after the environment is Ready. `session list` includes the durable environment
state. An `exec` request against a non-Ready Session fails rather than running
outside the reviewed environment.

## Agents

| Command | Purpose |
| --- | --- |
| `axocoatl agents list [-c, --config CONFIG]` | List configured Agents |
| `axocoatl agents status [-c, --config CONFIG]` | Show status for all Agents |
| `axocoatl agents restart <AGENT_ID> [-c, --config CONFIG]` | Ask the running daemon to restart one Agent |

List/status can use daemon IPC or an in-process fallback. Restart requires a
running daemon. Its config option does not reload that file into the daemon;
the Agent respawns from the daemon's current in-memory config.

## CLI Skills templates

| Command | Purpose |
| --- | --- |
| `axocoatl skills list` | List the compiled prompt templates `summarize`, `code_review`, `research`, and `translate` |
| `axocoatl skills run <NAME> [PARAMS]...` | Render one template from trailing `key=value` parameters and print it |

The rendered prompt is not sent to an Agent. Pipe or paste it into a request if
desired. These commands are separate from configured YAML Skills; use Settings
or `POST /api/skills/{id}/fire` for those event-producing records.

## MCP

| Command | Purpose |
| --- | --- |
| `axocoatl mcp servers [-c, --config CONFIG]` | List connected MCP servers |
| `axocoatl mcp tools [-c, --config CONFIG] [-s, --server SERVER]` | List discovered tools, optionally for one server |
| `axocoatl mcp serve [-c, --config CONFIG]` | Speak MCP over stdio and expose Agents as `agent_<id>` tools |

Queries use the running daemon when available, otherwise an in-process
bootstrap. `mcp serve` reserves stdout for protocol messages; logs use stderr.

## Token report

```text
axocoatl tokens report [-c, --config CONFIG]
```

Prints per-Agent input/output/reasoning usage available to the current daemon or fallback
runtime. It is runtime accounting, not a provider invoice.

## Workflow compatibility

| Command | Purpose |
| --- | --- |
| `axocoatl workflow list [-c, --config CONFIG]` | List manual records projected from the canonical Automation store |
| `axocoatl workflow run <WORKFLOW_ID> -i, --input <INPUT> [-c, --config CONFIG]` | Execute one manual Automation and wait for its result |

This compatibility view does not expose full Automation CRUD, folders,
triggers, run history, or Interrupt controls. Use Settings or the HTTP API.

## Benchmark guidance

```text
axocoatl benchmark [NAME]
```

`NAME` defaults to `all`. The current command does not execute a benchmark; it
prints guidance to use the repository's Criterion harness through `cargo
bench`. Run those commands from a source checkout.

## Background service

| Command | Purpose |
| --- | --- |
| `axocoatl service install [-c, --config CONFIG]` | Write/register a per-user systemd or launchd definition; config defaults to the resolved user configuration and is recorded as an absolute path. Records a `PATH` that contains the install-time `podman`, and `CONTAINER_CONNECTION`/`CONTAINER_HOST` when set; on macOS, logs to `~/Library/Logs/Axocoatl/daemon.log` |
| `axocoatl service start` | Start now and enable at login |
| `axocoatl service stop` | Stop without uninstalling |
| `axocoatl service status` | Report backend, installed/running/enabled state, detail, and where the logs are |
| `axocoatl service uninstall` | Stop, deregister, and remove the definition |

Install supports Linux systemd user units and macOS LaunchAgents. It does not
start the service or load dotenv files. If onboarding left a hosted-provider
environment reference instead of storing a supplied key, inject that variable
through the service manager; see [Run as a service](/operate/service/).

## Browser image

| Command | Purpose |
| --- | --- |
| `axocoatl browser install [--image IMAGE]` | Build the browser tools' image with Podman from the Containerfile and lock files embedded in Axocoatl: Node 22, Playwright 1.60.0 and Playwright's headless Chromium. `IMAGE` defaults to `localhost/axocoatl-browser:pw1.60.0`. Prints the image id |

The build downloads the pinned Node image, the locked Playwright packages and
Chromium. It is network access you start, on the host; Agents never trigger it. See
[Browser](/configure/browser/).

## Network policy

| Command | Purpose |
| --- | --- |
| `axocoatl network reload` | Ask the running daemon, over its IPC socket, to read the configuration file it was started with again and apply `sandbox.egress.allow`, `sandbox.egress.private_destinations`, `sandbox.egress.routes`, `credentials`, `browser.allow` and `browser.private_destinations` to new and running Sessions. Prints what was applied with each entry a list gained (`+`) or lost (`-`), each running Session's new policy revision with the open connections it closed, the Sessions that kept their policy, and the settings that need a restart. Exits with status 1 when the daemon is not running, was not started from a file, the file is invalid or inside a Session's Workspace (these change nothing), or a running Session kept its policy because its new one could not be recorded; running the command again retries those Sessions |

The whole file is validated. Every other difference from the configuration the
daemon started with, such as `sandbox.network`, `sandbox.egress.sidecar_network`,
`max_connections`, adding or removing the `browser` block, Agents or providers, is
listed as `restart_required` and not applied. A configuration file inside the
Workspace of one of the daemon's Sessions is not reloaded, because that Session's
Agents can edit it; check it and restart the daemon instead. The same reload is
[`POST /api/network/reload`](/reference/http-api/#reload-the-network-allowlists). See
[Network egress](/configure/sandboxes/#network-egress).

## Loadout runs

These commands talk to the running daemon over its HTTP API. They find it at `--url`,
else `AXOCOATL_URL`, else the configured server address, and authenticate with
`AXOCOATL_TOKEN`, else the data root's `local-api-token`. They never start a daemon.

| Command | Purpose |
| --- | --- |
| `axocoatl run <LOADOUT> (--task <TEXT> \| --task-file <FILE\|->) [--repo DIR] [--junit FILE] [--record FILE] [--model ROLE=PROVIDER:MODEL]... [--param NAME=VALUE]... [--check CMD] [--setup CMD] [--keep none\|branch\|pr] [--json] [--url URL] [-c, --config CONFIG]` | Run a [loadout](/configure/loadouts/) headless and exit with its code: 0 pass, 1 checks failed, 2 needs attention, 3 usage, 4 daemon unavailable, 5 infrastructure, 6 interrupted. See [`axocoatl run`](/reference/run/) |
| `axocoatl loadouts list [--url URL]` | List the built-in loadouts and yours, with kind, version, opt-in, warnings, and the error and path of a file that cannot be used |
| `axocoatl loadouts show <ID> [--url URL]` | Print one loadout's exact text, parameters and graph |
| `axocoatl loadouts validate <FILE>` | Parse and validate a loadout file without the daemon; prints warnings such as `same_model_reviewer` |
| `axocoatl record verify <FILE>` | Check a [record bundle](/reference/run/#record-bundle)'s header, section order, line count and SHA-256; exits 0, or 2 on a mismatch |

## Secrets and recipes

| Command | Purpose |
| --- | --- |
| `axocoatl secret set <NAME>` | Read one value from standard input, never from an argument, and store it as `secrets/<NAME>` in the data root (`0600`, replaced atomically). It is never printed. A route's `credential` can name it. See [Store the credential](/configure/external-agents/#store-the-credential) |
| `axocoatl secret list` | Print the stored secret names, never values |
| `axocoatl secret remove <NAME>` | Delete one stored secret |
| `axocoatl recipe build <RECIPE>...` | Build one Session image with Podman from Axocoatl's pinned recipes `claude-code`, `codex` and `e2e`, combined in that order, and record its image id; Sessions trust it by that id |
| `axocoatl recipe list` | List the recipes and the images built from them |

`recipe build` downloads its base image and the pinned programs; that is network access
you start, on your computer. See [External agents](/configure/external-agents/) and
[The e2e check](/configure/e2e-check/).

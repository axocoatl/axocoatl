The daemon listens on `http://127.0.0.1:8080` by default and, on loopback with
no configured credentials, requires its per-daemon local API token (see below).
JSON errors generally
use `{ "error": "message" }`. The router in `axocoatl-server/src/lib.rs` and
handler Serde types remain authoritative; there is not yet a generated OpenAPI
document.

The docs content check compares every literal router path with this page and
the [WebSocket reference](/reference/websocket/).

## Authentication, CORS, and rate limits

Every workbench and control-router route that reads or changes state requires a
credential. The dedicated Preview virtual Host is intercepted before that router
and is constrained separately by its exact Session/port Host and browser-origin
boundary.

**Local token (default).** On a loopback listener with no `server.auth`
credentials, the credential is the per-daemon token in the data root's
`local-api-token` file. Send it in one of three forms:

```http
Authorization: Bearer <token>
x-api-key: <token>
Cookie: axocoatl-token-<port>=<token>
```

Browsers get the cookie by opening the sign-in link that `axocoatl dev`,
`axocoatl serve`, or `axocoatl url` prints. `GET /?token=<token>` answers
`303 See Other` to the same path and query without `token`, sets the cookie
(HttpOnly, SameSite=Strict, `Path=/`, `Max-Age=2592000`), and sends
`Referrer-Policy: no-referrer` and `Cache-Control: no-store`. A wrong token,
or `/` without a credential, returns `401` with a short sign-in page. The cookie
is ignored on requests marked `Sec-Fetch-Site: cross-site` or `same-site`.
Public paths in this mode: `/health`, `/health/ready`, `/health/live`, `/ui/*`,
`/vendor/*`, `/lattice/*`, `/brand/*`, `/axo-tap.js`, and the sign-in page at
`/`. `server.auth.allow_unauthenticated: true` turns the token off but keeps
the Host check described below.

**Configured credentials.** With `server.auth.api_keys` or `bearer_tokens`,
send one of:

```http
x-api-key: <key>
Authorization: Bearer <token>
```

Only the health probes are public, there is no sign-in cookie, and an empty
configured value never matches. All comparisons are constant time.

Checks run in this order: an unexpected Host (`421`), a disallowed browser
origin (`403`), then the credential (`401`). An empty `server.cors_origins`
allows same-origin workbench requests only. Browser writes and WebSockets with
an opaque `Origin: null` are always rejected; other cross-origin browser writes
require an explicitly allowed origin. On a loopback listener without configured
credentials, including with `allow_unauthenticated`, a Host other than
`localhost` or a loopback IP literal is rejected to prevent DNS rebinding. Origin-less CLI clients remain supported. Cross-origin
preflight for the control router advertises HEAD, GET, POST, PUT, PATCH, and
DELETE. Control-router rate limiting is disabled by default and applies per
client IP when enabled; Preview traffic stays outside that middleware.

Preview applications use a separate virtual origin shaped like
`<session>-p<port>.localhost:<listener-port>`. That Host is intercepted
before the workbench router, so no `/api`, `/ws`, app-shell, or static-asset
path can fall through to the control origin. Each Session and logical port has
its own browser storage/cookie origin. Modern browsers can block ordinary app
cookies while that origin is embedded; the workbench's **Open full preview**
action opens the same virtual URL top-level with `noopener`, where host-only
cookies work without becoming shared sibling cookies. A browser GET or HEAD
for the exact `/` workbench document on a loopback IP literal redirects to
`localhost` on the same listener and preserves the query. API, health, and
asset URLs do not redirect.

## Native Session controls

These routes use the same authenticated Session owner as ordinary Send. A preview
is read-only; Apply binds the reviewed request and exact revisions. Retrying an
uncertain reply must reuse that request unchanged. Stale revisions are conflicts,
not permission to choose another activation or team.

`GET /api/session-teams` returns config-owned records of this shape:

```json
[
  {
    "id": "feature-team",
    "name": "Feature team",
    "agents": ["planner", "coder", "reviewer"],
    "entry_point": "planner"
  }
]
```

The `workflow_id` stored by a Lattice Session must be an `id` from this response.
This inventory is deliberately independent of the mutable Automation records
returned by `/api/workflows`.

Workspace paths and Session `working_dir` values are canonical absolute paths.
Every Session response carries its durable `workspace_id`; `working_dir` remains
for execution and compatibility clients.

`environment.state` is `unprepared`, `awaiting_approval`, `preparing`, `ready`,
or `failed`. A setup command is executable only when the durable Session record
binds `setup_approved:true` to that exact text. A reviewed API request can grant
that approval; the operator's visible devcontainer default described below can
grant it only while the Session remains unreviewed. Clearing the command with
`setup_reviewed:true` is an explicit no-setup decision. Expected
runtime/setup failures return the updated Session in `failed` state so clients
can render retained evidence; malformed consent is `400`, and an active turn or
Attempt ownership conflict is `409`. File, task, Git, Preview, turn, and Ways
execution fail closed until the environment is Ready.

Live-checkout routes return `404` for a missing Session and `409` for every
existing non-Ready environment. This applies to Session file tree/read/write,
tasks and terminal attach, Git, Preview, HTTP execute, and Ways routes that
start work or inspect a live checkout. Durable History and attachments,
environment review/rebuild, completed Attempt results and cost, and the exact
Keep/Discard recovery actions remain available so a failed Session can still be
understood or resolved.

`GET /api/fs/project?path=…` includes runtime capability metadata. Under E2B,
`supports_session_image` is false and `template` names the daemon-configured
runtime; create or reconfigure rejects an explicit/devcontainer OCI image
before provisioning. `auto_approve_devcontainer_setup` exposes the operator
default for the exact devcontainer command. A browser/API request with
`setup_reviewed:true` remains authoritative, including an unchecked veto;
lockfile-detected commands are never covered by that policy.

Session `mode` is tagged JSON such as
`{"kind":"single_agent","agent_id":"coder"}` or
`{"kind":"lattice","workflow_id":"feature-team"}` or
`{"kind":"custom","agents":["planner","coder","reviewer"]}`. In compatibility
(`legacy_v1`) execution, Lattice mode resolves its stored team ID and Custom mode
resolves its stored Agent IDs against the current daemon configuration when each turn
starts. A single-Agent Session, a one-Agent team, a team whose entry point is a
Coordinator, or a request targeted to one Agent runs directly. A turn that would run
two or more Agents is refused before it starts; the error tells the operator to stop
Axocoatl, make a cold backup, and run `axocoatl session upgrade --confirm`.

### Session History versions

`/turns`, `/turns/{turn_id}`, and `/messages` take an optional `history_version`
query parameter:

- `history_version=1` returns the legacy 1.0 shape: turn records with `id`,
  `user_input`, `final_output`, `status`, and their execution events from `/turns`,
  and `role`/`content` messages from `/messages`. A Session whose History holds
  native execution refuses it with `400`, because legacy rows cannot represent that
  work.
- `history_version=2` returns versioned entries. Each names its source:
  `{"history_version": "legacy_v1", "turn": {…}}` for a turn recorded by the
  compatibility path, and `{"history_version": "execution_v2", "turn": {…}}` for a
  native turn. `/messages` entries carry `content` in place of `turn`.
- Without the parameter, a Session whose History holds native execution answers as
  `history_version=2`, and every other Session answers exactly as `history_version=1`.
  Read each entry's `history_version` rather than assuming one shape.

```bash
# curl reads the header from stdin, so the token stays out of the process list.
# DATA_ROOT is the daemon's data root, which holds local-api-token.
printf 'Authorization: Bearer %s\n' "$(cat "$DATA_ROOT/local-api-token")" |
  curl -s -H @- "http://127.0.0.1:8080/api/sessions/$SESSION/turns?history_version=2"
```

```json
[
  {
    "history_version": "execution_v2",
    "turn": {
      "owner": { "workspace_id": "…", "session_id": "…" },
      "turn_id": "turn-3f0c…",
      "revision": 14,
      "state": "needs_attention",
      "superseded": false,
      "epochs": [],
      "legacy_predecessor": null,
      "request": {
        "status": "available",
        "reference": "…",
        "content": { "display_input": "Fix the failing test", "…": "…" }
      },
      "activations": []
    }
  }
]
```

A native turn's `state` is `running`, `needs_attention`, `completed`, `cancelled`, or
`finished`. Evidence such as `request` and each activation's output carries a
`status` of `available`, `missing`, or `not_recorded`; only `available` has
`content`. The `control-plane` endpoint below is the per-turn detail view.

### A new request while a turn needs attention

A native Session runs one turn at a time. While its current turn needs attention,
a new request (`POST /api/sessions/{id}/execute` or the WebSocket `session`
command) is refused with `409` or `session-request-rejected`, and nothing starts or
closes. The error names the turn and the two ways out, both through
`POST /api/sessions/{id}/turns/{turn_id}/control-commands`:

- Continue that turn with the message: action `revise`, the exact activation of an
  Agent with an accepted answer, and the message as `instruction`. `continue`
  restarts stopped work without a message.
- Finish it as it is, then send the request again as a new turn: action `finish`
  with a confirmed `partial_finish` built from `turn_controls.partial_finish` in the
  turn's `control-plane`. Only the accepted final answers it selects carry into the
  next turn's conversation; an activation that failed or was interrupted has no
  accepted answer, so its work does not carry forward.

The app offers the same two choices when a message is sent while the turn needs
attention.

### Session network record

`GET /api/sessions/{id}/network` returns the Session's network mode and the events
in its network record. Reading never creates a record: a Session with no network
activity returns an empty list.

```json
{
  "session_id": "ses-…",
  "mode": "bridge",
  "sidecar": null,
  "policies": [],
  "private_destinations": [],
  "record": {"events": 3, "bytes": 412, "max_events": 50000, "full": false, "gaps": 0},
  "events": [
    {"v": 1, "seq": 1, "ts_ms": 1790000000000, "event": {"kind": "sidecar", "state": "ready", "generation": 1}}
  ],
  "next_after": 1
}
```

`mode` is `sandbox.network`. Pass `next_after` back as `after` to read on. Each
event has a `kind`: `policy`, `sidecar`, `bind`, `unbind`, `open`, `close`, `web` or
`limit`. An `open` event names the destination `host` and `port`, its
`conn_kind` (`connect` for a tunnel or `http`), the `decision` (`allow` or `deny`)
with its `reason` and `status`, the addresses used, and the tool call (`binding`)
whose credential it presented. Credentials appear only as 16-hex tags. A `close`
event adds the bytes sent and received and the duration. `record.full` means new
connections are refused; `gaps` counts places where a sequence number was skipped.
Under `network: egress`, `sidecar` reports the egress proxy of the Session's running
runtime (`state` is `starting`, `ready`, `restarting`, `failed` or `stopped`, with its
`generation` and the number of `restarts`), and `policies` lists each scope's compiled
policy: `session` (your `sandbox.egress` list plus this Session's allows),
`provisioning` (the Alpine, Debian and Ubuntu mirrors) and `browser` when the browser
tool is configured. Each rule has an `id`, its `text` and its `source`. Both are empty
under `bridge` and `none`, and while the Session has no running runtime.

### Turn control plane

The `control-plane` endpoint returns `schema_version: 1`, the source
`history_version`, exact Session and turn identities, nodes, activation histories,
and causal evidence. Evidence values carry an explicit `status`: `available`,
`not_recorded`, `unknown`, `missing`, `unavailable`, or `truncated`. A truncated
preview includes its original byte length. Clients must not turn unavailable usage
into zero or missing output into a successful empty answer.

In a native turn, an edge of kind `delegated_by` runs from a lead's node to a helper
node the lead admitted through `delegate`; its `summary` names the helper template and
its `evidence` is the helper's admission grant. It is not a dependency: the lead
waits for the helper inside its own activation, and the helper does not gate it.

Compatibility Session history is identified as `legacy_v1`. Its activation references
retain their recorded generation when available; they do not invent execution
epochs or current Agent definitions. Per-activation Stop, Retry, Guide, and Revise
capabilities are disabled for these historical identities. Reading this endpoint
does not mutate the turn or start execution.

Native `execution_v2` capability entries distinguish an enabled live action from
an optional `requires_revalidation: true` request after restart. A recovery request
keeps `enabled: false`: the read did not attach a runtime or establish authority.
The existing control-command POST reconnects the Session and validates its exact
revision, epoch, repository, grant, and remaining budget before applying it.
Recovered Revise, Continue, and Finish retain their original identities and may
be refused. Failed or interrupted work in a paused epoch is selected through
Continue. Closed turns, superseded conversation history, and isolated Ways do
not offer these cooperative recovery requests.

Native turn history retains `repository_reattachments` with the exact original
and reacquired repository descriptors; these records document host reattachment
without changing original activation inputs or grants, authorizing work, or replaying it.

Captured inline context has its own `reference_id` in the receiving turn. For a
`coordination_reference`, `metadata.reference_id` identifies the original evidence
alongside its exact source Session, turn, epoch, activation, and generation; for a
`ways_decision`, `metadata.decision_id` identifies the retained decision.

A native lead's `delegate` call whose raw return was lost retains a labeled
reconciliation result read from the command that admitted the helper and the
helper's canonical outcome: its accepted answer, or the error for a refused, failed,
or stopped helper. Recovery does not run the helper again or repeat a provider
request. An admitting command left requested or accepted by a crash admitted no
helper; the same reopen records that, and the lead may call `delegate` again.
Ordinary shell/tool effects are not automatically replayed.

For native cooperative turns, `turn_controls.partial_finish` supplies the exact
review for a human partial finish. The existing control-command POST uses
`action: "finish"` and an optional `partial_finish` object containing
`selected_activations`, `stop_activations`, `missing_conditions`, `unrun_nodes`, and
`confirmed: true`. Selected results must be current accepted sinks; the other lists
must match the reviewed state. Stale reviews are refused. Omitting `partial_finish`
retains normal Finish semantics. Partial finish records missing work explicitly and
waits for safe settlement; it does not grant an Agent permission to bypass checks.

A native turn whose team has required checks also carries `required_checks` in its
control plane: for each check, in order, its `argv` and the `state` of its latest run
(`pending`, `passed`, `failed`, `timed_out`, `outcome_unknown`, `unavailable` and so on),
with `exit_code`, `run_id`, `process_status` and bounded `stdout` and `stderr` previews
when recorded. Timeout, interruption, launch failure, no dispatch and a missing outcome
stay distinct, and a successful exit alone is not a readiness verdict. A check whose
record cannot be read is `unavailable` with a `reason`; it does not hide the rest of the
turn. `required_check_readiness` carries that verdict: `state` (`passed`, `failed`,
`not_run`, `skipped` or `unavailable`), a `reason` in words, and the `candidate_sha256`
tree it judged. Its conditions are named `required-check:0` (the capture before),
`required-check:1` to `required-check:n` (the checks), `required-check:n+1` (the capture
after) and `required-check:ready`. Selecting any of them in a Continue request, or
restarting any Agent, reruns both captures, every check and readiness. A check-only
Continue that the paying Agent's budget cannot cover is refused with the reason.

A native turn whose team has a required review carries `required_review` in its control
plane: the `reviewer` template, `state` (`not_run`, `running`, `approved`, `changes`,
`failed`, `skipped` or `unavailable`), a `reason` in words, the `verdict` (`approve`,
`changes` or `unreadable`), bounded `findings`, the `round` and `max_rounds`, `current`
(whether the verdict is about the current result) and the `candidate_sha256` tree the
reviewer was shown. The reviewer is the graph node `required-review` and its verdict the
condition `required-review:verdict`; selecting that condition in a Continue request runs
the reviewer again, and rerun checks or restarted work run it again too.

The directory must already exist when registering a new Workspace. The server has
no configured folder allowlist.

Rewind is blocked during an active turn or unresolved Attempt set and currently
requires an autonomous single-Agent Session. It changes the logical conversation head; it
does not restore files or reverse effects.

## Session files, tasks, Terminal, and Preview

| Method | Path | Request / behavior |
| --- | --- | --- |
| GET | `/api/sessions/{id}/tree?path=…` | Lazy one-level directory listing within Session root |
| GET | `/api/sessions/{id}/file?path=…` | Read one file, capped at 512 KiB |
| POST | `/api/sessions/{id}/file?path=…` | Atomically overwrite existing resolved path with `{content}` |
| GET | `/api/sessions/{id}/tasks` | Background task and terminal state |
| POST | `/api/sessions/{id}/tasks` | `{command, interactive?, rows?, cols?}`; uses or reconstructs the already-Ready sandbox and never prepares an unreviewed environment implicitly |
| GET (WS) | `/api/sessions/{id}/terminals/{tid}/ws` | Raw PTY output as binary; input binary/text; resize JSON |
| Any HTTP method | `/api/sessions/{id}/proxy/{port}` | Legacy response-sandboxed Preview proxy root |
| Any HTTP method | `/api/sessions/{id}/proxy/{port}/{*tail}` | Legacy response-sandboxed Preview proxy path |

File resolution rejects paths outside the canonical Session root. Tree, read,
and write execute through the Ready sandbox: local Podman operates on the
read-write Workspace bind, while E2B operates on its remote clone. There is no
host-filesystem fallback for a failed remote runtime or a container-local
dependency volume. The write endpoint does not create missing parent
directories. Terminal resize is `{"kind":"resize","rows":30,"cols":100}`.

The workbench opens the virtual Preview Host, not the legacy path. The Host
boundary validates the exact Session and logical port, resolves that pair to
the sandbox's dynamically assigned loopback transport, and forwards normal app
HTTP methods, query strings, request bodies, cookies, module/root assets, and
WebSocket upgrades. HTML receives the source-and-origin-pinned picker bridge;
non-HTML bodies stream without whole-response buffering. The upstream app sees
the validated virtual authority while the TCP connection remains loopback.
Sibling Sessions can therefore use the same logical port without sharing a
host port, browser origin, host-only cookies, or control-plane access. Rejection
of a parent-domain cookie such as `Domain=localhost` is browser policy; the
current Chromium journey verifies it, while the proxy forwards application
`Set-Cookie` headers unchanged. Both proxies remove `axocoatl-token-*` cookies
from forwarded requests and drop upstream `Set-Cookie` headers that would set
one. The legacy `/api/sessions/{id}/proxy/{port}` path sits behind API
authentication and never forwards Axocoatl credential headers. Its sandboxed
page has an opaque origin, so its subresource requests carry no SameSite=Strict
cookie; use it with a header credential.

Work in a Session

The durable loop comes first.

Conversation is the Session spine. Files, Terminal, Preview, context, History, tools, and Git open around the same folder-anchored Session.

01 · Ordinary path

One Agent, one repository job

Start with a concrete behavior and repository Check. The Agent diagnoses the defect, edits the implementation, runs the command, and leaves the result for review without committing.

02 · Work units

Workspace, Session, Turn

An authorized Workspace groups named Sessions. Returning to one restores its accepted Turn instead of creating another disposable conversation.

03 · Continuity

Reconnect to the exact Turn

Accepted work does not depend on one browser connection. Reload reconnects to the active Turn, and Stop leaves an honest cancelled state in History.

04 · Execution boundary

Terminal and Preview share the checkout

The Terminal identifies the Session's local Podman sandbox, runs the repository contract, and serves the application opened in Preview through an explicitly published port.

Choose the execution shape

Use more structure only when the work needs it.

A configured team collaborates on one result. Ways produces independent candidate implementations. Git remains the final repository handoff.

05 · Configured team

Architect → reviewer in one Custom Session

The Systems Architect runs first. The Critical Reviewer receives that output and returns a separate decision. This is a dependency-ordered Session, not several Ways.

06 · Optional decision mode

Compare independent Ways

Every Way receives the same task and Check command. While the decision is unresolved, Axocoatl keeps completion states, Outcome, Route, changed files, and Check evidence separate. Judge is optional; Keep selects one result and cleanup ends the candidate record.

07 · Repository ownership

Keep is not commit

Keep returns one checked result to the primary Session checkout. Source Control → Last turn filters the current Git diff to paths attributed to the kept Turn before any optional staging or commit; it is not a frozen per-turn diff.

Inspect the runtime underneath

Configuration and durable machinery support the workbench.

Agents, Skills, MCP servers, and Automations live in Settings. Typed events, approval gates, shared memory, and operator Interrupts remain explicit instead of turning into hidden magic.

08 · Settings

Configure one product

Agents and their provider/model assignments, Skills, MCP servers, and Automations stay in Settings rather than becoming peer destinations beside the Session. Provider endpoints and credentials remain explicit in axocoatl.yaml.

09 · Typed events

A Skill can trigger an Automation

The Skill publishes its declared event. The event lattice carries it to configured observers, and the matching Automation trigger starts an inspectable durable run.

10 · MCP approval

A new permission pauses the call

With no matching saved decision, a normal Session Turn pauses before a deterministic local MCP tool executes. Deny prevents dispatch; Allow once returns bounded tool evidence and the final answer to History.

11 · Shared core memory

Share one block explicitly

One configured Agent writes a named shared block through a visible tool call. After daemon restart, another Agent receives the exact value in a separate Session whose transcript remains distinct.

12 · Operator judgment

Pause and resume an Automation

A top-level Interrupt parks the run with upstream node state intact. Operator guidance resumes from that checkpoint and the completed Result remains in run history.

Provider integration

Use OpenRouter with your agents.

Sign in to OpenRouter in your browser from axocoatl onboard or axocoatl connect openrouter, use OpenRouter credits, and assign eligible text and tool models to the agents that work inside your Sessions.

Install Axocoatl →OpenRouter in onboarding
First run

Configure OpenRouter once.

Run axocoatl onboard and choose OpenRouter. Confirm credit billing with no connected BYOK provider keys: native Sessions do not support BYOK, and refuse to send a call when the configuration declares it. Onboarding then offers to sign you in to OpenRouter in your browser, which stores the key OpenRouter issues in Axocoatl's secret store, never in the configuration, and uses a key you connected with axocoatl connect openrouter without asking. If you enter a key instead, the API-key prompt is masked, and a supplied key is stored with the provider and starting Agent in the current user's owner-only Axocoatl configuration.

Onboarding creates no project folder or repository. After axocoatl dev opens the workbench, choose Open workspace… and select the repository you want to use. Model availability, pricing, routing, and account access remain controlled by OpenRouter.

  1. Connect your account

    Choose OpenRouter during onboarding and confirm its billing mode.

  2. Choose your work

    Open a repository as a Workspace and start a Session.

  3. Review the team

    Choose eligible models and approve their limits in Team & budget.

Use it in the workbench

Choose the model for the job.

Agents are configuration records. Native Sessions accept reviewed local Ollama and eligible OpenRouter-credit profiles. Select the Agent and review its explicit limits in Team & budget before execution; other hosted adapters remain on compatibility paths.

Roles

Different agents, different models

Use a focused model for a narrow builder and a larger model for a coordinator or difficult repository task.

Hybrid

Local and hosted together

Keep one Agent on Ollama and another on OpenRouter. Optional Ways can compare configured agents when the decision merits it.

Cost

Approve the budget

Native Sessions reserve each call against the approved allowance using the retained endpoint’s token and price limits. Missing final usage stays unknown.

Advanced configuration

Keep environment injection explicit.

If you prefer process-environment injection, choose the environment variable when onboarding asks for the key, or manage an explicit YAML configuration. Export OPENROUTER_API_KEY in the process that starts Axocoatl and pass an explicit configuration path when it is not the user default.

Axocoatl does not load dotenv files automatically. Protect environment files, explicit configurations, shell history, and backups as secrets.

advanced axocoatl.yaml
providers:
  openrouter_billing: credits
  openrouter:
    api_key: "${OPENROUTER_API_KEY}"

agents:
  - id: builder
    name: Builder
    provider: openrouter
    model: "${OPENROUTER_MODEL}"
    tools: [read_file, list_dir, grep, glob, write_file, edit_file, bash]
    sampling:
      max_tokens: 2048
Attribution

The client identifies Axocoatl.

Calls to the OpenRouter endpoint include HTTP-Referer: https://axocoatl.ai and an Axocoatl application-title header. These headers identify the calling application. They do not imply a directory listing, rank, partnership, or endorsement.

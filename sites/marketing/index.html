Claude Code, Codex or a local model works in a sandbox its credential never enters. When it says it is done, the host runs your tests on the final files and a different model reviews the change. Every run ends with an exit code for CI and a receipt signed on your computer.

The receipt

Hand the verdict to someone who didn't watch.

When a run finishes, passing or not, the daemon signs a receipt with an Ed25519 key kept in your data directory. A reviewer, a teammate or a CI job can check it later, offline, against the keys they trust.

Printed by axocoatl receipt show, which reads a receipt without verifying it. One line is left out: the network policy of the provisioning scope, which lists the package mirrors the sandbox image may reach while it is set up.

  1. What it holds

    The files the run changed, each with its SHA-256 as the required checks judged them. The sandbox and its network policy. Each check with its command and exit code. The review, with its model, verdict and rounds. The models that wrote and reviewed. The verdict and the exit code.

  2. What it proves, and what it does not

    It proves which key signed which facts and, checked against a checkout, that the checkout has the files the receipt names. It does not prove that the change is correct, that the tests are good tests, or that the review was right. A key copied from your data directory signs as well as yours.

  3. Verify it offline

    axocoatl receipt verify needs no daemon, no Podman and no network. It checks the signature against the key lines you trust (axocoatl receipt key prints this computer's) and, with --repo, every covered file in a checkout. Exit 0 means a trusted key signed it and the files match; 1 not a receipt, or a signature that does not verify; 2 a key you did not give as trusted; 4 a file that differs.

  4. In the pull request and in CI

    --keep pr commits the files the receipt covers to a new branch, with Axocoatl-Run and Axocoatl-Receipt trailers, and opens a pull request whose description carries the receipt. In GitHub Actions, axocoatl/axocoatl/actions/verify-receipt@v1.4.0 reads the trusted keys from the base branch, never the pull request, and fails a receipt signed by a key the base branch does not list, one that does not cover every changed file, and by default one whose run did not pass. With require-receipt: false, as in the docs' example, a pull request without a receipt passes with a notice; by default it fails.

What a receipt holds, field by field, and how to check it in CI →

axocoatl run

The host decides when it is done.

A loadout is a YAML recipe for one run: its Agents (the model-driven workers) and their models, the checks that must pass, the reviewer, the network, the budgets and the prompt. axocoatl run hands one to the running daemon and waits for the verdict.

  1. A sandbox with no direct network

    The daemon creates a Session for the repository (one durable work item: its conversation, the sandbox its tools run in, and its record) and runs its tools in a rootless Podman container as a non-root user. In a loadout run the container has no direct network access: it reaches the outside only through the daemon's egress proxy and routes, which decide and record every connection. By default a route to a model API reads each model call before it leaves, and refuses and records one that asks the provider to fetch a URL, search the web, run a tool itself or connect to an MCP server.

  2. Checks on the final files

    After the writer finishes, the host runs the repository's check command on the exact final files, with a timeout. Whether the tests passed comes from the host, not from the model.

  3. Review by a different model

    A reviewer on the model you name reads the result in a fresh conversation with read-only tools, and approves or asks for changes, for up to 3 rounds. The writer must accept or reject every finding with a reason; a finding left unanswered makes the run need attention. A reviewer on the writer's own model gets a warning, not a refusal.

  4. A verdict CI can read

    Exit code 0 means pass, 1 a check failed, 2 the run needs attention; 3 to 7 cover usage errors, an unreachable daemon, infrastructure, an interrupt, and another run or Session turn holding the repository. --junit writes the checks, review, answers and findings as JUnit. --record writes the whole run as one file that ends with its line count and SHA-256, which axocoatl record verify checks. The record is checksummed, not signed.

  5. A signed receipt

    When the run finishes, passing or not, the daemon signs a receipt of the files it changed and what the host enforced. --receipt writes it. What it holds and who can check it →

  6. Keep as PR

    The changes stay in your working tree, uncommitted. --keep branch commits exactly the run's changed paths to a new branch with your git, with Axocoatl-Run and Axocoatl-Receipt trailers, and refuses a path edited after the checks judged it; --keep pr also pushes that branch and opens a pull request with gh whose description carries the receipt. Your index, current branch and working tree stay as they were.

Five loadouts ship built in.

fix · fix-claude-code · fix-codex

Make a change

One writer, the repository's check command as a required check, and a required review by another model for up to 3 rounds, with every finding answered. fix-claude-code and fix-codex run it with Claude Code or Codex as the writer.

qa

Explore an app

One browser explorer. Each finding names a Playwright reproduction that the host re-runs on the build under test and, if you give one, a clean reference build: confirmed only when it fails on the first and passes on the second.

audit · opt-in

Read a whole codebase

A planner splits the scope into 2 to 8 areas, the host gives every file to one area, read-only workers read their areas in parallel, and an integrator merges the findings. Files nobody read are listed as not covered.

External agents

Claude Code and Codex, inside the sandbox.

The built-in fix-claude-code and fix-codex run fix with the pinned Claude Code CLI or Codex CLI as the writer. It runs inside the Session container as the non-root writer user, not in your shell, and the host runs the same checks and review on what it leaves.

Claude Code needs a Claude Pro or Max plan and the claude CLI on your computer; Codex signs in with your ChatGPT plan. Both run in an image that adds the program to your repository's toolchain: the run detects the language from package.json, pyproject.toml or requirements, go.mod or Cargo.toml, installs the dependencies with only the package registries open for that step, and then the writer works, so the repository's own check, such as npm test, pytest or go test ./..., runs.

Its credential stays on your computer. axocoatl connect claude-code runs claude setup-token and stores the token without showing it; axocoatl connect codex runs codex login in a throwaway container and stores your ChatGPT sign-in. The daemon adds the credential on the host to each model request the route allows, and the container holds a placeholder. Every model call is in the Session's network record, and the program's output is parsed into the Session record.

To change the model, the budgets or the checks, write your own loadout with runtime: claude-code or runtime: codex.

What the receipt rests on

Mechanisms, not promises.

A receipt is worth what the host enforces whatever the model says: where tools run, who may write, which checks must pass, what a run may spend, and what gets recorded.

Isolation built in

Tools run in a sandbox

Every Session's repository tools run in a rootless Podman container; the web and MCP tools run on the host. Read-only helpers get no file-writing tools, and the kernel blocks their shell from writing, creating, renaming or deleting repository files and from opening TCP connections (Landlock, Linux 6.7 or later); otherwise they get no shell. Loadout runs have no direct network access. Interactive Sessions use Podman's bridge network by default; set network: none for repositories you don't trust.

A complete record

The host decides, and keeps it

Required checks run on the exact final files, by the host, not the model. A required review runs a read-only reviewer the host starts. Budgets you approve are charged with what each call actually used and carry across restarts. Every model call, tool call, budget decision and check stays in the Session, and every axocoatl run that finishes gets a receipt signed on your computer.

Any model, per Agent

Local or hosted

Each Agent has its own provider and model: local models through Ollama, hosted models through OpenRouter, with budgets enforced on both, or the Claude Code or Codex CLI as a loadout's writer. A provider call that fails transiently, or a stream that ends early, is retried once, and a request that would overflow the context is trimmed instead of failing.

A different reviewer helped.

# Team & budget → Required review → Reviewer
Cross-model review

A local writer. A different reviewer.

Headless, axocoatl run fix takes the reviewer's model as --model reviewer=…. In the browser workbench, give a reviewer template a different model, on the same machine or through OpenRouter, and make it the team's required reviewer. After the lead finishes and your checks pass, the host starts the reviewer in a fresh conversation on the exact result. Requested changes go back to the lead; the turn completes only when the reviewer approves.

The reviewer measured above was gpt-oss 120B, running locally. gpt-oss:20b, the reviewer that fits a 48 GB Mac, has not been measured, and neither have reviewers through OpenRouter.

Reviewers raise false alarms too, so the fix writer answers each finding with accept or reject and a reason instead of changing code for every one.

In the browser workbench

The lead writes. Everything else reads.

The same daemon serves a workbench in your browser for work you want to watch. A new Session starts with one Agent, the lead, under limits you approve in Team & budget. You can let it delegate to read-only helpers: Scout answers questions about the code, Reviewer reviews a change. Each helper starts in an empty conversation and hands one answer back. Helpers cost extra tokens; one Agent is the cheaper choice for small tasks.

Add required checks and the host runs them after the Agents finish, between two captures of the repository. Add a required review and the host runs a read-only reviewer on the result for a bounded number of rounds. The turn completes only when both pass on the exact final tree.

One durable work surface

The record sits beside the repository.

Each Session keeps its conversation, its Turns (one accepted request each), Agent activity and budget decisions, while Files, Terminal, Preview, and Source Control show the repository as it is now.

Turn

Accept first

Each Turn records its request and context before the Agent starts. Output, tool evidence, failure, cancellation, and interruption remain attached to the Session.

History

Search and export

Completed, failed, stopped and interrupted work stays in the Session's History. Search it, or export a Session as Markdown or JSON.

Git

Review the change

Filter Source Control to the latest attributed Turn, inspect paths and hunks, then stage and commit when the result holds up. Axocoatl does not commit for you.

Your machine or your infrastructure

One executable. Your browser.

Install one axocoatl executable. It starts the local Rust daemon, which runs axocoatl run and serves the workbench to the browser you already use; the workbench assets are embedded. Podman is the local sandbox requirement; axocoatl onboard sets it up, asking first. Docker is not supported; Podman can run alongside it. Run it on a laptop, or as a service on a machine you control.

Configure Axocoatl once for the current OS user; onboarding creates no project. Hosted providers, integrations, downloads, and E2B Cloud are explicit network paths, and the first daemon start downloads an 87 MB embedding model from huggingface.co. Local-first is the default, not an offline guarantee.

Run it on a real repository.

Install Axocoatl, pick a writer and a different reviewer, let the host's checks decide when the work is done, and keep the receipt.

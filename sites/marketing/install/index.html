Install

Run it on your hardware.

Install the prebuilt release on macOS 11 or newer, on GNU/Linux with glibc 2.35 or newer, or inside WSL2 on Windows (not yet verified). Then axocoatl onboard sets up a writer and a reviewer, and asks before each download or change. Headless runs and native Sessions use Podman as their sandbox. Onboarding installs Podman with Homebrew on an Apple-silicon Mac, or with apt, dnf, pacman or zypper on Linux. On an Apple-silicon Mac without Homebrew it points to the podman.io installer, on an Intel Mac to the Podman 5.8 package, and on another Linux it says what to install; it refuses Ubuntu 22.04 and older. On a Mac it then creates and starts the Podman machine.

Recommended

Install the latest release.

The installer detects macOS or GNU/Linux on x86_64 or ARM64, downloads the matching GitHub release, and requires and verifies its published SHA-256 file. Before download it requires Linux to report glibc 2.35 or newer and macOS to report version 11 or newer.

curl -fsSL https://axocoatl.ai/install.sh | sh

Run it in Terminal on macOS, in a Linux shell, or inside WSL2 on Windows, not in PowerShell. It installs to /usr/local/bin when that is writable, else to ~/.local/bin; when that directory is not on your PATH, it asks before adding one line to the startup files your shell reads in a new terminal and a new login, and prints the line instead when it cannot ask. Review the installer, the released one this command runs, before piping it to a shell.

What the 1.5.0 release gate requires
  • From this install command to passing runs on a Mac on Apple silicon, with a person answering onboarding, on an account that starts without Axocoatl, its data or stored credentials, Podman or Ollama: onboarding installs Podman and Ollama with Homebrew and sets up local models, then signs in Claude Code, Codex and OpenRouter in the browser
  • On Linux, on an account that starts without Axocoatl, its data or stored credentials, or Podman (the gate's instructions make a new user with adduser in a new Ubuntu 24.04 VM): onboarding installs Podman with apt and connects OpenRouter through its browser sign-in for the models the runs use; in CI, on Ubuntu 24.04 on x86_64 and arm64, onboarding with no terminal against a scripted model server
  • fix passes on Node.js, Python, Rust and Go repositories on each; fix-claude-code and fix-codex on Node.js and Python; the Always-On Service and the workbench in Safari on the Mac; every receipt verified
  • No release until the signed evidence shows each path; only a logged override by a listed maintainer gets past it
What is not yet verified
  • Intel Macs
  • Ubuntu 22.04, Debian 12 and Fedora with SELinux
  • WSL2 on Windows
  • Local models on memory other than the gate Mac's: the gate checks neither that Mac's memory nor which models onboarding chose there; its evidence names both
Before you start

What it needs, and what it downloads.

The built-in fix, fix-claude-code and fix-codex loadouts require a writer, a repository check and a read-only reviewer. Onboarding sets up a writer and a different reviewer as their defaults. qa uses one browser explorer; audit uses a planner, read-only workers and an integrator, without a required reviewer.

Requirements
  • Rootless Podman for headless runs and native Sessions. On a Mac it runs in a Linux virtual machine. Onboarding asks before installing Podman with Homebrew on Apple silicon or with a package manager it knows on Linux, and otherwise names the installer; it asks before creating the machine. Docker is not supported; Podman can run alongside it.
  • A writer: Claude Code (a Claude Pro or Max plan, and the claude CLI on this computer), Codex (signed in with your ChatGPT plan), a local model through Ollama, or an eligible hosted model paid with OpenRouter credits
  • A reviewer: a local model through Ollama 0.40.6 or a later 0.x release (GGUF models; a release newer than the audited 0.40 line serves a model only after the contract probes pass for it), or a hosted one paid with OpenRouter credits
  • For --keep pr: git, the gh CLI signed in, and a GitHub remote

Loadout receipts mark accepted Ollama releases newer than the audited 0.40 line as unaudited. Dashboard-turn receipts do not retain runtime versions.

Memory for local models
  • Models already on your Ollama server come first: when they include a pair that fits this computer, onboarding suggests those
  • Otherwise, 48 to 95 GB: onboarding offers the local pair, qwen3-coder:30b writing and gpt-oss:20b reviewing; a fix run calls the reviewer only after the writer and the checks finish. How well gpt-oss:20b reviews has not been measured
  • Otherwise, less than 48 GB: onboarding has no default local pair, and first offers OpenRouter for the reviewer or both, or Claude Code or Codex as the writer
  • gpt-oss:120b, the reviewer we measured, needs about 96 GB of memory or more
  • The 1.5.0 release gate requires runs with the local models onboarding sets up on its Mac to pass. It checks neither that Mac's memory nor which models onboarding chose there; its evidence names both
What gets downloaded
  • The Podman machine image on a Mac: about 0.9 GB
  • The Claude Code image: about 0.6 to 0.9 GB; the Codex image: about 0.8 to 1.2 GB
  • Local models: qwen3-coder:30b 18.6 GB, gpt-oss:20b 13.8 GB (gpt-oss:120b 65.4 GB)
  • The first daemon start downloads an 87 MB embedding model from huggingface.co
  • A run's sandbox pulls its base image and packages the first time

First run

Configure Axocoatl, then open your work.

onboard sets up Axocoatl once for the current OS user: Podman and its machine where it can install them (otherwise it says what to install), the writer (Claude Code or Codex signed in through your browser, a local model, or an eligible OpenRouter model), and a reviewer. It asks before each download or change, and writes the user configuration and data location; it does not create a project folder, Workspace, Session, or repository. doctor checks the sandbox, the models, the writers and the daemon and reports the exact fix for each failure. --start none returns to the shell after setup; an optional sample fix stops its temporary daemon afterwards. Resolve any doctor failures, then run dev and leave that first terminal open. It starts the daemon, IPC server and browser app. Open the sign-in link it prints, or run axocoatl url in a second terminal. If a daemon or Always-On Service already runs with this configuration, use it instead; after changing configuration, restart it as the onboarding reference describes.

In the local app, choose Open workspace… to authorize the repository you want to use (a Workspace is a repository folder you named and authorized), then create a Session, one durable work item with its conversation and record. Review its proposed runtime and setup command before anything in the repository runs. Before the first native turn, open Team & budget, set the limits and expiry, and Apply.

Headless

Run a loadout from your shell.

A loadout is a YAML recipe for one run: its Agents, models, checks or review, network, budgets and prompt. axocoatl run hands one to a running daemon (axocoatl dev or the service) and never starts one. It prints a summary and can write JUnit, a record bundle and the run's signed receipt. Its exit code gives a script the outcome: 0 pass, 1 a check failed, 2 needs attention. A refusal before admission has no run receipt; a signing failure is recorded without changing the run verdict. Verify the receipt separately when you require one.

The built-in fix loadout runs one writer, your repository's check command and a required review. Onboarding requires different models. A same-model pair inherited from setup is refused; explicitly choosing both models permits it with a warning. With a local or OpenRouter writer it uses the writer and reviewer onboarding set up; with Claude Code or Codex as the writer, run fix-claude-code or fix-codex instead, with the same flags (below). --model writer=… or --model reviewer=… chooses others for one run.

The run detects the repository's language from package.json, pyproject.toml or requirements*.txt, go.mod or Cargo.toml, runs in that language's official image, and installs the dependencies, such as npm ci or pip install -e '.[test]', with only that ecosystem's package registries open for that step; then the writer works, and the host runs the check, such as npm test, pytest or go test ./.... Repository toolchains →

Use the second terminal while the daemon stays running. Replace the repository path and task, start from a clean checkout or disposable copy, and run its tests first. The evidence directory stays outside the repository. Keep this terminal open to retain its variables, and copy the evidence elsewhere if you need it after temporary files are cleared. --require-pass requires a passing verdict as well as a valid receipt; read the diff before committing.

Claude Code or Codex

Put an external agent in the sandbox.

The built-in fix-claude-code and fix-codex run fix with the Claude Code CLI or the Codex CLI as the writer. It runs inside the Session container as a non-root user; its credential stays on your computer, and the daemon adds it on the host to each model request the route allows. Claude Code needs a Claude Pro or Max plan and the claude CLI on this computer; Codex signs in with your ChatGPT plan. Both run in an image that adds the program to your repository's toolchain, with the dependencies installed first, so the repository's own check, such as npm test, pytest or go test ./..., runs as it does for fix.

  1. Set it up with onboarding

    Run axocoatl onboard --start none and choose Claude Code or Codex as the writer. It builds the program's Session image with Podman, signs you in through your browser, and sets up a reviewer. Claude Code's token is captured through a terminal filter. An uncertain credential redraw is refused with nothing stored. To do the same by hand: axocoatl recipe build claude-code and axocoatl connect claude-code (it runs claude setup-token), or axocoatl recipe build codex and axocoatl connect codex (your ChatGPT sign-in, in a browser).

  2. Leave the daemon running

    Run axocoatl doctor and resolve any failures, then run axocoatl dev in the first terminal and leave it open. Use an existing daemon if it already has this configuration; restart it after changing setup, as onboarding describes.

  3. Run one command in the second terminal

    From your repository, choose the command for your writer. Add the evidence flags and verification from the headless example.

    axocoatl run fix-claude-code --task "Paging skips the last item"
axocoatl run fix-codex --task "Paging skips the last item"

    The host runs the checks and the review on what the program leaves, as for any writer. The review uses the reviewer onboarding set up; --model reviewer=… names another. The run says which stored credential it sent.

  4. Or write your own loadout

    To change the model, the budgets or the checks, save a loadout with runtime: claude-code or runtime: codex in the loadouts directory beside your configuration: ~/Library/Application Support/Axocoatl/loadouts/ on macOS, ~/.config/axocoatl/loadouts/ on Linux. The docs have one to copy.

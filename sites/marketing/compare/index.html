What runs around the agent.

Claude Code and Codex are coding agents. Axocoatl is a harness around one: it runs them, or its own Agents on a model you choose, and leaves to the host the decisions a model should not make about its own work. This page compares mechanisms. It makes no claim about the quality of results; nothing here measured that.

Questions to ask of any setup

The questions, answered for Axocoatl.

Each answer describes a loadout run (axocoatl run, Axocoatl 1.3) and links to where the documentation states it. A loadout is a YAML recipe for one run. Ask the same questions of whatever you use now.

Who runs the checks, and on which files?
The host. After the writer finishes, Axocoatl runs the loadout's required checks (for fix, the repository's check command) on the exact final files, each with a timeout. A check that did not run makes the run need attention; it never counts as a pass. Fix, QA and audit runs →
Does a different model review the change?
With fix, a reviewer on the model you name reads the result in a fresh conversation with read-only tools and approves or asks for changes, for up to 3 rounds. The writer must accept or reject every finding with a reason, and an unanswered finding makes the run need attention. A reviewer on the writer's own model is warned about, not refused. Cross-model review →
Where does the model credential live?
On your computer. For Axocoatl's own Agents the daemon makes the model calls, and provider keys are not passed into the container. For the Claude Code and Codex CLIs, the daemon adds the stored credential on the host to each request the route allows, and the container holds a placeholder. A token that an API returns in a response body would still reach the container. External agents →
What can the agent reach on the network?
In a loadout run, the Session container has no direct network access: it reaches the outside only through the daemon's egress proxy and routes, which decide and record every connection. By default a route to a model API reads each model call before it leaves, and refuses and records one that asks the provider to fetch a URL, search the web, run a tool itself or connect to an MCP server. Interactive Sessions in the browser workbench use Podman's bridge network by default. Security boundary →
Where does the agent run?
In a rootless Podman container, as a non-root user, through Axocoatl's hardened in-sandbox supervisor: the writer's tools, the required checks and an external CLI alike. The repository is a read-write bind inside that container. Axocoatl's own Agents' tool calls are reserved against their grant before they run; an external CLI's own tool calls are recorded, not admitted one by one.
What is recorded, and can you check it later?
Every model call, tool call, budget decision, check and network event of the run's Session. --record writes the whole run as one JSON Lines file that ends with its line count and SHA-256, and axocoatl record verify checks both. The record is checksummed, not signed. axocoatl run →
What does CI get?
An exit code: 0 pass, 1 a check failed, 2 needs attention, 3 usage, 4 daemon unavailable, 5 infrastructure, 6 interrupted, 7 busy. With --junit, a JUnit file of the checks, the review, the writer's answers, the findings and what was not covered.
What happens to the changes?
They stay in your working tree, uncommitted. --keep branch commits exactly the run's changed paths to a new branch with your git and a temporary index; --keep pr also pushes that branch and opens a pull request with gh. Your index, current branch and working tree are not changed. Keep as PR →
What can it spend?
Each Agent runs under a budget. A call from Axocoatl's own Agents is reserved against it before it runs and charged with what the provider reported. An external CLI's activation reserves what its grant allows before the program starts, and the host stops the program when its request count runs out: that bounds the activation, not each call.
Three setups

Where Axocoatl differs.

Each card states what Axocoatl does. For what another tool does, read its own documentation.

Claude Code or Codex, directly

Same program, other surroundings

Axocoatl runs the same CLI, pinned by its recipe, as a loadout's writer. What changes is around it: the program runs in the Session container instead of your shell, its credential is added on the host, and the host, not the program, runs the checks and the review and decides the exit code. Their documentation: Claude Code, Codex.

An agent in a devcontainer

A container is one part

A devcontainer gives the agent a container to work in. Questions that remain: is the model credential inside the container the agent controls, who runs the tests and on which files, does another model review the change, and what record is left once the container is gone? The Dev Container specification describes the container.

Parallel-agent workbenches

One writer by default

Running several agents side by side is one way to get more answers. Axocoatl's built-in loadouts run one writer (fix) or one explorer (qa); audit, with parallel read-only workers, runs only when you name it. In the browser workbench, Explore several ways compares attempts in separate checkouts and keeps one. Either way, ask which result reaches your branch, and who checked it.

Where it stops

What Axocoatl does not do.

  • It does not judge quality for you. A check and a reviewer decide pass or attention, and a reviewer can raise false alarms; the writer's answers are recorded so you can see which ones it rejected.
  • It warns about a reviewer on the writer's own model; it does not refuse one.
  • Its record is checksummed, not signed.
  • It is not a sandbox runtime. Interactive Sessions use bridge networking by default, and a token an API returns in a response body reaches the container.
  • The built-in loadouts of 1.3 have not been measured. What was measured, and how →

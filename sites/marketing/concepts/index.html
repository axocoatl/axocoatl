How it works

The Session is the spine.

Conversation, context, files, Terminal, Preview, tools, History, and Git review belong to one folder-anchored unit of work. Runtime machinery stays underneath it.

One work surface

Start with the work.

Configure Axocoatl once for the current OS user, run axocoatl dev, and open the loopback workbench in your browser. Onboarding creates no project. Choose Open workspace… to authorize a repository, then create or resume a Session and ask normally.

The request is accepted into a durable Session ledger before execution begins. Conversation is the resting canvas. Files and Source Control, Preview, comparison, and the agent graph open as focused tools. Ways opens only when several attempts need configuration or review. Terminal stays in its bottom dock.

  1. Workspace

    An authorized project directory that groups Sessions.

  2. Session

    Persistent work and conversation anchored to that directory.

  3. Turn

    A durable request, context snapshot, execution facts, output, and final lifecycle state.

A normal turn

Accept first. Execute second.

Attach a file for Once or keep it selected for the Session. Axocoatl records the request and immutable context snapshot before the agent begins, so the visible conversation does not depend on a streaming connection staying open.

Stop addresses the exact active turn. Completed, failed, cancelled, and interrupted work remains reachable in History. Review the result against the repository and inspect Last turn through Git.

The surrounding workbench

Open tools around the conversation.

The Session remains the resting canvas. Supporting surfaces take focus when the job needs them and return you to the same conversation.

Continuity

Context and History

Attach bounded context to one turn or the Session, then search or export the durable conversation. Native turns retain exact generation controls; legacy single-Agent history supports rewind at a turn boundary.

Detection is not consent: before repository tools become Ready, Axocoatl shows the proposed runtime image and exact setup command for review. An unchecked detected command does not run merely because it was found.

Execution shapes

Use the structure the work needs.

Axocoatl starts with one Agent in one Session. A configured team and several Ways are explicit alternatives for different kinds of work.

Default

One Agent

One configured Agent works through the repository and conversation. Repository file and shell execution runs inside the Session sandbox; integrations retain their explicitly configured boundaries. Watch ordinary repository work →

Autonomous team

Coordination map

Exact named dependencies activate each role. Agents receive only the handoffs that caused them to run, and the causal map stays with the Session turn. Native Coordinators create Workers from approved templates and limits, with their parent ownership recorded in the same turn. Watch the handoff →

Decision mode

Ways

Independent attempts start from the same task and repository state, then run in separate working copies and sandboxes. Watch the comparison →

The structures are different. An autonomous multi-Agent turn-scoped lattice coordinates cooperating roles inside one Session and leaves a durable map. A native Coordinator creates scoped Worker activations within that recorded turn. Ways isolate competing implementations. The process-wide event lattice carries typed notifications. An Automation graph executes durable work outside the canonical Session transcript.

Optional decision mode

Explore several ways when needed.

The normal path uses the Agent or configured team that fits the work. When implementation choices deserve independent evidence, the Session can own several isolated attempts without turning them into separate chats.

  1. Start from the same state

    Every way receives the same task and repository snapshot, plus the same provider-safe projection of prior Session context. Native provider tool transactions stay in canonical History rather than being replayed into a different model. Choose a different configured agent, provider, or model for each one.

  2. Run in isolated working copies

    Each way gets an independent no-hardlinks clone mounted as the sole workspace in a fresh rootless Podman container.

  3. Check and compare

    Keep every attempt's completion state visible, run the repository Check command, then compare Outcome, Route, changed files, usage, known cost, and optional Judge ranking.

  4. Keep one, then review Git

    A passing, non-empty result can return to the Session checkout. Keep does not merge or commit; Last turn remains available for deliberate review.

Current boundary: Explore several ways requires a single autonomous-Agent Session using the local Podman backend; coordinator and worker roles stay on the normal Session path. Each way uses its configured primary provider/model directly so retained identity and cost stay accurate. Session attachments are not yet passed to attempts. MCP tools, Skills, and web search are withheld until their external effects have set-scoped rollback semantics.

Agents and tools

Configuration stays in Settings.

Runtime capabilities extend Session work. They do not become a second app or a row of peer destinations.

Agents

Choose the execution shape

Run one configured Agent or a multi-agent Session, with local or remote model providers assigned to the roles that handle the work.

Extensions

Add Skills and MCP servers

Connect MCP tools for normal Session work. Publish typed Skills as events that can reach configured observers or trigger Automations.

Automation

Configure repeatable work

Create, run, and review durable Automation graphs and their run history in Settings, separate from the canonical Session transcript.

Typed events

The event lattice carries typed events.

A Skill publishes the event types declared in its configuration. The event lattice delivers each notification to configured observers and a bounded recent-events view, while the Automation dispatcher evaluates triggers against the same typed feed.

The event lattice is transport, not an Agent graph, a set of Ways, or an Automation graph. The matching Automation remains an explicit durable workflow with its own run history.

  1. Fire the Skill

    The configured Skill publishes its declared event with producer and payload.

  2. Match the trigger

    An On Skill or On Event trigger selects the Automation that should react.

  3. Inspect the run

    The resulting Automation and node state remain reachable in run history.

External tools

New MCP permissions wait for approval.

A compatibility Session Agent can discover a configured MCP tool, but discovery is not permission. A call with no matching saved decision pauses the exact Session Turn before dispatch; a saved allow or deny decision is applied without prompting again.

After an allowed call, the returned value, bounded tool evidence, and final answer remain together on the durable Turn. This film uses a deterministic local MCP server and compatibility execution. Native Session turns do not currently expose this configured MCP registry.

Workspace knowledge

Remember the decision and its source.

Native Sessions share accepted Markdown knowledge inside their Workspace. Notes retain versions, source hashes, typed links, and origin. The Knowledge inspector offers editing, proposal review, backlinks, a code index, and a graph linking notes to source and execution evidence.

Agents can retrieve relevant notes and propose revisions. Automatic publication requires accepted work; an isolated Way also requires its retained Keep selection. A concurrent edit produces a conflict. A saved interpretation remains something to check against its sources.

Inspect and maintain knowledge →

  1. Record what matters

    Keep a decision, convention, finding, or pitfall with its source references and links to other notes.

  2. Recheck changed evidence

    Refresh the observed source index. Rust, JavaScript, TypeScript, TSX, and Python definitions and import syntax help locate relevant code; this is not a complete call graph.

  3. Use it in the next Session

    Attach the selected revision or prepare an investigation in chat. Knowledge is Workspace-owned, while each Session keeps its own conversation and execution history.

Runtime underneath

Durable where durability matters.

Actors

Supervised execution

Configured agents run as actors inside one Rust daemon. The daemon owns providers, tools, events, and sandbox lifecycle.

History

Canonical Session ledger

Accepted turns, bounded tool evidence, output, failure, cancellation, and interruption remain in canonical History across reconnects. After a daemon restart, interrupted work remains visible. Native work requires explicit continuation; it is not silently replayed.

Isolation

Your sandbox choice

Rootless Podman is local by default. E2B Cloud is an explicit remote option for compatibility execution; native repository tools currently require Podman.

Workspace knowledge

Keep a decision across Sessions.

Save a note with its source hash and a typed link to another note. After restart, a separate Session can retrieve the same accepted revision through the native knowledge tool. The two conversations remain separate.

Backlinks make the relationship discoverable. Source context remains something to recheck: retaining a note does not make every interpretation current or correct.

  1. Record the source

    Write a note with the relevant repository path and observed hash.

  2. Connect the decision

    Add a typed link and inspect the resulting backlink.

  3. Reuse the exact revision

    Restart and open another Session in the Workspace. Its native Agent can retrieve the saved note with its origin.

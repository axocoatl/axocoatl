How it works

What the host enforces.

Axocoatl runs coding agents on your own machine or infrastructure. Trust rests on things the host does whatever the model says: where tools run, who may write, which checks must pass, what a run may spend, what gets recorded, and which model each Agent uses. This page states each one and where it stops.

Isolation built in

Tools run in a sandbox. Helpers cannot write.

Every Session's repository tools run in a rootless Podman container with no-new-privileges and dropped capabilities; E2B Cloud is an explicit remote option on the compatibility path. Model provider API keys stay in the daemon and are not passed into the container. Network access is on by default; set network: none for repositories you don't trust.

An Agent with writes: [] is a read-only helper. It is not offered write_file or edit_file, and its shell runs under Linux Landlock (Linux 6.7 or later), which refuses writing, creating, renaming or deleting repository files and opening TCP connections. Landlock does not cover permission bits or timestamps, which a shell that runs as root, or any on macOS, can still change. Where Landlock cannot be applied, its shell does not run.

Several Agents can share one checkout with their own write scopes. File tools refuse paths outside an Agent's scope before writing. After it finishes, Axocoatl compares complete, digest-verified snapshots of the repository from before and after its work; a change outside its paths fails that work and is kept for review. For an Agent with a shell, that check is review evidence, not confinement.

Where it stops: Axocoatl is not a sandbox runtime. Sandbox runtimes control what a process can reach: files, network destinations, and credentials. The Workspace is a read-write bind inside the container, files in it are visible to tools, and network: none does not stop the daemon itself from calling providers or MCP servers. Any model, per Agent

Pick the model for the job.

Each Agent template names its own provider and model. Native Sessions, with approved budgets, run local models through Ollama and hosted models through OpenRouter; Anthropic, OpenAI, Gemini and Mistral adapters remain on the compatibility path. A writer and its required reviewer can therefore use different models.

In a pre-registered benchmark (6 Python tasks, 25 withheld tests, local qwen3-coder 30B writer, one run per task, temperature 0), one Axocoatl Agent passed 17 of 25 tests. With a Required review by a stronger local model, gpt-oss 120B, the same writer passed 19 of 25 at 2.6× the tokens; the reviewer reported 15 defects and 14 were real. More looks by the same model added nothing: a fresh same-model reviewer approved every change, including three with real defects.

The measured reviewer ran locally. A reviewer through OpenRouter is configured the same way but has not been measured.

Start with the work.

Configure Axocoatl once for the current OS user, run axocoatl dev, and open the loopback workbench in your browser. Onboarding creates no project. Choose Open workspace… to authorize a repository, then create or resume a Session and ask normally.

A complete record

The host decides when a turn is done.

Required checks are commands Axocoatl runs in the Session's repository after the Agents finish, each between two captures of the repository. A required review runs a read-only reviewer in a fresh conversation, for 1 to 3 rounds; requested changes go back to the lead. The turn completes only when every check passes and the reviewer approves the exact final tree. Both are off until you add them in Team & budget.

Each Agent's writes list names the paths it may change. Read-only helpers get no file-writing tools, and their shell runs under Linux Landlock, which refuses writing, creating, renaming or deleting repository files and opening TCP connections, where Linux 6.7 or later allows it; otherwise they get no shell. A path-scoped writer's file tools refuse other paths, and every change it made is checked after it finishes. For a writer with a shell, that check is review evidence, not confinement.

Every Agent runs under a grant with the limits you approved. Each provider and tool call is reserved against it before it runs; once the provider reports what a call used, only that stays charged. Grants and budgets carry across restarts. The Session durably records every model call, tool call, budget decision and check.

Optional decision mode

Explore several ways when needed.

The normal path is the lead and its helpers, or one Agent. When implementation choices deserve independent evidence, the Session can own several isolated attempts without turning them into separate chats.

  1. Start from the same state

    Every way receives the same task and repository snapshot, plus the same provider-safe projection of prior Session context. Native provider tool transactions stay in canonical History rather than being replayed into a different model. Choose a different configured agent, provider, or model for each one.

  2. Run in isolated working copies

    Each way gets an independent no-hardlinks clone mounted as the sole workspace in a fresh rootless Podman container.

  3. Check and compare

    Keep every attempt's completion state visible, run the repository Check command, then compare Outcome, Route, changed files, usage, known cost, and optional Judge ranking.

  4. Keep one, then review Git

    A passing, non-empty result can return to the Session checkout. Keep does not merge or commit; Last turn remains available for deliberate review.

Current boundary: Explore several ways requires a single autonomous-Agent Session using the local Podman backend; coordinator and worker roles stay on the normal Session path. Each way uses its configured primary provider/model directly so retained identity and cost stay accurate. Session attachments are not yet passed to attempts. MCP tools, Skills, and web search are withheld until their external effects have set-scoped rollback semantics.

Typed events

The event feed carries typed events.

A Skill publishes the event types declared in its configuration. The event feed delivers each notification to configured observers and a bounded recent-events view, while the Automation dispatcher evaluates triggers against the same feed.

The event feed is transport, not an Agent graph, a set of Ways, or an Automation graph. The matching Automation remains an explicit durable workflow with its own run history.

  1. Fire the Skill

    The configured Skill publishes its declared event with producer and payload.

  2. Match the trigger

    An On Skill or On Event trigger selects the Automation that should react.

  3. Inspect the run

    The resulting Automation and node state remain reachable in run history.

External tools

New MCP permissions wait for approval.

A compatibility Session Agent can discover a configured MCP tool, but discovery is not permission. A call with no matching saved decision pauses the exact Session Turn before dispatch; a saved allow or deny decision is applied without prompting again.

After an allowed call, the returned value, bounded tool evidence, and final answer remain together on the durable Turn. This film uses a deterministic local MCP server and compatibility execution. Native Session turns do not currently expose this configured MCP registry.

Workspace knowledge

Remember the decision and its source.

Native Sessions share accepted Markdown knowledge inside their Workspace. Notes retain versions, source hashes, typed links, and origin. The Knowledge inspector offers editing, proposal review, backlinks, a code index, and a graph linking notes to source and execution evidence.

Agents can retrieve relevant notes and propose revisions. Automatic publication requires accepted work; an isolated Way also requires its retained Keep selection. A concurrent edit produces a conflict. A saved interpretation remains something to check against its sources.

Inspect and maintain knowledge →

  1. Record what matters

    Keep a decision, convention, finding, or pitfall with its source references and links to other notes.

  2. Recheck changed evidence

    Refresh the observed source index. Rust, JavaScript, TypeScript, TSX, and Python definitions and import syntax help locate relevant code; this is not a complete call graph.

  3. Use it in the next Session

    Attach the selected revision or prepare an investigation in chat. Knowledge is Workspace-owned, while each Session keeps its own conversation and execution history.

Runtime underneath

Durable where durability matters.

Native execution handles provider failures and short context windows: a transient provider error or an Ollama stream that ends early is retried once, older tool output is replaced by a short placeholder in later requests, a request that would overflow the context window is trimmed instead of failing, and what still fails is recorded.

Actors

Supervised execution

Configured agents run as actors inside one Rust daemon. The daemon owns providers, tools, events, and sandbox lifecycle.

History

Canonical Session ledger

Accepted turns, bounded tool evidence, output, failure, cancellation, and interruption remain in canonical History across reconnects. After a daemon restart, interrupted work remains visible. Native work requires explicit continuation; it is not silently replayed.

Isolation

Your sandbox choice

Tools run in a rootless Podman container. Network access is on by default; set network: none for repositories you don't trust. E2B Cloud is an explicit remote option for compatibility execution; native repository tools currently require Podman.

Workspace knowledge

Keep a decision across Sessions.

Save a note with its source hash and a typed link to another note. After restart, a separate Session can retrieve the same accepted revision through the native knowledge tool. The two conversations remain separate.

Backlinks make the relationship discoverable. Source context remains something to recheck: retaining a note does not make every interpretation current or correct.

  1. Record the source

    Write a note with the relevant repository path and observed hash.

  2. Connect the decision

    Add a typed link and inspect the resulting backlink.

  3. Reuse the exact revision

    Restart and open another Session in the Workspace. Its native Agent can retrieve the saved note with its origin.

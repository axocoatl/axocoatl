Why Axocoatl

An agent’s “done” is not evidence.

Agents now write more code than the people around them can read. When one says it is done, that is a claim about its own work. Axocoatl has the host decide when the work is done, then hands you a receipt that someone who didn't watch can check.

The problem

Grading its own work added nothing.

The obvious fix is to ask the agent to check itself. In our benchmark that did not help.

An Agent that reviewed its own work passed 17 of 25 withheld tests, the same as one pass, at 3.5 times the tokens. A fresh reviewer on the same model also passed 17, and approved every change, including three with real defects. A stronger, different reviewer took the same writer to 19 of 25, at 2.6 times the tokens.

Measured on small local models: a qwen3-coder 30B writer and a gpt-oss 120B reviewer, 6 Python maintenance tasks frozen in advance, 25 withheld tests the agents never saw, one run per task at temperature 0. One pass and the different reviewer ran through Axocoatl 1.1.0; the two same-model reviews ran in a plain agent loop, without Axocoatl. It is one small benchmark, not a claim that Axocoatl makes agents better. The reviewer ran locally; reviewers through OpenRouter have not been measured.

So the host decides

The host decides, not the agent.

Axocoatl takes the decisions a model should not make about its own work and gives them to the host: the computer that runs the Axocoatl daemon.

  • The agent, Claude Code, Codex or a model you choose, works in a rootless Podman container as a non-root user. Its model credential stays outside: the daemon makes the model calls for its own Agents, and adds the credential on the host to each request it allows for Claude Code or Codex, so the container holds a placeholder.
  • In a headless run the container has no direct network access. It reaches the outside only through the daemon's egress proxy, which decides and records every connection.
  • When the agent says it is done, the host runs your checks on the exact final files, with a timeout. A check that did not run never counts as a pass.
  • A different model then reviews the result in a fresh conversation with read-only tools, for up to 3 rounds. The writer must accept or reject every finding with a reason; a finding left unanswered makes the run need attention. A reviewer on the writer's own model gets a warning, not a refusal.
  • The run ends with an exit code CI can read: 0 pass, 1 a check failed, 2 needs attention.

Then it hands you a receipt

Evidence someone else can check.

When the run finishes, passing or not, the daemon signs a receipt with a key kept on your computer. It lists the files the run changed, each with its SHA-256 as the checks judged it, and the sandbox and network policy, the checks, the review, the models and the verdict.

  • Keep as PR commits those files to a new branch, with Axocoatl-Run and Axocoatl-Receipt trailers, and opens a pull request whose description carries the receipt.
  • In GitHub Actions, the verify-receipt Action reads the trusted keys from the base branch, never from the pull request, and fails a receipt signed by a key the base branch does not list or one that does not cover every changed file. A pull request without a receipt fails by default, or passes with a notice when the workflow sets require-receipt: false.
  • Anyone can run axocoatl receipt verify offline, against the keys they trust and a checkout.

A receipt proves which key signed which facts. It does not prove that the change is correct, and a key copied from your data directory signs as well as yours.

Why a local binary

It runs on your computer.

Axocoatl is one Rust executable, licensed Apache-2.0. There is no Axocoatl account, hosted control plane or product telemetry. The models are yours to choose: local models through Ollama, hosted models through OpenRouter, or the Claude Code and Codex CLIs with your own sign-in. The signing key stays in your data directory, and a run calls no Axocoatl service. Your receipts keep verifying offline with the executable you have. Native Ollama Sessions accept Ollama 0.40.6, the release audited for this version, and later 0.x releases; on a release newer than the audited 0.40 line a model serves only after the contract probes pass for it, and the receipt marks it unaudited. A new major Ollama release needs a newer Axocoatl.

This does not mean nothing ever reaches a network. Providers, MCP servers, web search and page fetches, webhooks, the optional remote sandbox, Podman image or package downloads, the browser tool's declared hosts and the downloads its image build makes, requests Axocoatl sends on egress routes, and the one-time 87 MB embedding-model download from huggingface.co, on the first daemon start, can use the network. sandbox.network: none blocks code and commands inside the local Podman sandbox and turns off the native web tools; daemon-side integrations remain separate paths.

When to use the workbench

Watch the work when you want to.

The same daemon serves a workbench in your browser for work you want to watch or steer. There, a Session (one durable work item anchored to a repository folder: its conversation, the sandbox its tools run in, and its record) keeps the conversation beside Files, Terminal, Preview and Source Control. A Session can require the same checks and review as a headless run, and keeps the same record. Axocoatl does not commit for you; you review the Git changes and commit.

When an implementation choice is genuinely ambiguous, turn on Explore several ways. Each Way is a separate attempt from the same task and repository snapshot. Compare their outcomes, diffs and cost, keep one, and it returns to your checkout uncommitted. One answer is the default; Ways are for a hard decision.

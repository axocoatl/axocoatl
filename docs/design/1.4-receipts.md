# Axocoatl 1.4: signed receipts

Status: built in parallel branches from `main` at `c8bced0` (1.3.1) and integrated on
`release/1.4.0` (section 4, **Landed**). This
document is the contract between the branches. Where it and the code disagree, the code's
types win and the owner of the file fixes this document. Decisions marked **(maintainer)**
are recommendations recorded for the maintainer to confirm. C (sections 2.1 to 2.7) is
built on `feat/receipts`; where building it settled or changed this contract, the section
says **Built:**. D (the Action) is built on `feat/receipts` too and verified locally (section
3 says **Built:**); its first run on a real pull request is pending.

## 0. Why

Axocoatl already records what happened in a run and already has the host, not the agent,
decide whether the work passed: required checks run on the exact final files, and a required
review by a different model whose findings the writer must answer. What it cannot do yet is
hand that verdict to someone else in a form they can check without trusting the person who
ran it. The record bundle proves it is intact (its last line is a SHA-256 of every earlier
byte), not who produced it: anyone who edits it can recompute the hash.

A receipt closes that gap. It is a small signed statement, made by the daemon when a run
finishes, that says which files the run changed (with the digest of each file's content as
the checks judged it), what the host enforced (sandbox, network policy, checks, review,
adjudications, budgets), which programs and models wrote and reviewed, and the verdict.
Keep as PR carries it into the pull request; a verifier checks the signature against keys
the receiving repository trusts and checks the pull request's files against the digests.

### Invariants

1. Isolation is never weakened; every 1.3 invariant in `1.3-loadouts.md` section 0 holds.
2. The signing key never leaves the data root: not in a log, record, message, API response,
   container or command line. Only the public key is shown.
3. A receipt never says more than the host observed. A field the host could not establish is
   absent or says so (`"source": "workspace_at_finish"`), never guessed.
4. Nothing new needs an account or the network. Signing and verifying work offline.
5. No AI attribution in commits; nothing is pushed or published without the maintainer.

## 2. Receipts (C)

### 2.1 Key

- One Ed25519 key per data root, made by the daemon the first time it signs (or by
  `axocoatl receipt key`), with `ring` (already a dependency of `axocoatl-daemon`):
  `Ed25519KeyPair::generate_pkcs8`, stored with the secret store (`secret_store::set_secret`)
  as the secret `receipt-signing-key` (`0600`, written atomically, under the secrets lock).
  Reading it uses the same store. It is never a route credential: the egress broker refuses
  to send it. **Built:** the stored value is the PKCS#8 v2 document, base64, inside one
  line of JSON, `{"format":"axocoatl.receipt-signing-key/1","algorithm":"ed25519","pkcs8":"…"}`
  (`receipt_key::KEY_VALUE_PREFIX`), so the broker refuses the value itself however a route
  names its file or variable (`MANAGED_VALUE_PREFIX`-style), and also refuses a credential
  named `receipt-signing-key` and the secret store never offers it as a route's source.
- Key id: `sha256:` + hex SHA-256 of the 32-byte raw public key. Display form: the first 16
  hex characters.
- `axocoatl receipt key` prints one line for a trusted-keys file and exits 0:
  `ed25519 <base64 raw public key> axocoatl@<hostname> <key id prefix>`. It makes the key when
  none exists (saying so), using the data root of `--config` or `AXOCOATL_DATA_DIR`.
- `GET /api/receipts/key` returns `{ "algorithm": "ed25519", "public_key": base64, "key_id": …,
  "line": … }` (`line` as `axocoatl receipt key` prints it) and, like `receipt key`, makes
  the key when there is none, so Settings can show it before the first run.
- Rotation: `axocoatl receipt key --rotate` replaces it and prints the new line; old receipts
  stay verifiable with the old public key line. **Built.**

### 2.2 Statement

An [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md):

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [ { "name": "src/lib.rs", "digest": { "sha256": "<hex>" } } ],
  "predicateType": "https://axocoatl.ai/receipt/v1",
  "predicate": { … }
}
```

- `subject`: one entry per path the run changed that exists after the run (the same paths
  Keep as PR attributes, `keep_pr::RunAttribution`), sorted by name, with the SHA-256 of the
  file's content (for a symlink, of its target, as the capture manifest records it). Source,
  in order of preference: the manifest of the final candidate's check capture
  (`BeforeCheck` of the last turn that ran checks), else the last writer activation's After
  capture, when complete (`manifest_complete`); else the files read on the host when the run
  finishes. `predicate.files.source` says which: `judged_capture`, `after_capture` or
  `workspace_at_finish`. Removed paths go in `predicate.files.removed`. A run that changed no
  file has an empty `subject`. Unattributable activations go in `predicate.files.unattributed`
  (with Keep's reason) and make `predicate.files.complete` false.
- `predicate` (field order fixed by the Rust struct; every map a `BTreeMap`):
  - `run`: `run_id`, `session_id`, `started_at_ms`, `finished_at_ms`, `axocoatl_version`,
    `task_sha256` (the task text itself is not repeated; it is in the record).
  - `repository`: `base_commit` (HEAD when the run started, from the manifest), `dirty_paths`
    (manifest), `origin_url` when the repository has an `origin` remote (read with host git
    the way Keep reads it; absent otherwise).
  - `loadout`: `id`, `version`, `digest`.
  - `agents`: per Agent slot: `id`, `role`, `runtime` (`native`, `claude-code`, `codex`),
    `program_version` for external programs (pinned versions), `provider`, `model` as resolved,
    `credential` name for external writers (never the value).
  - `sandbox`: backend, `network` (`egress` / `none` / `bridge`), `workload`, the egress
    allowlist hosts, and each route's host and rules as the Session policy recorded them
    (from the route's `canonical()`), including whether the provider-fetch guard was on (A).
    **Built:** `policies`, one per scope of the Session's network record (`session`,
    `provisioning`, `browser`): the last `Policy` event's `revision`, `digest` (SHA-256 of the
    canonical compiled policy, which covers each route's `canonical()`) and `rules` (the
    rendered allowlist hosts and routes: host, ports, rules, credential name, who may use
    it). The route's `canonical()` JSON itself is not copied: it holds local credential file
    paths, which a receipt published in a pull request must not carry; its digest is.
    **Built (with A, on `release/1.4.0`):** each policy also has `routes`, one per route
    line of its recorded rules (`egress_broker::rules::RecordedRoute::parse` reads back
    what `Route::policy_text` rendered): `id` (`route#<n>` or `host_ollama`), `host` and
    `provider_fetch`, `refuse` when the route checked model-call bodies, `allow` when
    `provider_fetch: allow` sent them unread, absent for a route that reads no bodies. It
    comes from the record the Session ran under, not from the configuration at signing
    time. An empty list is left out of the statement.
  - `network`: the Outcome's `NetworkSummary` (requests, refused, hosts).
  - `checks`: per check: `name`, `state`, `exit_code`, `duration_ms`, and the command.
    **Built:** `timeout_ms` and `candidate_sha256` (the tree it ran on) instead of
    `duration_ms`, which the 1.3 Outcome does not record (a field the host did not
    establish is absent, invariant 3).
  - `review`: model, verdict, rounds used, number of findings; `adjudications`: per finding
    `id` and `decision`.
  - `verdict`, `exit_code`, `attention`, `not_covered` (count and areas), `warnings` (codes).
  - `usage`: tokens, `cost_usd`, `cost_known`, `cost_computed`. **Built:** also the exact
    `cost_microunits` and `complete`.
  - `files`: `source`, `removed`, `complete`, `unattributed`. **Built:** also
    `tree_sha256` (the capture's tree, for a capture source), `links` (subjects that are
    symbolic links, so a verifier checks the kind as well as the digest) and
    `read_at_finish` (subjects whose digest was read when the run finished although the
    source is a capture: paths that were as in `HEAD` in the captured tree).
  - **Built, not in the proposal:** `signer`: `algorithm`, base64 `public_key`, `key_id`.
    A DSSE signature carries only a key id, so without the public key `verify` could not
    tell "valid, by a key you do not trust" (exit 2) from a broken signature (exit 1).
    Trust never comes from this field: a verifier trusts only the keys it is given, and the
    signer named must be the key that signed.
- Serialization: `serde_json::to_vec` of the struct, no pretty printing. Signature
  verification covers the exact payload bytes, so verifiers never re-serialize.
- **Built (subjects):** the "final candidate's check capture" is the capture whose tree is
  the one the readiness review of the required checks judged. In 1.3 a check's own view
  never named a tree, so `CheckResult.candidate_sha256` was always empty; the observation
  now fills it from the readiness review for each check that ran. A capture keeps its
  whole manifest only up to 8 KiB (roughly 80 files), which almost every real repository
  exceeds, so a capture (output format 2) also records the manifest lines of every path
  that differs from `HEAD` in the tree it verified stable: the tracked paths a diff
  against a fresh index of `HEAD` names and the untracked ones, each with its mode, kind
  and digest, and a path gone from the tree as `deleted`. These lines are bounded by the
  changed paths, not the repository: up to 10,000 paths, and only while the capture's
  whole output stays within the 768 KiB its check definition retains (after the patch,
  the manifest prefix and a comparison's list). A receipt takes each path's digest from
  the whole manifest when it hashes to the tree digest, else from these lines; a path
  they do not hold was as in `HEAD` in that tree (a change the run undid) and is read when
  the run finishes and named in `files.read_at_finish`. Only a capture that recorded
  neither (more than 10,000 changed paths, a patch that leaves no room, or a check group
  admitted with 1.3's capture command, which keeps running it) falls back to
  `workspace_at_finish`. A path in Git's own directory, a
  path that is not plain or not a file or link, and a turn the Session's history does not
  hold go to `unattributed`. The run's turns are its Outcome's and those its record
  started, so a run a restart ended is not shown as changing nothing.
- **Built (repository):** `origin_url` is `git_host::normalize_to_https` of the remote
  (credentials removed); a remote that is a local path is left out.

### 2.3 Envelope

A [DSSE](https://github.com/secure-systems-lab/dsse/blob/master/envelope.md) envelope, media
type `application/vnd.dsse.envelope.v1+json`:

```json
{ "payloadType": "application/vnd.in-toto+json",
  "payload": "<base64 statement>",
  "signatures": [ { "keyid": "sha256:<hex>", "sig": "<base64 ed25519 signature>" } ] }
```

The signature is over DSSE's PAE: `"DSSEv1" SP len(type) SP type SP len(body) SP body`.
Ed25519 is deterministic, so signing the same statement twice gives the same bytes.

### 2.4 When it is made, where it is kept

- The driver signs right after `host.finish(&run.run_id, &outcome)` writes `outcome.json`
  (`crates/axocoatl-daemon/src/loadout/driver.rs`), for every finished run whatever its
  verdict. It is written once as `{data root}/loadout-runs/{run_id}/receipt.dsse.json`
  (`0600`) through `RunRecordStore`. A failure to sign is recorded as a run warning
  (`receipt_unavailable`, with why) and never changes the verdict or exit code, so a key
  problem cannot turn a failing run into a passing one or the reverse.
  **Built: the driver signs right *before* the `Ended` event and `outcome.json`**
  (`RunHost::seal`, daemon `seal_loadout_run`), from the final Outcome. The Outcome is
  written once, so a `receipt_unavailable` warning written after it could not be in it;
  and a client that sees the run finished (`axocoatl run`, the bundle, the panel) would
  otherwise race the receipt. `RunRecordStore::write_receipt` replaces a receipt only while
  `outcome.json` does not exist (a finish that never completed); after that it is written
  once, and `receipt` serves it only for a finished run. Runs that end at admission
  (environment failed), after a driver error (`fail_run`) and at a restart
  (`recover_loadout_runs`) are sealed the same way.
- `GET /api/runs/{run_id}/receipt` serves it (404 until the run finished, with a message).
- Record bundle: schema `axocoatl.record-bundle/2` adds a last section `receipt` (the
  envelope as JSON) after `run_event`. `axocoatl record verify` accepts `/1` and `/2`.
  A bundle of a run without a receipt has no `receipt` line.

### 2.5 CLI

- `axocoatl run … --receipt FILE`: writes the envelope when the run finished, as `--junit`
  and `--record` do (also on a failing run). When the run was never admitted there is nothing
  to sign: write nothing and say so.
- `axocoatl receipt show FILE|-`: the statement in words (run, verdict, checks, review,
  models, files, key id). Does not verify; says so.
- `axocoatl receipt verify FILE|- [--key LINE]… [--keys FILE] [--repo DIR] [--record BUNDLE] [--json]`:
  1. parses the envelope and statement (refusing unknown `_type`/`predicateType`);
  2. checks the signature against each trusted key (`--key` lines, `--keys` file in the
     `axocoatl receipt key` format, `#` comments); with no trusted key given it reports the key
     id and exits with "signature valid, signer not trusted" (its own exit code);
  3. with `--repo DIR`, hashes each subject path in that checkout and checks each removed path
     is absent; any difference is listed;
  4. with `--record`, verifies the bundle (`verify_bundle`) and that its `receipt` section is
     this envelope and names the same run.
  Exit codes: 0 valid and trusted (and matching, for the checks asked); 1 bad signature or
  malformed; 2 valid signature but untrusted signer; 3 usage; 4 files or record do not match.
  **Built:** when several apply, the first of 1, 2, 4 wins (an untrusted signer's subjects
  are only claims). `show` and `verify` also read text holding the pull request block (a
  saved description), which the Action can pass on standard input. A command line clap
  refuses exits 3 for `run`, `loadouts`, `record` and `receipt`, not clap's 2.
- `axocoatl receipt key [--rotate]` (2.1).
- Never needs a running daemon, Podman or the network: `verify` and `show` are pure.

### 2.6 Keep as PR

- Before committing, Keep reads the run's receipt and hashes each path it is about to commit
  in the working tree. A path whose content differs from its subject (or a removed path that
  exists again) is refused: "`<path>` changed after the run's checks judged it; Keep commits
  only what the receipt covers". A run with no receipt keeps today's behavior and says the
  pull request has no receipt.
- The commit message gains trailers `Axocoatl-Run: <run id>` and
  `Axocoatl-Receipt: sha256:<SHA-256 of the statement payload>`.
- The pull request body gains a **Receipt** section near the top: signer key id, verdict,
  checks, review model and verdict, writer program and model, files covered, and how to
  verify; then the envelope, base64, inside
  `<!-- axocoatl-receipt:v1` … `-->`. The body cut (`MAX_BODY_CHARS`) never cuts this block.
- **Built:** the receipt check runs before the status-time check, so an edited covered file
  is refused with the receipt's words; a path the receipt does not cover, a removed path
  that exists again, an unreadable receipt and another run's receipt are refused too. The
  block is at the end of the body, in lines of 76; a block over 40,000 characters (a
  receipt of thousands of files) is left out and the body says to verify from the run's
  record. Keep's response gains `receipt` (the statement's `sha256:`), which `axocoatl run
  --keep` prints. A later Keep that reuses the branch an earlier one created commits
  nothing and checks nothing.

### 2.7 Web UI

- Run outcome panel (`axocoatl-server/static/ui/run-outcome.js`): a "Receipt" line with the
  signer key id, files covered and a download link to `/api/runs/{id}/receipt`; when signing
  failed, the warning.
- Settings shows the public key line with a copy button, next to Loadouts (no new top-level
  destination; see `AGENTS.md`). **Built:** a "Receipts → Signing key" group in the
  Loadouts section's list.

## 3. verify-receipt Action (D)

A composite action at `actions/verify-receipt/action.yml`, used as
`axocoatl/axocoatl/actions/verify-receipt@v1.4.0`:

- installs the pinned Axocoatl release for the runner (Linux x86_64 or ARM64) and checks the
  archive against the release's published checksum;
- reads the pull request body from `GITHUB_EVENT_PATH` and extracts the envelope block;
- reads the trusted keys from the BASE branch (`gh api …/contents/<keys-file>?ref=<base sha>`),
  never from the pull request's head, so a pull request cannot add its own key;
- runs `axocoatl receipt verify - --keys … --repo .` on the checked-out head and lists the
  pull request's changed files (`gh api …/pulls/<n>/files`); a changed file the receipt does
  not cover fails unless `allow-uncovered-files: true`;
- writes a job summary (verdict, checks, review, models, signer) and fails on any problem;
  `require-receipt: false` makes a pull request without a receipt pass with a notice.

It is verified end to end on a real GitHub pull request before it is documented as working.

**Built:**

- `actions/verify-receipt/action.yml` runs two bash steps, `install.sh` and `verify.sh`;
  every input reaches them through `env`, never as an expression in a script. Inputs:
  `version` (default `v1.4.0`, the tag this branch releases as), `sha256`, `keys-file`
  (default `.axocoatl/receipt-keys`), `require-receipt` (`true`), `require-pass`
  (`true`, not in the proposal: a valid receipt of a run that did not pass fails),
  `allow-uncovered-files` (`false`), `github-token` and `binary` (an executable already on
  the runner, for testing a build). Outputs: `result`, `run-id`, `verdict`, `key-id`.
- Install: the release workflow publishes `axocoatl-<tag>-<target>.tar.gz` and
  `<archive>.sha256` (one line, `<sha256>  <archive>`) for `x86_64-unknown-linux-gnu` and
  `aarch64-unknown-linux-gnu`; the step maps `RUNNER_ARCH` `X64`/`ARM64` to those, downloads
  both from `github.com/axocoatl/axocoatl/releases/download/<tag>/` over HTTPS, requires
  the manifest's exact form, compares the archive's SHA-256 with it and with the `sha256`
  input when given, extracts only `axocoatl`, and requires `axocoatl --version` to be
  `axocoatl <version>`. The release's checksum file comes from the same release as the
  archive, so it catches a corrupted download, not a replaced release; the `sha256` input
  pins the archive itself.
- Verify: the checkout must be the event's head commit (actions/checkout checks out a
  merge commit for `pull_request` unless given `ref`) with no local changes to tracked
  files. The keys come from `gh api -H 'Accept: application/vnd.github.raw+json'
  repos/<base repo>/contents/<keys-file>?ref=<base sha>`; a 404 means no key is trusted,
  so the receipt is untrusted with that said. The verify `--json` report decides the
  result (1 `malformed`/`invalid`, 2 `untrusted`, 3 and anything else `error`, 4
  `mismatch`, each mismatch annotated). Changed files: `gh api --paginate
  repos/<repo>/pulls/<n>/files?per_page=100`; a removed file must be among
  `files.removed`, a renamed file's new path among the subjects and its old path among
  `files.removed`, any other file among the subjects. The pull request is read again
  afterwards: a head that moved fails the check, and a listing that is not its
  `changed_files` fails it too, except past GitHub's 3,000-file listing limit, which counts
  as uncovered. Annotations escape `%` and line breaks, so a path cannot start a workflow
  command; the job summary escapes Markdown.
- Tested by `scripts/test-verify-receipt-action.sh` (run by the native gate): a fake `gh`
  serving a local repository's contents at a ref, its pull request files a page at a time
  and its head; a fake `curl` serving release archives; crafted event files; receipts
  signed with throwaway OpenSSL Ed25519 keys and checked by the real binary. Cases: valid
  (123 changed files over two pages, a removal, a rename, a symbolic link, CRLF line
  endings), no receipt with `require-receipt` true and false, an untrusted key, the key
  added only in the head (to a base keys file, and as a new file on a base without one),
  a one-byte mismatch, an uncovered extra file (refused, and allowed as a warning), a
  checkout not at the head, a local change, a head that moved, a verdict that is not
  `pass` (refused, and allowed), a changed payload, a bad keys path, a bad boolean, a
  non-pull-request event; and the install step's checksum, pin, manifest form, version,
  missing release, runner and `binary` cases. A small runner stand-in also runs
  `action.yml` itself (each step's env from its expressions and input defaults, the
  install step's output, the action's outputs) for a valid receipt, a key added in the
  head and an allowed uncovered file. actionlint does not read composite actions:
  `scripts/run-actionlint.sh` runs its pinned ShellCheck on the actions' scripts, and
  `scripts/check-workflow-contracts.rb` checks each composite action's steps (a shell
  named, no expression in a script, declared inputs only, actions pinned).
- Not yet done: a run on a real GitHub pull request (it needs a test repository the
  maintainer approves), so the docs say "verified locally; first real pull request run
  pending".

## 4. Provider-fetch guard (A), built-in agent loadouts (B), site (E)

A, B and E are specified in their branches' task statements; their results are summarized
here when they land. Decisions recorded so far:

- **(maintainer)** A: on routes to known model APIs (`api.anthropic.com`, `api.openai.com`,
  `chatgpt.com`, `openrouter.ai`), the broker reads the JSON request body and refuses
  provider-side fetches (server tools, MCP connectors, URL-sourced images and files, web
  plugins) by default, with a per-route opt-out recorded in the Session policy.
- **(maintainer)** B: `fix-claude-code` and `fix-codex` become built-in ids; a person's own
  loadout file with either id is listed with an error that says how to rename it. A Codex
  writer's credential can resolve automatically to whichever of `codex-openai` and
  `codex-chatgpt` is stored, and the run records which one it used.
- **(maintainer)** C: a local Ed25519 key per data root (no account, offline); Sigstore
  keyless later. Receipts for every finished run, not only passing ones. Keep refuses files
  changed after they were judged.

**Landed.** A and E shipped first as 1.3.2 (`release/1.3.2`): the check covers
`api.anthropic.com`, `api.openai.com`, `chatgpt.com`, `openrouter.ai`,
`generativelanguage.googleapis.com`, `api.mistral.ai`, `api.x.ai` and
`ai-gateway.vercel.sh`, and the AI SDK's own Vercel AI Gateway protocol (`/v<N>/ai/…`) is
refused with `ai_sdk_gateway_refused`, naming the gateway's OpenAI-compatible API
(**(maintainer)**, recorded 2026-10-14: keep refusing it rather than read an undocumented
protocol). B and C were integrated on `release/1.4.0`, where:

- a receipt's `agents` entry names the credential admission chose for an external writer
  (`RunManifest::credentials`, so `fix-codex`'s `auto` is resolved), falling back to the
  loadout's own name for a manifest without it, never to `auto`;
- `sandbox.policies[].routes` records each route's body check (section 2.2);
- the Podman tests of the built-in `fix-claude-code` and `fix-codex` against fake model
  APIs also verify the run's receipt: its signature, the writer's runtime, pinned program
  version, model and credential, and `provider_fetch: refuse` on the route to its model
  API.

## 5. Done means

- A real `axocoatl run fix …` produces a receipt; `axocoatl receipt verify --repo` passes on
  the untouched checkout and fails after a one-byte edit; Keep as PR opens a pull request whose
  body carries the receipt; the Action passes on that pull request and fails on a pull request
  with an extra commit or an untrusted key. Each of these is run, not only unit-tested.
- `./scripts/preflight.sh` is green; CHANGELOG, README, docs and marketing say exactly what
  ships.
